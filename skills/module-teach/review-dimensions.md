# module-teach · 评审维度（SSOT）

> **定位**：`module-teach` 全部评审节点的维度定义**单一事实源**。
> `topic-teach` 的教学类维度（教学法视角 / 学习者视角 / 专项 A、B、C）**不在此**（见 `topic-teach/review-dimensions.md`）。
>
> **谁来读**：
> ① **主 agent 内联评审** → 直接读本文件。它与 `SKILL.md` **同目录**，属"同 skill 内相对路径"，**必然可达**，不依赖子 agent 是否已创建。
> ② **委派子 agent** → 本文件全文作为 **【评审维度】输入**传入。
>
> **优先级**：调用方传入的【评审维度】> `course-reviewer` 内的兜底副本。**两份不一致时以本文件为准**，兜底副本不得用于覆盖或补充。
>
> **改维度时**：本文件是 SSOT；改完须同步 `agents/course-reviewer/agent.md` 的**兜底骨架清单**（维度名 + 一句话判据）。

## 适用范围

覆盖 module-teach 的两类评审节点：

| 节点 | 模块类（完整模式） | 变更类 | 叠用维度 |
|---|---|---|---|
| 大纲评审（Phase 1） | 单实例 `pedagogy` | 跳过 | **D8**（零术语可达性） |
| 解读评审（Phase 2） | **双实例** | **单实例 `pedagogy`** | **D**（变更类叠加 **E**） |
| 收尾评审（Phase 7） | **双实例** | 单实例 `pedagogy` | **D**（变更类叠加 **E**） |

> 节点路由见 `SKILL.md`「course-reviewer 评审执行规则 · 评审节点与模式」；本文件只定义**维度**。
> **两类对象共用**：模块类走 D；变更类走 D + E。变更类**不适用** D8（它是模块类大纲/收尾特有）。

### D. 代码讲解（module-teach · 模块类与变更类共用）

代码讲解的失真方式与通用知识教学不同——它不缺"生动"，缺的是**每个结论都能对上代码**。故 D 维度的重心在证据。**（D8 是唯一例外：它判"读者进得来"的门槛，不是证据。）**

| # | 维度 | 检查点 | 不达标 |
|---|------|--------|--------|
| D1 | **可溯源** | 每条结论是否带 `file://路径#Lx-Ly`；行号区间是否覆盖被论述代码的实际跨度（`Lx-Lx` 单点不合规） | **P0** |
| D2 | **无编造** | 有无"听起来合理但代码里没有"的结论（如臆测的缓存策略、不存在的错误处理分支）；拿不准的是否已降级为"待确认" | **P0** |
| D3 | **范围标注完整** | `[通用]` / `[专用]` 是否逐讲解点标注；`[通用]` 部分的外部文档链接是否真实存在 | P1 |
| D4 | **认知阶梯不倒序** | 是否先讲机制再讲概念、先讲实操再讲原理；术语是否未铺垫就出现 | P1 |
| D5 | **叙事 / 直述判定成立** | 采用叙事时五幕是否完整（尤其第四幕"验证"是否用了**真实调用链 / 真实 before-after**，而非假想示例）；采用直述模式时标注的理由是否成立 | P1 |
| D6 | **图表选型合规** | 默认 Mermaid；出现 SVG 触发信号（分支回环密 / 需泳道语义 / 数据结构内部结构 / 算法执行过程等）时是否改用独立 SVG 文件并入 `assets/`（kebab-case）；**C 类四型**（空间布局 / 集合・范围关系 / 多概念对比分类 / 层级・分层结构）是否直接出 SVG 而未退化为 `A --> B`（判定表 SSOT 见 `use_skill("topic-teach")` 的「表现形式规范 · 图表选型 C 类」）——退化即 P1；每图后是否有 `图表来源` 与**一句话读图指引**（缺指引 → P1） | P1 |
| D7 | **章节来源完整** | 每个 `##` / `###` 小节末尾是否有 `章节来源`（纯概念节可豁免）；汇总进最终文档后来源是否丢失 | P1 |
| D8 | **零术语可达性**（仅模块类；适用「大纲评审」与「收尾评审」两个节点） | ① 是否有「一句话本质」且**通篇不含技术名词**？② 是否有**零术语直觉主图**（独立 SVG 入 `assets/`），且**图上无技术名词**、带一句话读图指引？③ 「特性卡」是否给出"代价"（只列优点 = 宣传稿）？④ 术语首次正式登场时是否回指直觉层的说法（不出现两套词汇对不上）？**①–③ 任一缺失（含大纲缺失，或汇总进最终文档后丢失）→ P0**：读者进不来；④ 缺失 → P1 | **P0** |

> **D8 与评审视角**：D8 判的是"**进得来**"的门槛，由大纲 / 收尾节点的评审实例负责，**不因此增设第二实例**——它用的是可客观判定的锚点（术语清单、图上文字、特性卡列数、读图指引有无），不依赖主观阅读体验。**反面锚点**：直觉主图若只是"物理索引→写别名→读别名"几个术语框相连，属术语关系图，判 D8 不达标。
>
> **⚠️ 有意妥协（须显式记录，勿当成已完成新人视角）**：「没学过的人能否看懂」**本质属 learner 判断**，而**大纲节点是 pedagogy 单实例**——本文件反复强调"新人视角是独立的第二视角"，此处是已知张力。故 D8 在该节点**只作锚点式形式检查**（锚点齐不齐、图上有没有术语），**不声称完成了实质可读性判断**；收尾节点是双实例，由 learner 一并把关实质可读性。

- **新人视角（learner）补充**：作为刚接手这段代码的新人，具体在**哪一节**读不懂？哪个术语没铺垫？读完全文能否一句话说清"这段代码在系统里干什么、边界在哪"？
- **pedagogy 视角补充**：结构与 Phase 0 确认的范围 / 学习目标是否匹配？有无超纲或遗漏？

### E. 变更讲解（module-teach · 变更类专用，叠加在 D 之上）

变更讲解有两类特有的失真：**编造作者动机**（把推断当显式）与**凭空想象影响面**（diff 里没有调用方）。E 维度专门压这两点。

| # | 维度 | 检查点 | 不达标 |
|---|------|--------|--------|
| E1 | **意图标注诚实** | `[显式]` 是否真的写在 commit message / PR 描述 / 注释里；**没写却被标成 `[显式]` = 编造作者动机** | **P0** |
| E2 | **影响面有实证** | 每条"影响谁"是否有 `impact` / grep / 源码证据；凭 diff 文本推断或未标来源的一律降级为"待确认" | **P0** |
| E3 | **before→after 准确** | 对照是否与真实 diff 一致（**最常见失真：把 diff 读反、漏 hunk、把格式化当语义改动**） | **P0** |
| E4 | **只描述不裁决** | 是否出现"这个改动不该合""这里写错了"等裁决性表述 → 应改写为风险点描述，判定权归 `code-review` 与用户 | **P0** |
| E5 | **噪音改动已归组** | 格式化 / 依赖升级类改动是否单独归组并一笔带过，未淹没真正的语义改动 | P1 |
| E6 | **推断有依据** | 每条 `[推断]` 是否给了来自 diff 的具体依据；只有结论没有依据的推断视为编造 | P1 |
| E7 | **待确认清单可用** | `05-风险与待确认.md` 的"需向作者确认"是否是**交付给用户的行动项**，而非 AI 的自问自答 | P1 |

- **新人视角补充**：不看原始 PR、只读这份材料，能否理解"这次改动为什么做"？哪处改动读完仍不知道它解决什么问题？
- **pedagogy 视角补充**：改动分组是否**按意图**而非按文件？规模标注是否准确（它决定读者对风险的第一判断）？

## 质量自检清单（返回前过一遍）

1. 结论是否一句话说清通过与否 + 意见数量？
2. P0 / P1 / P2 分级是否合理，P0 是否确实是"必须改"级别？
3. 是否对照了 Phase 0 确认的对象 / 范围 / 学习目标，以及 `reference.md` §1 通用格式规范？
4. 时效敏感内容是否标注"需主 Agent 核查"而非妄下结论？

## 代码 / 变更讲解附加

5. **代码讲解**：专项维度 **D1 / D2**（可溯源 / 无编造）是否逐条核查？`file://` 行号区间是否真的覆盖被论述代码的实际跨度（`Lx-Lx` 单点不合规）？
6. **变更讲解**：专项维度 **E1 / E2 / E3 / E4**（意图诚实 / 影响面实证 / 对照准确 / 只描述不裁决）是否逐条核查？有无把推断写成 `[显式]`、或出现"不该合"这类裁决性表述？
7. **零术语可达性（D8，仅模块类大纲 / 收尾节点）**：一句话本质 / 直觉主图 / 特性卡三要素是否齐备，且图上一律无技术名词？
