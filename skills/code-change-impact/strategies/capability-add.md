# 能力新增类 影响策略

## 概述

**目的**：新增能力的典型风险不是"新代码写错了"，而是**新东西没接上**（写了没人读、加了没消费、开了没生效），以及**接的过程中碰坏了旧路径**。本策略用"贯通性两问"作为主检查。

**使用场景**：新功能 / 新接口 / 新字段 / 新开关的改动需要合入前背书。

## 增量必查（四维之外额外必查）

| # | 必查项 | 必查问句 | 未通过时 |
|---|--------|----------|----------|
| 1 | **正向贯通** | 新输入从入口一路走到最终落点了吗？中间哪一跳断了？ | 断链 = 意图未达成，Step 2 判 D |
| 2 | **反向贯通** | 新增的产出（字段/事件/接口/表）有人生产、有人消费吗？ | 死字段/死接口 → 标 🟡 待确认 |
| 3 | **旧路径未破坏** | 新增分支是否改变了既有分支的判定顺序、默认值、权限拦截？ | 任一改变 → 升级 🔴 |
| 4 | **默认值与开关** | 开关默认值是什么？灰度期新旧行为如何共存？关掉后是否完全回到旧行为？ | 关不干净 → 🔴 |
| 5 | **边界与限额** | 新能力是否引入配额、超时、长度、并发上限？超限行为是什么？ | 未定义 → 🟡 |
| 6 | **兼容窗口** | 新旧客户端/调用方并存时，旧版本看到新字段/新接口会怎样？ | 列兼容策略 |

**第 1、2 项必须成对做**：只做正向会漏"加了没人用"，只做反向会漏"接了一半"。

## 维度优先级调整

| 维度 | 默认 | 本策略 | 理由 |
|------|------|--------|------|
| 调用链（3.1） | 🔴 | 🔴 | 看新增节点的上游接入方是否齐全 |
| 数据流（3.3） | 🟡 | **🔴 必给结论** | 贯通性本质就是数据流是否连到底 |
| 条件路径（3.2） | 🟡 | 🟡 | 仅当新增判断插入既有分支链时升级 |

## 必测清单

- [ ] 新链路端到端跑通（入口 → 落点 → 可观测结果）
- [ ] 开关关闭时，行为与改动前完全一致（对照测试）
- [ ] 新旧版本客户端/调用方并存场景
- [ ] 新增边界（超限、空值、未授权）的行为
- [ ] 旧功能回归用例全绿

## 反向：能力移除 / 下线

删除接口、字段、页面、配置属于**能力新增的反面**，但风险形状与"新增"不同，**多数不归本策略**——按移除对象分流：

| 移除对象 | 走哪个策略 | 额外必查 |
|----------|-----------|----------|
| 接口 / 方法 / 字段 / 事件 | **契约变更**（消费方断裂） | 逐个消费方确认已迁移，否则删除即线上报错 |
| 表 / 列 / 缓存键 / 枚举值 | **数据与状态变更**（存量数据） | 历史数据与回滚路径 |
| 页面 / 入口 / 开关 | 能力新增（按"旧路径未破坏"反向核） | 是否有用户仍在用（埋点/访问日志） |

> 识别规则：diff 里出现 `delete` / `remove` / 下线开关置 false / 标记 `@Deprecated` 时，按上表至少启用两个策略。

## 不做什么

| 不做 | 交给 |
|------|------|
| 需求完整性、该不该做、负向场景设计 | `requirement-mining` / `negative-requirement` |
| 验收指标是否达标 | `acceptance-verify` |
| 实现完成度总结 | `implementation-report` |
| 新增功能的场景推演与需求覆盖度 | `scenario-rehearsal` 的 `strategies/feature.md` |
