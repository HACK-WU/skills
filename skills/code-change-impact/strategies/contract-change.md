# 契约变更类 影响策略

## 概述

**目的**：契约变更的影响面**必然是全部消费方**，没有"抽样"可言。本策略的价值是把"调用方清单"变成"逐条语义核对"——编译通过不等于语义成立。

**使用场景**：改方法签名、返回值、异常、API 路由、DTO、事件格式、公共类/基类/中间件时。**无论改动动机是什么，只要命中即为必选策略**（见 SKILL.md 策略识别规则 1）。

## 增量必查（四维之外额外必查）

| # | 必查项 | 必查问句 | 未通过时 |
|---|--------|----------|----------|
| 1 | **消费方穷举** | 调用方清单是否穷举？是否含测试、脚本、定时任务、外部 SDK、其他仓库？ | 清单不全 → 该条降为 ⚠️，不得标 ✅ |
| 2 | **调用形态差异** | 命名参数调用、默认值省略、可变参数、反射/动态调用、字符串拼出的方法名，是否都被覆盖？ | 列出未覆盖形态 |
| 3 | **语义而非编译** | 签名兼容但语义变了（返回 `None` 而非抛异常、空列表而非缺失键、异步变同步）的调用方，能正确处理吗？ | 逐条升级 🔴 |
| 4 | **序列化契约** | 对外 API / 事件 / 消息的字段增删改，反序列化端（旧客户端、下游消费者、离线任务）能容忍吗？ | 列兼容策略与窗口 |
| 5 | **异常契约** | 异常类型、错误码、HTTP 状态是否变化？调用方的 catch / 重试 / 告警规则是否还匹配？ | 匹配不上 → 🔴 |
| 6 | **文档与 SDK** | OpenAPI、接口文档、SDK、Mock、契约测试是否需要同步？ | 列同步项 |

**第 3 项是本策略最常漏的**：编译期无感、运行期爆炸。凡是"返回值可空 / 集合可能为空 / 异常改为返回码"这类改动，必须逐个消费方读代码确认。

## 维度优先级调整

| 维度 | 默认 | 本策略 | 理由 |
|------|------|--------|------|
| 调用链（3.1） | 🔴 | **🔴 逐个给结论，禁止抽样** | 契约变更的影响面就是消费方全集 |
| 数据流（3.3） | 🟡 | **🔴 必给结论** | 返回值/异常/副作用的变化是契约的核心 |
| 条件路径（3.2） | 🟡 | 🔴 | 契约在边界值（空、超长、异常）上的行为最易变 |
| 执行场景（3.4） | 🟡 | 🟡 | 涉及并发语义（如加锁范围）时升级 |

## 必测清单

- [ ] 每个调用方的既有测试通过（含集成/契约测试）
- [ ] 边界值：空集合、`None`、超长、非法枚举
- [ ] 旧版本客户端/下游消费者对新格式的兼容测试
- [ ] 异常路径：异常类型与错误码断言
- [ ] 公开 API 的 OpenAPI/SDK 回归

## 不做什么

| 不做 | 交给 |
|------|------|
| 契约设计是否合理、抽象是否选错 | `design-review` / `code-review` |
| 接口设计文档编写 | `api-design` |
| 跨模块耦合关系的沉淀 | `strong-relation`（本 skill 只做本次改动的影响推理，不沉淀长期关系） |
