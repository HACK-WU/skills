# 前端体验走查（frontend-walkthrough）

## 概述（AI 说明层）

**目的**：解决两个盲区。① **用起来卡手**：页面能打开、功能都齐全，但用户处处别扭；② **看着没坏、其实会坏**：接口还没回来 / 已经失败 / 结果乱序返回时用户继续操作，造成数据被覆盖、重复提交、旧结果盖掉新结果、上一条数据串到下一条。把"反复点前端页面、看效果、试交互、挑问题"这件高频工作，变成 AI 可执行的**真实操作走查 + 缺陷推演**：像真人一样遍历页面与状态，同时沿时间轴推演异步态与动作的组合，产出带证据的发现清单。

**功能**：
- **取证档位自适应**：先探测浏览器实操能力（A 可实操 / B 半实操 / C 纯静态）并写入报告，能力不足时明确降级，**不假装体验过**
- **白盒规划 + 黑盒体验**：先读前端代码穷举入口、状态与分支（规划"要点什么"），再像真人一样操作观察（体验判据不来自代码）
- **功能回归清单**：正式走查前先把改动代码翻译成"受影响功能"清单（调用方 / 数据消费方 / 共享能力 / 页面入口，每批 ≤12 项、用户语言），逐项勾选闭环才收工——防"改动点正常就宣布没问题"
- **状态矩阵遍历**：逐页覆盖默认 / 加载 / 空 / 错误 / 无权限 / 长文本 / 大数据量 / 窄屏 八态
- **隐藏缺陷推演（两条腿）**：A 腿把「异步态（未发起 / 请求中 / 失败 / 超时 / 乱序 / 200 但业务错误 / 401）× 动作（点按钮 / 改筛选 / 切页 / 连点 / 关弹窗 / 返回）」交叉；B 腿按**十类缺陷族**过（状态一致性 / 生命周期副作用 / 表单输入 / 边界计算展示 / 权限安全 / 路由导航 / 集成发版 / 环境兼容 / 错误兜底）；先出**缺陷假设**，再回实操**定向复现**——时序类 🟡 到复现才 🟢，写法缺失类代码即 🟢
- **五类发现合并为一张清单**：体验优化 / 实现修复 / **潜在缺陷** / 加载性能 / 体验增强建议
- **双视角研判**：用户视角（任务场景轴）+ 产品经理视角（Kano + 价值×成本，口径复用 `product-manager`）
- 加载性能做到**体检级**：发现问题 + 定位方向 + 给证据；深入优化方案交 `performance-analysis`
- **视觉参考库基线（可选）**：项目有 `ui-tools/design-reference/` 时，以它作为本次视觉基线；只读，漂移按「有意偏离 / 实现误差 / 参考过时」分类

**使用场景**：
- 用户说"帮我走查一下前端"、"体验一下这个页面"、"点一遍看看有什么问题"
- 产品已有前端页面，想系统性找出体验缺陷与可优化点
- 上线前 / 改版后想知道"用户会在哪里卡住"、"什么地方会出错"
- 用户说"前端体验审计"、"看看前端实现有什么问题"
- 用户问"这个页面有什么隐藏 bug"、"接口慢/挂了/报错时点按钮会怎样"、"边界数据会不会崩"
- 用户问"这前端还有哪些常见坑 / 线上容易出什么问题"（权限绕过、发版白屏、路由 404、表单脏输入等）
- 用户说"这次改动 / 这个 PR 的前端部分验一下"（走**定向模式**，接手 `code-review` 交接单）

## 定位

```
已有前端页面（或 code-review 的改动交接单）→ frontend-walkthrough（本 skill）→ 发现清单（一张）
                                                    ↓
                     实施：request-guard → code-review
                     潜在缺陷复现后要定位根因/修复：debug
                     产品级功能缺失：product-manager M3
                     深入性能优化：performance-analysis
```

- **输入**：可运行的前端应用（URL / 服务地址 / 测试账号）或源码 + 画面材料；**定向走查**时另收 `code-review` 的交接单（见下「两种模式」）
- **输出**：一份前端走查报告（默认对话输出；用户要求落盘时写 `.walkthrough/{slug}-{YYYYMMDD}.md`）
- **边界**：只判断不改码；性能只到体检级；视觉只报"影响可用性"的问题；缺陷只到"会怎么坏 + 怎么触发"，根因定位与修复交 `debug`

### 与邻接 skill 的分工（防重叠）

| 邻接 skill | 它回答的问题 | 本 skill 回答的问题 |
|---|---|---|
| `product-manager` M2 / M4 | 产品视角：下一版该做什么、界面观感好不好 | 前端实现视角：**做出来的东西，用户用起来卡在哪、哪里会坏** |
| `scenario-rehearsal`（代码模式） | 通用纸上执行：给定场景实例，沿代码追状态演进与终态（任意代码/函数） | 只做**前端页面级**缺陷推演（时序矩阵 + 十类缺陷族），且推演必须回实操复现才算发现 |
| `e2e-testing`（动态体验验证） | 功能**对不对**（需求规格驱动的黑盒验收，须 e2e 前置） | **好不好用 / 会不会坏**（用户标准驱动的体验体检 + 缺陷推演，不要求 e2e 前置） |
| `code-review` | 变更 diff 的代码质量（含命名 / 架构 / 设计模式）；阶段 9.5 会把前端改动交过来做定向走查 | 存量前端代码的**体验相关**实现与**逻辑会坏**之处（不点评代码质量）；定向模式下只走其交接单的改动面 |
| `debug` | 定位**已发生**故障的根因并修复 | 判"会不会坏、怎么触发"，交复现步骤；根因与修复不在此展开 |
| `performance-analysis` | 后端接口 / 链路性能与优化方案 | 前端加载性能的**问题发现与定位方向** |
| `ui-designer` / `interaction-design` | 从零设计视觉方案 / 交互逻辑 | 审查**已实现**的页面体验 |
| `acceptance-verify` | 这一版达标没有（按验收指标逐条判） | 下一版该优化什么 |

> **视觉边界（刻意的）**：本 skill 只报**影响可用性**的显示问题（状态不可见、文案溢出截断、数据格式化错误、错位导致误读、对比度不足、点击区域过小、窄屏折行错乱）；**纯美术观感**（配色品味、精致度、动效美感）交 `product-manager` M4 或 `ui-designer`。
> **缺陷边界（刻意的）**：只报**能说清触发条件与后果**的缺陷（"详情未返回时点保存 → 空值覆盖原数据""低权限账号手输 URL → 看到无权限页"）；"理论上可能"但给不出触发路径、需毫秒级交错、或后端已兜住且前端无可见后果的，不报（见「误报过滤」）。

**何时不使用本 skill**：只想审一段代码变更 → `code-review`；只想验功能达标 → `acceptance-verify`；只想跑通链路 → `e2e-testing`；只想知道后端为什么慢 → `performance-analysis`；要重新设计界面 → `ui-designer`；已知某个 Bug 要查根因 → `debug`。

## 两种模式（先判断走哪种）

| 模式 | 触发 | 输入 | 范围 |
|---|---|---|---|
| **全量走查**（默认） | "走查一下前端""体验这个页面""点一遍看看" | 页面 / 模块 / 整站 | 入口穷举 → 状态矩阵 → 按**页面类型**预筛族 |
| **定向走查** | `code-review` 阶段 9.5 交接单；或用户说"这次改动帮我走一遍" | diff + 交接单 | 只走改动面 + 一步下游，按**改动性质**裁维度 |

### 定向走查（diff 驱动）

**输入契约**：`code-review` 的交接单——改动性质 / 涉及页面与路由 / 改动入口 / 必点路径 / 明确跳过的维度 / review 已覆盖 / 环境与副作用 / UI 参考库版本与涉及组件（可选）。**缺字段先问，不猜**。带参考库字段时读 `ui-tools/design-reference/meta.json` + `INDEX.md` 对应组件，版本不一致记 ⚠️；不修改参考库；无则按通用视觉基线。

**四条硬规则**：

1. **范围只到改动面 + 一步下游**：路由表只用来定位交接单里的页面，**不用来扩面**（要全站请用户显式改口成全量走查）
2. **按改动性质裁维度**：裁掉的维度写进报告「明确未覆盖」并给理由，**禁止留空或写"不涉及"了事**
3. **不重复 review 已覆盖的检查**：布局与已确认图的一致性归 `code-review` 阶段 5；本 skill 在布局上只报**运行时**不可用（溢出、遮挡、折行错乱、点击区域过小）
4. **不形成环、不越界**：本 skill **不回跳 `code-review` 重跑 review**（只按「回传」写结论）；裁掉布局时也**不给布局优化建议**（那是体验 / 设计范畴），布局上只报运行时破版

**维度裁剪表**：

| 改动性质 | 布局 / 样式 | 交互流程 | 状态与数据 | 缺陷族 | 加载性能 |
|---|---|---|---|---|---|
| **纯交互逻辑**（事件 / 状态 / 流程 / 校验 / 提交） | **跳过** | ✅ 必查 | ✅ | 1 / 2 / 3 / 4 / 10 | 不做 |
| 纯样式取值（组件内颜色 / 字号 / 间距，不动结构） | ✅ 仅核取值是否生效 | 轻微 | — | 9 | 轻 |
| 布局 / 结构 / 断点 / 显隐 | ✅ 必查（对照已确认图） | ✅ | ✅ | 5 / 9 | ✅ |
| 数据请求 / 接口契约 | 跳过 | ✅ | ✅ | 1 / 5 | ✅ |
| 权限 / 鉴权 | 跳过 | ✅ | ✅ | 6 / 7 | — |
| 路由 / 导航 | 跳过 | ✅ | ✅ | 7 | — |
| 文案 / i18n | 只核长度是否溢出 | 轻微 | — | 5c | — |

> **"跳过布局"≠"放过可用性显示问题"**：交互改动新增的按钮 / 文案导致的溢出、遮挡、错位**仍要报**——那是可用性缺陷，不是审美（见「视觉边界」）。
> **反向也成立**：纯样式取值（如组件内换色）不触发布局走查，但要核"取值是否真的生效"（改错变量名是真实高频缺陷）。
> **例外（重要）**：改的是**全局 token / 主题变量 / 设计系统变量**（全站生效）时，按「布局结构」处理——必须查布局，不能只核取值生效：一行全局变量等于全站改版。

**流程差异（相对全量走查）**：

| 阶段 | 全量走查 | 定向走查 |
|---|---|---|
| 0 范围锁定 | 问"整站还是模块" | 直接用交接单锁定，**不再问范围**（只补缺字段） |
| 0.5 功能面收敛 | 路由表 + 组件树建清单 | 用 diff / 交接单建清单（交接单给了「受影响功能面」就直接采用再核对） |
| 1 代码直读 | 路由表穷举入口 + 状态矩阵盘点 | 只读改动入口及其上下游（不做全站穷举） |
| **1.5 缺陷推演** | 全族按页面类型预筛 | **主战场**：按改动性质裁族后逐条推，必点路径直接从交接单取 |
| 2 操作走查 | 八态 + 三类路径 + 场景轴 | 只走「必点路径」+ 一步下游；八态只造与改动相关的 |
| 3 性能 | 按需 | 按裁剪表决定（纯交互逻辑不做） |
| 4 / 5 研判与报告 | 照常 | 照常，多一节「本次范围与跳过项」 |

**回传**：结论回写 `code-review` 报告——阻塞级发现以 `QW*` 编号追加其 §1.2（**归属必标**：本次引入 / 本次激活 / 既有 / 待确认）并改写合入结论（对齐其阶段 9.5「回写」与约束 19）；非阻塞项作为「走查补充」追加、不改评分；两份报告合入结论不一致时以**更保守**者为准。

## 核心原则

1. **走查是"操作"，不是"看图"**：截图只作证据，结论必须来自真实操作路径；只截图不点，等于没走查
2. **档位诚实**：先探测取证能力再动手；拿不到画面 / 起不了服务就降级，并在报告头声明——**禁止假装体验过**
3. **读代码有三个正当用途**：① 穷举入口与状态，防漏点（规划"要点什么"）；② 实现类判定——"有没有做"代码即一手证据（见「取证档位」）；③ **缺陷推演**——推"异步态 × 动作"组合下会不会坏（阶段 1.5）。**唯独不能用它判"体验好不好"**："代码里有 loading 分支" ≠ 用户看得到，体验判据只能来自操作观察
4. **人性化必须锚定可检验场景**：禁止"用户可能会困惑"这类空泛揣测；每条发现要能回答——**哪类用户、在什么任务下、遇到什么现象**
5. **证据三级制**：`🟢` 实操实测 / 代码实证 ｜ `🟡` 静态可证（结构 / 配置间接推断；**含缺陷推演**——路径可证但未运行）｜ `🔴` 推断。`🔴` 只进「待确认清单」且必须配验证方法
6. **一张清单**：体验优化 / 实现修复 / **潜在缺陷** / 加载性能 / 体验增强建议五类合并输出，用「来源」列区分，禁止多张打架
7. **只判断不改码**：输出清单与建议方向；实施交 `request-guard` → `code-review`
8. **排除项也值钱**：明确写"经走查排除：XX 维度无问题（依据：{证据}）"，避免用户重复排查
9. **有意取舍不当缺陷**：MVP 有意省略的（未做暗色、未做 i18n、未做批量导入）标"可能是有意取舍，需确认"
10. **涉及真实副作用先确认**：走查中的下单 / 删除 / 支付 / 发通知等操作，须在测试环境进行，环境不明时先问用户
11. **推演是假设，复现才算发现**：时序 / 组合类结论一律 `🟡` + `[需运行验证]`，**禁写"必现 / 已确认 bug"**；写法缺失类可 `🟢`（代码即证据）；实操复现成功升 `🟢`，复现不了要如实写"未复现 + 试过哪些手段"，**不得反推"此处没问题"**
12. **缺陷只报到"会怎么坏、怎么触发"**：根因定位与修复是 `debug` 的事；本 skill 交的是可复现的时序 + 现象 + `file:line`，让下游不必重新取证
13. **参考库只读**：`ui-tools/design-reference/` 只作视觉基线，不修改；漂移区分「有意偏离 / 实现误差 / 参考过时」，只报影响可用性的偏离，纯美术差异交 `design-review` / `ui-designer`；参考库缺失按通用基线，不阻塞

## 取证档位（先探测，后动手）

| 档 | 条件 | 能做什么 | 证据上限 |
|---|---|---|---|
| **A 可实操** | 有浏览器工具（`use_skill("agent-browser")` / `use_skill("playwright-cli")`）且服务能起 | 真实点击遍历、截图、读控制台与网络、采集性能指标（须工具支持脚本求值，否则走降级链） | `🟢` |
| **B 半实操** | 页面能打开但 AI 拿不到画面（只能开预览）或无法操作 | 读代码静态推演（`🟡`）+ 给出**肉眼检查清单**请用户按项提供截图 / 录屏；用户提供的画面可作 `🟢` 证据 | `🟢`（用户画面）/ `🟡`（静态） |
| **C 纯静态** | 服务起不来 / 无浏览器 / 无任何画面 | 只读前端代码（实现类判定 + 阶段 1.5 推演） | 实现类 `🟢`；逻辑推演 `🟡`；**体验类结论强制 `🔴`** |

**判定类型 × 手段**（决定单条结论能标多高）：

| 判定类型 | 例子 | 代码直读 | 实操 |
|---|---|---|---|
| **符合性**：有没有做 | "有没有空态""提交有没有防重复""错误文案带原因吗" | `🟢` 首选 | `🟢` |
| **体验性**：顺不顺、够不够 | "反馈及时吗""几步能完成""能恢复吗" | `🟡` 只能证"分支存在" | `🟢` |
| **逻辑性**：会不会坏 | "接口没回来就点保存会怎样""连续改筛选，旧结果会盖掉新的吗" | `🟡` 可证路径与分支存在，不证运行时交错；**写法缺失类**（没判断 / 没转义 / 没 cleanup）直接 `🟢` | `🟢` 能复现时（复现即从假设升级为确认缺陷） |
| **安全性**：能不能被绕过 / 注入 | "按钮隐藏了接口还能调吗""用户输入进没进 `v-html`""token 存在哪" | `🟢` 写法可证（缺失即证据） | `🟡` 可利用性需构造请求，本 skill 不展开攻击链 |
| **视觉性**：好不好看 | 对齐、层级、美观 | `🔴` 不可用（明确色值除外） | `🟢` |

> **C 档不等于没价值**：实现类问题（状态缺失、错误处理缺口、无障碍属性缺失、性能反模式）代码直读即 `🟢` 一手证据；**阶段 1.5 的缺陷推演在 C 档同样可做**（出 `🟡` 假设 + 复现步骤，等用户执行或升级档位后即可定论）——被禁止的只是"用代码推断体验"与"把推演说成已复现"。
> **代码直读证什么**：可证"写法存在 / 缺失"（有没有 loading 分支、有没有 label），**不证"运行时行为正确"**（分支会不会被走到、提示会不会被条件挡住）——涉及运行时行为的结论标 `[需运行验证]`。
> **能力探测是硬步骤**：不得跳过探测直接宣称"我体验过了"；降级声明必须写进报告头。B / C 档具体怎么做得有价值，见 [references/08-degrade-pitfalls.md](references/08-degrade-pitfalls.md)。

## 工作流

```
阶段 0 范围锁定与档位探测 → 阶段 0.5 功能面收敛（功能回归清单）
→ 阶段 1 前端代码直读（白盒规划 + 实现审查）
→ 阶段 1.5 缺陷推演（十类缺陷族 + 异步态矩阵，只出假设 + 复现步骤）
→ 阶段 2 真实操作走查（黑盒体验 + 定向复现假设）→ 阶段 3 加载性能体检
→ 阶段 4 双视角研判与优先级（先清单回归，再排序）→ 阶段 5 走查报告
```

> **页面多时分批**：每批 ≤8 个页面/功能域，出一批计划 → 执行 → 小结 → 再走下一批，避免一次性铺开失控。**阶段 0.5 → 1 → 1.5 → 2 为一轮**，按批执行，不跨批攒假设与清单。
> **推演与实操是一对**：阶段 1.5 只产出"可疑"，阶段 2 才是"定论"——两边任一缺失都会退化（只推演 = 一堆不可信的"可能会"；只实操 = 全靠运气碰不上时序缺陷）。
> **清单是范围的唯一凭据**：阶段 0.5 的功能回归清单决定"这次走什么"，阶段 4 的清单回归决定"能不能收工"——两头都不许凭感觉扩或缩。
> **定向走查少走弯路**：接手 review 交接单时，阶段 0 不再问范围、阶段 0.5 直接用 diff 建清单、阶段 1 只读改动入口、阶段 3 常直接跳过——省下的时间全部投到阶段 1.5（见「定向走查」）。
> **细则按包读，不全读**：`references/` 下 10 个包——每轮必读 [01-walk](references/01-walk.md)（阶段 1–2）与 [07-triage-report](references/07-triage-report.md)（阶段 4–5）；有异步依赖加 [02-timing](references/02-timing.md)；再按预筛命中的族读 [03](references/03-families-state-form.md) / [04](references/04-families-security-routing.md) / [05](references/05-families-runtime.md)；阶段 3 读 [06](references/06-performance.md)；非 A 档读 [08](references/08-degrade-pitfalls.md)；建功能回归清单读 [10](references/10-impact-list.md)。选包矩阵见 [references/INDEX.md](references/INDEX.md)。

### 阶段 0：范围锁定与档位探测

1. **锁定对象**：页面 / 入口清单、角色（普通用户 / 管理员）、目标功能域；范围不清先问一句（"走查整站还是某个模块？"）。**定向模式跳过此问**——范围由交接单给定，只补缺字段
2. **探测档位**（A / B / C），**写入报告头**
3. **备环境**：服务地址、测试账号、数据准备（空态 / 大数据量 / 长文本是否需要构造）
4. **确认副作用边界**：涉及真实写操作的，先与用户确认测试环境可用
5. **读取参考库（若有）**：读 `ui-tools/design-reference/meta.json` + `INDEX.md`，记录基线版本与使用组件；无则按通用视觉基线，不阻塞

### 阶段 0.5：功能面收敛（功能回归清单）

**目的**：把"改了什么代码"翻译成"页面上哪些功能会受影响"，形成本次走查的**唯一范围表**。没有这一步，走查很容易只走改动点就宣布"没问题"——**改动点正常 ≠ 消费它的功能正常**。

> 只读 diff 与引用点，不展开全站阅读（那是阶段 1）；产出是"要查哪些功能"，不是"代码怎么实现的"。

**四类来源（逐类过，防漏）**：

| 来源 | 问句 | 怎么取 |
|---|---|---|
| **调用方** | 谁调用被改的函数 / 组件？ | grep 引用点、组件复用处（≥2 处即每处一项） |
| **数据消费方** | 谁用了被改的字段 / 接口 / store / 事件？ | `.fe-index/` 的 `apis/*.md` 反查页面；`use_skill("relation-lookup")`（未安装跳过）；grep 字段名与 store key |
| **共享能力** | 改的是公共组件 / hook / 工具 / 请求封装吗？ | 引用计数 ≥2 → 每个使用页面各一项 |
| **页面入口** | 改的页面从哪进？ | 路由表 / 菜单 / 深链 / 通知跳转 |

**清单字段（每项一行，表放报告 §2）**：

| 功能项（用户语言） | 入口 | 关联改动 | 预期 | 判定 | 证据 |
|---|---|---|---|---|---|
| 订单备注保存 | 列表 → 详情 → 编辑 → 保存 | `OrderEdit.vue:88` 空值初始化 | 原备注不被清空 | ⬜ 待查 | — |

- **功能项必须用用户语言**（"订单备注保存"而非 `handleSave`）——否则无法向用户确认，也无法与报告发现一一对应
- **判定只允许三态**：`✅ 已验证（附证据）` / `❌ 有问题（转发现清单）` / `⚠️ 未验证（写原因 + 补验方法）`；`⬜` 只是初始占位，**收工时仍为 `⬜` 视同留空**
- **禁止留空与裸 ✅**：`✅` 无证据按 `⚠️` 处理（复用约束 9 的覆盖率门禁）
- **上限 ≤12 项/批**（按批算，不按整次走查算）：超出按"用户可见 × 本页相关"取舍，其余写一行"跨模块影响面未覆盖，建议转 `code-change-impact`"（它是穷举级，本 skill 只到改动面 + 一步下游）
- **共享组件 / hook 的直接使用页属于本次范围**（它们是直接消费方，不算扩面）；"使用页的下游"才越界

**两种模式的清单来源**：

| 模式 | 来源 |
|---|---|
| 定向走查 | diff / 交接单的「改动入口」+ 四类反查；交接单若已给「受影响功能面」→ **先翻译成用户语言的功能项**再核对（review 给的可能是"store 的 5 个消费者"这类代码语言），并补上它没覆盖的来源 |
| 全量走查 | 路由表 + 组件树（本页有哪些功能区块）→ 同样过四类来源，只是"被改代码"换成"本次要走的模块" |

> 模板、取数细节、常见漏项（props / hook / store 消费者、公共组件复用、轮询与埋点、导出与权限菜单、移动端另一入口）见 [references/10-impact-list.md](references/10-impact-list.md)。

### 阶段 1：前端代码直读（白盒规划 + 实现审查）

两个目的：规划"要点什么"（防漏），以及直接判定实现类问题（符合性 `🟢`）。

1. **入口穷举**：从路由表 / 页面组件导出页面清单逐项登记（防只查首页）。**定向模式不做全站穷举**——只读交接单里的改动入口及其上下游（见「定向走查」）
   - **有索引时先查**：仓库已建 `.fe-index/` → `use_skill("index-lookup")` 读 `INDEX.md` 命中前端条目，直接拿 `pages/*.md`（页面清单 + 各页接口/组件）与 `apis/*.md`（接口反查），省一次全站搜索；无索引 / 未命中 / 过期 → 按原流程，不阻塞
2. **状态矩阵盘点**：每页八态在代码里的实现情况——默认 / 加载 / 空 / 错误 / 无权限 / 长文本 / 大数据量 / 窄屏
3. **交互实现检查**（体验相关，不点评命名与架构）：
   - 表单：校验时机（失焦 vs 只能提交后才发现）、错误是否定位到字段、必填标识
   - 提交：loading 态、防重复提交、成功反馈、失败反馈（原因 + 下一步）
   - 危险操作：二次确认、可否撤销
   - 长任务：进度反馈、可中断
   - 列表：分页 / 虚拟滚动、批量操作、筛选与翻页状态保持
   - 中断恢复：刷新 / 返回后状态是否保留
   - 默认值与记忆：常用值是否预填、上次选择是否记住
4. **可用性实现初筛**：键盘可达（Tab 顺序 / Esc 关闭 / Enter 提交）、语义标签与 label 关联、焦点管理（弹窗开 / 关）、点击区域尺寸、对比度（有明确色值时可判）
5. **性能反模式初筛**：首屏阻塞资源、未懒加载 / 未代码分割、图片未优化、请求瀑布（串行）、重复请求与无缓存、长列表未虚拟化、输入无防抖、超大依赖
6. **参考库基线核对（有则做）**：按 `INDEX.md` 找本页使用组件，核对 token / 状态**实现**是否与参考一致；视觉观感留给阶段 2；记录基线版本；只读，不修改参考库
7. **产出走查计划**：按阶段 0.5 的功能清单逐项安排路径（正面 / 边界 / 负面）+ 每步的观察点 → 交阶段 2 执行；清单里排不进本次的项要写明原因，不许静默丢

> 阶段 1 的实现类问题可即时成结论（`🟢`）；但"体验好不好"的判定必须留给阶段 2。
> **与阶段 1.5 的分工**：这里判"有没有做"（有没有防重复提交，`🟢`）；阶段 1.5 判"做了、但某个时序下不够"（禁用只在成功回调里加，请求未返回时仍可点，`🟡`）。同一现象只出一次结论——归因到时序的进 1.5，纯缺失的留这里。
> 详细检查表见 [references/01-walk.md](references/01-walk.md)。

### 阶段 1.5：缺陷推演（挖隐藏 bug）

**目标**：找出"页面看着正常、但用户一操作就坏"的地方。前端缺陷不止时序一类，用**两条腿**覆盖：

- **A 腿｜时序轴**：同一操作在不同异步态 / 不同时刻结果不同（"接口没回来就点按钮"属于这类）
- **B 腿｜清单轴**：数据、输入、权限、路由、集成、环境的组合，在某个真实输入下就坏

**做与不做**：

| 页面类型 | 处理 |
|---|---|
| 有异步依赖 **且** 有可写动作（提交 / 保存 / 删除 / 支付 / 上传 / 导出 / 批量 / 状态切换） | A 腿 + B 腿都做 |
| 有异步依赖、只读（纯展示 / 列表查看） | A 腿降为"未就绪 / 失败 / 形态"，B 腿过族 5、7、3 |
| 无异步、无写操作（静态页 / 文档页） | 跳过，覆盖表记 `-` 不适用 |

1. **列三张清单**（从代码里抠，带 `file:line`）：
   - **异步源**：页面依赖的接口、轮询 / 定时器、WebSocket / SSE、本地缓存、路由参数触发的请求
     - 有 `.fe-index/` 时：`use_skill("index-lookup")` 取 `apis/*.md` 反查该页依赖的接口，直接充当异步源清单；无索引则 grep 请求调用点
   - **可写动作**：提交、保存、删除、支付、上传、导出、批量、开关切换
   - **状态落点**：组件 state、全局 store、URL 参数、localStorage（决定"残留 / 串台"的风险面）
   - 关键问句：**这个动作要用的数据从哪来？** 来自异步接口，就存在"没就绪也能操作"的窗口
   - **另加项目不变量**：仓库根存在 `.review-invariants.md` 时，其每条声明（如"权限必须在接口层校验""金额只传整数分"）作为第 4 类输入，逐条问"这里还能被绕过吗"；文件不存在则跳过（不新建、不阻塞）
2. **A 腿：交叉推演「异步态 × 动作」**（只推"可能真坏"的格，不做全表穷举）：
   - 异步态：未发起 / 请求中 / 失败 / 超时 / **乱序返回（后发先至）** / HTTP 200 但业务错误码 / 会话过期（401）
   - 动作：点主按钮 / 改筛选·翻页·排序 / 切 tab 或路由 / 关弹窗再打开 / 连续快速点击 / 返回上一页
   - 四个追问角度：**就绪拦截**（数据没到能点吗）／**失败收尾**（失败后停在哪、残缺数据还能用吗）／**重复执行**（连点、重试、返回再提交）／**竞态与残留**（旧结果盖新的、上一条串下一条、多标签页并发）
3. **B 腿：十类缺陷族**（按页面类型只过相关的 3-5 族，**不是逐页全过**）：

| # | 缺陷族 | 推演问句（问"哪种真实输入 / 状态下就坏"） |
|---|---|---|
| 1 | 时序与并发 | 接口未返回 / 失败 / 乱序时点按钮会怎样？（A 腿矩阵）多标签页同时改呢？ |
| 2 | 状态一致性 | 同一个值存了两份吗？直接改对象 / 数组了吗？受控与非受控混用？初始值只取一次？ |
| 3 | 生命周期与副作用 | 效应依赖缺项 / 自激循环？卸载后还写状态？定时器与监听清了吗？条件渲染把输入框、富文本重建了吗？`key` 用 index 状态串位？ |
| 4 | 表单与输入 | 前端校验和后端一致吗？异步校验没回来就能提交吗？输入法组合态 / 粘贴带空格 / 全角 / emoji / 超长会怎样？上传中断、成功后不清表单？ |
| 5 | 边界、计算与展示 | 空数组 / 缺字段 / `null` / `0` / 负数 / 超量 / 大整数 / 非法日期 / 时区，哪个白屏或算错？金额、折扣、百分比、单位换算的顺序与精度对吗？长文本截断后能看全文吗？ |
| 6 | 权限与安全 | 前端把校验当安全边界了吗？按钮 / 路由级权限能绕过吗（URL 直达、改接口参数、Tab 聚焦隐藏控件）？用户输入进了 `v-html` / `innerHTML` 吗？token 落在哪？跳转有白名单吗？ |
| 7 | 导航与路由 | 刷新会 404 吗？深链缺参 / 非法参会崩吗？返回后筛选与滚动还在吗？守卫会死循环吗？URL 里的中文 / `+` / 空格编码对吗？ |
| 8 | 集成与依赖 | 第三方 SDK（埋点 / 地图 / 支付 / 验证码）超时失败有降级吗？**发版后旧页面拿不到新 chunk 会白屏吗**？跨域 / 混合内容 / CDN 404？ |
| 9 | 环境与兼容 | 窄屏破版、软键盘遮挡、Safari 差异（日期解析 / 正则 / `100vh`）、缩放与字体放大、暗色、打印，哪一处不可操作？ |
| 10 | 错误兜底 | 白屏有 ErrorBoundary 吗？错误码分类处理了吗？`catch` 是空的吗？有重试与降级 UI 吗？失败后用户知道下一步吗？ |

> **按页面类型预筛**（省时且不漏关键）：列表 / 表格 → 5·7·1·3；表单 / 编辑 → 4·1·2；详情 / 展示 → 5·3·6；后台管理 → 6·10；上传 / 富文本 / 画布 → 4·6·3；移动端 H5 → 9·7·4；支付 / 订单 / 金额 → 5·1·6。
> 逐族细则按包读（先看 [references/INDEX.md](references/INDEX.md) 的阅读矩阵，**只读命中包**）：族 1 → [02-timing.md](references/02-timing.md)；族 2–5 → [03-families-state-form.md](references/03-families-state-form.md)；族 6–7 → [04-families-security-routing.md](references/04-families-security-routing.md)；族 8–10 → [05-families-runtime.md](references/05-families-runtime.md)。

4. **每条假设写成可复现实例**（写不出复现步骤的，不算发现）：

```text
触发条件：详情页 GET /order/1 未返回时点「保存」；账号=编辑者
预期：按钮禁用，或提交时等待数据就绪
推演：表单以空初始值提交 → 原数据被覆盖为空（OrderForm.vue:88）
复现步骤：DevTools 限速 Slow 3G → 打开详情 → 立即点保存 → 回列表看数据是否被清空
后果 / 影响谁：编辑过订单的用户；数据丢失不可逆
证据：🟡 代码可证，[需运行验证]
```

5. **证据分三轨（不要一律 `🟡`）**：
   - **写法缺失**（没有权限判断、没有转义、没有 cleanup、没有超时、没有 ErrorBoundary）→ 代码直读 `🟢`，缺失本身就是证据
   - **时序 / 组合会坏**（未就绪即提交、竞态覆盖、边界输入炸掉）→ 推演 `🟡` + `[需运行验证]`，实操复现升 `🟢`
   - **不可静态确定**（三方库内部、后端真实返回、可利用性）→ 只列假设，`🔴` 进待确认并给验证方法
6. **诚实边界与预算**：
   - **禁止编造运行时数值与攻击链**（"余额变成 -9.99""构造 payload 可窃取 token"式臆造，对齐 `scenario-rehearsal` 披露护栏）
   - **推演 ≠ 推测**：允许的是"触发条件 + 复现步骤 + 标未验证"的假设；"感觉这里可能有问题""用户或许会困惑"这类**无触发路径**的猜测一律不写（与 `code-review` 约束 30「不报没有触发路径的风险」同源）
   - 调度顺序、三方内部行为、后端真实返回，静态不可确定 → 只列假设、不下判定
   - 每页 **≤6 条**假设，优先"能写坏数据 / 重复提交 / 不可逆 / 越权可见"；清单不是越长越好（越长越没人验）
7. **交接给阶段 2**：每条假设带复现步骤与观察点，进阶段 2 定向复现；**每批复现上限 ≤10 条**（超出按"后果严重度 × 可复现性"取前 10，其余标 `🟡` 并写清步骤交用户自查）——复现是为了定论，不是为了把清单全验一遍。

### 阶段 2：真实操作走查（黑盒体验 + 定向复现）

**操作纪律**：像真人一样点击 / 输入 / 等待，边操作边记录；**不用代码实现解释观察结果**——用户看不到内部处理，只看得到结果。

1. **按计划遍历**：逐页触发状态矩阵八态（怎么造出加载 / 空 / 错误态见 [references/01-walk.md](references/01-walk.md)）；**边走边在功能清单上记判定**（`✅/❌/⚠️` + 证据），不要留到最后回忆
2. **三类路径**：正面（正常用）／边界（0 条、10000 条、超长文本、特殊字符）／负面（故意误操作）
3. **场景轴走查**（用户视角的核心，替代空泛的"用户体验"）：

| 场景轴 | 问句 |
|---|---|
| 新用户首次 | 找得到入口吗？知道下一步吗？空态有引导吗？术语不看文档能懂吗？ |
| 高频老用户 | 几步完成？重复输入多吗？有批量 / 快捷键 / 记忆吗？ |
| 误操作 | 能撤销吗？确认合理吗？错误提示说人话吗？ |
| 中断 / 异常 | 刷新能恢复吗？断网怎么办？超时怎么办？重复提交会怎样？ |
| 极端数据 | 超长文本怎么显示？空值 / null / undefined 怎么显示？ |

4. **每条发现记录**：现象 → 复现步骤 → 影响谁（哪类用户 / 哪个任务）→ 证据（截图 / `file:line`）→ 建议方向
5. **定向复现阶段 1.5 的缺陷假设**（默认按假设里的复现步骤逐条试，不额外发挥）：
   - **复现成功** → 证据升 `🟢`（实测复现），来源记「潜在缺陷」，登记实际观察到的现象（如"列表数据被清空"）
   - **复现不成功** → 记「未复现」入报告第 5 节，写明尝试过的手段与环境（限速档位 / 是否断网 / 连点次数），**不得据此宣称此处没问题**
   - **环境造不出该时序**（需特定网络抖动、需后端配合返回乱序）→ 保留 `🟡` `[需运行验证]` 进待确认清单
   - **非时序族按手段表造**：形态 → 改 mock 数据（缺字段 / `null` / `0` / 超长）；输入 → 全角、首尾空格、emoji、超长、极值；权限 → 低权限账号或手改 URL / query；兼容 → 改视口与缩放；集成 → block SDK 域名、停在旧 chunk（见 [references/02-timing.md](references/02-timing.md)「复现手段」）
   - 副作用提醒：复现"重复提交 / 覆盖数据"类缺陷只用测试数据，见阶段 0 的环境边界

### 阶段 3：加载性能体检（体检级）

**只回答"有没有问题、在哪"，不给优化方案**（深入交 `performance-analysis`）。采集与降级细则见 [references/06-performance.md](references/06-performance.md)。

1. 有实操能力时采集：首屏时间、LCP / CLS / INP、TTFB（浏览器 Performance API / 性能面板 / Lighthouse）
2. 资源维度：瀑布是否有串行阻塞、图片体积、重复 / 无用请求
3. 有构建产物时：包体积与依赖构成
4. **无实测时**：只报代码层反模式（`🟡`），报告头声明"未实测"
5. 产出格式：现象 + 证据 + 影响 + **定位方向**（如"首屏被 X 阻塞""首屏图 3MB"）；优化方案与收益量化不在本 skill 范围

### 阶段 4：双视角研判与优先级

0. **清单回归（先核清单，再排优先级）**：逐项回填阶段 0.5 的功能回归清单——`✅` 须附证据（截图编号 / `file:line` / 排除理由）、`❌` 转成发现条目、`⚠️` 写原因与补验方法（**`⚠️` 视为已闭环**，结论就是"未验证"，不算没做完）；**只有空白或仍为 `⬜` 才算未完成**，报告头标「覆盖不完整」。先做这步的好处：`❌` 项还来得及进 Kano 与优先级排序
1. **先过滤误报**：过一遍误报过滤清单（见 [references/07-triage-report.md](references/07-triage-report.md)「误报过滤清单」）——有意取舍 / 第三方默认行为 / 纯美术观感 / **理论上不可达或需毫秒级交错的竞态**默认不算问题；被过滤项写入报告第 5 节并给依据
2. **归属核对**（分拣越界项）：产品级功能缺失 → 交 `product-manager` M3；纯代码质量（命名 / 架构 / 设计模式）→ 不进本清单；后端性能 → 交 `performance-analysis`；**与异步时序无关、点了就坏的功能错误 → 交 `debug`**（本清单只录现象 + 复现步骤，不占条目）；**时序类潜在缺陷即使已复现也留在本清单**，根因定位与修复在实施阶段交 `debug`
3. **用户视角**：影响谁（新用户 / 老用户 / 管理员）× 影响什么任务 × 发生频率
4. **PM 视角**：Kano 分类 + 价值 × 成本评分（口径见 `use_skill("product-manager")` 的 `reference.md` 第一节；未安装则按其口径自主推理，不阻塞）
5. **优先级**：P0（核心任务被卡住，或高频 + 低成本）→ P1 → P2；**P0 必须写明理由**；判定依据不足标 `Kano 待定` 并进待确认，不得默认按"期望"参与排序
   - **潜在缺陷另有 P0 门槛**：已复现且后果为「写坏 / 丢失数据、重复提交造成重复数据或重复扣款、不可逆操作、越权可见」→ P0（按"可能造成损失"套用核心任务那条）；重复查询 / 重复导出这类可清理、无副作用的，不套 P0；未复现的假设最高 P1，且必须在理由里写"未复现"
   - **P3 默认不报**：纯约定 / 风格类（token 硬编码、命名、目录归属、绕过组件封装）可独立成立，但**不得编造用户影响**；默认不进清单，用户要求"彻底审计"时才展开并标 P3（见约束 14）
6. **合并输出**：一张清单，「来源」列区分（体验优化 / 实现修复 / 潜在缺陷 / 加载性能 / 体验增强）

## 约束

1. 报告头必须声明取证档位与证据等级；无实操时禁止出现"已体验 / 操作确认"式表述
2. `🔴` 不进结论区，只进「待确认清单」且必须配验证方法
3. **先操作后结论**：没有操作路径支撑的体验结论不得标 `🟢`
4. **不臆造用户心理**：每条发现必须能回答"哪类用户在什么任务下遇到什么现象"
5. 不修改产品代码；性能只到体检级；视觉只报影响可用性的
6. 一张清单，禁止分表输出（报告第 4 节是同一清单的**专项展开**——只展开已有条目，不算第二张表）
7. 涉及真实副作用（下单 / 删除 / 支付）的操作须在测试环境进行，环境不明先问
8. 一次走查区间内的"排除项"必须如实写出，不得只报问题
9. **覆盖率门禁**：覆盖矩阵与「经走查排除」的每个结论必须可追溯证据（截图编号 / 发现编号 / `file:line`）——追溯不到的项一律标 ⚠️，**禁止用裸 ✅ 充数**（"没查"不得写成"无问题"）；**证据必须真实存在且可复核**，编造证据按报告作废处理
10. **时序 / 组合类结论不得标 `🟢`**：未复现一律 `🟡` + `[需运行验证]`，禁写"必现 / 已确认 bug"；复现失败要写"未复现 + 尝试手段"，不得反推"没问题"（写法缺失类不受此限，代码即证据）
11. **禁止编造运行时值、执行轨迹与攻击链**：调度顺序、三方库内部行为、后端真实返回、可利用性等静态不可确定处，只列假设与验证方法，不写看似精确的状态值或 payload（比模糊结论更危险）
12. **潜在缺陷必须带复现五要素**：触发条件（数据 / 账号 / 时序 / 输入）、操作、观察点、预期 vs 实际、后果与影响谁——缺一不得进发现清单，可先留待确认
13. **安全只报前端可见面**：只报"把校验当边界 / 未转义 / 敏感信息落地 / 可绕过"这类写法缺口与后果，**不构造利用链、不做渗透**；深入安全审计交专门流程
14. **约定类可独立成立，但禁编造用户影响**：违反项目约定（token / 命名 / 目录 / 封装）**不必挂"用户受影响"才能报**，但**不得编造用户影响**（"用户会觉得界面不统一""用户会困惑"这类无证据后果一律不写）；此类问题默认 P3、默认不进清单，用户要求彻底审计时才展开
15. **定向走查按交接单裁维度**：接手 `code-review` 交接单时，范围只到改动面 + 一步下游（**共享组件 / hook 的直接使用页算改动面，不是越界**）；裁掉的维度必须在「明确未覆盖」写理由；**禁止**"顺手看一眼"扩到全站（要全站须用户显式改口），也**禁止**把 review 已核对的布局一致性再核一遍
16. **功能回归清单必建必闭环**：正式走查前必须有功能回归清单（**每批 ≤12 项**、用户语言、四类来源过一遍），完成后逐项闭环（`✅` 附证据 / `❌` 转发现 / `⚠️` 写原因），**只有空白或 `⬜` 视为未完成**（报告头标「覆盖不完整」）；清单只放报告 §2，**不新增第二张发现表**
17. **参考库只读，漂移分类**：`ui-tools/design-reference/` 只作视觉基线，不修改；参考不一致按「有意偏离 / 实现误差 / 参考过时」分类，只报影响可用性的偏离；纯美术差异交 `design-review` / `ui-designer`；无参考库时按通用基线，不阻塞

## 反模式

- ❌ **只截图不点**，就写"体验流畅 / 存在卡点" → 走查是操作流，不是静态看图
- ❌ **无画面假装看过**："页面层级混乱、配色不协调"（其实从未看到渲染结果）→ 必须降级声明
- ❌ **用代码推断体验**："代码里有 loading 分支，所以加载反馈没问题" → 有分支 ≠ 用户看得到，属 `🟡`
- ❌ **把 `🔴` 推断写进执行摘要** → 报告作废重写
- ❌ **滑成 `code-review`**：点评组件命名、状态管理选型、设计模式、目录结构 → 看到自己在写这类内容立即停
- ❌ **滑成后端性能分析**：去分析 SQL、接口 RT、加缓存 → 前端加载性能才是本条线
- ❌ **滑成 `product-manager` M2/M3**：开始规划"下一版该加什么功能" → 本 skill 只报**让现有功能更好用**的增强建议，产品级功能缺失交接 M3
- ❌ **空泛的人性化断言**："用户体验不够友好""交互不够顺畅" → 必须锚定具体场景 + 可观察现象
- ❌ **只报问题不报排除项** → 用户会重复排查已确认无问题的维度
- ❌ **用裸 ✅ 充数**：覆盖矩阵打了 ✅ 却追溯不到任何证据（截图 / 发现编号 / `file:line`）→ 一律改标 ⚠️，**"没查"不得写成"无问题"**
- ❌ **把有意取舍当缺陷**：未做暗色模式 / 未做国际化直接判为缺陷 → 标"需确认是否有意"
- ❌ **把推演当实测**："快速切筛选必现数据错乱"（从未跑过一次）→ 推演最高 `🟡`，标 `[需运行验证]`
- ❌ **只查"有没有 catch"**：看到有 catch / 有 loading 就收工 → 要追问"失败之后用户还能点什么、残缺数据还在界面上吗"
- ❌ **只推成功态**：只推"接口正常返回后一切正常" → 必须推未返回 / 失败 / 超时 / 乱序 / HTTP 200 但业务错误码 / 401
- ❌ **推演清单铺满矩阵**：一页几十条"理论上可能" → 每页 ≤6 条，优先能写坏数据 / 重复提交 / 不可逆的
- ❌ **编造运行时数值**：写出精确的"余额 -9.99"，代码里却拿不出依据 → 只写"可能为负 / 可能被覆盖"并给验证方法
- ❌ **拿理论竞态凑数**：需毫秒级交错、或有全局兜底（请求拦截器 / ErrorBoundary / 幂等键）已覆盖 → 先确认可达性，再决定报不报
- ❌ **把潜在缺陷当体验优化报**："接口失败无提示"其实会让人提交空数据，却按 P2 排 → 来源标「潜在缺陷」，按缺陷门槛定级
- ❌ **十族逐页全过**：把清单当宗教，每页把十族挨个问一遍 → 按页面类型预筛 3-5 族，否则时间全耗在不相干的族上
- ❌ **把隐藏缺陷写成渗透报告**：构造 payload、编利用链、下"可被拖库"结论 → 只报前端写法缺口与后果，可利用性标"待安全评估"
- ❌ **因后端有校验就洗白前端**：后端兜住了 ≠ 没问题（前端假成功、越权可见、提示误导）→ 照报并注明后端是否兜住
- ❌ **只盯异步不看集成**：漏掉"发版后旧 chunk 白屏""SDK 挂了整页空白"这类线上投诉最多的 → 族 8 必过一遍
- ❌ **把防御性建议当缺陷**："建议加防抖""建议补埋点"却没触发路径 → 归体验增强，不进潜在缺陷
- ❌ **给约定类问题编用户影响**："这里硬编码色值，用户会觉得界面不统一" → 约定类可独立成立，但不得虚构用户影响；无证据按 P3 默认不报
- ❌ **结尾问"要不要我帮你改"**：报告只交清单与方向，改码由用户显式发起（`request-guard`）——不把"改不改"变成悬空问题
- ❌ **空泛赞赏**："整体体验不错，继续保持""界面做得挺清爽" → 只写具体可复核的排除项与发现，不写鼓励段落
- ❌ **出多张清单**：体验一份、性能一份、实现一份，用户自己合并 → 违反核心原则 6
- ❌ **给假精确**："预计提升转化 12%""约 3 人日" → 无数据支撑时只给价值 / 成本的高中低
- ❌ **把参考库当生产组件**：直接复制参考 HTML/CSS 进项目，或把参考库当可 import 包
- ❌ **未经确认改参考库**：走查中顺手改 `components/*.html` / `tokens.css` → 参考库只读，更新走同步闸门
- ❌ **无参考库却声称按参考核对**：没读 `INDEX.md` / `meta.json` 就写"已对齐参考库" → 标「未启用」或 ❌

## 与相关 skill 的关系

| skill | 关系 |
|-------|------|
| `product-manager` | 双视角口径来源（Kano / 价值×成本 / 证据三级制）；**产品级功能缺失**交其 M3；M2 / M4 与本 skill 的分工见「定位」 |
| `agent-browser` / `playwright-cli` | 取证工具（A 档实操）；不可用时按 B / C 档降级 |
| `e2e-testing` | 其「动态体验验证」与本 skill 最近，但**前置门禁（须 e2e 全 PASS）与判定对象不同**（见「定位」分工表）；其分批循环思想可借鉴 |
| `code-review` | 实施优化后的代码质量把关 |
| `debug` | 潜在缺陷复现后交它定位根因与修复；本 skill 不查根因（例如"为什么 `finally` 没写"） |
| `scenario-rehearsal` | 推演方法来源（场景实例化 / 纸上执行 / 置信度与降级护栏）；本 skill 只做页面级「异步态 × 动作」，且必须回实操复现；通用代码推演仍走它的代码模式 |
| `request-guard` | 实施前刹车 |
| `performance-analysis` | 接收本 skill 的性能体检发现，做深入定位与优化方案 |
| `ui-designer` / `interaction-design` | 视觉 / 交互的重新设计 |
| `acceptance-verify` | 它判"这一版达标没有"，本 skill 判"下一版该优化什么" |
| `ui-to-ascii` | 需把走查画面转成文本存档时可用；走查给出**布局类改动建议**时，实施前须经其「界面确认闸门」出图并取得用户确认（本 skill 只给建议、不落地） |
| `expert-solution-workflow` | 走查前查可复用经验 / 解决方案（未安装则跳过，不阻塞） |
