# 细则 10｜功能回归清单（阶段 0.5：改动面 → 受影响功能）

> **何时读**：进入阶段 0.5 建清单时；阶段 4 做「清单回归」时。
> 一句话：**改动点正常 ≠ 消费它的功能正常**——共享 hook 改一行，所有调用它的页面都可能是坑。

## 一、这一层为什么不能省

| 没有清单 | 有清单 |
|---|---|
| 走了改动点 → 说"没问题" | 逐项确认"受影响的功能" |
| 范围靠感觉，扩面/缩面都无痕 | 范围是写下来的表，扩缩都要改表 |
| 用户问"都查了吗"无法回答 | 逐项 ✅/❌/⚠️，能指着表回答 |

## 二、四类来源怎么取数

**1）调用方**
- grep 被改组件 / 函数名，看 import 点与模板使用点
- 组件被复用（`<SharedTable>`）→ **每个使用页各一项**，不要合并成"公共组件一项"
- 判定：出现 ≥2 处且渲染路径不同 → 每处独立一项

**2）数据消费方**
- 接口：`.fe-index/` 的 `apis/*.md` 反查页面；无索引则 grep URL 常量或 `api/` 方法名
- 字段：grep 字段名（注意解构 `const { remark }`、别名 `remark: r`、模板 `order.remark`）
- store / 全局状态：grep store hook、`mapState`、selector 名
- 事件 / 回调 / 消息：grep 事件名与订阅点
- 跨模块强关联：`use_skill("relation-lookup")`（未安装跳过，不阻塞）

**3）共享能力**
- 判据：被改文件被 **≥2 处 import** → 共享组件 / hook / 工具 / 请求封装
- 处理：每个使用者页面各一项 —— 这一步最容易漏，也最常出跨页回归
- **不算扩面**：使用页是"直接消费方"，属改动面；越界的是"使用页的下游"（那里再往下追就该交 `code-change-impact`）

**4）页面入口**
- 路由表（含动态参数 / 重定向）、菜单配置、深链格式、通知与邮件里的跳转
- 同一页面多个入口 → 记一项，但在「入口」列写清"N 个入口"

## 三、清单模板

```markdown
| 功能项（用户语言） | 入口 | 关联改动 | 预期 | 判定 | 证据 |
|---|---|---|---|---|---|
| 订单备注保存 | 列表 → 详情 → 编辑 → 保存 | `OrderEdit.vue:88` 空值初始化 | 原备注不被清空 | ✅ | 录屏 S15 |
| 订单导出 | 列表 → 导出 | `useExport.ts:21` 去重 key | 连点只出 1 个任务 | ⚠️ | 无环境，未验证；补验：本地起服连点 ×3 |
```

**判定三态（只允许这三种）**：

| 判定 | 含义 | 必须有 |
|---|---|---|
| `✅` | 已验证没问题 | 证据：截图 / 录屏编号、`file:line`、或"经确认属有意取舍"的依据 |
| `❌` | 有问题 | 转成发现条目（来源列写清） |
| `⚠️` | 未验证 | 原因 + 补验方法（无环境 / 造不出数据 / 需后端配合） |

**留空 = 未完成**：不允许出现空白判定；`⬜` 只是初始占位，**收工时仍为 `⬜` 视同留空**；报告头标「覆盖不完整」。

## 四、上限与取舍（每批 ≤12 项）

**上限按批算，不按整次走查算**：整站走查本就分批（SKILL：每批 ≤8 个页面/功能域 → 阶段 0.5 → 1 → 1.5 → 2 为一轮），每批各自 ≤12 项；否则整站走查永远超限、只能不停写"未覆盖"。

超出时按顺序保留：

1. **用户可见**的功能（能点出一个结果 / 一次状态变化的）
2. **本页 + 一步下游**（与 SKILL 定向模式的范围一致）
3. **改动直接消费的**（数据消费方优先于调用方：改了字段，读它的页面比调它的函数更容易坏）

舍弃的部分不要静默，写一行：

```text
跨模块影响面未覆盖：另有 6 处调用（报表、通知、移动端），建议转 code-change-impact 穷举
```

## 五、常见漏项（真实高频）

- **props 透传**：改的是子组件，父的调用点传参方式也要一项
- **hook / composable 的隐式消费者**：不 import 组件但用了同一逻辑
- **store 跨页面消费**：A 页写、B 页读（改 A 的写入格式 → B 的展示也受影响）
- **不点也会变**：轮询 / WebSocket 推送 / 定时刷新
- **非主路径功能**：埋点、导出、打印、分享
- **权限菜单**：低权限看不到入口 → 高权限走一遍 + 低权限走一遍（越权可见是 P0）
- **多端另一入口**：Web 与 H5 共用接口但不同页面
- **嵌入场景**：iframe / 微前端宿主页
- **外部深链**：邮件、短信、站内信、第三方回跳

## 六、与 `code-change-impact` 的边界

| 维度 | 本清单 | `code-change-impact` |
|---|---|---|
| 粒度 | 页面功能项（用户语言） | 调用方 / 消费方穷举 + 回归风险背书 |
| 规模 | 每批 ≤12 项 | 不限，逐消费方取证 |
| 用途 | 决定走查什么、能否收工 | 决定这次改动会不会把别处写坏 |

**升级信号（命中就建议转）**：改公共组件 / 请求封装 / 全局 store；影响面 >12；跨仓库（前端改、SDK 消费）。

## 七、清单回归（阶段 4 第 0 步）

逐项过一遍，四个动作：

| 现状 | 动作 |
|---|---|
| 空白 | 补查；补不了 → 标 `⚠️` 写原因 |
| 打了 `✅` 但无证据 | 降为 `⚠️`（裸 ✅ 一律不算） |
| `❌` | 生成发现条目（来源列区分），进 Kano 与优先级 |
| `⚠️` | 保留并进「待确认清单」，写补验方法 |

报告头判据（别把 `⚠️` 当没做完）：

| 清单状态 | 报告头写什么 |
|---|---|
| 存在空白或 `⬜`，或 `✅` 无证据（裸 ✅，已降 ⚠️） | 「覆盖不完整」 |
| 全部为 `✅` / `❌` / `⚠️` 三态之一 | 「功能面已闭环（N 项：✅x / ❌y / ⚠️z）」——`⚠️` 的结论就是"未验证"，属已闭环 |

## 八、常见坑

| 坑 | 表现 | 正确做法 |
|---|---|---|
| 用代码语言命名 | `handleSave`、`setState` | 用功能名（"订单备注保存"），否则用户无法确认 |
| 一项顶多页 | "共享表格组件" 一项 | 每个使用页面各一项 |
| 全打勾 | 12 项全 ✅ 但没证据 | 每项挂证据，否则降 ⚠️ |
| 清单膨胀 | 单批 30+ 项 | 每批 ≤12 + 取舍 + 写清舍弃了什么 |
| 建完不用 | 清单躺在报告，走查另起一套 | 阶段 2 必须严格按清单逐项勾 |
