# 细则 09｜定向走查（diff 驱动：交接单消费 + 性质判据）

> **何时读**：接手 `code-review` 阶段 9.5 的交接单，或用户说"这次改动 / 这个 PR 的前端部分验一下"。
> 定向模式的目标不是"查得更多"，而是**把力气全押在改动面上**——布局与设计合理性多半已由 review 核对过，重复核对是双审。

## 一、交接单怎么读

- **缺字段先问，不猜**：最少要拿到「改动性质 / 涉及页面与路由 / 必点路径 / 环境与副作用」四项；缺环境即按 C 档处理（不启用走查，见第四节）。
- **交接单与 diff 冲突时以 diff 为准**：交接单可能是上游凭 diff 摘要写的，不全或过时；读到实际代码发现性质不同（如声明"纯逻辑"却新增了 DOM 结构），按实际改判并向用户说明。
- **「明确跳过维度」不是免检**：它表示"本次不涉及"或"别人已查过"，照抄进报告「明确未覆盖」并**保留原理由**，不要改写成"无问题"。

## 二、改动性质怎么判（从 diff 特征反推）

| diff 特征 | 改动性质 | 裁剪后必做 |
|---|---|---|
| 改事件处理 / 状态 / 流程 / 校验 / 提交逻辑 | **纯交互逻辑** | 族 1·2·3·4·10；**布局跳过** |
| 只改样式取值（颜色 / 字号 / 间距 token），不动选择器结构与条件渲染 | 纯样式取值 | 族 9 + **取值是否真的生效**；交互轻微 |
| 改选择器结构、新增/删除 DOM、栅格、断点、显隐条件 | **布局结构** | 布局必查（对照已确认图）+ 族 5·9 |
| 改请求参数 / 接口调用 / 响应处理 / 缓存 | 数据请求 | 族 1·5；性能按需 |
| 改权限判断 / 角色 / 路由守卫 / 菜单可见性 | 权限鉴权 | 族 6·7 |
| 改路由表 / 参数解析 / 深链 / 返回行为 | 路由导航 | 族 7 |
| 只改文案 / i18n key | 文案 | 5c 长度是否溢出 |
| 混合改动（常见） | 取**主导性质** + 次要性质各取必做项 | 取并集，但仍裁掉明确不涉及的 |

> **判定口诀**：**是否新增 / 删除 / 移动了 DOM 结构，或改变了断点与显隐？** 是 → 布局必须查；否 → 布局跳过。
> **反向陷阱**：纯 token 换色容易被认为是"样式肯定没问题"，但改错变量名 / 覆盖顺序错 → 颜色不生效，这是真实高频缺陷，必须核"取值生效"而不是核"好看"。

## 三、必点路径怎么来（交接单缺这一栏时自己推）

从 diff 反推三类，**每类 ≤2 条、总数 ≤5 条**（定向模式比全量更克制）：

1. **时序**：改动处依赖的异步源——改的正好是"保存 / 提交 / 删除"？→ 未就绪、失败、连点时它会怎样
2. **边界**：改动新增的判断（`if (x)` / `x?.map` / 类型转换）→ `x` 为 `null` / `0` / `''` / 空数组 / 超长 / 极值时走哪条
3. **回归**：被改函数的上游调用点（谁还在用它）→ 至少走一次原路径，确认没被改坏

> **两套预算别混**：**必点路径 ≤5 条**限的是"要点几遍"；**推演假设仍按每页 ≤6 条**（见 SKILL 阶段 1.5）——5 条路径可以支撑 6 条假设，反之亦然。

## 四、与 code-review 的分工（防双审）

| 维度 | code-review 阶段 5 | 本 skill 定向模式 |
|---|---|---|
| 布局与已确认 ASCII 图的一致性 | ✅ 已核（基线存在时） | ❌ **不重复** |
| 运行时破版（溢出 / 遮挡 / 折行 / 点击区过小） | ❌ 静态看不出 | ✅ 有画面时报 |
| 体验顺不顺（路径长短 / 反馈） | ❌ 不判 | ✅ 但只判改动面 |
| 逻辑会不会坏（时序 / 状态 / 边界） | ❌ 静态审查 | ✅ **阶段 1.5 主战场** |
| 代码质量（命名 / 架构 / 模式） | ✅ | ❌ 不评审 |

> **C 档时的自检**：如果你发现自己在写"代码里没有 loading 分支"这类**符合性**结论，说明这其实是 review 的活——定向走查在 C 档只剩"缺陷推演"有价值，其余应交回 review。

## 五、报告差异（定向模式必加一节）

```markdown
## 2. 范围与覆盖
- 模式：定向（来源：code-review 阶段 9.5 交接单）
- 改动性质：纯交互逻辑 → 布局 / 样式维度按交接单跳过（理由：diff 未触及 DOM 结构、断点、显隐）
- 必点路径：3 条（执行 3 / 复现 2 / 未复现 1）
- 明确未覆盖：布局与视觉设计合理性（review 阶段 5 已核）；加载性能（本次未触及资源与首屏）
- 推演覆盖：1 个页面 × 4 条假设（已复现 2 / 未复现 1 / 假设不成立 1）
```

## 六、回传规则

| 走查结果 | 回写动作 |
|---|---|
| **阻塞级**（写坏数据 / 越权可见 / 关键流程不可用） | 以 `QW*` 编号追加到 review 报告 §1.2（**归属必标** 🟥/🟧/⬜/❓）、附本报告指针，并改写 §2.1 合入结论 |
| 非阻塞发现 | 追加「走查补充」节，**不改评分** |
| 两份报告结论冲突 | 取**更保守**者，并在两处注明冲突点 |
| 本次走 C 档 / 未复现 | 不动 review 结论，只标"未验证" |

## 七、常见坑

| 坑 | 表现 | 正确做法 |
|---|---|---|
| 借定向之名做全量 | "顺手把首页也点了" | 只走交接单范围；要扩面先让用户改口 |
| 裁维度不写理由 | 报告"布局：无" | 写"未触及结构 / 断点 / 显隐，按交接单跳过" |
| 把 review 已核的对图再核一遍 | 双份布局结论、互相矛盾 | 布局只报**运行时**破版 |
| 无环境硬跑 | 出一份与 review 高度重复的静态报告 | C 档不启用，写明理由 |
| 走了改动面就宣布"功能正常" | 超出本 skill 边界 | 功能对不对归 `e2e-testing` / `acceptance-verify` |
| 只走 happy path | 正路点了都说"正常" | 必点路径必须含时序 / 边界 / 回归三类 |
