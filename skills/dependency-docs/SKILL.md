# 第三方依赖文档整理器

## 概述

**目的**：在设计阶段前识别并整理第三方依赖文档，为技术设计提供完整的外部依赖信息

**功能**：扫描需求中的外部系统、API、SDK 等依赖，收集关键信息，生成结构化文档存入需求目录

**使用场景**：
- 需求涉及第三方 API、SDK、外部服务时
- 设计前需要梳理外部依赖关系时
- 需要整理第三方文档供后续设计参考时

## 何时使用

在以下情况使用本 skill：

- 需求涉及**第三方 API、SDK、外部服务**
- 设计前需要**梳理外部依赖关系**
- 需要**整理第三方文档**供后续设计参考

## 核心原则

1. **前置整理**：在设计阶段前完成，为设计提供输入
2. **结构化输出**：统一格式，便于后续引用
3. **灵活拆分**：根据依赖数量和复杂度，选择单文档或多文档模式

---

## 工作流

```
阶段 1：依赖识别       → 扫描需求，识别所有第三方依赖
阶段 2：信息收集       → 整理每个依赖的关键信息
阶段 3：文档生成       → 生成结构化文档
阶段 4：落盘归档       → 存入需求目录
```

---

## 阶段 1：依赖识别

### 输入

需求描述或需求挖掘报告

### 识别维度

| 依赖类型 | 识别信号 | 示例 |
|----------|---------|------|
| 第三方 API | 调用外部 HTTP 接口 | OpenAI API、Stripe 支付 |
| 第三方 SDK | 引入外部库/包 | AWS SDK、Google Maps SDK |
| 外部服务 | 依赖外部系统能力 | Redis、消息队列、CDN |
| 数据源 | 连接外部数据库/数据源 | 第三方数据提供商 |

### 输出

```text
📦 第三方依赖清单
━━━━━━━━━━━━━━━━

| # | 依赖名称 | 类型 | 用途 | 信息完整度 |
|---|----------|------|------|-----------|
| 1 | OpenAI API | 第三方 API | 文本生成 | 需补充 |
| 2 | Stripe | 第三方 API | 支付处理 | 需补充 |

共识别 N 个第三方依赖。
请确认清单是否完整？是否有遗漏的依赖？
```

## 阶段 2：信息收集

对每个依赖收集关键信息：

### 信息模板

| 字段 | 说明 | 必填 |
|------|------|:----:|
| 名称 | 依赖名称 | ✓ |
| 类型 | API / SDK / 服务 / 数据源 | ✓ |
| 官方文档 | 文档链接 | ✓ |
| 用途 | 在本需求中的具体作用 | ✓ |
| 接口列表 | 使用到的具体接口/方法 | ✓ |
| 认证方式 | API Key / OAuth / 其他 | ✓ |
| 限流策略 | 频率限制、配额 | |
| 版本要求 | 最低/推荐版本 | |
| 备选方案 | 可替代的其他服务 | |
| 风险点 | 稳定性、成本、合规等 | |

### 信息来源

1. **用户提供**：用户直接提供文档链接或关键信息
2. **WebFetch 抓取**：抓取官方文档页面
3. **WebSearch 搜索**：搜索最新文档和使用示例

### 文档模式选择

| 依赖数量 | 复杂度 | 推荐模式 |

| 1-2 个 | 低 | 单文档 |
| 3-5 个 | 中 | 单文档（分区） |
| >5 个 | 高 | 多文档（每个依赖一个文件） |

## 阶段 4：落盘归档

### 存储位置

检查项目中是否已配置存储位置（`.requirements/config`）：

- **已配置**：读取 `storage_path`，文档存放在 `{storage_path}/{YYYY-MM-DD}-{功能名称}/dependencies/`
- **未配置**：询问用户，给出默认建议 `.requirements/`

### 落盘流程

1. 创建目录：`mkdir -p {storage_path}/{功能名称}/dependencies/`
2. 写入文档
3. 需求管理集成（如已配置）：

```bash
# 单文档
req update {REQ-NNN} \
  --docs add dependencies/dependencies.md,reference \
  --changelog "整理第三方依赖文档"

# 多文档
req update {REQ-NNN} \
  --docs add dependencies/README.md,reference \
  --docs add dependencies/{依赖名}.md,reference \
  --changelog "整理第三方依赖文档"
```

### 输出确认

```text
✅ 第三方依赖文档已生成

文档位置：{path}/dependencies/
文档数量：{N} 个文件

是否需要对外部依赖进行 Demo 验证？
- 验证内容：编写验证脚本，确认第三方 API/SDK 的可用性
- 安全要求：敏感信息（API Key、Token 等）从环境变量读取，不写入代码

请选择 [是/否]：
```

## 阶段 5（可选）：Demo 验证

当用户选择对依赖进行 Demo 验证时触发。

### 触发条件

用户在阶段 4 确认后选择“是”

### 验证脚本规范

#### 安全要求（强制）

- **禁止硬编码**：API Key、Token、密码等敏感信息不得写入脚本
- **环境变量读取**：所有敏感配置从环境变量获取
- **示例模板**：

```python
import os
import requests

# 从环境变量读取敏感信息
API_KEY = os.environ.get("SERVICE_API_KEY")
if not API_KEY:
    raise ValueError("请设置环境变量 SERVICE_API_KEY")

# 验证 API 可用性
def test_api_connection():
    response = requests.get(
        "https://api.example.com/health",
        headers={"Authorization": f"Bearer {API_KEY}"}
    )
    return response.status_code == 200
```

#### 脚本结构

```markdown
# {依赖名称} Demo 验证

## 前置条件
- 设置环境变量：`export SERVICE_API_KEY=your_key`
- 安装依赖：`pip install requests`

## 验证脚本
```python
{验证代码}
```

## 运行方式
```bash
python verify_{依赖名}.py
```

## 预期结果
- 连接成功：输出 “✅ 验证通过”
- 连接失败：输出具体错误信息
```

### 存储位置

验证脚本存放在依赖文档同级目录：

```
dependencies/
├── dependencies.md（或 README.md + 多个依赖文档）
├── verify/
│   ├── verify_{依赖名}.py
│   └── README.md（运行说明）
```

### 落盘流程

1. 创建目录：`mkdir -p {path}/dependencies/verify/`
2. 编写验证脚本
3. 编写运行说明（`verify/README.md`）
4. 需求管理集成（如已配置）：

```bash
req update {REQ-NNN} \
  --docs add dependencies/verify/README.md,reference \
  --changelog "添加依赖验证脚本"
```

---

## 反模式

- ❌ 只列名称不整理详情：文档必须包含接口清单、认证方式等关键信息
- ❌ 信息过时：优先使用 WebFetch 获取最新文档
- ❌ 遗漏依赖：设计阶段才发现未整理的依赖会打断流程
- ❌ 文档无结构：必须使用统一模板，便于后续引用
- ❌ 硬编码敏感信息：API Key、Token 等不得写入脚本，必须从环境变量读取

---

## 需求管理集成

当项目配置了 `.requirements/config` 时，dependency-docs 在落盘后自动执行集成操作：

### 存储路径映射

| 产出物 | 存储路径 | docs 类型 |
|--------|----------|----------|
| 依赖索引 | `dependencies/README.md` | `reference` |
| 单个依赖文档 | `dependencies/{名称}.md` | `reference` |
| 单文档模式 | `dependencies/dependencies.md` | `reference` |
| 验证脚本 | `dependencies/verify/verify_{依赖名}.py` | `reference` |
| 验证说明 | `dependencies/verify/README.md` | `reference` |
