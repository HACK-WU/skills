# create-skill 参考

本文件是 `SKILL.md` 的渐进式展开层，承载四块内容：

1. [形态 → 标杆 skill 对照表](#形态--标杆-skill-对照表)（阶段 1.5 的 L0 用）
2. [参照调研输出模板（详版）](#参照调研输出模板详版)
3. [参照调研示例](#参照调研示例)
4. [description 精简细则](#description-精简细则)（「编写有效的描述」的展开层）

> **引用约定**：标杆 skill 一律以**名称**指代，需要调用时走 `use_skill("<name>")`，不写文件路径（skill 可被单独安装，兄弟目录不保证存在）。

---

## 形态 → 标杆 skill 对照表

**用法**：先判断待建 skill 的形态 → 取该形态下 2-3 个标杆 → 读它们的 `SKILL.md`（只看骨架与约定，不看正文细节）→ 按五个维度提取借鉴点。

| 形态 | 特征 | 标杆 skill（本仓库） | 学它什么 |
|---|---|---|---|
| **守门 / 决策** | 输出"通过 / 拦截 / 路由"结论，有否决权 | `loop-discovery`、`request-guard` | 阶梯式判定表、结论→下一步动作表、触发短语 enum 式列举 |
| **分析 / 审查** | 多维度评估 + 严重度分级报告 | `code-review`、`design-review`、`ecosystem-review` | 维度表 + 证据状态阶梯 + 严重度图例 + 结尾反模式清单 |
| **生成 / 写作** | 产出文档，重结构与全局一致性 | `design-craft`、`document-writer`、`api-design` | 父/子文档拆分、渐进式展开、模板库外置 |
| **编排 / 派发** | 拆子任务并行，主 agent 汇总 | `task-dispatch`、`auto-review`、`expert-team` | 子任务卡契约、汇总复核协议、降级串行路径 |
| **调研 / 检索** | 查现有资产，命中/未命中分支 | `code-survey`、`expert-lookup`、`solution-lookup` | 分层检索顺序、命中/未命中分支、工具不可用降级 |
| **验证 / 测试** | 跑通判据，产出证据 | `acceptance-verify`、`e2e-testing`、`scenario-rehearsal` | 三层证据结构、happy/异常/边界路径、推演方法论 |
| **沉淀 / 记录** | 写入持久资产 | `solution-capture`、`memory-creator`、`ki-memory-write` | 查重、格式硬约束、降级不阻塞 |
| **教学 / 讲解** | 长内容、分阶段、重产物结构 | `topic-teach`、`module-teach` | 阶段化产物树、大块细则外置 `reference.md`、独立评审维度文件 |
| **工具 / 索引** | 确定性操作 + 薄封装 | `web-index`、`gitnexus-index` | 确定性工作交给脚本、skill 只做薄封装、消费/建造双模式分离 |
| **创建 / 元** | 指导创建某类资产 | `create-skill`、`create-rules`、`create-sub-agent` | 前置守门、AI 说明层、SSOT 指路 |
| **需求 / 拆解** | 从输入推导输出清单 | `requirement-mining`、`work-breakdown`、`test-planner` | 「现状 → 预期」图示、checklist 驱动、落盘位置判断 |

**形态判定不出时**：按"主产出是什么"倒推——产出是**结论**→ 守门/分析；产出是**文档**→ 生成；产出是**多个并发成果**→ 编排；产出是**查到了什么**→ 调研；产出是**通过/不通过**→ 验证。

**L0 的额外要求**：除了形态标杆，还要扫一眼**同主题** skill（关键词重叠的），确认不是重复造轮子——但注意，这里的"确认"只影响**怎么写**；是否新建由 `loop-discovery` 裁定。**若本次创建已经过 `loop-discovery` 路由**（其 Step 2 已扫描本地覆盖），这一步可省略，不重复劳动。

## 参照调研输出模板（详版）

```text
🔍 参照调研（Prior Art）

意图：<一句话描述待建 skill>

- L0 同族标杆：<skill>（形态：<形态>）/ <skill>（形态：<形态>）
- L1 管理源：<命中项 / 无>
- L2 社区：<命中项 + 来源 / 无 / 跳过（原因：网络不可用 / 用户要求 / 微调现有）>

可借鉴点：
1. [触发词] <具体写法> ← <来源>
2. [结构] <文件怎么拆> ← <来源>
3. [工作流] <阶段怎么划> ← <来源>
4. [反模式] <坑> ← <来源>
5. [生态咬合] <与谁交接、SSOT 落在哪> ← <来源>

不适用点：
- <外部样本与本仓库规范冲突的部分，及丢弃理由>
- <外部样本过长/过细，压缩方案>
```

**字段说明**：

| 字段 | 要求 |
|---|---|
| 可借鉴点 | 3-5 条，每条**必须标来源**（哪个 skill 或哪个 URL）；只写"要怎么做"，不写背景铺垫 |
| 不适用点 | 至少扫一遍"外部样本 vs 本仓库规范"的冲突；没有就写"无" |
| L2 跳过 | 必须写原因——**"跳过"不写原因等于没做** |

## 参照调研示例

**场景**：要建一个「数据库变更评审」skill（审查 SQL / 迁移脚本 / DDL 变更）。

```text
🔍 参照调研（Prior Art）

意图：新建「数据库变更评审」skill，审查迁移脚本的风险与规范

- L0 同族标杆：code-review（形态：分析/审查）、design-review（形态：分析/审查）
- L1 管理源：无同类
- L2 社区：命中 2 个（某仓库 db-migration-review skill、某团队迁移 checklist 博客），仅取清单结构

可借鉴点：
1. [触发词] design-review 的 description 显式声明"支持任意格式文档评审" → 本 skill 写清
   "SQL / 迁移脚本 / DDL 变更 / 加字段 / 改索引"，避免只写"数据库评审"导致漏触发
2. [结构] code-review 把"维度定义 + 报告格式"放主文件、细则外置 reference.md
   → 本 skill 照此拆：主文件放维度表与报告格式，checklist 放 reference.md
3. [工作流] code-review 的"七维度 + 严重度三级（🔴🟡🟢）" → 本 skill 沿用严重度图例，
   维度改为：锁表风险 / 回滚可行性 / 数据一致性 / 索引影响 / 兼容性
4. [反模式] 社区清单里的"只审语法不审锁表"、"忽略大表 DDL 的执行窗口"
   → 抄进本 skill 反模式表（这是外部参照里性价比最高的一条）
5. [生态咬合] 补「与相关 skill 的关系」表：与 design-review（上游设计评审）、
   code-review（同族但不管 SQL 特性）划边界，交接走 use_skill()

不适用点：
- 社区样本无 AI 说明层（与本仓库规范冲突）→ 丢弃，按本仓库"目的/功能/使用场景"三要素重写
- 社区样本列了 40 条检查项 → 超精简原则，压缩为 8 条核心项，其余外置 reference.md
```

**后续**：这份小结直接进入阶段 2（设计），决定名称 `db-migration-review`、description 措辞、文件拆分与维度表——全程**没有**因为"社区已经有类似的"而中止创建。

## description 精简细则

> `SKILL.md`「编写有效的描述」给硬约束；这里给"为什么短 / 该放哪 / 怎么改"的细则与实例。

### 为什么必须短（不是审美，是可见性）

描述在技能清单中是**截断展示**的，超过截断线的内容**根本不会被读到**——排在末尾的触发词等于没写。

**实测（2026-09-23 批量收敛前）**：`performance-analysis` 的描述长 579 字符，末尾 13 个触发短语（"性能分析"、"为什么这么慢"、"接口 RT 高"…）与 3 条边界声明在清单里**全部不可见**。写的越长，可见的触发信息未必越多。

**反直觉点**：长描述的动机通常是"怕漏触发"，结果恰相反——内容被稀释 + 尾部被截断 → 触发能力下降。

### 内容归位表

| 内容 | 进 description？ | 该放哪 |
|---|---|---|
| 做什么 + 产出 | ✅ 必需（句 1） | — |
| `触发：` + 3-5 个高信号触发词 | ✅ 必需（句 2） | — |
| 触发词全集、长尾口语表述 | ❌ | 正文「使用场景」（AI 说明层） |
| 工作流步骤 / 阶段划分 | ❌ | 正文「工作流」 |
| 模式枚举（M1/M2/M3、S1/S2/S3） | ❌ | 正文「概述」，一行概括即可 |
| 落盘路径 / 产出文件名 | ❌ | 正文（且易随版本过期） |
| 边界声明（"XX 属 code-review"） | ❌ | 正文「与相关 skill 的关系」表 |
| 降级策略 / 工具不可用分支 | ❌ | 正文 |
| 严重度图例、报告骨架、检查清单 | ❌ | 正文或本文件 |

### 改写对照（本仓库真实样本，2026-09-23 数据）

| 现状（仍超预算） | 字符 | 目标（1-2 句） | 约字符 |
|---|---|---|---|
| `performance-analysis`：能力段塞了盘点 / 量化 / 两条路建议，再加 **12 个触发词**枚举 | 237 | 对接口/请求链路做性能分析，定位瓶颈并给出优化建议与验证计划。触发："性能分析"、"为什么这么慢"、"接口响应慢"。 | 72 |
| `module-teach`：两类讲解对象的阶段链（大纲 → wiki → 推演）+ 8-9 个触发词 | 212 | 系统讲解本项目代码（模块或某次变更），产出可反复查阅的学习材料。触发："讲讲这个模块"、"帮我搞懂这块代码"、"讲讲这个 commit"。 | 74 |
| `expert-team`：两层资产 + 子专家 / 专题 + 落盘路径 + 8 个触发词 | 153 | 派多个专家子 agent 并行深挖一个业务模块，产出可复用的模块知识包。触发："掌握这个模块"、"梳理这个模块"。 | 64 |

**存量分布（61 个 skill，同批数据）**：≤120 字符 **23** 个 / 121-200 字符 **34** 个 / >200 字符 **4** 个（`performance-analysis` 237、`module-teach` 212、`web-index` 209、`product-manager` 205）；触发词普遍 **8-18 个**，远超 ≤5 的建议。

> 对照用于演示**写法**，不代表这些 skill 已按目标改写；存量是否收敛由用户决定，但**新建/改造时必须按目标写**。
>
> **取舍提示**：触发词多的描述在触发竞争中有数量优势，精简后的 skill 只能靠句 2 里那 3-5 个**区分词**取胜——写短可以，区分词不能省。

### 自查三步

1. **数句数**：第三句起一律删——先删工作流步骤，再删边界声明
2. **数字符**：>200 字符直接重写；120-200 字符逐句过"删掉它还能不能选中"这一问
3. **看位置**：核心触发词是否落在**前 120 字符**内？不在就挪到 `触发：` 之后
