# 待生效变更策略参考（写入侧）

ki-memory-write 的「待生效变更」策略细则。主流程见 SKILL.md。调用方为 `code-review`（阶段 2.3，发现改动会让既有知识资产失准但变更尚未合入时登记）。查询待生效变更走 `use_skill("ki-memory-lookup")`。

## 定位

待生效变更 = **知识资产待合入变更台账**。

现有 ki 体系隐含假设"代码状态 = 最终状态"，所有写入都默认即时生效。但 **PR / 需求未合入时代码是"提议中"**——此时若直接改记忆，一旦 PR 被拒或被改，记忆就错了；若什么都不做，等合入后上下文早凉了，又没人记得该改什么。

台账解决的就是这个时序缺口：**在上下文最新鲜时把"该改成什么"写下来，等变更落地再执行**。

**与 `expert-lookup` Step 4.5 新鲜度检查的分工**（互补，不重叠）：

| | expert-lookup Step 4.5 | 待生效变更台账 |
|---|---|---|
| 方向 | **事后发现**：代码已经变了 → 反查记忆是否过期 | **事前预约**：知道要变、还不能改 → 先记账 |
| 触发 | 基线 commit..HEAD 的 diff | code-review 主动登记 |
| 输出 | "记忆可能过期，去核对" | "资产 X 合并后应改成 Y"（含现成答案） |

台账的价值恰好在于它**带着答案**：Step 4.5 只能告诉你"该核对了"，台账直接告诉你"改成什么"。

## 覆盖范围（不限于 ki 记忆）

台账登记的是**任何会因本次变更而失准的知识资产**，不止 ki 记忆：

| 资产类型 | 坐标写法 | 示例 |
|----------|----------|------|
| ki 记忆 | `{group}/{relation}` | `错误库/支付/连接池耗尽` |
| 专家资产 | `.module-experts/{模块}/{文件名}`（可带小节） | `.module-experts/订单服务/C2-能力契约.md` |
| wiki | `{wiki 路径}`（可带锚点） | `wiki/部署运维/发布流程` |
| 项目文档 | `{文档路径}` | `docs/api-design.md` |

## 准入门槛（防灌水，硬约束）

台账一旦灌水就没人愿意查，直接退化成死账。**只登记"确实会导致既有资产失准"的变更**：

| 情形 | 是否登记 |
|------|----------|
| 变更会**推翻/修改**既有资产的结论（接口签名改了、配置项换名、模块职责调整） | ✅ 登记 |
| 变更会让既有资产整体**失效**（模块被删除、方案被替换） | ✅ 登记（变更类型 = 失效） |
| 纯**新增**内容，不影响任何既有资产 | ❌ 不登记（合入后直接按常规流程写记忆即可） |
| 变更未合入，且**不确定**是否会让资产失准 | ❌ 不登记（避免噪声；宁可漏登，不可灌水） |

## 写入 API

统一用 `ki_bulk_sync_relation`（与其余六类同一 API），**额外带 `vector=false`**。

| API | 用途 | 关键参数 |
|-----|------|----------|
| `ki_bulk_sync_relation` | 批量写入待生效变更条目 | `scope`（项目标识）、`items[]`（每条含 `group`/`relation`/`module_info`/`tags`）、**`vector=false`** |

- **scope**：项目标识（与其余六类一致）
- **group**：`待生效变更/{功能模块名}`（父目录固定「待生效变更」，子目录按功能模块名动态创建；无明确归属模块的归 `待生效变更/通用`）
- **relation**：`{变更主题}`（短短语，如「支付回调接口签名变更」；不含特殊字符）
- **tags**：`pending`（供查询侧 `ki_query_group` 直查时标识；**本类不进向量，tags 对 `ki_search` 无意义**）
- **module_info**：变更详情（见下方字段模板）
- **keywords**：**不写**——不参与语义检索，写了无收益

> **为什么 `vector=false`**：台账是待办清单不是知识。进向量后，用户问"这个报错怎么解"却召回一条待办条目，是纯噪声。纯 KB 模式让它只走索引直查，两头都干净。
>
> **为什么不需要 `ki_store`**：`vector` 是 `sync_relation` 系列的参数，控制"是否生成向量"，KB 照常写入。这与 `ki_store`"只写向量不写 KB"是两回事——**禁用 `ki_store` 的禁令在本策略下依然完全有效**。

## 字段模板（一个待生效变更 = 一条 relation）

```
【待生效变更｜{变更主题}】
- 触发来源：{PR#128 / commit / 需求名}（**优先写 PR 号**——PR 与 commit 可自动判定是否合入，需求名只能人工确认）
- 资产类型：{ki 记忆 / 专家资产 / wiki / 项目文档}
- 影响资产：{精确坐标，见「覆盖范围」表}
- 变更类型：{新增资产 / 修改 / 失效}（**「新增资产」≠ 准入门槛里"纯新增不登记"**——后者指代码是新增的但不影响既有资产；前者指本次变更需要**新增一条知识资产**，如新模块要建专题记忆）
- 当前内容：{资产现在写的是什么，一句话}
- 合并后应为：{合入后应改写成什么——核心字段，写全}
- 状态：{待生效 / 已合入待结账 / 已废弃}
- 登记时间：{YYYY-MM-DD}
```

**字段填充规则**：

- **合并后应为**（核心）：**趁上下文最新鲜时把目标内容写全**，不要写"需更新为最新签名"这类占位——否则合入后还得重新分析一遍，台账价值归零。这是整个设计的关键字段
- **影响资产**：必须是**精确坐标**（group/relation 或文件路径），不能写"支付相关记忆"——结账时靠它定位，模糊坐标等于没法结账
- **当前内容**：写现在的内容，便于结账时快速比对确认没错位
- **状态**：三态流转见下方状态机；**不写「已结账」**——已结账的条目直接删除，不留残骸。`已合入待结账` **不是必经中间态**，仅在"检测到已合入但本次暂不结账"时标注（如用户明确说先不结账）；正常流程检测到合入即直接结账并删除条目，无需先改状态

## 状态机

```
登记 → 待生效
         ├─ 变更合入 → 已合入待结账 → 结账（**先落地正式变更 → 再删除台账条目**）→ 【条目消失】
         └─ 变更被拒/放弃 → 已废弃 → 删除条目 → 【条目消失】
```

## 结账流程（合入后执行）

**执行顺序不能颠倒**：

1. 按「合并后应为」落地正式变更——**按资产类型分叉**（覆盖范围有四类，不只有 ki 记忆）：
   - **ki 记忆** → 走 ki-memory-write 常规流程（Step 1~4），**group 为目标资产的真实 group**（如 `错误库/支付`），不再是 `待生效变更/{模块}`
   - **专家资产 / wiki / 项目文档** → 按「影响资产」坐标定位并**直接修改对应文件**，不走 ki 写入
2. 确认变更已落盘（记忆可检索 / 文件已保存）
3. `ki_delete_relation` 删除台账条目——**双侧删除**（KB + 向量）且 **wiki 同步删除**
   - ⚠️ 此处的"wiki 同步删除"指 **ki 导出的 wiki 中该台账条目本身**，**不是**「影响资产」指向的项目 wiki 文件——后者是项目里的独立文件，已在步骤 1 按「合并后应为」改好，**不会被本步骤删除**
4. 同步删除 `AGENTS.md` 中的指针行

> **为什么先写后删**：反序会在"正式记忆写入失败、台账已删"时永久丢失这条待办。先写后删保证任何中断点都能从台账恢复。
>
> **`已废弃` 条目**：变更被拒 / 放弃时，**跳过第 1、2 步**（不需要落地任何变更），直接走第 3、4 步删除。"已废弃"只是删除前的**瞬时标注**（想留痕可先改状态再删），**不作为持久状态保留**——无效待办留在台账里就是噪声。与上方状态机图「已废弃 → 删除条目」一致。

## 与 AGENTS.md 的分工（避免双源）

台账条目数少但对"别忘记"的要求极高，所以需要一处**每会话自动可见**的提醒。分工：

| 载体 | 内容 | 职责 |
|------|------|------|
| ki 台账（`待生效变更/{模块}`） | **完整条目**（SSOT，含「合并后应为」） | 持久存储 + 精确定位 |
| `AGENTS.md` | **一行指针**，不含条目内容 | 被动提醒"有账要清" |

指针行写法（**必须带自解释指令行**）：

```markdown
## 待生效记忆变更
- 共 2 条待结账，见 ki 台账 `待生效变更`（PR#128 合并后清理）
  ⚠️ 见到本行即执行结账检测：use_skill("ki-memory-lookup") 待生效变更策略 → 逐条判定变更是否已合入 → 已合入的提示用户结账
```

> **为什么必须带指令行**：台账的**唯一自动检测点是 `code-review` 阶段 2.3**。若 PR 合入后不再走 code-review（合入即切走、或改动由他人合入），就没有任何自动时机触发结账，台账沦为死账。AGENTS.md 每会话自动注入，把"该做什么"写进指针行本身，等于给台账加了一个**不依赖任何 skill 挂载点**的兜底触发——无需改动 `ki-search-first` 等规则即可生效。
>
> **为什么 AGENTS.md 不复制条目内容**：复制即双源，合并后要双删（内容 + 指针），任一漏删就漂移。指针行只承担"提醒 + 触发指令"职责，内容单一源在 ki，结账后只需删这一行。

## 写入要点

- **一条变更一条 relation**：同一 PR 影响多个资产 → 按资产分别登记（各自有独立的「合并后应为」，合并成一条会互相干扰）
- **重复触发即更新**：同一 PR 对同一资产的变更重复触发登记 → 更新「合并后应为」，**不新建条目**（对齐 Step 3.6 查重前置）
- **生命周期尽量短**：PR 合入即结账，不留过夜账。台账长期有条目 = 流程没跑通，不是设计问题
- **同一资产被多个未合入变更影响时**：按变更分别登记（各自有独立的「合并后应为」）。结账按合入顺序执行，**后结账的必须先重读资产当前内容**——前一个变更可能已改写过该资产，此时「合并后应为」需按新内容重新表述，**不可直接套用登记时的原文**（套用会覆盖掉前一个变更的成果）
- **不进向量**：校验落盘用 `ki_query_group` 直查，**不可用 `ki_search`**——不进向量必然搜不到，搜不到不等于写入失败
- **删除仅限本类**：`ki_delete_relation` 只用于本策略结账，其余六类不删除（知识资产演进靠覆盖更新）

## 降级

ki 不可用时跳过写入，改为**直接写入 `AGENTS.md`**（此时 AGENTS.md 承载**完整条目**而非指针——降级模式的例外，保证待办不丢），不阻塞 `code-review` 主流程（与其余六类的降级约定一致）。

**ki 恢复后补登**：按字段模板将条目写入 `待生效变更/{模块}`，并**同步把 `AGENTS.md` 里的完整条目替换回标准指针行**（含指令行）——否则降级模式遗留的完整条目会与 ki 条目形成双源，回到本策略要避免的老问题。
