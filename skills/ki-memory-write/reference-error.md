# 错误库策略参考（写入侧）

ki-memory-write 的「错误库」策略细则。主流程见 SKILL.md。调用方为 `debug`（Step 5 回归验证通过后）、`solution-capture`（Step 7 更新索引之后）。查询错误库走 `use_skill("ki-memory-lookup")`。

## 定位

错误库 = **报错文本 → 根因/解法** 的语义映射原子。

`.solutions/` 是**文件级**资产，前提是你能找对那个文件。但报错文本变体极多（路径不同、版本号不同、堆栈行号不同），INDEX.md 的关键词匹配命中率很低——错误库让 AI **贴整段堆栈进去也能语义命中**，这是文件方案做不到的。

**与 `.solutions/` 的分工**（沿用专题记忆"路标不复制本体"原则）：

| | `.solutions/` | 错误库 ki 原子 |
|---|---|---|
| 形态 | 完整可执行的解决方案 skill（能加载、能跑步骤） | 语义路标（报错原文 → 根因/解法摘要） |
| 查找方式 | INDEX.md 关键词匹配（需找对文件） | 语义检索（贴报错原文即命中） |
| 内容 | 完整步骤 + 关键代码 + 注意事项 | 摘要 + 指向 `.solutions/{分类}/{ID}/` |

二者互补：错误库负责"找到"，`.solutions/` 负责"照做"。**错误库不复制方案正文**，只存路标 + 指向。

## 准入门槛（写入前置，硬约束）

错误库的最大风险不是查不到，是**噪声淹没 + 重复爆炸**。注意 `ki_manage_index_create` **无 delete 操作**，灌进去的噪声 group 删不掉。两条硬约束：

### 1. 查重前置（必做）

写入前先 `ki_search(query="{报错特征}", tags="error")` 查重：

- **命中** → **更新**已有条目（补报错变体、复现次数、更优解法），**不新建**
- **不命中** → 新建

**命中判定规则**（防止 AI 每次都判"不命中"而新建重复条目）：

| 情形 | 判定 | 动作 |
|------|------|------|
| 异常类型相同 **且** 根因相同 | 同一条 | 更新（补变体 / 次数 / 更优解法） |
| 同一异常类型但**根因不同**（如都是 `ConnectionError`，一次连接池耗尽、一次 DNS 解析失败） | 不同条 | 新建，relation 用错误特征区分 |
| 判定存疑 | **按"同一条"处理** | 宁可合并更新，不可重复新建 |

其余五类 relation 天然唯一，错误库没有这个约束必然爆炸——同一报错换个路径、换个版本号就是"新错误"。

### 2. 非平凡门槛

只记**非平凡**错误（沿用 `solution-capture` 的判定标准，满足任一）：

- 解决过程涉及 3 个以上步骤
- 需要查找文档、试错、调试才能解决
- 问题具有复现性，可能再次遇到
- 解决方案包含非显而易见的技巧或注意事项
- 涉及特定工具/框架的坑或最佳实践

**不记**：拼写错误、路径写错、语法错误、一次性的环境偶发问题。

## 写入 API

统一用 `ki_bulk_sync_relation` 批量写入（与其余五类同一 API，按 group 区分）。

| API | 用途 | 关键参数 |
|-----|------|----------|
| `ki_bulk_sync_relation` | 批量写入错误库原子 | `scope`（项目标识）、`items[]`（每条含 `group`/`relation`/`module_info`/`tags`） |

- **scope**：项目标识（与 expert-team 其他 ki 写入一致）
- **group**：`错误库/{功能模块名}`（父目录固定「错误库」，子目录按功能模块名动态创建）
  - **子目录按模块名**，与其余五类口径统一；技术栈/工具名写进正文与 keywords，**不占 group 位**
  - **无明确归属模块**（Docker / Nginx / 工具链 / 语言级问题）→ 归 `错误库/通用`
- **relation**：错误特征（短短语，如「Redis 连接池耗尽」）
  - **贴报错原文是 `module_info` 的事，不是 relation 的事**——relation 是精确匹配键，必须是稳定可复述的短语
- **tags**：`error`（供查询侧用 `tags="error"` 过滤）
- **module_info**：错误详情（见下方字段模板）

## 字段模板（一个错误特征 = 一条 relation）

```
【错误库｜{错误特征}】
- 报错原文片段：{3-8 行关键堆栈或报错文本，保留异常类型 + 关键 message}
- 现象：{外在表现，一句话}
- 根因：{为什么会这样}
- 解法：{最小修复 1-3 步}
- 验证方式：{怎么确认修好了：命令 / 测试用例 / 观察指标}
- 关联方案：{.solutions/{分类}/{ID}/，无则「无」}
```

**字段填充规则**：

- **报错原文片段**：只留**特征串**（异常类型 + 关键 message），剥掉易变部分（绝对路径、随机 ID、行号、版本号）——保留易变部分会导致换个环境就命中不了
- **解法**：最小修复步骤，不贴完整实现（完整方案在 `.solutions/`）
- **关联方案**：已沉淀到 `.solutions/` 时必填路径；未沉淀写「无」

## 写入要点

- **仅独立使用时写**：`debug` 被 `api-testing` / `e2e-testing` / `demo-verify` 转调时，由调用方决定是否写入，**不在被转调路径上无条件写**（对齐 debug「需求管理集成」的既有约定）
- **批量写入**：错误多时用 `ki_bulk_sync_relation` 一次写入多条（单次 ≤ 50 条，超出分批）
- **tag 固定 `error`**：与 `api` / `data` / `relation` / `decision` 区分，查询侧可用 `tags="error"` 精确过滤
- **路标式不复制方案**：只存"报错 → 根因/解法"入口，完整步骤指向 `.solutions/`

## 降级

ki 不可用时跳过写错误库，不阻塞调用方主流程（与其余五类的降级约定一致）。
