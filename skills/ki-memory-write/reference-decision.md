# 决策记忆策略参考（写入侧）

ki-memory-write 的「决策记忆」策略细则。主流程见 SKILL.md。调用方为 `expert-team`（Step 8.6，识别模块关键决策后调用）。查询决策记忆走 `use_skill("ki-memory-lookup")`。

## 定位

决策记忆 = **"当初为什么这么定、砍掉的备选是什么"** 的持久化记录。其余五类记忆答"模块有什么 / 接口在哪 / 数据怎么流 / 和谁耦合 / 报错怎么解"，决策记忆答**"为什么"**——git log 只告诉你改了什么，不告诉你为什么。

**与 GitNexus 的关系**：GitNexus 答"代码现在长什么样"，决策记忆答"当初为什么这样"。两者叠加才是完整的影响分析——只知现状不知成因，改代码时无法判断"这个选择是否该被推翻"。

## 证据门（写入前置，硬约束）

决策记忆的最大风险是**编造**。调用方多为**事后反推**（expert-team 建专家资产时模块早已存在）：代码里只有结果没有过程，git log 只说改了什么，commit message 可能含糊。AI 极易臆造"当时的考虑"。

**臆造的决策比没有更糟**——它会污染 `request-guard`（"历史决策说否决了 webhook"→ 其实从没人这么决定过）与 `code-review` 的判断，且因为是"记忆"，AI 会默认其可信。

**优先记有证据的决策**，证据来源限三类：

| 证据类型 | 说明 |
|----------|------|
| 文档明写 | 设计文档 / ADR 明确写出（含 design-craft 落盘的「关键决策点」表、requirement-mining 的「关键决策点」小节） |
| 提交说明 | commit message / PR 描述明确说明 |
| 代码注释 | 代码注释 / docstring 明确写出（如 `# 不用 webhook：依赖方不支持回调`） |

**先找再判**：三类证据需**主动挖掘**，不被动等待——写前先查：① 项目设计文档目录（含 design-craft 落盘的「关键决策点」表）② `git log -S{关键符号}` / PR 描述 ③ 关键实现处的代码注释。**老模块常三类全无**，此时按下表 `[推测]` 分级处理，不要直接放弃整条决策。

**低置信度决策用 `[推测]` 标注**（对齐 `debug`「无证据支撑的推断标注 `[推测]`」的既有约定）：

| 情形 | 处理 |
|------|------|
| 有三类证据之一 | 正常记录，证据来源写明出处 |
| **无直接证据，但代码结构强烈暗示**（如"明显是轮询实现且全模块无任何 webhook 相关代码""配置项里留了未启用的重试开关"） | **可记录**，决策字段前置 `[推测]`，证据来源写「无直接证据，基于{具体结构}推断」 |
| 纯猜测，无任何结构支撑 | **禁止记录** |

> `[推测]` 记录提供的是**线索**而非事实——查询侧须按标注降级使用（见 `ki-memory-lookup` 决策记忆策略）。宁可给一条带标注的线索，也不要让"为什么"这一层长期空白。

**`[推测]` 的两条附加约束**（防止证据门被"加个标注就行"架空）：

1. **限量**：单个模块 `[推测]` 条目**不超过 3 条**，只记最关键、最可能被追问"为什么"的决策。超出说明证据挖掘不充分，应先回到代码/文档补证据，而不是继续堆推测条目
2. **可被坐实**：`[推测]` 是**过渡态不是终态**——后续若获得证据（翻到设计文档、问到当事人、git log 翻出说明），应更新该条目：**补上证据来源并移除 `[推测]` 标记**，不让它长期停留在推测态

- **红线——不推测填充**：字段空缺写「无」，**不因模板要求而编造备选方案与否决理由**。注意与 `[推测]` 标注的区别：**标注"这是推测"是允许的，编造"曾经考虑过某方案但因 X 否决"是禁止的**
- **标注证据来源**：每条决策注明来源（设计文档路径 / commit hash / 注释位置 / 推断依据），便于后续复核与失效清理

## 写入 API

统一用 `ki_bulk_sync_relation` 批量写入（与其余五类同一 API，按 group 区分）。

| API | 用途 | 关键参数 |
|-----|------|----------|
| `ki_bulk_sync_relation` | 批量写入决策记忆原子 | `scope`（项目标识）、`items[]`（每条含 `group`/`relation`/`module_info`/`tags`） |

- **scope**：项目标识（与 expert-team 其他 ki 写入一致）
- **group**：`决策记录/{功能模块名}`（父目录固定「决策记录」，子目录按功能模块名动态创建）
- **relation**：`{分类}-{决策主题}`（如 `技术选型-轮询而非webhook`、`性能取舍-订单查询加缓存`；**不含 `→` 等特殊字符**）
  - **带分类前缀的目的是"列目录即可判断"**：查询侧用 `ki_query_group(mode="full")` 列出 relation 清单时，前缀让决策一眼按分类归拢
  - 长度风险可忽略：`ki_get_module_info` 的 `relation` 虽是精确匹配，但名称是从清单**复制**而非手打，不会因变长取不中
- **tags**：`decision`（供查询侧用 `tags="decision"` 过滤）
- **module_info**：决策内容（见下方字段模板）

## 决策分类（文本标注，不占 tag 位）

**分类只作为 `module_info` 的文本字段 + `keywords` 存在，`tags` 恒定 `decision`**。

> **为什么分类不能用独立 tag**：`ki_search` 的 `tags` 多值是**逗号分隔的 OR 组合**，无法表达"既是决策记忆、又属于某分类"的 AND 过滤；一旦给分类开独立 tag（如 `decision-性能`），`tags="decision"` 就收不住范围。分类只能是文本标注。

### 主分类（必填，单选，按**决策性质**分）

| 主分类 | 约束的是什么 | 示例 | 「重新评估触发条件」的常见形态 |
|--------|-------------|------|---------------------------|
| 技术选型 | 选了哪个技术 / 组件 / 方案 | 用轮询不用 webhook；Redis 而非 Memcached | 依赖方支持新能力、组件停止维护 |
| 架构设计 | 模块划分、职责边界、同步/异步 | 拆子服务 vs 单体；写路径异步化 | 规模 / 复杂度越线 |
| 接口契约 | 对外 API / 数据结构约定 | 状态用枚举不用布尔；返回结构扁平化 | 调用方需求变化、版本升级 |
| 性能取舍 | 为吞吐 / 延迟 / 资源做的权衡 | 加缓存牺牲强一致；批量写牺牲实时性 | 阈值突破（QPS / 延迟 / 数据量） |
| 兼容处理 | 为兼容历史 / 外部做的妥协 | 保留旧字段、双写过渡期 | 依赖方升级完成、历史数据清理完 |
| 安全合规 | 为安全 / 合规做的约束 | 敏感字段脱敏、鉴权方式 | 合规要求变化 |
| 其他 | 不属于以上（不确定时归此） | — | — |

> **为什么按"性质"而非"动机"分**：按动机分（优化 / 踩坑 / 降本）**不正交**——一条决策常同时"既为优化又为避坑"，归类二义；且"踩坑"与专题记忆的「高频坑」、`C0` 的已知问题、错误库三类**重叠**，会造成双源漂移。性质维度正交且可判定，动机降级为下方可选标注（你仍能按"优化""避坑"检索到）。

### 动机标注（可选，0-2 个短标签）

`优化` / `避坑` / `降本` / `可维护性` / `赶工期` …（不封闭，可按需增补；无则写「无」）

**硬约束——标 `避坑` 必须写明避的是什么坑**：格式 `避坑：{现象 → 后果}`（如 `避坑：批量插入不分批 → 连接池耗尽`）。**写不出具体坑就不许标**——否则"避坑"会退化成垃圾桶，并与错误库 / 已知坑抢地盘。

### 分类词进 keywords

分类词与动机词会真实出现在 `module_info` 中，符合 keywords「须为自然语言词且真实出现在原文」的规则，**建议一并写入 `keywords`**（3-5 个），提升按分类检索的命中率。

## 字段模板（一个决策 = 一条 relation）

```
【决策记录｜{决策主题}】
- 分类：{技术选型 / 架构设计 / 接口契约 / 性能取舍 / 兼容处理 / 安全合规 / 其他}（必填单选）
- 动机：{优化 / 避坑（须写明"现象→后果"）/ 降本 …，0-2 个；无则「无」}
- 决策：{最终选了什么，含关键参数/阈值}（无直接证据时前置 `[推测]`）
- 背景约束：{当时为什么必须这么选，1-2 条硬约束}
- 被否决方案：
  - {方案A}：否决理由 {…}
  - {方案B}：否决理由 {…}
- 重新评估触发条件：{可观测判据，如 QPS>5000 / 消息延迟>1s / 依赖方支持 webhook}
- 关联代码：{关键类/方法 @ 文件路径}
- 证据来源：{设计文档路径 / commit hash / 代码注释位置}
```

**字段填充规则**：

- **被否决方案**：事后场景（expert-team）常拿不到备选，允许写「无」——**不因字段空缺而编造备选与否决理由**
- **重新评估触发条件**：必须是**可观测判据**（阈值 / 依赖变化 / 技术栈支持），写不出就写「无」；禁止"性能不足时""业务变化时"这类不可判定的空话
- **关联 commit**（可选）：短 hash + 一句话；rebase/squash 后可能失效，**失效不阻塞**——模块名 + 决策主题本身已可定位，与专题记忆"路径失效不误导跳转"同理
- **证据来源**（必填）：有证据的写明出处（设计文档路径 / commit hash / 注释位置）；`[推测]` 条目写「无直接证据，基于{具体结构}推断」。**纯猜测（无任何结构支撑）的决策整体不写入**，故不会出现"既无证据又无推断依据"的条目

## 写入要点

- **跳过条件**（对齐 Step 8.3/8.4 的"无则跳过"模式）：模块无明显非显然设计选择（纯 CRUD）→ 跳过；无任何证据支撑的决策 → 跳过，**不写空记录**
- **一时一策**：每个决策一条 relation，不合并多决策到一条
- **路标不复制本体**：ki 存决策要点 + 证据来源；完整上下文指向专家资产 `C5-关键决策.md` 或源设计文档，避免双源漂移
- **tag 固定 `decision`**：与 `api` / `data` / `relation` / `error` 区分，查询侧可用 `tags="decision"` 精确过滤；**分类不另开 tag**（理由见「决策分类」节）
- **建议带 `keywords`**：把分类词 + 动机词 + 模块名一并写入（须为自然语言词且真实出现在 `module_info` 中），提升按分类检索命中率

## 降级

ki 不可用时跳过写决策记忆，不阻塞调用方落盘（与其余五类的降级约定一致）。
