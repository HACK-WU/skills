# plan-track 参考

本文件是 `plan-track` 的细节补充：字段详解 → 清单增补 → 跨会话续做 → 完整示例 → 目录管理。

## 1. 字段详解

### 1.1 plan.md frontmatter

| 字段 | 必填 | 说明 |
|------|------|------|
| `task` | 是 | 一句话任务名，与目录 slug 对应，便于检索 |
| `status` | 是 | `进行中` / `已阻塞` / `已完成` / `已放弃`；**只在这四个里取值** |
| `created` / `updated` | 是 | 建档日 / 最后更新日；`updated` 每次改动都必须刷新，它是"文档是否还活着"的唯一信号 |
| `related` | 否 | 关联需求 ID / **需求名（报告未落盘时的唯一标识，如 `requirement-mining` 快速实现路径未走 8.2 落盘；建议带日期或限定词，避免同名需求被 Step 1 查重误判为同源）** / 设计文档相对路径；**单向引用**——只写指向，不把需求内容复制进来（复制即双源） |

> **两套状态别混**：frontmatter 的 `status` 描述**任务整体**（四个值）；工作项表里的状态描述**单项**（六个值）。不要把单项状态写进 frontmatter，也不要在工作项表里写"已阻塞"以外的整体状态。

### 1.2 完成判据 vs 工作项

两者常被混为一谈，边界如下：

| | 完成判据 | 工作项 |
|---|---|---|
| 回答的问题 | "整件事做完了长什么样" | "要做哪几步" |
| 数量 | 1-3 条 | 3-8 条（粗粒度） |
| 形态 | 可观测状态（判据） | 可执行动作（任务） |
| 与清单的关系 | `checklist.md` 的 A 组直接对齐它 | 每项的证据回填到 plan.md，不重复进清单 |

### 1.3 证据分级（写进「证据」列）

| 级别 | 写法示例 | 能否支撑「已完成」 |
|------|----------|------------------|
| 强 | `pytest tests/test_order.py::test_timeout → 3 passed` | ✅ 可以 |
| 中 | `src/order/service.py:120-146 已改 + 手工跑通 create 流程` | ✅ 可以 |
| 弱 | `已读代码确认逻辑正确` | ❌ **只能标「已改未验」** |
| 无 | `-` | ❌ 只能标「待办 / 进行中」 |

**原则**：证据要能被**另一个不知道上下文的人复核**——写"跑过了"不算，写清跑的是什么、看到什么才算。

### 1.4 注意事项（执行护栏）

plan.md 里唯一**面向过程**的一节：工作项与判据管"做成什么"，它管"过程中别踩什么"。它拦的失败形态是**"每项都标了完成、证据也齐全，但方向已经偏了"**——这类失败另外三处都拦不住。

**与相邻内容的边界**（别写成同一件事的三个副本）：

| | 完成判据 | 注意事项（护栏） | 决策与偏差 | 清单项 |
|---|---|---|---|---|
| 时态 | 终态（做完后） | 全程（执行中） | 事后（已发生） | 验收时 |
| 内容 | 达成什么状态 | 不能做什么 / 必须做什么 | 改了什么、为什么 | 逐条判定通过与否 |
| 数量 | 1-3 条 | 3-7 条（无则整节省略） | 不定 | 骨架 + 类型增补 + E 组 |
| 失效方式 | 达成即勾 | **裁决留痕，不删行** | 不改历史 | 只回填，不改题 |

**写法正反例**（判据：能回答"守住了 / 没守住"，且有外部来源）：

| 反例（不合格） | 正例 |
|---|---|
| 注意代码质量 | 不在 `service.go` 里新增硬编码阈值，统一走 `config.Timeout` |
| 尽量保持向后兼容 | 不得改动 `/api/v1/order` 现有响应字段，新增字段只增不删 |
| 小心并发问题 | 幂等键校验必须先查后写，且查写在同一个事务内 |
| 注意别影响其他模块 | 改 `parse_iso8601` 前先全仓搜调用点逐个确认（当前 7 处） |

**引用写法**：工作项「证据」列与清单「证据」列用 `守 #N → 已确认（怎么确认的）`，N 为护栏编号。**编号只追加、不重排**（删行或裁决后编号不复用）——否则跨会话里已写下的 `守 #N` 会指向别的护栏。

**不适用时的处置**（三步，**不要删行**——删行等于把已知风险从台账抹掉）：

```
1. 护栏行「备注」标 [已裁决不适用]
2. 「决策与偏差」追加一行：事项 / 裁决 / 原因
3. checklist E 组对应条目仍回填：✅ 通过，证据写"已裁决不适用，见决策与偏差 #N"
```

**执行中新发现的护栏**：plan.md 追加行（标注 `[执行中发现]`）→ **同一批**在 checklist E 组补一条 → 后续工作项按它约束。只加 plan 不加清单，验收必然漏检。

## 2. 清单增补项（按任务类型叠加到 A/B/C/D 骨架）

| 任务类型 | 建议增补 |
|----------|----------|
| 代码实现 | 边界条件 / 空值 / 并发路径有对应处理；新增公开接口有文档或注释 |
| 脚本 / CLI | 参数非法时的行为已验证；退出码符合预期；幂等性已确认（可重复执行） |
| 文档 / 技能文件 | frontmatter 合法；围栏配对；跨文件引用目标存在（用 `use_skill` 而非相对路径） |
| 配置 / 部署 | 配置项有默认值；改动的配置已在目标环境核对；回滚方式明确 |
| 数据变更 | 变更前后数据量/结构对比；不可逆操作有备份或 dry-run 记录 |
| 前端 | 关键交互路径实跑过；异常/空数据显示正确；无控制台报错 |
| 排查类任务 | 根因有证据支撑（不是"可能"）；复现步骤可重放；修复后原现象不再出现 |

**增补项同样要定严重度**：判据同 SKILL.md（P0 = 不通过会产出错误结果 / 数据损坏 / 交付不可用 / 未验证即交付；P1 = 可延后）。

**取舍规则**：增补项只加**本任务真正可能出错**的那几条——清单越长，越会被整体跳过。

### 2.1 清单项 C1「影响面排查」的最小动作（不依赖任何外部工具）

| 场景 | 最小动作 |
|------|----------|
| 改了函数 / 方法签名 | 全仓搜索该符号的调用点，逐个确认是否需同步改 |
| 改了数据结构 / 字段 | 搜索该字段的读点与写点，确认消费端不需要适配 |
| 改了对外接口 / 配置项 | 查 README、文档、配置文件、路由注册处的引用 |
| 改了共享工具 / 公共模块 | 搜索其全部引用方，按"引用方是否受影响"逐个判定 |

**判定底线**：排查手段不足（如动态调用、反射、外部分布式消费方）时**只能标 ⚠️ 存疑并写明缺什么**，不得标 ✅——"查不到"不等于"没有影响"。

### 2.2 E 组（护栏组）的生成规则

E 组不是"任务类型增补"，而是 **plan.md「注意事项」的镜像**——生成规则：

| 规则 | 说明 |
|------|------|
| 一对一 | 注意事项 #n → E 组 En，条数相同、顺序相同 |
| 严重度 | 取注意事项「违反后果」列：错结果 / 数据损坏 / 不可逆 → P0；可维护性 / 体验 → P1 |
| 问法转换 | 把"不要做什么"改写成可判定的问句（"是否未在 `service.go` 新增硬编码阈值？"） |
| 去重 | 与 A/B/C/D 既有项等价的护栏**不单列**（改写既有项或并入工作项备注）；E 组只收"骨架没有、本任务特有"的约束 |
| 同步修改 | plan 侧新增 / 裁决护栏时，E 组**同一批**改完；只改一侧即违反核心原则 8 |
| 无护栏 | plan.md 没有该节 → checklist **不建 E 组**（建空组 = 假动作） |

**取舍同样适用**：护栏超过 7 条时先怀疑任务该拆，而不是照单全收进清单——清单越长，越会被整体跳过。

## 3. 跨会话续做流程

中断后（新窗口 / 新会话 / 隔天继续）按以下顺序恢复，**不要凭记忆开工**：

```
1. 读 .plans/{最近目录}/plan.md
   ├─ 看 frontmatter.status：已完成 / 已放弃 → 无需续做
   └─ 进行中 / 已阻塞 → 继续
2. 定位续做点（按优先级）
   ├─ 有「进行中」→ 从它继续
   ├─ 有「已改未验」→ 先验证再往下（最容易漏的一步）
   └─ 全「待办」→ 从第 1 项开始
3. 读「注意事项（执行护栏）」→ 本轮动作按它约束（**续做时最容易忘的一节**）
4. 读「决策与偏差」→ 避免重复踩已否决的方案
5. 读最后 3 条「进度日志」→ 确认"下次从哪继续"的交代
6. 开工，并在本轮结束前回写 plan.md
```

**中断前必做**：在「进度日志」写清"下次从哪继续"一句话——这是给未来的自己（或下一个窗口）留的路标。

## 5. `.plans/` 目录管理

| 事项 | 约定 |
|------|------|
| 位置 | 项目根 `.plans/`（隐藏目录）；跨仓库任务放**主仓库根**，不散落 |
| 命名 | `{YYYY-MM-DD}-{kebab-case-slug}`；同日多任务靠 slug 区分 |
| 并行任务 | 一个任务一个目录，互不覆盖；不要把多个任务塞进同一份 plan.md |
| 入库 | **不主动改 `.gitignore`**。两种模式 skill 行为一致：**入库**（团队可见、PR 里可审，代价是计划噪声进 diff）/ **忽略**（工作区干净，代价是只对本机可见）——由用户 / 团队决定 |
| 续做复用 | 同源任务（同名 / 同 `related` / 同 slug）**复用原目录**，不新建——见 SKILL.md Step 1「先查重」 |
| 清理 | 不删除；确需清理时由用户手动执行（与 `temp-and-timeout` 的"AI 不主动删"纪律一致） |
| 归档 | 长期不用的计划保持原状即可，`status` 字段本身就是检索依据 |

## 6. 与相邻能力的边界

> 下表全部是**可选衔接**，不是必经流程——本 skill 不要求任何前置文档，也不强制任何下游交接。
> 但**收尾顺序固定**：自评审 → `auto-review`（产出物审查闭环）→ `acceptance-verify`（交付验收）→ `implementation-report`（归档），**不可倒置**。

| 相邻能力 | 分工 |
|----------|------|
| `requirement-mining` | 需求分析完成后用户选"直接实现（快速实现）" → 该 skill **默认交接本 skill 建档**：工作项取需求清单 REQ-*、完成判据取需求验证标准、`related` 填需求 ID（该路径跳过设计文档，台账是唯一的进度与验证载体）；**本 skill 侧仍按「不建档」清单自判**，任务平凡则不建、不阻塞 |
| `work-breakdown` | 产出工作项清单（不执行、不跟踪）→ 直接作为本计划的工作项来源 |
| 骨架状态台账（如 `skeleton-status.md`） | 阶段内细分 → 纳入本计划的工作项，**不另立平行台账** |
| `auto-review`（规则强制） | 文件级、每次写入后自动闭环 → 与本 skill 的任务级自评审**叠加**，互不替代 |
| `acceptance-verify` | 交付前、用户指定 → 本 skill 的自评审是内部闸门，**不能替代它** |
| `implementation-report` | 事后归档实际实现与偏差 → 收尾时交接 |
| `task-dispatch` | 并行子任务调度与合并 → 其进度可作为本计划中一个工作项的内部细节 |
