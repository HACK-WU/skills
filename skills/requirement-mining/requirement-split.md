# 子需求拆分（requirement-split）

> 本文件是 `requirement-mining` 的内置能力，**不是独立 skill**。当用户在 Step 8 选择「子需求拆分」行动时加载本文件。非必做。

## 定位

将一个已转译完成的大需求，拆分为多个**边界清晰、可独立消费**的子需求文档，供后续在**不同对话窗**分别设计或实现，加速交付进度。

**与相邻能力的边界**（三拆分工）：

| 能力 | 拆什么 | 产出 | 用途 |
|---|---|---|---|
| 本能力（子需求拆分） | 需求（语义边界） | 子需求文档 | 多窗口并行 |
| `work-breakdown` | 工作项（垂直切片） | 工作项清单 W-01… | 单窗口内分批实施 |
| `design-craft` 阶段 2.5 | 设计（技术边界） | 设计子文档 | 技术设计 |

## 核心原则

1. **按需求边界拆，不按代码模块拆**：效果导向。代码只用于校验"这个子需求能否独立交付"，不决定"怎么切"
2. **父子双层**：父需求文档承载全局约束，子需求文档只写自己，**引用不复制**（复制 = 双源漂移，反而更易跑偏）
3. **需求视角，不碰设计**：子需求仍是需求文档（场景/验收/依赖/边界），接口契约、数据模型、时序交给 `design-craft`
4. **独立才并行**：不独立的子需求拆了反而更慢（互相等待 + 返工）
5. **全局视野三道防线**：父文档全局约束 / 子需求上下游接口声明 / 共享术语速查

## 执行流程

### Step 1：拆分范围确认

- 读取 requirement-mining 输出的需求清单（REQ-XX 列表 + 依赖图 + 验收标准）
- 确认拆分粒度：一个子需求 = **一个或多个 REQ 的聚合**，构成一个可独立交付的需求单元（有独立场景 + 独立验收 + 边界清晰）
- 拆分依据是**需求边界**（功能域），不是代码模块
- 必要时读相关代码，**只用于校验可独立性**（这个子需求涉及的范围能否独立交付），不用于决定怎么切

### Step 2：产出父需求文档（全局层）

父需求文档承载所有窗口共享的全局上下文，每个窗口开工前**必读**。

必含内容：

| 章节 | 作用 |
|---|---|
| 需求全景 | 核心目标、完整场景地图、用户角色 |
| 子需求索引表 | 编号 / 名称 / 一句话职责 / 依赖 / 优先级 |
| 共享术语速查 | 跨子需求共享术语的精确定义（防各窗口用词不一致） |
| 全局非功能约束 | 性能/安全/可用性等跨子需求的统一要求 |
| 边界声明 | 本需求整体不做什么（防各窗口范围蔓延） |
| 关键决策留痕 | requirement-mining「根本性分析」的关键决策点（引用其报告） |

### Step 3：拆分子需求 + 独立性校验

对每个子需求产出：

- 场景、验收标准、异常场景、依赖
- **上下游接口声明**：我依赖谁的输出、谁依赖我的输出（让每个窗口知道自己在全局中的位置）
- 边界声明：本子需求不做什么
- **边界置信度**：需求阶段信息少，边界存疑的标 ⚠️（提示后续窗口这里的边界可能要调）

**独立性校验**（复用 work-breakdown 判据）：

| 判定 | 条件 | 处理 |
|---|---|---|
| ✅ 可独立 | 无共享写依赖，可独立交付 | 可并行 |
| ⚠️ 弱依赖 | 有依赖但有默认值/桩可兜底 | 标注兜底方案 |
| ❌ 强依赖 | 必须等另一个完成才能开始 | 合并，或明确标注顺序 |

**HITL 标注**：需人工决策的子需求单独标注——这类窗口会卡住，不能与 AFK 子需求混批并行。

### Step 4：子需求文档落盘

- **落盘位置**：需求目录下 `sub-requirements/` 子目录，每个子需求一个独立文档（`SR-XX-{名称}.md`）
- **父需求文档**：落在需求目录根，命名为 `parent-requirement.md`（与 `requirement.md` 需求挖掘报告区分——后者是原始需求清单，前者是拆分后的全局层）
- 子需求文档含父文档指针（**引用不复制**）

### Step 5：复杂度下沉

对每个子需求**单独**评估复杂度（复用 requirement-mining Step 6.6 的维度）：

- **低复杂度** → 后续窗口可直接实现
- **中/高复杂度** → 后续窗口先走 `design-craft` 再实现

### Step 6：进度记录（多窗口手动并行）

多窗口并行时（用户在**新对话窗**分别实现子需求，**非 agent 派发**，无主 agent 统一协调），进度记录是用户掌握全局的看板：

- **权威状态**：每个子需求文档（`SR-XX.md`）顶部的「状态」标记——各窗口只写自己的文件，**无并发冲突**
- **汇总视图**：父需求文档（`parent-requirement.md`）子需求索引表的「状态」列——人类可读的全局看板

状态取值：`待开始` / `进行中` / `已完成` / `阻塞`（+原因）

**更新约定**：
- 每个窗口开始实现时，把自己子需求的状态改「进行中」，完成改「已完成」，卡住改「阻塞 + 原因」
- 更新 `parent-requirement.md` 状态列时，**先读最新版再改、只改自己那一行**（多窗口并发写有覆盖风险）

**整合兜底**：
- 整合阶段重扫 `sub-requirements/` 目录，以各子需求文档的实际状态为准，重建父文档状态列（覆盖可能丢失的更新）

```markdown
- ...

## 4. 异常场景
- ...

```

## 与 design-craft 阶段 2.5 的接力

- requirement-mining 拆出**需求子项**（需求视角：场景/验收/依赖）
- `design-craft` 检测到上游已拆 → **复用不重拆**，转译为**设计子需求**（设计视角：补接口契约/数据模型/时序）
- 子需求边界存疑（⚠️）的，design-craft 阶段 2.3 交互对象总览时重点核对边界

## 与 work-breakdown 的接力

- 本能力拆「窗口之间」的子需求；单个子需求在独立窗口内若仍横跨多层，可再走 `work-breakdown` 拆「窗口之内」的工作项（垂直切片）
- 若子需求已小到 = 一个工作项，则 work-breakdown 也用不上，直接 design-craft / 实现
