# 文档质量检查规则

生成文档的最后一步，逐条检查以下规则。不通过 → 修正 → 重新检查 → 直到全部通过。

## 禁止模式（Q-01 到 Q-06）

### Q-01：占位符检测

**检测关键词**（不区分大小写，含变体）：

```
TODO, FIXME, TBD, WIP, Coming soon, COMING SOON,
待办, 待完成, 待补充, 占位, 占位符, 后续补充,
Work in progress, UNDER CONSTRUCTION, tbd, wip
```

**例外**：若在 CONTRIBUTING.md 中引用项目的公开 Roadmap，且链接到 Issue/TAPD，允许出现。

**违规处理**：删除该占位符及其所在的句子。若整个章节因此变空，删除该章节。

### Q-02：无输出的命令

**检测模式**：

```
# 违规：命令块之后无输出
```bash
$ npm install
```

# 合规：命令块之后有输出
```bash
$ npm install
# → added 142 packages in 3s
```
```

**适用场景**：安装命令、CLI 命令、脚本执行、API 调用结果。

**违规处理**：补充输出或效果描述。若无法确定真实输出，标注 `<!-- 输出需验证 -->`。

### Q-03：无输入输出的 API 描述

**检测模式**：

```
# 违规：只描述功能，无示例
### `fetch(url)`
发送 HTTP 请求。

# 合规：完整的输入输出
### `fetch(url, options?)`
发送 HTTP 请求。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| url | string | 是 | 请求地址 |
| options | object | 否 | 请求配置 |

**返回值**：`Promise<Response>`

**示例**：
```js
const res = await client.fetch("/api/users").json()
// → { data: [{ id: 1, name: "Alice" }], total: 1 }
```
```

**违规处理**：补充黄金模板格式。若信息不足，标注 `<!-- 参数从代码推断，请验证 -->`。

### Q-04：推卸式引用

**检测模式**：

```
See source code for details
请查看源码
源码里有注释
refer to the source
详见代码实现
详见源代码
```

**违规处理**：改为内联概要说明。若确实无法概括，改为：

> 实现细节见 `{文件路径}:{行号}` 的 `{函数名}` 函数。

### Q-05：模糊表述

**检测模式**：

```
Supports all options
支持所有选项
Various options available
all standard features
多种方式
各种配置
```

**违规处理**：列出具体选项/配置。若数量太多（> 20 个），列出最常用的 5 个 + 链接到完整列表。

### Q-06：空心章节

**检测方式**：章节标题后有内容但内容 < 20 个词，且不包含代码块或列表。

**违规处理**：补足内容，或删除该章节并从导航中移除链接。

## 结构完整性检查

### README 检查

- [ ] 概述章节包含三要素（做什么 + 解决什么 + 与方案对比）
- [ ] 安装章节包含前置条件 + 安装命令 + 验证方法
- [ ] 快速开始章节可在 30 秒内读完
- [ ] 每个子文档导航链接附有一句话说明
- [ ] README 总行数 ≤ 120 行
- [ ] 章节数 ≥ 5 时 README 包含目录索引（TOC），目录项与各 H2 标题一一对应（增删/改名标题时同步更新目录）
- [ ] 目录位于标题/副标题/徽章之后、正文内容之前

### 子文档检查

- [ ] 概述章节说明该文档与 README 的关系
- [ ] 底部有「相关文档」章节，链接回 README 和其他子文档
- [ ] 独立可读（不依赖 README 上下文即可理解）

## 示例完整性检查

### API/接口检查

对每个对外暴露的接口：

- [ ] 有完整的参数说明（名称 + 类型 + 是否必填 + 说明）
- [ ] 有返回值类型和说明
- [ ] 有可执行的示例代码
- [ ] 有示例输出（实际输出或预期输出描述）
- [ ] 有边界情况或注意事项说明（若有的话）

### CLI 命令检查

对每个命令：

- [ ] 有完整的命令格式（含所有选项）
- [ ] 有终端输出示例（粘贴或合理构造）
- [ ] 选项有类型和默认值说明

### 配置项检查

对配置文档中的每个配置项：

- [ ] 有类型说明
- [ ] 有默认值
- [ ] 有使用场景或效果说明

---

## 内容一致性检查

- [ ] 子文档间无重复内容（同一信息只在一处写全，其他处链接引用）
- [ ] 所有内部链接（指向其他 .md 文件）的文件名与实际生成的对应
- [ ] README 中的 API/命令速览与子文档中的完整描述不矛盾

## 图表检查（mermaid / SVG）

### 图表选型检查

- [ ] 关系图（流程/时序/状态/ER）默认使用 mermaid，未错误使用 SVG
- [ ] 出现切换 SVG 触发信号（分支回环密集/交叉连线多/需泳道/扇入扇出大）的图已改用 SVG，未强留 mermaid
- [ ] **架构图（模块总览）统一使用 SVG**，未错误使用 mermaid
- [ ] 视觉布局图、需精确样式、需独立复用的图使用 SVG，未错误使用 mermaid
- [ ] 选型依据见 `references/strategies.md`「图表选型规则」

### mermaid 检查

- [ ] mermaid 代码块以 ```mermaid 开始，语法可被标准渲染器解析
- [ ] 节点数 ≤ 10，图不拥挤（超限则改用 SVG 或拆分多图）
- [ ] 无 `graph TD` 之类默认模板残留（根据实际结构选 `flowchart`/`sequenceDiagram`/`stateDiagram`/`erDiagram`）

### SVG 检查

- [ ] 独立 SVG 文件存在且被文档正确引用（`![说明](./assets/xxx.svg)`，路径正确）
- [ ] SVG 文件名符合 kebab-case 规范（全小写短横线、语义化），无中文/空格/无意义命名
- [ ] 内联 SVG 结构完整：含 `viewBox`、闭合标签、无未定义引用
- [ ] 文本标签清晰可读，字号合适（不被缩放失真）
- [ ] AI 生成仅限结构化简单 SVG；复杂视觉图已标注「需设计工具产出」，未用占位符敷衍
- [ ] 未将截图/位图伪装成 SVG（内容应是矢量图形）

## 专业性检查（GitHub 开源级）

> 本节确保文档达到 GitHub 上优质开源项目的专业水准。面向的主要场景：仓库 README、API 文档、配置指南、贡献指南等。

### P-01：目标读者定位

- [ ] 概述章节能让目标读者在 10 秒内判断"这是否是我需要的"
- [ ] 快速开始的内容难度匹配目标读者（新手友好 vs 假设基础知识的取舍明确）
- [ ] 技术深度逐层递进：概述 → 快速开始 → 详细文档，不跳跃
- [ ] 若项目有多类读者（使用者 / 贡献者 / 扩展者），在 README 导航中分别指引对应文档

### P-02：术语一致性

- [ ] 同一概念全篇使用同一术语（如不同时用"插件"/"扩展"/"附加组件"指代同一事物）
- [ ] 首次出现的缩写/专有名词给出全称或解释（如 "CLI（Command Line Interface）"）
- [ ] 技术名词与项目代码中的命名一致（如代码用 `config` 则文档不用 `设置`）
- [ ] 与同生态主流项目的术语习惯对齐（如 Node.js 项目用"包"而非"模块"指 npm package）

### P-03：视觉专业度

#### 徽章（Badges）

- [ ] README 顶部包含标准徽章区（至少包含：版本号 / 许可证 / 构建状态）
- [ ] 徽章使用 shields.io 或同类服务动态生成（非静态图片）
- [ ] 徽章排列整齐（单行内，不超过 6 个，超出则换行分组）
- [ ] 徽章链接指向有意义的目标（版本 → changelog / 许可证 → LICENSE / 构建状态 → CI 页面）

#### 代码块

- [ ] 所有代码块标注语言标识（\`\`\`js / \`\`\`bash / \`\`\`python 等），无裸 \`\`\`
- [ ] 命令行示例以 `$ ` 或 `>` 开头提示符，输出以 `# →` 或注释形式区分
- [ ] 长代码块（> 15 行）附带说明注释，非纯代码堆砌
- [ ] 示例代码可直接复制运行（无 `...` / `// 其他代码` 省略）

#### 表格与列表

- [ ] 表格用于结构化数据（参数 / 配置项 / 对比），非装饰用途
- [ ] 列表项长度均匀（无一项占半屏而其他一行的情况）
- [ ] 嵌套层级 ≤ 3 层（过深嵌套改用子章节或表格）

#### 标题层级

- [ ] README 标题从 `##` 开始（`#` 仅一次用于文档标题）
- [ ] 标题层级连续（无 `##` 跳到 `####` 的情况）
- [ ] 同级标题语义粒度一致（不会有的 `##` 下 2 行内容、有的下 50 行）

### P-04：语言风格

- [ ] 无口语化表达（"其实"、"的话"、"的话就"、"蛮"、"挺"等）
- [ ] 无冗余修饰（"非常"、"极其"、"超级"、"真正的"等程度副词，除非技术上有区分必要）
- [ ] 使用主动语态和祈使句（"安装依赖"而非"依赖应当被安装"；"运行测试"而非"测试可以被运行"）
- [ ] 中英文混排规范：中文文案中英文两侧加空格（`安装 Node.js 依赖`），专有名词/代码标识符除外
- [ ] 标点统一：中文语境用全角标点（`，。：！？`），代码/英文语境用半角

### P-05：首屏价值密度

- [ ] README 前 30 行（约一屏）包含：项目名称 + 一句话定位 + 徽章 + 最简安装 + 最简效果
- [ ] 打开 README 即可知：这是什么、解决什么问题、能不能直接用
- [ ] 目录索引允许放在标题/徽章之后，但必须确保价值信息（最简安装 + 最简效果）仍在 30 行内可见；不在首屏最顶部放长介绍/变更日志/贡献者列表等低优先级信息
- [ ] 项目 Logo（若有）尺寸适中（≤ 128px），不占用首屏主要空间

### P-06：外部链接与引用

- [ ] 所有外部 URL 可访问（非死链）
- [ ] 外部链接附简短说明（非裸 URL）
- [ ] 引用的 issue/PR 编号自动链接（GitHub 自动渲染 `#123` 格式）
- [ ] 版本号引用具体（`v1.2.3` 而非"最新版本"）
