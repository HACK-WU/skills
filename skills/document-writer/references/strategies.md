# 项目文档策略矩阵

本文档定义各项目类型的文档编写策略。策略 = 章节模板 + 内容深度要求 + 示例规则。

## 通用规则（所有类型适用）

### 图表选型规则（mermaid vs SVG）

文档中的图表按以下因子决策，**先判图本质，再查复杂度/环境/复用**（核心四因子：图本质、复杂度、渲染环境、复用需求；样式需求与资产来源为辅助参考）：

| 决策因子 | 用 mermaid | 用 SVG |
|----------|-----------|--------|
| **图本质**（核心） | 关系图：节点+连线的结构化表达（流程图/时序图/状态图/ER 图/甘特图/类图） | 视觉设计图：布局、形状、色彩、图标、品牌化表现（架构拓扑、UI 布局、装饰性示意图） |
| **复杂度**（核心） | 节点 ≤ 10 且拓扑简单（线性/树状、分支回环少）、自动布局即可 | 拓扑稠密/嵌套深，或**分支回环多导致 mermaid 布局杂乱**（mermaid 自动布局会乱，即使节点 ≤ 10） |
| **渲染环境**（核心） | 目标平台支持 mermaid 渲染（GitHub、VitePress、Typora 等） | 平台不支持 mermaid，或需 PDF/邮件等静态导出 |
| **复用需求**（核心） | 仅在文档内查看，随文档维护 | 需独立 `.svg` 文件供下载/嵌入其他载体/设计工具编辑 |
| **样式需求**（辅助） | 接受默认主题即可 | 需品牌色、自定义形状、图标、精确排版 |
| **资产来源**（辅助） | AI 直接写 mermaid 文本（零成本、可版本化） | 已有设计工具产出的现成 SVG，或 AI 生成结构化简单 SVG |

**切换到 SVG 的触发信号**（出现任一即改 SVG，**即使节点 ≤ 10**）：

- **分支/回环密集**：大量 if-else、循环回边、异常分支，mermaid 自动布局后边线缠绕、节点重叠
- **交叉连线多**：多条边跨节点交叉，读起来费劲
- **需泳道/分区语义**：流程需按角色/系统分泳道（mermaid 泳道支持有限）
- **扇入/扇出大**：多源汇聚（多上游流入一节点）或单源分叉（一节点分流到多下游）
- **需精确位置/方向控制**：强调阅读顺序、层级对齐、同层并列

**反向约束**：默认仍用 mermaid；**仅当出现上述触发信号才改用 SVG**，不得因"SVG 更精美"随意替换简单图。

**SVG 两种产出形式**：

1. **独立 SVG 文件**（优先）：写入 `assets/` 目录（相对各文档所在目录），文档用 `![说明](./assets/xxx.svg)` 引用。GitHub 等主流平台均支持 `<img>` 引用 SVG 文件
2. **内联 SVG**（仅限明确支持内联 HTML 的渲染环境，如 VitePress/VuePress 配置后）：`<svg>` 直接嵌入文档。**GitHub 会剥离内联 `<svg>` 标签，读者将看到空白——默认不用内联形式**

**SVG 文件命名规范**：

- 命名风格：kebab-case（全小写 + 短横线），如 `architecture-overview.svg`
- 语义化：`{图作用}-{图主题}.svg`，如 `deployment-topology.svg`、`ui-homepage-layout.svg`
- 存放：与引用它的文档同目录的 `assets/` 下，路径与 `![...]` 引用一致
- 禁用：中文、空格、大写、无意义命名（`img1.svg`）、过短缩写（`arch.svg`）
- 一图一文件，同名复用直接引用同一文件，不复制副本

**AI 生成 SVG 的能力边界**：

- ✅ 可生成：结构化简单 SVG（节点框 + 连线 + 文本标签的流程/拓扑示意）、图标化图形
- ✅ 可生成：CSS 微动画（渐入、高亮闪烁、路径描边等 `@keyframes` 简单动画，用于强调关键变化）
- ✅ 可生成：轻量数据图表（坐标轴 + 曲线/柱状 + 关键点标注，如时间复杂度曲线、趋势对比图）
- ❌ 不应生成：复杂视觉设计（多层渐变、复杂曲线、拟物图标、品牌级插画）、SMIL 动画（兼容性差）、JS 交互（Markdown 渲染环境会剥离）——标注「需设计工具产出」并给占位说明，不得用占位符敷衍

### SVG 动画使用原则

> 动画是可选增强层，不是默认产出。必须遵守以下约束：

| 动画类型 | 技术手段 | GitHub | VitePress / VS Code / Typora | 推荐度 |
|----------|---------|:------:|:---------------------------:|:-----:|
| **CSS `@keyframes`** | `<style>` 内嵌或 `<animate>` CSS 替代 | ⚠️ 基本可用（`<img>` 引用时部分受限） | ✅ 完全支持 | ✅ **首选** |
| **SMIL `<animate>`** | SVG 原生动画标签 | ❌ 被剥离 | ⚠️ 部分支持 | ❌ 不推荐 |
| **JS 驱动** | `<script>` + DOM 操作 | ❌ 被安全策略剥离 | ❌ 被剥离 | ❌ 禁止 |

**核心原则**：

1. **动画是增强不是依赖**：每张 SVG 必须在**无动画时仍可理解**（静态帧就是完整的信息载体）；动画仅用于降低认知负担（如逐步揭示、高亮关键变化）
2. **CSS 动画场景**（推荐使用的 3 种）：
   - **逐步揭示（Reveal）**：按序淡入各元素（`opacity: 0 → 1` + `animation-delay` 阶梯延迟）
   - **高亮强调（Highlight）**：关键元素脉冲发光或颜色变化
   - **路径描边（Draw）**：线条从起点到终点动态绘制（适用于流程/路径类图）
3. **禁止事项**：
   - 不用 SMIL `<animate>` / `<animateTransform>`（GitHub 等主流平台不支持）
   - 不用 JS（所有 Markdown 渲染环境都会剥离 `<script>`）
   - 不做"纯炫技"动画（旋转、弹跳、粒子效果等与目标无关的视觉噪音）
4. **降级策略**：当不确定目标渲染环境是否支持 CSS 动画时，产出**纯静态 SVG**

> **一句话总结**：*能不动就不动；动就用 CSS `@keyframes`；动画掉了也不能影响理解。*

**常见图表速查**：

| 图表场景 | 默认选型 | 例外 |
|----------|----------|------|
| 流程图 / 时序图 / 状态图 / ER 图 | mermaid | 节点 > 10、或出现切换 SVG 触发信号（分支回环密/交叉连线/需泳道/扇入扇出大）→ SVG |
| 架构图（模块总览） | **SVG（统一默认）** | - |
| 部署拓扑图 | SVG | 简单线性部署（≤ 5 节点）→ mermaid |
| UI 布局 / 界面示意 | SVG | - |
| 数据流 / 依赖关系 | mermaid | 链路 > 10 跳、或扇入扇出大/多源汇聚 → SVG |

**判断口诀**：*能讲清关系的用 mermaid；关系复杂到 mermaid 讲不清（分支回环密、连线缠绕）就"画"成 SVG。*

## 通用规则（所有类型适用）

### 目录索引（TOC）规范

各类型 README 结构表中的「标题 + 徽章」之后、「概述」之前，按以下规范加入目录（章节数较少时不加，见适用条件）：

| 项目 | 规范 |
|------|------|
| **位置** | 标题 + 副标题 + 徽章之后、正文第一个章节之前 |
| **内容** | 列出正文全部 H2 章节，与标题一一对应（含编号/emoji 时目录项须同步） |
| **格式** | `- 章节名` 无序列表（推荐带锚点链接；emoji 前缀可选，如 `📑 目录`） |
| **适用条件** | 章节数 ≥ 5 的文档建议加目录；简短文档（< 5 章节）可不加 |
| **维护** | 正文 H2 增删/改名时同步更新目录，避免目录与章节不同步或死链 |

### 概述章节的三要素

```
## 概述

{项目名} 是一个 {一句话定性}。

**解决的问题**：{用 2-3 句说明它解决什么痛点}

**与其他方案的区别**：
- 与 {方案A} 相比：{核心差异}
- 与 {方案B} 相比：{核心差异}
```

### 安装章节的三要素

```
## 安装

### 前置条件
- {运行时/框架版本要求，如 Node.js >= 18}
- {其他依赖，如需要安装 xxx}

### 安装命令
{完整的安装命令，含包管理器选择}

### 验证安装
{一条命令验证安装成功 + 预期输出}
```

## 策略 5：混合型

项目同时满足多种类型特征时，合并对应策略。

**合并规则**：

| 维度 | 合并方式 |
|------|----------|
| README 章节 | 取各类型章节的并集，去除重复章节 |
| 子文档列表 | 取各类型子文档的并集，同名文档只保留一份 |
| 拆分阈值 | 各类型独立计算，任意类型触发即生成对应子文档 |
| 示例策略 | 按主类型选取，辅类型只补充差异点 |

**主类型判定**：当多种类型并存时，按以下优先级确定主类型：
1. 用户明确指定的类型
2. 入口文件所在的类型（CLI 入口 → 主类型为 CLI）
3. 对外暴露 API 最多的类型（API 数量 > CLI 命令数 → 主类型为库）

**常见混合场景**：

| 混合类型 | 典型例子 | README 特点 |
|----------|----------|-------------|
| 库 + CLI | axios 附带 `axios-cli` | 库的章节为主，额外加「CLI 使用」章节 |
| 库 + 插件 | ESLint 自定义规则 + ESLint 插件 | 插件的章节为主，额外加「作为库使用」章节 |
| CLI + Web | CLI 工具附带管理面板 | CLI 章节为主，额外加「管理面板」章节 |

**输出判定时说明合并了哪几种类型以及主类型**。

## 验证方法速查

每个策略产出的文档，用以下方法快速验证：

| 类型 | 快速验证 |
|------|----------|
| 库/SDK | 打开 API Reference → 随机挑一个 API → 复制示例代码 → 预期能跑通 |
| CLI 工具 | 打开 Command Reference → 随机挑一个命令 → 复制到终端 → 预期输出与文档一致 |
| Web 应用 | 按 README 快速启动步骤操作 → 应能访问到本地服务 |
| 插件 | 按 README 最简配置操作 → 插件应在宿主中正常激活 |
