# 细则：证据固定与可选排查报告

> **何时读**：排查开始建案例、每轮取证后固定证据、排查完成询问是否生成报告时。
> **配套**：[SKILL.md](../SKILL.md)「证据固定与可选报告」、[remote-forensics.md](remote-forensics.md)。

## 1. 目录与忽略规则

```text
.debug/{case-slug}-{YYYYMMDD}/
├── meta.json          # 案例元数据
├── evidence.md        # 只追加的证据台账
├── artifacts/
│   ├── repro-local.py # 本地一键复现（如需要）
│   ├── query-r1.py    # 线上只读片段（带任务 marker）
│   └── r1-output.txt  # 用户回传的原始输出（脱敏后）
└── report.md          # 可选，本地副本；要入库的报告另存到 review/debug-report.md
```

- `case-slug` 用 kebab-case 英文，从 Bug 摘要派生，例如 `order-callback-timeout`。
- 日期用 `YYYYMMDD`；同一天同 slug 已存在 → 询问「续查 / 新建并加 `-2`」，不覆盖。
- 创建案例目录时同时写 `.debug/.gitignore`：

```gitignore
# 本地排查证据，禁止提交（可能含原始响应/日志）
*
```

- **已存在 `.debug/.gitignore` 时只读不改**：保留用户已有规则；若缺少 `*`，提示用户手动补，不覆盖。
- **不修改项目根 `.gitignore`**；不自动提交。若团队希望把忽略规则纳入版本库，由用户显式在根 `.gitignore` 加 `.debug/`。
- `.debug/` 内的所有文件默认都是本地工作底稿，不随仓库分发。

## 2. 案例元数据

`meta.json` 建议字段：

```json
{
  "case_id": "DBG-20261026-order-callback",
  "slug": "order-callback-timeout",
  "created_at": "2026-10-26T14:05:00+08:00",
  "updated_at": "2026-10-26T15:20:00+08:00",
  "status": "排查中",
  "repo": "/path/to/repo",
  "branch": "main",
  "commit": "abc1234",
  "environment": "prod",
  "app_version": "1.8.2",
  "framework_version": "Django 4.2",
  "operator": "user",
  "summary": "订单支付回调后状态未更新"
}
```

- `status`：排查中 / 已定位 / 已修复 / 已阻塞 / 已放弃。
- 不写真实 token、密码、连接串、个人数据。
- 如果线上版本无法确认，写 `unknown`，不要猜。

## 3. 证据台账

`evidence.md` 只追加、不覆盖。每条证据一个二级标题：

```markdown
## E-03 | 2026-10-26 14:32 | 线上代执行 | 有效
- 假设：H2 支付回调未更新订单状态
- 环境：prod / commit abc123 / Django 4.2
- 查询：artifacts/query-r1.py（sha256 可选）
- 期望结构：id:int, status:enum, paid_at:ISO|null
- 回传：artifacts/r1-output.txt（sha256 可选）
- 对账：marker ✅ / 结构 ✅ / 语义 ✅ / 完整性 ✅
- 结论：支持 H2
- 脱敏：手机号 / 地址已打码
```

- “来源”只用：`本地实测` / `线上代执行` / `静态分析` / `用户描述`。
- 无效轮也要写，状态标 `❌ 无效（回传不符）`，并写原因；不要删除。
- 证据里引用代码文件，不复制大段代码；报告再按需引用。
- 每条证据记录时间；生产数据是快照，时间决定它是否还成立。
- **单条证据限长**：建议 ≤200 行 / ≤50KB；超出时只存摘要 + 文件路径 + hash，并让用户缩小查询或分页，避免台账膨胀与上下文爆炸。

## 4. 写入时机（自动，不询问）

| 节点 | 固定什么 |
|---|---|
| Step 0 | 环境、分支、commit、版本、原始报错/日志片段 |
| Step 1 | 最小复现命令/脚本、复现结果 |
| Step 2 | 每条日志 / 测试 / 插桩证据 |
| 远程每一轮 | 任务卡、查询代码、用户回传的原始输出、对账结果（含无效轮） |
| Step 4 | 根因结论、证据链、根因树 |
| Step 5 | 修复 diff、回归结果、清理确认 |

- **立即写，不攒到最后**：上下文压缩、会话中断、用户换窗口都会让“最后补写”失败。
- 写入失败不阻塞排查，但必须告警，并把证据摘要回退到对话里，提示用户手动保存。
- 不覆盖旧条目；新结论另起一条，旧结论保留（可标“已被 E-05 取代”）。
- **并发提示**：同一案例不要并行开两个排查会话；确需并行时用不同 `case-slug`/目录，避免证据交叉覆盖。

## 5. 断点续查

Step 0 先检查 `.debug/`：

- 有同主题案例 → 询问「续查旧案例 / 新建案例」。
- 续查时先读 `meta.json` 与 `evidence.md`，从最后一条证据继续；不要重跑已确认的查询。
- 没有案例 → 新建目录并写 `meta.json`。
- 证据台账是恢复入口，不要只依赖对话记忆。

## 6. 脱敏与安全

- 写入前脱敏：手机号、邮箱、身份证、银行卡、支付流水号、地址、token、cookie、Authorization、内网 IP、带密码的连接串。
- 保留可调试性：例如手机号只留后 4 位、ID 可用哈希/尾号、金额可保留但不要带用户身份。
- 用户回传后 AI 再扫一遍；发现凭证泄露 → 停止写入、提示轮换、报告中不复述。
- 不把原始未脱敏输出写入 `.debug/`、报告或错误库。
- `.debug/.gitignore` 只防误提交，不替代脱敏。
- 落盘前可运行 `check_readonly.py --lang text <文件>` 只扫敏感信息；有命中先脱敏再写入。

## 7. 可选排查报告

### 7.1 何时询问

- Step 4 根因定位后，或 Step 5 修复验证后，询问一次：
  - 已修复 → “是否生成详细排查报告？”
  - 仅定位未修复 → 也可生成，但报告状态标「仅定位未修复」。
- 用户拒绝 → 保留证据台账，告知后续说“生成排查报告”可补。
- 不默认生成；不自动写 `review/debug-report.md`。
- **报告只能从证据台账生成**：台账缺失或条目不全时，报告标「证据不完整」，不得凭对话记忆补写查询/output/根因证据。

### 7.2 报告模板

````markdown
# Bug 排查报告：{标题}

- 状态：已修复 / 仅定位未修复 / 待确认
- 案例 ID：DBG-...
- 环境：本地 / 线上（版本 / commit）
- 证据台账：.debug/{case-slug}-{YYYYMMDD}/evidence.md

## 1. 结论摘要

{3–5 条结论；每条注明证据来源}

## 2. 现象与影响

{现象原文、影响范围、发生时间、复现频率}

## 3. 复现

### 3.1 本地一键复现

```bash
{命令}
```

{前置条件、测试数据、预期失败现象}

### 3.2 线上只读核查（人工代执行）

```python
# DBG-R1
{只读查询代码}
```

- 执行环境：{prod / staging}
- 期望结构：{字段 / 类型 / 约束}
- 回传数据：见第 4 节 E-03

## 4. 证据链

| ID | 来源 | 命令 / 查询 | 真实响应（已脱敏） | 对账 | 结论 |
|---|---|---|---|---|---|
| E-01 | 本地实测 | `pytest ...` | `...` | - | 复现成功 |
| E-03 | 线上代执行 | `query-r1.py` | `{"id":12345,"status":"paid"}` | ✅ | 支持 H2 |

> 无效轮单独列在表后，不混入有效证据。

## 5. 根因

**根因总结**：{先用一句话说清“为什么坏”，让读者不读树也能明白结论。}

```text
{现象}
  ▼
{直接原因}（证据：E-03）
  ▼
{根本原因 ← 根因}
  ├─ {触发条件 1}
  └─ {触发条件 2}
  ▼
{引入点}
```

**排查路径总结**：{一句话说明“怎么一步步收敛到上面的根因”。}

```text
{H1（证伪：证据）} → {H2（证伪：证据）} → {H3 ← 证实（证据）}
```

> 两棵树都必须先有总结再出现；禁止裸树。节点 ≤15、层级 ≤4。

## 6. 修复与回归

{修复方案、最小改动、回归命令与结果、未修复时的建议}

## 7. 影响面与风险

{如做过 code-change-impact，引用其结论；没有则写“未评估”}

## 8. 未决 / 待确认

{无效轮说明、版本差异、无法线上复核的点、需要用户拍板的事项}

## 附录：证据文件清单

- `.debug/{case}/artifacts/query-r1.py`
- `.debug/{case}/artifacts/r1-output.txt`
- `.debug/{case}/meta.json`
````

### 7.3 文字树硬规则

1. **先总结、后树**：每棵树前必须有一句总结性说明，写清“这棵树要表达什么结论”。
2. **禁止裸树**：没有前置总结的文字树视为报告缺陷。
3. **树不是结论的全部**：总结必须能独立读懂；树用于展示分支与因果，不替代文字。
4. **沿用既有最小语法**：`│` + `▼` 串联，`├─` / `└─` 分支；关键节点标 `← 根因` / `← 待验证`；节点 ≤15、层级 ≤4。
5. **只画结构**：排查路径、根因链、影响链；清单仍用表格，不把清单硬画成树。
6. **与表格分工**：证据明细用表格；因果/路径用树。同一内容不要既画树又铺一张大表。
7. **代码标注执行环境**：报告中每段代码标 `仅本地/测试` 或 `线上只读`；本地复现代码可能写测试数据，禁止在线上执行；线上片段必须通过 `check_readonly.py`。

### 7.4 报告路径

| 场景 | 路径 |
|---|---|
| 有 `.requirements` 且关联 REQ | `review/debug-report.md`，用 `req update --docs add review/debug-report.md,review` 注册 |
| 无 REQ，用户要留存 | 用户指定路径；默认 `.debug/{case}/report.md`（本地，不提交） |
| 用户拒绝生成 | 不写报告；保留 `evidence.md`，后续可补 |

## 8. 与其他报告/ skill 的边界

| 报告 / skill | 回答什么 | 与本报告的关系 |
|---|---|---|
| `debug` 排查报告 | 为什么坏、证据是什么、怎么修 | 本报告 |
| `implementation-report` | 需求最终实现了什么 | 交付报告；可引用本报告，不复制 |
| `acceptance-verify` | 这一版是否达标 | 验收报告；不替代 |
| `code-change-impact` | 改动会牵连谁 | 影响分析；本报告可引用其结论 |

## 9. 常见坑

| 坑 | 表现 | 正确做法 |
|---|---|---|
| 裸树 | 报告直接出现一棵树，读者不知道在说什么 | 树前加一句总结；总结能独立读懂 |
| 树太深 | 15 层嵌套、几十个节点 | 节点 ≤15、层级 ≤4；拆成“根因树 + 排查路径树” |
| 树代替结论 | 只有树，没有一句根因总结 | 总结在前，树在后 |
| 证据缺失 | 报告只有结论，没有查询/输出 | 每条结论挂证据 ID；证据台账可追溯 |
| 只有摘要没有真实数据 | 写“返回正常”，没有原始输出 | 附脱敏后的真实响应 |
| 无效轮混入证据 | 粘错的数据被当成业务异常 | 单列“未采用证据”并说明原因 |
| 原始数据落盘 | 报告/台账含手机号、token | 写入前脱敏；不落原始值 |
| 报告凭记忆补证据 | 台账缺条目，AI 用对话记忆补 output | 只从台账生成；缺失标「证据不完整」 |
| 覆盖已有忽略规则 | 直接把 `.debug/.gitignore` 重写为 `*` | 已存在则保留；缺规则只提示用户 |
| 证据文件过大 | 整页日志/全量 rows 写进 evidence.md | 单条 ≤200 行/≤50KB；超限存摘要+路径+hash |
| 报告过早生成 | 根因未确认就出完整报告 | Step 4/5 后再问；未修复标状态 |
| 报告重复交付报告 | 把 implementation-report 的内容抄一遍 | 只写排查；交付/验收报告引用本报告 |
| 路径误提交 | `.debug/report.md` 被 git 跟踪 | `.debug/.gitignore` 为 `*`；入库报告另存 |
