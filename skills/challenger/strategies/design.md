# 设计文档质疑策略

> 此文件为设计文档（方案/架构/API 设计等）的质疑策略，用于对**尚未实现的设计**进行二次质疑。
> 适用对象：scheme.md、设计文档、架构方案、API 设计稿等。

## 核心理念

**质疑者的角色定位**：不信任任何"设计已完备/已通过"的结论，假设设计一定存在遗漏、风险或不合理之处，然后寻找证据。

**设计文档质疑的核心假设**：设计 = 目标达成 + 方案可行 + 风险可控 + 场景完备

**与 design-review 的区别**：design-review 是**一次评审**（结构化找问题、分级、给修改建议）；本策略是**二次质疑**（假设"已通过评审"的设计仍有问题，对抗式寻找证据，并给出替代方案）。

**质疑的核心问题**：

1. 目标理解正确吗？方案真的解决了目标问题吗？
2. 方案技术上可行吗？技术选型与依赖清晰合理吗？
3. 场景完备吗？主流程/分支/异常/边界/兼容性/新增数据贯通都覆盖了吗？
4. 风险识别全吗？应对措施真的有效吗？
5. 有更简单或更优的替代方案吗？

## 阶段0：设计上下文确认

> **核心理念**：在质疑之前，必须先确认设计的目标、范围和约束，避免基于错误理解进行质疑。

### 阶段目标

确保质疑者理解设计意图，避免"误读方案后挑刺"。

### 质疑步骤

#### 步骤0.1：明确设计目标

**核心问题**：这个设计要解决什么问题？

**必须确认的信息**：
- 设计要达成的核心目标是什么？
- 目标的衡量标准是什么（可观测、可验证）？
- 目标是否有优先级（核心目标 vs 次要目标）？

#### 步骤0.2：确认设计范围

**核心问题**：设计覆盖了什么、不覆盖什么？

**必须确认的信息**：
- 设计包含哪些模块/接口/流程？
- 设计明确排除的范围是什么？
- 与现有系统的边界在哪里？

#### 步骤0.3：识别约束与假设

**核心问题**：设计建立在哪些前提之上？

**约束与假设类型**：

| 类型 | 描述 | 示例 |
|------|------|------|
| **技术约束** | 技术栈、依赖版本、平台限制 | 必须用 Python 3.10、单机部署 |
| **业务约束** | 业务规则、合规要求 | 金融精度、数据留存周期 |
| **资源约束** | 性能、容量、成本预算 | QPS ≥ 1000、单请求 < 200ms |
| **隐含假设** | 设计未明说但默认成立的前提 | 假设用户量稳定、假设网络可靠 |

**质疑问题**：
1. 哪些假设如果失效，方案就会崩塌？
2. 约束是否被设计真正遵守了？
3. 是否存在未被声明的隐含假设？

### 阶段输出

```
## 设计上下文确认

### 设计目标
- **核心目标**：<设计要解决的核心问题>
- **衡量标准**：<可观测的验收标准>
- **目标优先级**：<核心 vs 次要>

### 设计范围
- **覆盖范围**：<模块/接口/流程列表>
- **排除范围**：<明确不做的部分>
- **系统边界**：<与现有系统的接口边界>

### 约束与假设
- **技术约束**：<列表>
- **业务约束**：<列表>
- **资源约束**：<列表>
- **隐含假设**：<列表，标注失效后果>

### 确认状态
- ✅ 已确认 / ⚠️ 待确认 / ❌ 无法确认
```

## 阶段1：目标一致性质疑

> **核心理念**：方案可能"做得很好但解决错了问题"。

### 质疑步骤

#### 步骤1.1：目标理解验证

**质疑问题**：
1. 设计者对目标的理解是否准确？是否存在偷换目标？
2. 目标是否被拆解为可验证的子目标？
3. 子目标之和是否等价于总目标？

#### 步骤1.2：方案-目标匹配验证

**质疑问题**：
1. 方案的每个核心组件是否都直接服务于某个目标？
2. 有没有"为做而做"的过度设计（不服务任何目标）？
3. 目标是否被方案完整覆盖？有没有目标落空？

#### 步骤1.3：隐性目标识别

**隐性目标类型**：

| 类型 | 描述 | 质疑问题 |
|------|------|----------|
| **可维护性** | 后续是否易于修改扩展 | 方案是否埋下维护债务？ |
| **可观测性** | 运行时是否可监控可排查 | 出问题能否定位？ |
| **可回滚** | 上线失败能否回退 | 是否有回滚路径？ |
| **可演进** | 未来需求变化能否承接 | 方案是否锁死演进空间？ |

---

## 阶段2：可行性与技术选型质疑

> **核心理念**：方案在纸面上可能成立，但落地时未必可行。

### 质疑步骤

#### 步骤2.1：技术可行性验证

**质疑问题**：
1. 方案依赖的技术能力是否确实存在且成熟？
2. 是否有未验证的"假设性技术"（未实践过的 API/库/机制）？
3. 方案在目标运行环境下是否真的能跑通？

#### 步骤2.2：技术选型合理性验证

**质疑问题**：
1. 选型是否有充分理由？还是"顺手就用"？
2. 是否存在更合适的备选？为何排除？
3. 选型的版本/许可/维护状态是否满足要求？
4. 是否引入了过重或过新的依赖？

#### 步骤2.3：依赖与约束验证

**质疑问题**：
1. 依赖链是否清晰？是否有隐藏的传递依赖？
2. 依赖的稳定性、安全性、维护活跃度如何？
3. 设计声明的约束是否与实际依赖一致？

---

## 阶段3：场景完备性质疑（核心）

> **核心理念**：设计最容易在"非主流程"上翻车。

### 步骤3.1：主流程验证

**质疑问题**：
1. 主流程的每一步是否都有明确设计？
2. 步骤之间的数据/状态流转是否清晰且自洽？
3. 主流程是否真正可达目标？

### 步骤3.2：分支流程验证

**质疑问题**：
1. 所有条件分支是否都被设计覆盖？
2. 分支条件是否完备（无遗漏、无重叠）？
3. 分支的合并点是否明确？

### 步骤3.3：异常流程验证

**异常类型**：

| 类型 | 质疑问题 |
|------|----------|
| **输入异常** | 非法/空/超长/类型错误输入如何处理？ |
| **业务异常** | 业务规则违反、状态非法如何处理？ |
| **系统异常** | 网络/数据库/超时/资源耗尽如何处理？ |
| **并发异常** | 竞态、重复请求、乱序如何处理？ |

### 步骤3.4：边界条件验证

**质疑问题**：
1. 数据边界（最小/最大/空/零/满）如何处理？
2. 时间边界（起始/结束/跨周期/时区）如何处理？
3. 容量边界（单条/批量/超大）如何处理？
4. 状态边界（初始/中间/终态/异常态）如何处理？

### 步骤3.5：兼容性验证

**质疑问题**：
1. 与现有功能/接口是否冲突？
2. 数据格式/结构变化是否向后兼容？
3. 是否需要数据迁移？迁移方案是否设计？
4. 对调用方/下游的影响是否评估？

### 步骤3.6：新增数据贯通验证

> 设计中**新引入**的数据元素（接口字段/模型字段/表列/事件字段/配置项）没有存量链路作对比基准，主流程验证容易只看到"字段被定义了"，探不到链路断在半路。

**质疑问题**：
1. **正向贯通**：新增的字段/数据源，设计是否交代了从入口到最终落点的每一跳（接口 → 校验 → 处理 → 存储/发送）？有没有哪一跳缺失设计（如接口定义了字段但数据模型/表结构没有对应列）？
2. **反向消费**：新增的字段/产出，设计中谁生产它、谁消费它？无消费方的死字段、无生产方的空壳字段，是设计遗漏还是分阶段规划？
3. 消费方在系统外（前端/下游系统）时，对接约定是否已在设计中说明？

**证据要求**：逐跳列出新增数据的设计链路并标出缺失跳；断链即设计不完整，质疑成立；死字段/空壳字段要求设计方确认是否为后续阶段铺垫，确认不了则 🟡 中。

## 阶段4：风险与应对质疑

> **核心理念**：列出的风险未必真，没列的风险未必没有；应对措施未必有效。

### 质疑步骤

#### 步骤4.1：风险识别完整性

**质疑问题**：
1. 设计列出的风险清单是否完整？有没有明显遗漏的高危风险？
2. 是否低估了某些风险的可能性或影响？
3. 是否存在"已知未知"和"未知未知"未被预案覆盖？

#### 步骤4.2：应对措施有效性

**质疑问题**：
1. 每条应对措施是否真的能消解对应风险？还是只是"看起来在应对"？
2. 应对措施本身是否引入新风险？
3. 应对措施的触发条件、执行者、执行时机是否明确？

#### 步骤4.3：风险等级评估

| 等级 | 标准 | 处理方式 |
|------|------|----------|
| 🔴 **高风险** | 可能导致系统故障、数据丢失、安全漏洞 | 必须在上线前解决 |
| 🟡 **中风险** | 可能影响体验、增加维护成本、有潜在问题 | 建议处理 |
| 🟢 **低风险** | 影响较小、可接受 | 可选处理 |

---

## 阶段5：替代方案质疑

> **核心理念**：质疑不仅要指出问题，还要给出更好的可能。

### 质疑步骤

#### 步骤5.1：更简单方案

**质疑问题**：
1. 方案是否过度设计？有没有更简单的等价做法？
2. 能否复用现有能力/约定，而非新建？
3. 哪些部分可以删掉而不损失核心目标？

#### 步骤5.2：更稳健方案

**质疑问题**：
1. 在高风险点是否有更稳健的实现选择？
2. 是否有经过验证的成熟方案可替代自研？
3. 更稳健方案的代价（复杂度/成本）是否可接受？

#### 步骤5.3：整体替代方案（可选）

> 仅当认为整个方案方向有问题时，才提出完整替代方案。

---

## 阶段6：补充场景与遗漏识别

> **核心理念**：质疑者应主动补漏，即使某点暂不构成反对意见，只要影响方案完备性就应提出。

### 补充类型

| 类型 | 质疑问题 |
|------|----------|
| **遗漏场景** | 设计未考虑的使用场景有哪些？ |
| **边界情况** | 设计未覆盖的边界情况有哪些？ |
| **异常路径** | 设计未处理的异常/失败路径有哪些？ |
| **运行环境差异** | 不同部署环境/配置下的行为差异？ |
| **用户行为分支** | 用户非预期操作下的行为？ |
| **兼容性约束** | 与旧版本/外部系统的兼容约束？ |

---

## 阶段7：风险评估与建议

### 步骤7.1：识别风险

汇总阶段1-6的质疑结果，识别风险点。

### 步骤7.2：风险等级

按 🔴/🟡/🟢 分级，统计分布。每个风险必须附功能影响（引用对应反对意见的"预期 → 实际"），定级依据来自功能影响而非技术描述。

### 步骤7.3：行动建议

先给裁决结论（方案可进入开发 / 修改后进入 / 建议重做），再分档给出行动项，理由引用功能影响：

| 类型 | 标准 |
|------|------|
| **必须处理** | 高风险（🔴 功能影响）、必须在方案定稿/上线前解决 |
| **建议处理** | 中风险（🟡 功能影响）、建议纳入方案 |
| **可选处理** | 低风险、可选优化 |
