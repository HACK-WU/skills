# 模块专家团

## 概述

**目的**：把单个业务模块深度消化成一个"业务专家"资产包（知识文档 + 专用技能），供后续设计 / 排查 / 重构直接取用，避免每次重摸代码。

**功能**：模块范围扫描（AI 自行判断）→ 知识库优先查 → 派出多专家子 agent 并行产出技术切面 Wiki 文档 → 合成专家入口 → 调用 create-skill 生成领域专用技能 → 校验 → 落盘到 `.module-experts/{中文业务专家名}/`。

**使用场景**：
- 即将对某业务模块做重大设计 / 重构 / 迁移，需要先彻底掌握它
- 反复排查某业务模块问题，希望沉淀一份持久专家资产
- 新人 / 新 agent 接手某业务模块，需要快速建立全景认知
- 用户说"掌握这个模块""深度分析 xxx 模块""梳理这个模块的来龙去脉"时

## 组织模型：业务专家

> `.module-experts/` 的**子目录 = 业务专家**（按功能分类，中文业务名，如"告警处理专家""日志查询专家"）。每个专家内含 `agent.md` 名片 + 技术切面 Wiki 文档 + 专用技能目录。

```
.module-experts/
├── INDEX.md
├── 告警处理专家/                  # 专家 = 业务功能分类（中文名）
│   ├── agent.md                   # 专家职责摘要：这个专家是干嘛的（必出，轻量名片，不套 Wiki 格式）
│   ├── skills/                    # 该专家专用技能（标准 create-skill 格式，可直接加载）
│   │   └── add-alert-rule/
│   │       └── SKILL.md
│   ├── 01-架构.md                 # 技术切面 = code-to-wiki 风格 Wiki 页；兼作模块入口
│   ├── 02-实现.md
│   ├── 03-数据流转.md
│   ├── 04-模型.md
│   ├── 05-接口.md
│   ├── 06-测试.md
│   └── 07-运维.md
├── 日志查询专家/
│   └── ...
└── ...
```

- **专家目录**：中文业务名，由模块的业务功能派生（Step 0 与用户确认）
- **agent.md（必出）**：专家职责摘要，用一句话说明"这个专家是干嘛的"、负责哪些模块、何时找他；作为专家名片供后续查找，**不套 Wiki 格式**
- **技术切面 Wiki 文档**：`01-架构.md` ~ `07-运维.md`，每篇严格遵循 code-to-wiki 文档格式（见下一节），存放于专家目录下
- **skills/ 目录**：该专家的专用技能，由 `expert-team` 调用 `create-skill` 生成，遵循标准 skill 格式可直接加载；技能子目录名用 kebab-case（create-skill 要求）
- **模块入口**：`01-架构.md` 兼作总览与切面索引

## 文档格式规范（对齐 code-to-wiki，不跑工具）

> 本 skill 的切面 Wiki 文档**对齐** `code-to-wiki` skill 的**格式规范**，但为适配"按业务专家分包"的模型做了取舍：
> - **采纳**：`**本文引用的文件**` cite 块、中文锚点目录、`章节来源` / `图表来源`（`file://` + `#Lx-Ly` 行号区间）、Mermaid 配图、深度要求、R1–R7 规则。
> - **不采纳**：code-to-wiki 的"单一 7 节页面骨架"（简介 / 项目结构 / 核心组件 / 架构总览 / 组件详细分析 / 依赖关系分析 / 结论）。本 skill 把模块拆为 7 个业务切面文件，每篇**按本 skill 的切面调研清单组织章节**，而非套用其固定 7 节。
> - **不调用**：`codetowiki wiki-format` 校验工具；改为 AI 在 Step 6 按 R1–R7 手动自检。

### 每篇切面文档的骨架
```markdown
# {标题}
**本文引用的文件**
- [模块名](file://相对仓库根目录的路径)

## 目录
1. [简介](#简介)
2. [...](#...)
...

## 简介 ...
章节来源：[名称](file://相对路径#Lx-Ly)

## {切面核心章节，按 reference.md 调研清单组织} ...
章节来源：[名称](file://相对路径#Lx-Ly)

## 结论 ...
```
- 章节主题按 reference.md 各切面调研清单组织；每篇必须含 cite 块、目录、章节来源
- 架构 / 流程 / 状态机 / 依赖等处按需配 Mermaid 图，图后紧跟 `图表来源`

### 引用与来源规范（R 系列，AI 手动自检）
| 规则 | 要求 | 级别 |
|---|---|---|
| R1 | 标题下、目录前有 `**本文引用的文件**` cite 块（`[名称](file://相对路径)`，无需行号） | error |
| R2 | `## 目录` 条目与 `##` 章节一一对应（锚点用中文，如 `[核心组件](#核心组件)`） | error |
| R3 | 每个 `##`/`###` 小节末尾有 `章节来源`（`[名称](file://相对路径#Lx-Ly)`，须带行号区间）；纯概念节可豁免 | warning |
| R4 | 每个 Mermaid 图后紧跟 `图表来源`（同 R3 格式） | error |
| R5 | 所有引用路径均 `file://` 前缀 | error |
| R6 | 来源带 `#Lx-Ly` 行号区间且覆盖被论述代码实际跨度（单点 `Lx-Lx` 不合规） | warning |
| R7 | 内容深度：详细分析须 ≥2 设计维度（设计要点 / 关键流程 / 错误处理 / 风险控制）；架构 / 流程 / 依赖等按需配 ≥1 Mermaid 图 | warning（不可豁免） |

### 文件命名（对齐 code-to-wiki 中文序号前缀）
| 切面 | 文件 | 默认 |
|---|---|---|
| architecture | `01-架构.md` | 必出 |
| implementation | `02-实现.md` | 必出 |
| data-flow | `03-数据流转.md` | 按需 |
| models | `04-模型.md` | 按需 |
| api | `05-接口.md` | 按需 |
| tests | `06-测试.md` | 按需 |
| ops | `07-运维.md` | 按需 |

> `agent.md`（专家名片）不套 Wiki 格式，保持轻量。

| skill | 关系 |
|---|---|
| code-survey | 轻量、按需、跨多维度、一次性；本 skill 是单业务模块深挖、持久落盘 |

| **create-skill** | **本 skill 调用它生成专家的专用技能**；技能格式以 create-skill 规范为准，不在此重复定义 |
| **code-to-wiki** | **本 skill 的切面文档对齐其格式规范**（cite / 目录 / 章节来源 / 图表来源 / Mermaid / 深度 / R1–R7），但**不套用其单一 7 节骨架**、不调用其 `codetowiki` 校验工具 |

## 核心原则

1. **业务专家为轴**：`.module-experts/` 子目录是业务专家（中文名），不是技术切面
2. **单模块深挖**：一次只针对一个业务模块，不泛化到全项目
3. **按需切面**：根据模块性质选择产出哪些切面 Wiki 文档，不硬凑空文档（无 DB 不写 `04-模型.md`）
4. **知识库优先**：先查 ki（项目记忆 → KB），已知不重复读
5. **并行专家**：切面 ≥ 2 时用 task-dispatch 并行
6. **文档格式对齐 code-to-wiki**：每篇含 cite 块 / 目录 / 章节来源 / 按需 Mermaid，引用均 `file://` 带行号区间；不调用其校验工具，改由 AI 手动自检 R1–R7
7. **专用技能务实**：只对识别出的具体可复用操作任务调 create-skill 造技能，不造 stub
8. **不编造**：无内容则标注「该模块无此项」，不凑话

## 执行流程

### Step 0：确认模块边界与专家名

- 必须有明确的模块根路径（目录或包名）；路径不明确时仅问一次
- 由模块的业务功能派生**中文专家名**（如 `pkg/alert` → "告警处理专家"），与用户确认后定名
- 专家 = **业务功能域**（如"告警处理""日志查询"），一个专家可覆盖同一域下的多个相关模块；若同一模块按域需拆成多个专家，各自独立建目录
- 若 `.module-experts/{中文专家名}/` **已存在**：向用户确认是「合并补全」（保留现有文档，仅补缺失切面）还是「重建」（覆盖）。默认合并补全
- 专家名即目录名：`.module-experts/{中文专家名}/`

### Step 1：模块范围扫描（AI 自行判断）

主 agent 用 `list_dir` / `search_file` 快速摸清模块根目录结构，自行判断：

- 文件清单与语言 / 框架 / 测试目录 / 入口点
- **该产出哪些切面 Wiki 文档**（发现 DB / ORM / migration → `04-模型.md`；router / controller → `05-接口.md`；测试目录 → `06-测试.md`；配置 / 部署 → `07-运维.md`）
- 模块规模：源文件过多（如 > 200）时改为采样，不逐文件全读；采样后**保证完整性**：必读入口 / 主调用链 / 每个子目录至少 1 个代表文件。要求各子 agent 在切面文档的 `**本文引用的文件**` cite 块中注明「已采样 X/N 文件，覆盖核心路径」，并**列出已覆盖的子目录清单**，便于校验无遗漏，不假装全覆盖
- **记录关键文件路径与行号区间**，供后续各切面撰写时填充 cite / 章节来源

> 不依赖任何脚本，由 AI 基于目录结构与文件命名自行决策。

### Step 2：知识库优先查（如 ki 可用）

按 codekb-skill 规则，对目标模块先查 ki（项目记忆索引 → KB），命中则复用、跳过对应切面的部分代码阅读。无 ki 则跳过本步。

### Step 3：派出专家团（并行）

依据 Step 1 判断结果选择切面。切面 ≥ 2 时调用 task-dispatch 并行，每个切面一个子 agent。

- **task-name**：`module-expert-{专家名拼音或英文简称}`
- **子任务产出**：每个切面产出 `.module-experts/{中文专家名}/{NN-切面中文}.md`（中间产物可先写在 `.codebuddy/task-dispatch/.../subtasks/{NN}-{切面}/{NN-切面中文}.md`，完成后落盘到最终位置）
- **子 agent prompt 要点**：给定模块根 + 中文专家名 + 该切面调研清单（见 [reference.md](reference.md)，含 code-to-wiki 格式模板）+ 同批产出的其他切面清单（供 `01-架构.md` 预置索引）；用 search_content / search_file / read_file 调研并**记录文件路径与行号区间**；按切面模板产出，严格遵循 cite 块 / 目录 / 章节来源 / 图表来源 / `file://` / Mermaid / 深度规范

**切面定义**（适用时产出，文件名见上表）：

| 切面 | 文件 | 核心内容 |
|---|---|---|
| architecture | `01-架构.md` | 职责、边界、子模块、依赖图、分层；兼作模块入口与切面索引 |
| implementation | `02-实现.md` | 核心算法、设计模式、热点路径、关键类 |
| data-flow | `03-数据流转.md` | 入口 → 出口生命周期、状态流转、异步流 |
| models | `04-模型.md` | 数据模型、DB schema、ORM 映射、迁移、校验 |
| api | `05-接口.md` | 公开入口、契约、错误码、版本策略 |
| tests | `06-测试.md` | 单测位置、覆盖、模式、如何跑、缺口 |
| ops | `07-运维.md` | 配置、部署、feature flag、日志 / 监控 |

> `01-架构.md` 与 `02-实现.md` 为核心切面，默认必出；其余按适用性。

### Step 4：合成专家入口

主 agent 汇总各切面产出，写入两份文件：

**A. `agent.md`（专家名片，必出，不套 Wiki 格式）**——总结这个专家是干嘛的：
- 一句话职责：该专家负责的**业务领域**
- 负责的模块：`.module-experts/{中文专家名}/` 对应的模块根路径与一句话职责
- 何时找这个专家：列出典型使用场景
- 包含的资产：切面 Wiki 文档清单 + 专用技能清单（或「暂无」）
- 出处行：生成日期 + git commit

**B. `01-架构.md`** 补充（该篇已由各子 agent 产出初稿，主 agent 在此补全）：
- 切面索引：链接到同专家目录下其他切面文档（`./02-实现.md`、`./03-数据流转.md` 等）
- 关键发现 / 主要风险 / 常见坑（Top）
- 术语表
- 出处行：生成日期 + git commit（仅被动 provenance，不含同步校验逻辑）

### Step 5：造专用技能（调 create-skill）

基于已产出的切面文档，识别该业务领域中**具体、可复用的操作型任务**（如告警处理专家的"新增告警规则""排查告警不触发"）：

- 每识别出一个有价值的操作任务 → **调用 `create-skill` 技能**，在其指导下生成标准格式 `SKILL.md`，落盘到 `.module-experts/{中文专家名}/skills/{kebab-skill-name}/`
- 调用 `create-skill` 时**以非交互式方式生成**：直接将该技能的完整上下文（目标用途、触发短语、执行步骤、边界、示例）作为 prompt 一次性交给 create-skill，明确要求其直接输出最终 `SKILL.md` 内容（含 frontmatter 和正文），不在子流程内等待用户交互确认，避免子 agent / task-dispatch 子流程卡住
- **create-skill 调用失败或未返回有效 SKILL.md 时**：主 agent 按 `create-skill` 规范**自行生成**合规 `SKILL.md` 并落盘，不阻塞 expert-team 流程；并在 `agent.md` 中标注该技能为"主 agent 兜底生成"
- 技能格式以 create-skill 规范为准，本 skill 不重复定义
- **质量底线**：技能必须含真实触发短语与可执行步骤，禁止 stub；识别不出任何操作任务时，留空 `skills/` 并在 `agent.md` 注明「暂无专用技能」

### Step 6：校验（含格式自检）

主 agent 自检产出，**除内容完整性外，按 code-to-wiki 的 R1–R7 逐篇手动检查**（`agent.md` 除外）：

内容完整性：
- `agent.md` 与 `01-架构.md`、`02-实现.md` 必有且非空
- 各切面文档非空、无纯占位符（`TODO` / `待补充`）
- 无内容的切面标注「该模块无此项」而非留空
- `01-架构.md` 含切面索引
- `skills/` 下每个技能有合规 `SKILL.md`（frontmatter + 正文），无 stub

格式自检（R1–R7）：
- **R1** 每篇顶部有 `**本文引用的文件**` cite 块
- **R2** `## 目录` 条目与各 `##` 章节一一对应，锚点中文
- **R3** 每个 `##`/`###` 小节末尾有 `章节来源`（`file://` + `#Lx-Ly`）；纯概念节可豁免
- **R4** 每个 Mermaid 图后有 `图表来源`
- **R5** 所有引用路径均 `file://` 前缀
- **R6** 来源行号区间覆盖实际代码跨度（非单点）
- **R7** 详细分析 ≥2 设计维度；架构 / 流程 / 依赖等按需配 Mermaid 图

不合格 → 补全 / 修正对应切面后重检。

### Step 7：更新索引

在 `.module-experts/INDEX.md`（不存在则建）按专家追加 / 更新：

```
# 模块专家包索引
> 由 expert-team 自动维护（文档格式遵循 code-to-wiki）

## {中文专家名}  （职责摘要见 agent.md）
- 模块根：{path}
- 生成日期：{date}  git commit：{hash}
- 切面文档：01-架构, 02-实现, 03-数据流转, ...
- 专用技能：skills/{skill1}, skills/{skill2}（或「暂无」）
```

### Step 8：可选写 ki KB

将模块知识原子（按 codekb-skill 8 类白名单）写入 ki KB，便于后续 query 命中。专家文档内不重复堆 KB 原文，仅引用。

## 验证（测试方式）

1. 抽查：`01-架构.md` 能否脱离代码独立读懂该业务模块
2. 各切面文档是否遵循 code-to-wiki 格式（cite / 目录 / 章节来源 / 图表来源 / `file://` 行号 / Mermaid）
3. 无内容的切面是否标注「该模块无此项」而非编造
4. 核心切面（`01-架构.md` + `02-实现.md`）是否必出且非空
5. `skills/` 下技能是否为标准格式、含真实触发短语与步骤、非 stub
6. 格式自检 R1–R7 是否全部通过（不调用 `codetowiki` 工具，由 AI 手动核对）

## 行为边界

- 一次一个业务模块，不批量
- 专家目录用中文业务名；切面文档用 code-to-wiki 中文序号前缀（`01-架构.md` 等）；skills 子目录用 kebab-case
- 不内置过期同步 / 重跑机制（按决策）；文档为生成时快照
- 章节来源中的 `#Lx-Ly` 行号为**生成时快照**；因本 skill 不做过期同步，代码变更后行号可能失效——属已知权衡，不以过期行号否定文档其它内容
- 不调用 `codetowiki` 格式校验工具；格式合规由 AI 按 R1–R7 手动自检
- 不替代 code-survey 的设计前轻量调研
- 不写 memory；写 KB 走 codekb-skill 规则
- 专用技能格式交由 create-skill 规范，不在本 skill 内重复定义
