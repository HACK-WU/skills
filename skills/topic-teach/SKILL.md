# 通用知识教学（Topic Teach）

## 概述

**目的**：让 AI 充当"全科私教"，把学习任意知识主题这件事结构化成**可校验、渐进式、生动形象**的教学流程——从技术主题（k8s / docker / Python）到非技术主题（投资 / 理财），都能产出可反复查阅的学习材料。

**功能**：
- 双模式交付：大主题走**课程制**（多阶段大纲 → 阶段概览 → 分批知识点教学），小主题走**速览**（单篇讲透 + 延伸大纲）
- **故事化教学叙事骨架**：每课遵循"场景引入 → 认知冲突 → 层层揭示 → 实操验证 → 体系收束"五幕结构，以场景代入而非定义堆砌开场；大纲规划时同步设计故事主线，把架构/知识点拆成有情节推进的故事线
- **多阶段备课制**：正式讲解前先规划「阶段 → 课 → 知识点」三层大纲（通常 2–4 个阶段 = 完整学习旅程），并随学习进度 / 目标变更 / 重点变更**动态调整**（活文档）
- **评审把关**：多阶段大纲、阶段概览、学习路径总览经 `course-reviewer` 子 agent（教学法视角）评审；**每批教学内容必须经两个 `course-reviewer` 实例以不同视角（教学法视角 + 学习者视角）独立评审**，冲突由主 agent 裁决（教学逻辑 / 准确性 / 完整性 / 格式规范 / 一致性 + 场景吸引力 / 由浅入深 / 认知阶梯 / 故事弧 / 困惑点 / 全局定位），P0 问题清零后才交付用户；**评审以 `00-评审清单.md` 为强制检查点**（事前占位待办 + 事后勾选，未勾选 = 未评审）
- **分批生成**：以知识点为最小单位，每批 3–5 个知识点生成并确认，**禁止一次性生成整个阶段的内容**，保证质量与学习节奏
- **结课综合实战项目**（课程制默认必做）：全部阶段完成后产出**跨阶段整合**的实战项目——含覆盖知识点地图、≥2 个设计决策权衡、反例对照、验收清单，把散装知识点焊成整体能力（防退化成玩具 demo，复杂度有硬门槛）
- **实战经验 + 排障速查手册 + 场景解法库**：同一次生成三份互补产物——《实战经验》是**学习态**（适用边界 / 高频故障模式五段式 / 落地 Checklist），《排障速查手册》是**使用态**（按症状倒查的条件-动作表，机长 QRH 式），《场景解法库》是**设计态**（"新要求来了怎么设计"的多解法权衡，从会用走向会设计）
- **续学闭环**：每批产物末尾附**下一批接力提示词**，用户复制粘贴即可继续学习，无需重新描述上下文
- 每个核心概念在层层揭示中配生活化类比；流程 / 结构类内容用 Mermaid，复杂拓扑 / 学习路径图用 SVG
- 双轨领域适配：技术域给可运行的实操命令 / 代码，非技术域给案例推演 + "数字算给你看" + 风险提示
- 设"事实核查"质量闸门：时效敏感内容（版本号 / 行情 / 法规）按需联网核实并标注置信度，杜绝幻觉
- **以 Markdown 为主载体**；图表默认 Mermaid，复杂图用 SVG 独立文件（入 `assets/`），**不使用 HTML**
- **产物仓库卫生**：每完成一个课程单元（整课 / 实战项目 / 收尾产物）后，检查并增量维护产物仓库根 `.gitignore`——写课过程会持续产出依赖目录、构建产物、日志等"非教学产物"文件，配「禁止忽略清单」防误伤教学产物；另清理本轮亲手创建且已登记的临时文件（只认清单，禁用 `git clean -fd`）
- 可选知识点对齐：选择题自动评分、错题巩固、跨轮次追踪进步

**使用场景**：
- 系统学习一个新领域："教我 k8s""从零开始学 Python""理财入门"
- 快速搞懂一个概念："讲讲 docker 网络模式""什么是 ETF"
- 学完练手与避坑："给我个项目练手""k8s 生产上常见的坑""出问题时怎么排查"
- 续学与自测："继续学 k8s""考我一下 docker 知识"

**与 module-teach 的分工**：教学对象是**本项目的代码模块** → 用 `module-teach`（证据来自代码回读）；教学对象是**跨项目的通用知识** → 用本技能（证据来自内置知识 + 联网核查）。用户只说"考我一下"未指明对象时：当前会话在讲代码模块 → 路由到 module-teach；在讲通用主题 → 本技能；无上下文 → 询问用户要考哪个。

## 教学产物落盘

**产物仓库**：所有教学产物存放于一个独立的 git 仓库（或用户指定的产物目录）。每个主题一个目录 `{topic-slug}/`，**直接放在产物仓库根目录**（`topic-slug` 取主题的 kebab-case 英文名，如 `k8s-basics`、`personal-finance`）。不使用 `.teach-topics/` 等冗余前缀。

```
{topic-slug}/
├── 00-学习档案.md               # 学习者画像 + 模式 + 知识点级进度表 + 大纲调整记录 + 评审记录（断点续学依据）
├── 00-评审清单.md               # 评审强制检查点：事前占位待办 + 事后勾选（未勾选 = 评审未完成，禁止进入下一批）
├── 01-学习路径总览.md           # 学习目标 + 全阶段总览：各阶段目标/重点一览 + 阶段依赖图（SVG）
├── 02-课程目录.md               # 书本式课程目录：按阶段列出各课 / 速览 / 手册（已编写 = 链接，活文档）
├── assets/                      # 根级 SVG 图（学习路径总览 / 课程手册引用）
├── stages/                      # 课程制模式的阶段目录
│   ├── 1-基础知识学习/           # 阶段目录名 = {阶段序号}-{阶段名称}（用名称，不用 slug）
│   │   ├── overview.md          # 阶段概览：目标 / 学习重点 / 必须掌握的知识点 + 本阶段路径图（SVG）
│   │   ├── lessons/
│   │   │   ├── lesson-01-{课名}.md     # 课文件名用中文课名（与阶段目录名一致，全程中文）
│   │   │   └── lesson-02-{课名}.md
│   │   └── assets/              # 本阶段引用的 SVG 图
│   └── 2-进阶实战/
├── overview.md                  # 速览模式的单篇产物（含延伸大纲 + 接力提示词）
├── projects/                    # 结课综合实战项目（课程制 Phase 3，默认必做）
│   └── {项目名}/                # 目录名用中文项目名
│       ├── README.md            # 需求 / 目标 / 覆盖知识点地图 / 运行方式
│       ├── 设计决策.md          # ≥2 个权衡点：选项对比 → 选择 → 理由 → 代价
│       ├── 反例对照.md          # "能跑但很糟"的版本 + 逐条对比
│       ├── 实现/                # 技术域：可运行代码（中文注释）；非技术域此目录改名为 `推演/`，放完整决策推演
│       └── 验收清单.md          # 自测项：怎么确认自己真的做成了
├── final-课程手册.md            # 汇总手册（Markdown，含实战项目收录）
├── 08-实战经验.md               # 学习态：适用边界 / 高频故障模式五段式 / 落地 Checklist
├── 09-排障速查手册.md           # 使用态：按症状倒查的条件-动作表（机长 QRH 式）
├── 10-场景解法库.md             # 设计态："新要求来了怎么设计"的多解法权衡（先想后看）
├── 07-知识点对齐.md             # 最新一轮知识点对齐 + 成绩单（每轮覆盖更新，可选，命名与 module-teach 统一）
└── 知识点对齐记录/             # 历次知识点对齐记录（可选）
    ├── INDEX.md                 # 轮次索引：轮次/日期/正确率/错题知识点
    └── round-01.md
```

> **`07-知识点对齐.md` 的编号保持不变**（与 module-teach 统一约定），不因流程顺序在它之前而重编号——它是历史约定，改了会破坏跨技能一致性。新增产物从 `08` 起编。

**载体原则**：Markdown 是唯一主载体（课程/速览/汇总均为 `.md`）。图表默认用 Mermaid（内嵌代码块）；**仅当出现 SVG 触发信号**（分支回环密、交叉连线多、需泳道/分区语义、扇入扇出大、需精确位置/方向控制）或属于**学习路径 / 阶段依赖总览图**时，改用 SVG 独立文件（入 `assets/`，kebab-case 命名，如 `learning-path-overview.svg`）。**不使用 HTML**。

每写完一个批次 / 阶段文件，在对话中给一句摘要（本批要点 + 文件链接）+ **下一批接力提示词**，不要一次性把全文甩进对话。

## 产物仓库卫生（.gitignore 维护 + 临时文件清理 · SSOT）

教学产物落在 git 仓库里，而**写课过程本身就是持续产渣的过程**——尤其 Phase 3 实战项目的 `实现/` 一旦真跑起来，立刻生成依赖目录、构建产物、日志与本地配置。缺了忽略规则，`git status` 会被运行残留淹没，`git add .` 会把 `node_modules/` 这类几万文件的目录提进仓库。

**核心动作 = 两件事，每完成一个课程单元后各做一次**：

1. **忽略**：回头看一眼"这轮新增了哪些不属于教学产物的文件"，需要就补进 `.gitignore`——**可逆**（写错了删掉那行即可），故可以放手做
2. **清理**：删掉本轮**亲手创建且已登记在案的临时文件**——**不可逆**（未提交的文件没有 git 历史可恢复），故范围极窄，见「临时文件清理」

> 下文各钩子所称的「**卫生检查**」，即指这两件事一起做。

### 检查时机（分级，不一刀切）

| 时机 | 强度 | 说明 |
|------|------|------|
| **Phase 1.3 落盘** | **初始化** | 产物仓库根无 `.gitignore` → 按 [reference.md](reference.md) 模板创建基线（只建系统/编辑器组 + 通用过程残留组） |
| **Phase 2 整课完成**（写入「🧭 课程导航」时） | **必查** | 用户要求的"每个小课程写完一次"。课级检查，不随批次重复——一批一查太碎，且拆批中间态不代表最终产物形态 |
| **Phase 3 实战项目完成** | **必查（重点）** | 产渣最大来源：技术域 `实现/` 被运行后产生依赖目录/构建产物/日志；非技术域几乎不产渣，可只做快速确认 |
| **Phase 4 手册汇总** | 顺查 | 汇总拼接过程可能产生中间草稿，顺带清理 |
| **Phase 5 落盘收尾** | 顺查 | 纯 Markdown 产物，通常无新增，确认即可 |
| 速览模式写完 | 顺查 | 单篇 Markdown + 少量 SVG，通常无新增 |
| 断点续学进入时 | 补漏 | 产物仓库根无 `.gitignore` 但已有产物（上一轮漏建/被删）→ 补建基线，不阻塞续学 |

> **优先级低于评审**：本检查是落盘后的附加动作，**不得抢在评审之前**——本批评审 P0 未清零时，先完成评审与清单勾选，再回头做卫生检查（忽略 + 清理）。长流程中 AI 注意力有限，评审漏了会产出低质量课程，`.gitignore` 漏了或临时文件没清，事后补都来得及。

### 检查方法（四步）

1. **列出本轮新增**：`git status --porcelain`（未跟踪 + 已修改）。**只看本轮由教学产生的文件**——判定范围限定在 `{topic-slug}/` 与本轮实际落盘路径下。**用默认的目录聚合模式，禁止加 `-uall`**：首次检查时 `node_modules/` 之类可能尚未被忽略，逐文件展开会输出上万行淹没上下文（聚合后只是 `?? node_modules/` 一行）。产物仓库若同时是用户的工作项目，全仓库 `git status` 会混入大量与教学无关的未跟踪文件，**不得据此批量加规则**（错误忽略用户的源码比漏忽略危害大得多）。
2. **分类判定**：逐个问"这是**教学产物**（要提交）还是**过程残留**（要忽略）？"
   - 教学产物：`*.md`、`assets/*.svg`、`实现/` 下的源码、`知识点对齐记录/`、`.gitignore` 自身
   - 过程残留：依赖目录（`node_modules/`、`venv/`、`.venv/`、`__pycache__/`、`.mypy_cache/`、`vendor/`）、构建产物（`dist/`、`build/`、`target/`、`*.egg-info/`）、运行输出（`*.log`、`logs/`、`tmp/`、`*.tmp`、`.DS_Store`、`Thumbs.db`、`*.swp`）、本地配置与密钥（`.env`、`.env.local`、`.env.*.local`）
3. **只追加本轮实际出现的**：命中哪类加哪条，**不预先灌满模板**——没写 Python 就不加 `__pycache__/`，避免 `.gitignore` 变成没人看得懂的噪音。
4. **校验未误伤**：追加后须确认教学产物仍在跟踪范围内（`git status --porcelain` 中 `*.md` / `assets/*.svg` 仍可见；或 `git check-ignore -v {关键产物路径}` 无命中）。

### 禁止忽略清单（负向操作兜底）

以下**绝不能**进 `.gitignore`——它们是要提交的教学产物：

| 项 | 为什么不能忽略 |
|----|---------------|
| `*.md` | 全部课程正文、档案、手册、清单 |
| `assets/` 与 `**/*.svg` | SVG 图是教学产物（阶段依赖图 / 路径图 / 概念图），丢了图全废 |
| `实现/` `推演/` 目录下的源码 | 实战项目本体，只有其内部的依赖目录/构建产物该被忽略 |
| `stages/` `projects/` `知识点对齐记录/` | 产物主体目录 |

> **判定口诀**：*这个文件丢了，课程还完整吗？* 不完整 → 是教学产物，不能忽略；完整 → 是过程残留，可以忽略。
>
> **最易踩的坑**：为图省事写 `dist/`、`build/` 这类宽泛目录名时，若实战项目的示例目录恰好同名会被连带吞掉。写成 `/dist/`、`/build/`（锚定仓库根）或更精确的 `{项目路径}/dist/`，避免误伤。

### 临时文件清理（窄范围 · 只清自己创建的）

忽略是让文件"在 git 里隐身"，清理是从磁盘上删掉。**删除不可逆**，故清理范围必须比忽略窄得多——**只删本轮亲手创建、且明确登记在案的临时文件**。

**清理时机**：与 `.gitignore` 检查同一时机（见上方「检查时机」表，不在此重复枚举以免双源漂移）。**Phase 1.3 落盘除外**——此时尚无临时文件可清。

#### 地基：先登记，后清理

AI 创建任何临时文件时，**立即把路径记入本轮临时文件清单**（在对话中维护，不落盘）。清理时**只删清单内的路径**——没有登记的，一律不删。

> 安全性不来自"删除时再判断一次该不该删"（长上下文下这种判断会失真），而来自"创建时就登记"。这是整套机制的地基。
>
> **漏登记的失败方向是安全的**：忘了登记 → 清单为空 → 跳过清理 → 临时文件留在磁盘上（顶多下次被 `.gitignore` 收编）。宁可留下垃圾，也**绝不为了"完成清理动作"而现场凑一份清单**——那等于把安全边界拆了。
>
> **清单不落盘是刻意的**：**断点续学进入新会话时，上一轮清单已随会话消失**，本轮清单从空开始——不清上一轮的临时文件（它们要么已被 `.gitignore` 收编，要么由用户自行处理）。同样，**上下文被压缩 / 截断后不得凭"看起来像临时文件"重建清单**，清单为空就是为空，跳过。

**什么是临时文件**：生成过程中的中间草稿、格式转换的中间态、临时验证脚本、跑通即弃的探针文件。

#### 三重校验（缺一不删）

| # | 校验 | 说明 |
|---|------|------|
| 1 | **是本轮会话亲手创建的** | 在临时文件清单里有登记。用户创建的、既有目录下冒出来的、来源不明的 → **一律不删** |
| 2 | **不是教学产物** | `*.md`、`assets/*.svg`、`实现/` / `推演/` 下的源码**即使由 AI 亲手创建，也是最终产物**，绝不在清理范围（见「禁止忽略清单」） |
| 3 | **不是可再生的运行时产物** | `node_modules/`、`__pycache__/`、`venv/`、`dist/` 等是"可再生依赖"而非垃圾——删了 Phase 3 实战项目直接跑不起来，下次还得重装重建。它们归 `.gitignore` 管，**不归清理管** |

> **AI 自己创建 ≠ 可删**：本轮最大宗的创建物（课时 md、SVG、项目代码）恰恰是最不能删的。判断标准是"这个文件是**过程态**还是**终态**"，不是"是不是我建的"。

#### 执行流程

1. 取出本轮临时文件清单（**为空则跳过，不必在对话中提及**）
2. 逐条过三重校验，筛出待删项
3. **删除前在对话中列出待删清单**（一行摘要即可，让删除行为可追溯）
4. 执行删除 → 说明"已清理 N 个本轮临时文件"
5. 删除失败（文件占用 / 权限不足）→ 跳过并在对话中提示，**不重试、不阻塞教学流程**

#### 目录删除规则

优先**逐文件删除**；确需删临时目录时，必须**确认该目录本轮自建、且内部文件全部在清单内**才删。

- **禁止 `rm -rf` 一个未逐项核对过的目录**
- **禁止用 `git clean -fd` 批量删除**——它会连用户自己的未跟踪文件一起删掉，范围完全不可控（**.gitignore 检查里也禁用 `git clean` 做清理，只允许精确路径删除**）

### 行为边界

- **`.gitignore` 只追加，不删规则**：用户已有的忽略规则一律不动，即使看起来冗余。判断不了某条该不该删 → 不删。（删除动作只存在于「临时文件清理」，且只针对文件本身，不针对 `.gitignore` 里的行）
- **只动产物仓库根的 `.gitignore`**：不修改产物仓库之外（如用户主项目）的忽略文件。
- **产物仓库与工作项目同体时更保守**：若教学产物就落在用户正在开发的项目里，只追加「本轮教学明确产生的残留类型」，不碰项目自身的构建产物 / 依赖配置——那是用户已有约定的地盘。
- **非 git 环境跳过忽略检查**：落盘目录不是 git 仓库（用户指定的普通产物目录）时，跳过 **`.gitignore` 相关**检查，不提示、不阻塞；**临时文件清理与 git 无关，照常执行**。
- **不代为提交**：只维护 `.gitignore`，不执行 `git add` / `git commit`——提交时机归用户。
- **不确定时不加**：拿不准某文件是残留还是产物 → 保留为未跟踪并在对话中提一句，由用户决定，胜过静默吞掉。
- **清理只认清单**：清理的唯一依据是「本轮临时文件清单」，不是"现场判断它像不像临时文件"——现场判断在长上下文中会失真，清单不会。清单里没有的，一个都不删。
- **禁用 `git clean -fd`**：它会连用户自己的未跟踪文件一起删，范围不可控。清理只用**精确路径**的删除命令。
- **删除失败不重试**：文件占用 / 权限不足时跳过并在对话中提示，不重试、不阻塞教学流程。

## course-reviewer 评审执行规则（各评审节点通用）

所有评审节点统一按此规则执行。course-reviewer 支持**双模式**（教学法视角 `pedagogy` / 学习者视角 `learner`），由主 Agent 通过【评审模式】字段指定：

1. **可用性检查**：评审前检查 `course-reviewer` 子 agent 是否已创建（存在 `agents/course-reviewer/agent.md`）。
2. **已创建** → `use_agent(course-reviewer)`，按对应评审节点委派，**须在输入中指定【评审模式】**：
   - 大纲 / 阶段概览 / 路径总览评审：只委派 1 个实例，模式 = `pedagogy`
   - **批次内容评审 / 速览评审 / 结课实战项目评审 / 实战经验与排障手册评审 / 场景解法库评审**：**必须委派 2 个实例**，分别指定 `pedagogy` 和 `learner` 模式，独立评审
3. **未创建** → 二选一，**默认走"直接评审"，不阻塞教学流程**：
   - **直接评审（默认）**：主 agent 直接以 course-reviewer 的两种角色定位与对应评审维度执行评审。
     - 批次内容评审时，主 agent 先以教学法视角执行一轮（5 维度），再以学习者视角执行一轮（6 维度），输出两份独立意见。
     - **收尾产物评审（实战项目 / 经验 / 手册 / 场景解法库）**：两个视角均须**叠用 `agents/course-reviewer/agent.md` 的「专项评审维度 A / B」**（A1-A6 / B1-B8）——仅凭 5+6 通用维度会漏掉复杂度门槛与证据纪律这两类 P0 检查点（子 agent 委派时 agent.md 自含专项维度，内联时主 agent 必须主动读取）。
     - **内联模式独立性约束**：主 agent 内联评审时，学习者视角不得走过场——**必须逐项输出 L1-L6 完整评审表**（每维度至少 1 条意见或"无问题"），不得省略。主 agent 同时扮演生成者 + 两个评审者 + 裁决者四重身份，独立性最弱，须以完整输出补偿。在 `00-学习档案.md` 评审记录的「评审方式」标注「主 agent 内联（子 agent 未创建，独立性受限）」，并提醒用户"可创建独立 course-reviewer 子 agent 获得更独立的评审视角"。
   - **提醒创建**：若用户希望先建 agent，提示"course-reviewer 子 agent 尚未创建，可按 create-sub-agent 规范创建"；用户同意则调用 `create-sub-agent` 创建（或按 `agents/course-reviewer/agent.md` 定义落地），创建完成后回到正常委派流程。
4. **评审结论**：无论何种方式，评审结论均记入 `00-学习档案.md` 的「评审记录」表（P0 清零才放行）。
5. **评审清单强制检查点**：`00-评审清单.md` 是唯一可验证的**待办勾选**检查点（与学习档案「评审记录」表分工：清单管"待办勾选"，档案管"结论摘要"）。Phase 1 落盘时按已规划的阶段/课**占位**全部评审节点（`- [ ]`）；每批内容评审完成且 P0 清零后，**必须回到清单勾选对应条目**（`- [x]`）。**未勾选条目 = 评审未完成**，是断点续学时发现漏评审并补做的依据。

### 双模式冲突处理

两个实例（或主 agent 内联的两轮评审）的评审意见可能冲突：
- 如教学法视角说"知识点齐全 P0=0"，学习者视角说"第三幕认知跳跃 P0=1"
- **由主 Agent 自行裁决**：主 Agent 以自身判断决定最终采纳哪些意见
- 在 `00-学习档案.md` 评审记录的「意见摘要」中标注"双模式冲突，主 Agent 裁决：{裁决理由}"

## 工作流程

复制此清单并跟踪进度：

```
任务进度：
- [ ] Phase 0：确认主题与学习者画像
- [ ] Phase 0.5：模式判定（课程制 or 速览）
- [ ] Phase 1 备课：一次性生成多阶段大纲（阶段→课→知识点 + 故事主线）→ course-reviewer 评审（教学法视角）→ 落盘（路径总览 + 阶段概览 + 骨架）
- [ ] 课程制：Phase 2 分批次生成（每批 3-5 知识点：按五幕叙事骨架生成 → 双 agent 评审 → 确认 → 落盘）
- [ ] 速览：按五幕叙事骨架生成 overview.md（双 agent 评审）
- [ ] 每批产出后：事实核查闸门（不可跳过）+ 双 agent 评审 + 更新进度表与大纲 + 附下一批接力提示词
- [ ] Phase 3：综合实战项目（课程制默认必做：跨阶段整合 + 设计决策 + 反例对照 + 验收清单）
- [ ] Phase 4：课程手册汇总（含实战项目收录）
- [ ] Phase 5：实战经验 + 排障速查手册 + 场景解法库（一次生成三份，学习态 + 使用态 + 设计态）
- [ ] Phase 6：知识点对齐 · 选择题（可选）
```

> 讲解一律基于 AI 内置知识 + 按需联网核查，**不得编造不存在的 API、命令、数据或案例**。时效敏感结论必须走事实核查闸门。

### Phase 0：确认主题与学习者画像

先向用户确认（**主题**为必答项，其余均有默认值，用户跳过则用默认值并在学习档案中标注）：

1. **主题**：学什么（用户未明确时请其一句话描述，如"k8s 基础""ETF 投资入门"）。
2. **当前水平**（默认 `入门`）：
   - `零基础`：完全没接触过 → 类比更多、术语逐个通俗化、不假设任何背景。
   - `入门`：听说过、用过皮毛 → 正常节奏。
   - `进阶`：日常使用、想深入原理 → 少讲基础、多讲机制 / 权衡 / 底层。
3. **学习目标**（默认 `理解概念`）：
   - `理解概念`：搞懂"是什么、为什么、怎么工作"。
   - `动手实操`：每课实操环节加量，产出可照着做的步骤。
   - `应试认证`：如 CKA / 证券从业，讲解贴考纲、小测加量。
   - `决策参考`：如"要不要用 k8s""该不该买 ETF"，额外产出对比分析与决策清单。
4. **输出格式**（默认 `Markdown`）：Markdown 唯一必需主载体；图表默认 Mermaid，复杂图用 SVG 独立文件（入 `assets/`，选型规则见"表现形式规范"）。**不使用 HTML**。

**问题交互规则**：**主题**为必答项，其余 3 项均有默认值。为避免轻量提问被流程拖累——若用户的提问已是明确的单点概念（如"什么是 ETF""docker 网络模式讲讲"），跳过逐项确认，直接按默认画像进入 Phase 0.5（大概率判为速览），在产物顶部标注"按默认画像生成，可要求调整"；仅当主题是完整体系（将走课程制）时，才值得花一轮确认画像。

将画像写入 `00-学习档案.md` 顶部。

**断点续学**：用户说"继续学 XX"时，跳过 Phase 0：先在**产物仓库根** `list_dir` 列出已有主题目录，与用户口语主题做模糊匹配（如"继续学 k8s"匹配到 `k8s-basics/`）；命中唯一目录则先看 `02-课程目录.md` 课程目录（已编写 = 链接）快速定位，再读 `00-学习档案.md` 进度表 + `01-学习路径总览.md` 最新大纲 + `00-评审清单.md`（**先看大纲调整记录与评审记录，确认结构是否已变；并检查评审清单是否有未勾选条目——有则说明上一批评审被漏，先补评审再续学**）。

**续学落点判定**（按序判断，命中即停）：

| # | 条件 | 落点 |
|---|------|------|
| 1 | 清单有未勾选条目，**且其对应产物文件已存在**（课文件 / `projects/` / `08-`-`09-`） | **漏评审** → 先补做该条目的评审再继续 |
| 2 | 进度表有**非"已完成"**的知识点 | 从「当前阶段第一个未完成知识点」继续 Phase 2 |
| 3 | 知识点全部完成，但 `projects/` 不存在且未标注"用户跳过" | → **Phase 3 综合实战项目** |
| 4 | 实战项目完成（或已跳过），但 `08-`/`09-`/`10-` 任一不存在 | → **Phase 5 实战经验 + 排障速查手册 + 场景解法库** |
| 5 | 全部完成 | 询问用户想做什么（汇总手册 / 知识点对齐 / 深入新方向） |

> **第 1 条的判定关键是"产物是否已存在"**：清单未勾选 ≠ 漏评审——正常学到课 2 时，课 3 条目当然未勾选（还没学到）。**只有产物文件已落盘而清单未勾选，才是真的漏评审**。否则会误把"还没学到"当"漏评审"，卡住正常续学。
>
> **"继续学"不等于"继续听课"**：知识点讲完后还有 Phase 3 / 5 两个收尾环节。若直接回"都学完了"，就是默认跳过了它们——这正是这两个 Phase 最容易被漏掉的时刻，故在此显式判定。

命中多个或零个目录时，列出候选让用户选择，选不到则告知"未找到已有档案"并走全新流程。

### Phase 0.5：模式判定

按以下规则自动判定，判定结果告知用户（用户可覆盖）：

| 信号 | 模式 |
|------|------|
| 主题是完整体系（"学 k8s""理财入门""系统学 Python"），或预估需 ≥ 3 课才能讲透 | **课程制** |
| 主题是单点概念（"讲讲 docker 网络模式""什么是 ETF"），或用户说"快速 / 简单讲讲" | **速览** |
| 用户明确说"开个课程""分几课教我" / "一篇讲完" | 按用户说的定 |

速览模式中若发现主题实际很大（一篇讲不透），主动建议升级为课程制。

### Phase 1：备课——规划多阶段大纲（所有模式必做）

**学习是持续过程**，不能边讲边现想。课程制正式讲解前，先规划**完整的多阶段大纲**，回答"这次分几个阶段学、每阶段学什么、学到哪算一段落"。

#### Step 1.1 生成多阶段大纲 + 故事主线（一次性生成）

- 将主题拆为 **2–4 个阶段**（如「基础 → 进阶 → 实战」），每阶段一个主题段落，标注**阶段间前置依赖**。
- 每阶段细化为 **2–4 课**，每课再细化为 **2–5 个知识点**。
- 每个知识点再拆 **2–4 个关键点**（子概念 / 要点）——**关键点才是真正的最小教学单元**，确保大纲粒度足够细、目录足够详实。
- 每个知识点有清晰的教学目标，正文须**按「知识点六要素」展开**（一句话定义 → 直觉建立 → 核心原理 → 示例演示 → 常见误区 → 一句话记住，见 reference.md 单课模板），**不得只写一段泛泛而谈**。
- **同步设计故事主线**：按「教学叙事骨架」的"故事主线设计"方法，规划整个主题的叙事 spine（主角→冲突→转折→收束），每个阶段是故事的一个"章节"。故事主线写入大纲的「故事主线」字段。

结构示例（阶段 → 课 → 知识点 → 关键点 四层）：

```
故事主线：一个程序员从单机部署到管理万台集群的进化之路
  主角：Pod 生命周期  |  冲突：单机扛不住流量  |  收束：声明式管理万台集群

阶段 1：容器与 k8s 基础（"单机时代的终结"——为什么需要容器）
├── 课 1：容器基础
│   ├── 知识点：镜像与容器（关键点：镜像分层 / 容器与 VM 的区别 / 镜像仓库）
│   ├── 知识点：容器运行时（关键点：runc / containerd / CRI 接口）
│   └── 知识点：隔离原理（关键点：Namespace / Cgroups / 联合文件系统）
├── 课 2：Pod 基础
│   ├── 知识点：Pod 概念（关键点：最小调度单位 / 共享网络与存储 / 生命周期）
│   ├── 知识点：Pod YAML（关键点：四要素 / 容器字段 / 探针）
│   └── 知识点：多容器共享（关键点：localhost 互通 / 共享卷 / sidecar 模式）
阶段 2：调度与工作负载（"让机器自己干活"——如何声明式管理）
├── 课 3：Deployment
│   ├── 知识点：副本管理（关键点：ReplicaSet / 副本数控制 / 自愈）
│   ├── 知识点：滚动更新（关键点：maxSurge / maxUnavailable / 更新策略）
│   └── 知识点：回滚（关键点：revision 记录 / rollout undo / 失败回退）
```

#### Step 1.2 course-reviewer 评审大纲

- 按「course-reviewer 评审执行规则」对多阶段大纲做评审（已创建 → `use_agent(course-reviewer)`，模式 = `pedagogy`；未创建 → 直接评审），评审节点为"大纲评审"。
- 评审重点：阶段划分合理性、知识点顺序递进、前置依赖无缺口、覆盖面完整、**故事主线设计合理**（主角是否清晰、冲突是否真实、转折是否递进）。
- **P0 意见必须清零**（修订后复审），P1 / P2 酌情采纳；评审结论记入 `00-学习档案.md` 的"评审记录"表。

#### Step 1.3 评审通过后落盘（大纲一次性生成，不再单独占一轮用户确认）

- 评审通过后，大纲**一次性落盘**，不再单独占一轮用户确认。
- **故事主线轻量确认**：大纲在对话中展示时，故事主线部分加一句提示："📖 故事主线方向（主角：X / 冲突：Y / 收束：Z）是否合适？不合适可调整，其余结构已落盘。"这是轻量提醒而非阻塞流程——用户不回应则按已落盘主线继续；用户提出调整则更新主线及相关阶段概览后继续。故事主线贯穿全程，选错返工成本高，故单独提醒。
- 落盘内容：
  - `01-学习路径总览.md`：学习目标 + 全阶段总览（各阶段目标 + 重点一览 + 故事主线 + 阶段依赖图 SVG）。
  - 各阶段 `stages/{N}-{阶段名}/overview.md`：阶段概览（目标 / 学习重点 / 必须掌握的知识点 + 本阶段在故事主线中的章节定位 + 本阶段路径图 SVG）。
  - `00-学习档案.md`：初始化**知识点级进度表**。
  - `00-评审清单.md`：初始化评审清单，**一次性占位全部评审节点**——大纲评审 + 每课/批次内容评审（均为 `- [ ]`）。**课程制**另加两条收尾占位：**结课实战项目** + **实战经验 / 排障速查手册 / 场景解法库**；**速览模式不占位这两条**（速览不做 Phase 3 / 5，占位会产生永远无法勾选的死条目，干扰断点续学判定）。速览模式的「速览评审」条目由速览模式生成前自行初始化。占位粒度 = 批次：默认一课一批，占位到课即占位到批；一课需拆多批时，首批生成前将该课条目按批次拆为多条。
    > **两个收尾节点必须在课程制 Phase 1 就占位**：它们在流程末尾，若此刻不占位，AI 在长流程后极易漏掉（历史教训：评审写成流程文字 → 漏评审）。占位了 = 断点续学时可被发现并补做。
  - `02-课程目录.md`：初始化书本式目录（按阶段列出全部计划课 + 速览 / 手册条目，未编写 = 纯文本，模板见 [reference.md](reference.md)）。
  - `.gitignore`（产物仓库根）：不存在则**初始化基线**（模板见 [reference.md](reference.md)），只建系统/编辑器组与通用过程残留组；已存在则不动。后续增量维护（忽略 + 清理）见「产物仓库卫生」。
  - 各课骨架 `stages/{N}-{阶段名}/lessons/lesson-NN-{课名}.md`：只写课名 + **知识点清单（含每个知识点的关键点）** + 本课目标 + **本课在故事主线中的情节定位**，**正文留待 Phase 2 分批填充**（首批生成时在骨架上展开正文）。课文件名中的 `{课名}` 用**中文课名**（与阶段目录名一致，不用英文 slug）。

**用户调整处理**：大纲在对话中展示后，用户可随时增删调序。用户调整是最高权威；但若用户调整改变了前置依赖关系（如删除了前置课、调换了跨阶段顺序），须重过一轮 course-reviewer **轻量评审**（仅查前置缺口与完整性），通过后更新落盘文件。

> 模板见 [reference.md](reference.md)：多阶段大纲模板、学习路径总览模板、阶段概览模板。

### 大纲是活文档（动态调整）

大纲**不是一次性产物**，随学习推进持续调整，每次调整记录到 `00-学习档案.md` 的"大纲调整记录"表：

| 触发时机 | 调整动作 |
|----------|----------|
| 学完一批，发现节奏偏快 / 偏慢 | 增删知识点、拆分 / 合并课 |
| 用户目标变更（如从"理解概念"改"动手实操"） | 更新 `01-学习路径总览.md` 学习目标 + 调整各课实操比重、增删实操课 |
| 重点变更（用户想深挖某块） | 重排课程顺序、为某知识点加内容 |
| 出现新的前置知识缺口 | 在依赖图中补节点、插入前置课 |

**调整规则**：每次调整后更新 `01-学习路径总览.md` / 阶段 `overview.md` → 在 `00-学习档案.md` 追加一行调整记录（日期 / 调整内容 / 原因）→ **阶段大纲的结构性调整（增删阶段/课/知识点）须重新过 course-reviewer 大纲评审，并同步增删 `00-评审清单.md` 对应占位条目** → 对话中告知用户"大纲已调整：X"。

### Phase 2：分批次生成教学内容（课程制）

**核心规则：禁止一次性生成整个阶段的内容。** 以**知识点**为最小生成单位，按批次推进：

**批次划分**：
- 默认**以课为批次边界**：一课的知识点 ≤ 5 个 → 一课一批；> 5 个 → 拆多批（每批 3–5 个知识点）。
- **知识点细化后按篇幅灵活调整**：每个知识点含 2–4 个关键点、按六要素展开后篇幅增大，若单批内容过重，可将每批知识点数降至 **2–3 个**，以"单轮可消化、不超长"为准。
- 批次顺序 = 大纲顺序，严格从前置到后置。

**每批四步**（顺序执行，缺一不可）：
1. **生成**：按单课模板写本批知识点正文，**必须遵循「教学叙事骨架」五幕结构**。首批在 Phase 1 落盘的课骨架上**展开正文**（骨架含课名/知识点清单/本课目标/情节定位）；若本批即一课的全部知识点 → 直接成文 `lesson-NN-{课名}.md`；若是拆批的课 → 后续批次在既有课文件末尾**追加小节**（每小节 = 一个知识点）。
2. **双 agent 评审**：按「course-reviewer 评审执行规则」评审本批内容——**必须委派两个 course-reviewer 实例**，分别以 `pedagogy` 模式（教学法视角：内容准确性 + 格式规范 + 完整性）和 `learner` 模式（学习者视角：场景吸引力 + 由浅入深 + 认知阶梯 + 故事弧 + 困惑点 + 全局定位）独立评审。冲突由主 agent 裁决。P0 清零后**回到 `00-评审清单.md` 勾选本批条目**。
3. **用户确认**：评审 P0 清零后，对话中给一句摘要 + 文件链接 + **下一批接力提示词**，询问"继续下一批 / 先消化 / 调整节奏"。
4. **落盘**：用户确认继续后，更新 `00-学习档案.md` 进度表（本批知识点 → ✅ 已完成）+ 更新 `02-课程目录.md` 课程目录（本批课改为可点击链接）+ 检查是否需要**动态调整大纲**（按"大纲是活文档"规则）+ 写入下一批接力提示词。

**每批写完必做四件事**（顺序执行）：
1. 过一遍事实核查闸门（不可跳过）；
2. 过双 agent 评审（教学法视角 + 学习者视角，冲突主 agent 裁决），P0 清零后**勾选 `00-评审清单.md` 本批条目**；
3. 更新 `00-学习档案.md` 进度表 + 评审记录 + 更新 `02-课程目录.md` 课程目录 + 检查是否需调整大纲；
4. 对话中给一句本批摘要 + 文件链接 + **将接力提示词原样贴给用户**，然后询问"复制提示词继续下一批 / 先消化 / 调整节奏"。

**接力提示词模板**（写入产物末尾 + 对话中均使用）：

````markdown
## 🚀 下一批接力提示词

> 学完本批后，**复制下面这段文字发给 AI**，即可无缝进入下一批（无需重新描述上下文）：

```
继续学 {主题}。我的学习档案在 {topic-slug}/00-学习档案.md，
刚学完阶段 {X}《{阶段名}》的课《{课名}》知识点 {知识点1、知识点2…}，
请按大纲继续讲解下一批知识点。
```
````

> 接力提示词**随批次更新**，始终指向"下一批"（一课拆多批时，第二批生成后更新为指向第三批）。
> 若这是本阶段最后一批，改为"🎉 本阶段完成"提示 + 建议进入下一阶段（或先做阶段自测 / 阶段性总结）。
> 若这是**全部阶段**的最后一批，指向 **Phase 3 综合实战项目**（"课程知识已讲完，接下来做一个跨阶段整合的实战项目"），而不是就此结束——**知识讲完 ≠ 学完**。

**课程导航（上一课 / 下一课链接）**：整课完成（该课全部知识点批次写完、不再追加小节）时，在课文件末尾（接力提示词之后）追加「🧭 课程导航」区块，含上一课 / 下一课 / 返回目录三个链接（格式见 [reference.md](reference.md) 单课模板）：
- 上一课 / 下一课用课文件相对链接——同阶段直接 `lesson-XX-{课名}.md`，跨阶段 `../../{阶段名}/lessons/lesson-XX-{课名}.md`；
- 第一课省略「上一课」；最后一课的「下一课」改为「🎉 课程知识已讲完——接下来做综合实战项目」（链接回课程目录，**不写"本课程已完成"**——课时讲完 ≠ 学完，后面还有 Phase 3 / 5）；
- 该区块是**课级**导航，整课完成时一次写入，**不随批次更新**；拆批过程中（课未写完）不写。

**整课完成时追加一项：卫生检查**——课写完（导航区块落盘的同一时刻）执行（`.gitignore` 增量维护 + 本轮临时文件清理，流程见 SSOT 章节）。**课级一次，不每批做**。本轮既无新增残留、也无待清理临时文件则不动，也不必在对话中提及。

### 领域双轨适配（Phase 2 / 速览通用）

| 环节 | 技术域（k8s / docker / Python…） | 非技术域（投资 / 理财…） |
|------|--------------------------------|------------------------|
| 实操环节 | 可直接运行的命令 / 代码（含预期输出），课末附**命令速查卡** | 案例推演（虚构人物走一遍决策）+ **数字算给你看**（如复利 / 费率对比表格） |
| 图表偏好 | 架构图、时序图、状态图（Mermaid），复杂拓扑用 SVG | 决策流程图、对比表、饼图（Mermaid `pie`），复杂决策树用 SVG |
| **综合实战项目**（Phase 3） | **可运行**的多文件工程（含目录结构、模块划分、错误处理） | **完整决策推演**（一个人物/家庭从 0 到 1 走完全流程，含取舍与后果核算） |
| **实战经验 + 排障手册**（Phase 5） | 故障模式以**日志关键字 / 报错原文**索引；排障条目给命令与检查项 | 风险以**可观测信号**索引（如"连续 3 月跑输基准""接到索要验证码的电话"）；排障条目给处置动作与止损话术 |
| **场景解法库**（Phase 5） | 场景是**设计题**（"流量翻 10 倍""数据量翻 100 倍"），解法按层给多选项 + 代价 + 递进路径 | 场景是**决策题**（"通胀""单一收入""家庭变故"），解法按目标给多路径 + 后果核算 |
| 附加义务 | 标注命令 / API 适用的大版本 | **强制**：⚠️ 风险提示 + 免责声明 + 数据时点标注（模板见 [reference.md](reference.md)） |

**高风险领域红线**（投资 / 理财 / 医疗 / 法律）：只教知识与方法论，**不给个体化建议**（不推荐具体标的 / 药品 / 操作），每篇产物含免责声明，所有数字标注数据时点。

### 速览模式

单篇 `overview.md`，为单课模板的浓缩版：**顶部速览大纲**（本次核心 + 延伸方向）→ 场景引入 → 认知冲突 → 核心原理（层层揭示，含 ≥ 1 张 Mermaid 图，复杂拓扑用 SVG）→ 实操验证（回扣场景） → 体系收束 → 🐞 误区 → 一图总结 → 📚 官方文档（如有） → **延伸学习提示词**。同样遵循五幕叙事骨架（浓缩版）。生成前先初始化 `00-评审清单.md`（占位「速览评审」一条）；写完过事实核查闸门 + **双 agent 评审**（按「course-reviewer 评审执行规则」执行，教学法视角 + 学习者视角，冲突主 agent 裁决，P0 清零后交付），P0 清零后**勾选 `00-评审清单.md` 速览条目**。完成后在 `02-课程目录.md` 追加一条速览链接条目，并顺带过一遍卫生检查（速览只产 Markdown + 少量 SVG，通常既无新增残留、也无临时文件）。

> **速览模式不做 Phase 3 / Phase 5**：速览是一篇讲透的单点概念，综合性实战项目与领域排障手册与其篇幅、目标都不匹配。**不因"流程要求"而硬做**——改为在延伸学习提示词中给出"下一步实战建议"（见 reference.md「延伸学习提示词模板」），用户据此升级为课程制后才走 Phase 3 / 5。
>
> **速览升级为课程制时，须补占位**：速览阶段清单里没有两条收尾占位（见 Phase 1.3）。若用户从速览升级为课程制，走 Phase 0 重新规划后，**必须在 `00-评审清单.md` 补上「结课实战项目」与「实战经验 / 排障速查手册 / 场景解法库」两条 `- [ ]` 占位**——否则升级后的长流程同样会漏掉这两个收尾环节，速览阶段"不占位"的正确决策反而变成升级后的漏洞。

**速览也要可续**：速览不等于一次性。`overview.md` 顶部必须有"速览大纲"（本次讲什么 + 1–2 条延伸方向），末尾附**延伸学习提示词**——用户复制即可把速览升级为系统学习（或换主题继续），避免"讲完就断"。

**延伸学习提示词模板**（速览本身不做 Phase 3 / 5，故给两条路径——选第二条会先升级为课程制再走 Phase 3 / 5）：

````markdown
## 🚀 想深入？复制发给 AI

**升级为系统课程**（含结课实战项目与排障手册）：

```
我刚看了 {topic-slug}/overview.md 关于 {主题} 的速览，
想进一步学习，请按我的情况（{水平} / 目标 {目标}）把 {延伸方向} 展开成一个课程。
```

**直接要实战 / 避坑**：

```
我刚看了 {topic-slug}/overview.md 关于 {主题} 的速览，
请给我一个综合实战项目练手，或讲讲 {主题} 的实战经验、排障速查手册与场景解法库。
```
````

速览模式默认输出 Markdown（`overview.md`），不使用 HTML。

### 事实核查闸门（质量闸门，不可跳过）

每批产物（课时 / 速览 / 实战项目 / 实战经验与排障手册 / 场景解法库）写完后立即执行：

1. **扫描时效敏感内容**，类型包括：软件版本号与 API 变更、工具生态推荐（"目前主流用 X"）、价格 / 利率 / 汇率 / 行情、法规 / 税则 / 政策、统计数据。
2. **按需联网核查**：对扫描出的条目用 web 搜索核实，核实后在文中标注 `（核查于 YYYY-MM）`。
3. **无法核实的**：标注 `⏳ 置信度：低（截至训练知识，建议自行验证）`，不得以确定语气陈述。
4. **发现有误的**：立即修正原文，绝不带着错误结论进入下一批。
5. 非时效敏感但拿不准的结论（如某机制的细节行为），同样标注置信度，宁可示弱不可编造。
6. **起源/历史事实强制联网核实**：若本课含"起源背景"（作者、诞生年份、诞生动机、演化历程、解决的历史痛点等历史事实），**必须联网核实**，即使不涉及版本号/行情等时效敏感内容——历史事实凭内置知识易记错或编造。核实后标注 `（核查于 YYYY-MM）`；无法核实的标注 `⏳ 置信度：低` 并避免以确定语气陈述作者/年份。
7. **经验 / 排障手册 / 场景解法库从严**（Phase 5 专用）："经验"与"解法"是最容易编造的内容——AI 倾向于生成"听起来合理"的故障模式、修复步骤与设计方案。故收紧三条：① 每条「症状—根因—修复」与每个「场景解法」须可溯源（官方文档 / 联网核查 / 领域公认实践）；② 拿不准的一律标 `⏳ 置信度：低`，且**不得进入排障手册**（手册只收确定项）；③ 宁缺毋滥，凑不满条目就如实写已收录数，不硬凑。

### Phase 3：综合实战项目（课程制 · 默认必做）

**定位**：课程的"合奏"。Phase 2 每课的第四幕只验证**单个知识点**，本阶段是全流程唯一要求**跨阶段整合**的环节——把散装知识点焊成"能做出一个完整东西"的能力。

**触发时机**：全部阶段知识点完成（进度表无非"已完成"项）后**默认进入**，无需用户要求。用户可跳过（跳过后在 `00-学习档案.md` 大纲调整记录标注"用户跳过实战项目"）。速览模式不做（见速览模式说明）。

**为什么默认必做**：只学不做的课程，产出的是"知道"不是"会"。但仍允许用户跳过，尊重节奏。

#### 复杂度硬门槛（防退化成玩具 demo）

四条**必须同时满足**，缺一即判 P0：

| # | 门槛 | 判定标准 |
|---|------|----------|
| 1 | **跨阶段整合** | 覆盖 **≥3 个阶段**的知识点（阶段总数 < 3 时覆盖全部阶段），须在知识点地图中逐个回指具体课时 |
| 2 | **非功能约束** | 至少含 2 项工程约束：性能 / 错误处理 / 可维护性 / 安全 / 成本（按主题域选取） |
| 3 | **真权衡决策** | **≥2 个**"不止一个合理答案"的决策点，每个写清「选了什么 / 为什么 / 放弃的方案差在哪 / 付出的代价」 |
| 4 | **规模** | 技术域：多文件工程（有目录结构与模块划分），非单文件脚本；非技术域：完整决策链条（≥5 步推演），非单点判断 |

> **门槛 3 最易被敷衍**：把"唯一正确答案"包装成决策点不算。判定标准——*换个人来可能选另一个方案，且也有道理*。

#### 产物结构

`projects/{项目名}/`（目录名用**中文项目名**）：

| 文件 | 内容 |
|------|------|
| `README.md` | 一句话需求 + 目标 + **覆盖知识点地图**（表格：知识点 → 所属阶段/课 → 文件链接）+ 运行方式 + 目录说明 |
| `设计决策.md` | ≥2 个权衡点，每个五段式：候选方案对比 → 最终选择 → 选择理由 → 为此付出的代价 → 什么情况下该改选另一个 |
| `反例对照.md` | **看起来能跑但其实很糟**的版本 + 逐条对比（≥3 条差异，每条说清"为什么糟"） |
| `实现/` | 技术域：可运行代码（中文注释，关键处注明对应哪个知识点）；非技术域：完整决策推演记录 |
| `验收清单.md` | 自测项清单（怎么确认自己真的做成了），学习者可逐项勾选 |

#### 生成流程

1. **需求定义**：结合 `00-学习档案.md` 的学习目标定需求（`动手实操` → 偏工程实现；`决策参考` → 偏选型推演）
2. **知识点地图**：列出本项目覆盖的全部知识点，逐个回指阶段/课——**这是"整合"的证据，不是装饰**
3. **设计决策**：写 ≥2 个权衡点（五段式）
4. **参考实现**：技术域给可运行代码；非技术域给完整推演
5. **反例对照**：写"能跑但很糟"的版本 + 逐条对比
6. **验收清单**
7. **事实核查闸门**（不可跳过）
8. **双 agent 评审**（pedagogy + learner 双视角），P0 清零后**勾选 `00-评审清单.md` 的「结课实战项目」条目**
9. **卫生检查**（产渣最大来源，必做，**须在评审 P0 清零之后**）：① `.gitignore`——`实现/` 只要被实际运行过，就按 SSOT 四步追加依赖目录 / 构建产物 / 日志 / 本地配置类规则（**技术域是重点，非技术域可只做快速确认**），追加后必须校验 `实现/` 下的源码本身仍在跟踪范围内（`git check-ignore` 无命中）；② **临时文件清理**——验证项目可运行性时产生的临时脚本 / 探针文件是本节最大宗的临时产物，按三重校验清理

> **为什么卫生检查排在评审之后**：评审过程中会修订项目文件，可能删掉/改名实现文件、新增依赖——**在评审前做忽略与清理，判定依据会失效**（刚加的忽略规则可能针对一个即将被评审要求重写的目录）。先定稿，再谈卫生。这与 SSOT 章节「优先级低于评审」一致。

**评审新增检查项**（通用维度之外，course-reviewer 须额外查）：

- 复杂度四门槛是否**均**达标（尤其中门槛 3：决策点是否真有争议）
- 知识点地图是否真跨 ≥3 阶段（不是同一阶段凑数）
- 反例是否"看起来能跑"（明显错误没有教学价值）
- 技术域代码是否真能跑（命令 / 依赖 / 版本标注完整）

**阶段小项目（可选开关，默认关）**：每阶段结束时可加一个 mini 项目（覆盖本阶段即可，跨阶段门槛降为 1）。用户说"每个阶段都给我个小项目"时开启，并**同步在 `00-评审清单.md` 增加对应占位条目**。默认关闭，避免流程过重。

**追加多个项目**：用户要求"再给我一个项目"时允许追加，落点同为 `projects/{项目名}/`。每个项目**独立走完整的生成 + 评审流程**，并**在 `00-评审清单.md` 为该新增项目单开一条占位条目**——不与第一个项目共用一条（否则第二个项目的评审状态无法独立追踪）。

### Phase 4：课程手册汇总（课程制，含实战项目收录）

全部课时与 Phase 3 实战项目完成（或用户要求提前汇总）后，产出：

- **`final-课程手册.md`**：以 Markdown 汇总全部课时（Mermaid 以代码块嵌入，SVG 以 `![说明](./assets/xxx.svg)` 引用）。**md 是主载体，也是汇总手册的唯一必需格式。**
- **收录实战项目**：手册末尾追加 `## 综合实战项目` 章节——项目需求 + 覆盖知识点地图 + 设计决策摘要 + **链接回 `projects/{项目名}/README.md`**（不把整个项目源码抄进手册，手册只做索引与决策摘要）。用户跳过了实战项目则省略本章节。
- 更新 `02-课程目录.md`：追加手册链接条目与实战项目条目。
- 手册开头放 `01-学习路径总览.md` 的阶段总览（各阶段重点一览），各阶段按顺序展开。

汇总完整性检查：确认所有已完成课时均已纳入、路径总览与各阶段概览出现在手册开头、各课"一图总结"全部保留、**实战项目已收录（未跳过时）**。

`学习目标` 附加内容：
- `应试认证`：手册末尾追加 `## 考点速记`（高频考点清单 + 易混点对照表）。
- `决策参考`：手册末尾追加 `## 决策清单`（该不该用 / 买的判断条件 + 对比分析表）。

### Phase 5：实战经验 + 排障速查手册 + 场景解法库（一次生成三份）

**定位**：补上课堂只演 happy path 的缺口。同一次生成三份互补产物，覆盖三种认知状态：

| 产物 | 认知状态 | 回答的问题 | 姿态 |
|------|---------|-----------|------|
| `08-实战经验.md` | **学习态**（坐着读，要懂为什么） | 会踩什么坑、为什么会踩 | 被动 · 原理 |
| `09-排障速查手册.md` | **使用态**（崩了翻，只要答案） | 出错了怎么止血 | 被动 · 动作 |
| `10-场景解法库.md` | **设计态**（主动想，怎么设计） | 新要求来了怎么设计 | 主动 · 权衡 |

> 三份**分工不能混**：手册只给动作、经验层讲原理、解法库给多方案权衡。混在一起会同时毁掉三个——学习时读不到原理、紧急时读不完、设计时看不到选项。

**触发**：课程制在 Phase 4 之后默认进入；用户可提前触发（"给我讲讲生产上的坑""出问题时怎么排查""流量翻倍怎么扛"）；**速览模式不做**。

> **提前触发的素材纪律**：若在课时未完成时触发（如 Phase 2 学到一半），故障模式只能基于内置知识 + 联网核查，**无法结合本课程已教内容**。此时须在 `08-实战经验.md` 顶部标注：`⚠️ 本材料生成于课程未完成阶段（已完成 {N}/{M} 阶段），故障模式基于领域通用实践，未针对本课程知识点做定制`。**宁可标注，不可假装已结合课程内容**。

**为什么必须一次生成三份**：三份产物的素材源是同一批"领域典型失败模式 + 常见高难度场景"。分开生成 = 同一个坑写两遍、同一个场景两套解法 = 必然双源漂移。

#### 产物一 `08-实战经验.md`（学习态）

1. **适用边界与反模式**：什么场景**别用**它、什么时候该换方案。**"不该用"比"怎么用"更值钱**——这是从"会用"到"用对"的分界线。
2. **高频故障模式**（5–10 条）：每条固定**五段式** = `症状（可观测）→ 根因 → 排查路径 → 修复 → 预防`。
   症状必须可观测：写"服务很慢"无效，要写"P99 从 50ms 涨到 3s，且 CPU 正常"。
3. **落地 / 上线 Checklist**：投产前必查项（按主题定制：上线检查 / 配置基线 / 安全检查）
4. **真实事故案例复盘**（1–3 个，可选）：须**联网核查**真实事故并标注来源与时点；找不到可信案例则不写，**不虚构**。

#### 产物二 `09-排障速查手册.md`（使用态 · 机长 QRH 式）

五个硬特征，缺一个就退化成普通"常见错误列表"：

| # | 特征 | 要求 |
|---|------|------|
| 1 | **按症状倒查** | 开头是**索引表**：报错关键字 / 观测现象 → 条目 + 紧急度。是**检索入口**，不是目录 |
| 2 | **症状可观测** | 每条写明「一眼识别」：日志关键字 / 报错原文 / 现象特征 |
| 3 | **先止血后定位** | 第一条动作永远是**止损**（回滚 / 降级 / 隔离），不是查根因——线上没时间先搞清楚再动手 |
| 4 | **分支判定** | 用条件-动作表（若 X 则 A，否则 B），不是线性步骤清单 |
| 5 | **有升级出口** | 每条末尾「若无效 → 转 {具体去向}」，不留死胡同 |

**紧急度分级**：🔴 立即处理（业务已受损）/ 🟡 尽快处理（有风险未爆发）/ ⚪ 有时间再看（体验或优化问题）

**与经验层的交叉引用**：每条手册条目末尾附「想懂为什么 → [08-实战经验.md](../08-实战经验.md) · 故障模式 {N}」——**只写编号，不写锚点**（症状名是运行时才确定的内容，锚点会在替换占位符后失效）。**手册只给动作，不给原理**——原理在学习态读，紧急时不占认知带宽。

**条目格式**（完整模板见 [reference.md](reference.md)）：

```markdown
## 🔴 症状：{一句话症状}

**一眼识别**：{日志关键字 / 报错原文 / 现象特征}

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | {止损动作} | {恢复到什么状态} |
| 定位 1 | {第一条诊断} | {看到什么说明是什么问题} |
| 定位 2 | {第二条诊断} | {...} |
| 修复 | {具体动作} | {成功的标志} |
| 若无效 | → 转「{另一条目}」/ 转 `debug` 现场排查 | — |

**预防**：{一句话，怎么避免再发生}
**原理**：→ [{经验层对应故障模式编号}](../08-实战经验.md)
```

> 跨文件引用只写**编号**，不写锚点——症状名是运行时才确定的内容，锚点一旦替换占位符就失效。

#### 产物三 `10-场景解法库.md`（设计态 · 主动设计题）

把"会用"推进到"会设计"。每个场景是一道**开放设计题**：给一个高难度新要求，让学习者先自己想，再对照多种解法。

每个场景固定结构（**先想后看**，用 `<details>` 折叠解法，与课后小测答案折叠一致）：

| 部分 | 内容 |
|------|------|
| 场景描述 | 具体化、可观测（"QPS 从 500 涨到 5000，数据库先扛不住"） |
| 🔒 先自己想 | 一句话引导（"第一反应是加机器？加缓存？"） |
| 💡 提示（折叠） | 分层 / 分维度的思考方向，不直接给答案 |
| 📖 展开解法（折叠） | **解法一览**（≥3 个解法，含代价 + 适用边界）→ **推荐路径**（递进，不是一次全上）→ **知识点挂钩**（回指课程课时）→ **不适用边界**（什么时候别用） |

**四条硬要求**（缺一掉档）：

1. **多解法**：每场景 ≥3 个解法，带代价与适用边界——**只给一个"标准答案"就退化成普通教程**
2. **先想后看**：解法用 `<details>` 折叠，强制学习者先独立思考
3. **知识点挂钩**：每个解法回指课程课时——否则与课程脱节，成了孤立文章
4. **递进 + 边界**：有「推荐路径」（按什么顺序上）和「不适用」（什么时候别用）

**场景来源**：AI 按主题域生成 5–8 个**领域高频高难度场景**（技术域如流量翻 10 倍 / 数据量翻 100 倍 / 多机房容灾；非技术域如通胀 / 单一收入 / 家庭变故），每个解法必须可溯源（同证据纪律）。

#### 证据纪律（比正文更严）

"经验"是最容易编造的内容，故：

1. 每条「症状—根因—修复」必须可溯源：官方文档 / 联网核查 / 领域公认实践，三者居其一
2. 拿不准的标 `⏳ 置信度：低`，且**不得入手册**——手册只收确定项（不确定的可留在经验层并标注）
3. **宁缺毋滥**：凑不满 5 条就如实写"已收录 N 条"，**不硬凑凑数条目**
4. 涉及命令 / 参数 / 版本号的，走事实核查闸门并标注适用版本

#### 生成流程（三份一次产出）

1. **失败模式盘点**：基于已教内容 + 内置知识 + 联网核查，列出领域典型失败模式候选（8–15 条）
2. **高难度场景盘点**：列出领域高频高难度场景候选（8–10 个，"流量翻 10 倍""数据量翻 100 倍"类）
3. **筛选排序**：失败模式按「踩中概率 × 后果严重度」筛 5–10 条，场景按「常见度 × 决策价值」筛 5–8 个，**淘汰凑数项**（宁少勿滥的落实步骤）
4. **逐条溯源**：每条故障模式与每个场景解法补来源（官方文档 / 联网核查 / 领域公认实践）；不可溯源的一律标「置信度：低」或删，**绝不入手册 / 解法库的确定区**
5. **生成经验层**：按五段式讲机制（学习态）
6. **压缩出手册**：从经验层**同源压缩**为条件-动作表（使用态）——压缩不重写；每条手册条目回指经验层故障模式编号
7. **生成场景解法库**：每个场景按「多解法 → 递进路径 → 知识点挂钩 → 不适用边界」展开（设计态）；解法与经验层故障模式可互引（如"解法 A 做错会引发故障模式 3"）
8. **事实核查闸门**（走第 7 条从严规则）
9. **双 agent 评审**（pedagogy + learner，**叠用 course-reviewer 的「专项评审维度 B1-B8」；场景解法库另叠「专项评审维度 C1-C7」**），P0 清零后**勾选 `00-评审清单.md` 的「实战经验 / 排障速查手册 / 场景解法库」条目**
10. **落盘收尾**：更新 `02-课程目录.md`（三条目改链接）+ `00-学习档案.md` 评审记录 + 顺带过一遍卫生检查（纯 Markdown 产物通常既无新增残留、也无临时文件，确认即可）+ 给出指向 Phase 6（或复盘 / 深入方向）的结课提示词

> 同样原则适用于 **Phase 3 实战项目评审**：双 agent 评审时**叠用「专项评审维度 A1-A6」**——仅凭 pedagogy 5 维度 + learner 6 维度评不出复杂度门槛与决策点真争议。

#### 与 `debug` 的边界（SSOT）

- **本阶段**：预演**领域典型**失败模式的预案（"这类问题通常怎么排查"）
- **`debug` skill**：处理**实际发生**的具体 bug（"我这儿现在真的报错了"）
- **转交规则**：手册查不到当前症状 → `use_skill("debug")` 现场取证
- 本阶段**不负责定位任何具体 bug**

### Phase 6：知识点对齐 · 选择题（可选，仅用户要求时触发）

用户说"考我一下""出几道题""测测我"时进入。可**独立触发**（不必先完整学一遍）。

**机制与 module-teach Phase 8 完全一致**（历史读取、错题巩固 ≥1/2、指纹去重、题目规则、交互评分、round-NN 落盘、INDEX 追加、进步对比口径、再考一轮），**不在此重复定义**，直接按 [module-teach SKILL.md Phase 8](../module-teach/SKILL.md) 执行。本阶段仅列出通用知识域的 3 个差异点：

> **与 module-teach 的触发消歧**：出题对象是**本项目代码模块**（如"考我一下 order 模块"、`.teach/` 下有该模块产物）→ 用 `module-teach`；出题对象是**通用知识主题**（如"考我一下 k8s"、产物仓库根下有该主题目录）→ 用本技能。仅说"考我一下"未指明对象时，先问用户考代码模块还是通用知识，再择一触发。

1. **证据来源**（出题输入）：
   - **主题解析**：本会话教过 → 沿用 `{topic-slug}`；用户指定主题 → 直接用；首次独立触发 → 让用户说明主题，初始化 `{topic-slug}/知识点对齐记录/` 目录。
   - **易混点提取**：优先复用 `{topic-slug}/` 下已有课时 / 速览产物；产物缺失则基于内置知识提取（时效敏感的答案先过事实核查闸门）。通用知识域**无代码可溯源**，故不要求 `file://` 引用。
2. **干扰项防幻觉**：通用知识域无代码可溯源，凡拿不准干扰项是否真实存在（如某参数 / 某 API 是否真的有）时，先过事实核查闸门核实，无法确认为真实存在的干扰项不得入题。
3. **存储路径**：产物落在 `{topic-slug}/知识点对齐记录/`（而非 module-teach 的 `.teach/{module-slug}/`）；最新一轮覆盖更新 `07-知识点对齐.md`（文件名与 module-teach 统一，便于跨技能形成一致习惯）。

## 教学叙事骨架（故事化教学核心）

> 这是比"表现形式规范"更高优先级的**结构约束**。表现形式规范是修辞层（类比、emoji、术语通俗化），教学叙事骨架是结构层——决定每课"从哪里开场、怎么推进、在哪收束"。

### 核心理念

**不当教科书，当故事**：每课不是"定义→原理→实操"的线性堆砌，而是以场景代入开场、以认知冲突驱动、以层层揭示推进、以实操验证落地、以体系收束闭环的叙事弧。

### 每课五幕结构（课程制与速览通用）

每课的正文必须按以下五幕组织。五幕是**结构骨架**，不是机械填充——各幕篇幅按内容自然分配，但顺序不可调换、不可缺失。

| 幕 | 名称 | 核心任务 | 做什么 | 不做什么 |
|----|------|----------|--------|----------|
| 第一幕 | **起源与场景引入** | 讲来历 + 让学习者身临其境 | **（可选）先讲知识/技术的起源背景**（如何诞生、作者/团队、解决什么历史痛点，联网核实，见下方"起源背景"说明）→ 再给真实问题场景（技术域如"公司服务上线后扛不住流量"；非技术域如"小王想理财但不知从何开始"）。场景必须贴近学习者认知水平——场景本身不能比要讲的概念更难懂 | 不以定义开场；不以"今天我们学习 X"开场；不造场景（场景应是真实痛点）；起源背景不喧宾夺主（控制在 2-4 句） |
| 第二幕 | **认知冲突** | 制造"为什么需要这个知识"的求知欲 | 抛出场景中的矛盾/困惑（"为什么直接做会出问题？""为什么老办法不够用？"），让学习者先困惑再求知。冲突必须真实存在于场景中，不是硬造的 | 不直接给答案；不跳过冲突直接讲原理 |
| 第三幕 | **层层揭示** | 从直觉到抽象逐层展开 | 先给直觉化解释（类比 + 白话），再逐步引入术语和原理。每引入一个概念都回扣第一幕的场景。知识点按"感知层 → 概念层 → 机制层 → 实操层 → 定位层"的认知阶梯排列 | 不先讲底层原理再讲上层应用（禁止倒序）；不一次性甩出所有术语；不脱离场景讲纯理论 |
| 第四幕 | **实操验证** | 回扣场景，验证刚学的知识 | 技术域给可运行命令/代码验证第三幕讲的机制，且输出结果要回扣第一幕场景（如"你看，加了这个配置后服务扛住了流量"）；非技术域给案例推演 + "数字算给你看" | 实操与场景脱节（变成独立命令清单）；不回扣第一幕的问题 |
| 第五幕 | **体系收束** | 建立全局视角 | 回到全景，把本课知识点在整体架构/体系中的位置标出来。告诉学习者"现在你会了什么、接下来要学什么、为什么"。为下一课埋伏笔 | 只讲本课知识点就结束；不交代这课在整体中的位置 |

#### 起源背景（可选叙事元素，增强故事代入感）

当知识点/技术**有可考的起源**时（如 Elasticsearch、Linux、Docker 等有明确作者和诞生故事），在第一幕"起源与场景引入"中先讲它的来历，把"技术的诞生"变成故事的开场：

| 起源要点 | 说明 | 示例 |
|----------|------|------|
| **诞生背景** | 为什么会出现？当年面临什么痛点/局限 | "Lucene 索引库功能强但太复杂，普通人用不了" |
| **作者/团队** | 谁创造的？什么动机 | "Shay Banon 希望让搜索像数据库一样容易" |
| **关键转折** | 解决了什么痛点 / 击败了什么替代方案 | "把 Lucene 包成 RESTful 服务，开发者开箱即用" |
| **演进** | 现在的状态 / 重要里程碑 | "从搜索库成长为日志分析、AI 搜索平台" |

**触发条件**：仅当知识点**有明确、可考据的起源**时启用。纯概念性知识（如"什么是 HTTP 状态码"）或工具速查（如"git 命令清单"）无明确起源，不强制。
**篇幅约束**：起源背景是**背景简介**，控制在 2-4 句，不喧宾夺主——主体仍是本课知识点。若起源故事丰富且对理解主题有实质帮助，可适度展开但仍须服务于教学主线。
**真实性命门**：起源背景是**历史事实**（作者、年份、诞生动机），**必须联网核实**（见"事实核查闸门"），不得凭内置知识编造或含糊其辞。

#### 五幕退出机制（不适合时的降级路径）

五幕是**默认骨架**，但并非所有知识都适合故事化叙事。以下情况允许采用**直述模式**，在课文件顶部标注"本课采用直述模式，原因：{理由}"：

| 不适合五幕的知识类型 | 原因 | 直述模式怎么写 |
|---------------------|------|---------------|
| **参考性知识**（如"Python 内置函数清单""HTTP 状态码表"） | 无场景冲突可设，硬造场景反而干扰查阅 | 直接以表格 + 简要说明呈现，不强制五幕 |
| **纯定义性知识**（如"什么是变量""什么是字符串"） | 概念太基础，场景比概念更复杂 | 简短定义 + 代码示例 + 一句话记住 |
| **速查/命令手册**（如"git 常用命令""kubectl 速查"） | 学习目标是查阅而非理解 | 按功能分类列表，每条附简短示例 |

**判定规则**：主 agent 在 Phase 2 生成每课前判断是否适合五幕。若不适合，在该课骨架中标注"直述模式"及理由，双 agent 评审时**学习者视角增加一条检查**："本课是否适合直述模式？标注的理由是否成立？若强行套五幕是否会更差？"（L4 故事弧完整性在直述模式下降级为"结构完整性"检查——内容是否完整有序而非是否是故事弧）。**直述模式下「知识点六要素」同步降级**：保留「一句话定义 / 核心原理 / 一句话记住」，可省略「直觉建立 / 示例演示 / 常见误区」，避免简单概念被六要素撑得冗长。

### 故事主线设计（Phase 1 备课时同步规划）

整个主题需有一条**叙事 spine**——不是知识点罗列，而是一条故事线贯穿始终：

- **找主角**：整个主题的核心对象是什么？（如 k8s 的主角是"Pod 生命周期"、理财的主角是"复利与风险"）
- **找冲突**：主角要解决什么问题？为什么这个问题难/重要？
- **找转折**：每个阶段是故事的一个"章节"，每个章节有关键转折（引入新机制解决前一个章节遗留的问题）
- **找收束**：学完整个主题后，学习者应该能回答什么"大问题"？

示例：
- k8s 故事线 = "一个程序员从单机部署到管理万台集群的进化之路"
  - 阶段 1（容器与 Pod 基础）= "单机时代的终结"——为什么需要容器
  - 阶段 2（调度与工作负载）= "让机器自己干活"——如何声明式管理
  - 阶段 3（网络与服务）= "让世界看到你的服务"——如何对外暴露
- 理财故事线 = "小王从月光到财务自由的进阶之路"
  - 阶段 1（基础概念）= "钱去哪了"——收入与支出
  - 阶段 2（投资工具）= "让钱生钱"——复利与工具选择
  - 阶段 3（风险管理）= "守住钱"——风险与配置

故事主线写入大纲模板的「故事主线」字段，每课正文生成时以此 spine 串联。

### 认知阶梯约束

第三幕"层层揭示"中的知识点排列必须遵循认知阶梯：

| 层 | 目标 | 知识点类型 |
|----|------|-----------|
| 感知层 | 让学习者"见过这个东西" | 是什么、长什么样 |
| 概念层 | 让学习者"理解这个东西" | 为什么存在、解决什么问题 |
| 机制层 | 让学习者"搞懂它怎么工作" | 内部原理、工作流程 |
| 实操层 | 让学习者"能动手用它" | 命令、代码、配置 |
| 定位层 | 让学习者"知道它在全局中的位置" | 与其他组件的关系、适用场景 |

**禁止倒序**：不得先讲机制再讲概念，不得先讲实操再讲原理。每一层必须以前一层的理解为前提。

所有产物遵守：

1. **场景先行 + 类比辅助**：概念首次出现时不是先给定义，而是在五幕叙事中——先有场景引入（第一幕）建立直觉，再在层层揭示（第三幕）中用类比建立认知桥梁，最后引出术语定义。类比须在讲完原理后**指出类比失效的边界**，防止误导。类比不是开场修辞，而是贯穿第三幕的认知桥梁。
2. **图表选型（Mermaid + SVG 双引擎）**：流程 / 步骤 → flowchart；组件交互 → sequenceDiagram；概念从属 / 结构 → graph TD 或 classDiagram；状态流转 → stateDiagram；占比 → pie。SVG 有**两类触发信号**，命中任一即用 SVG（即使节点 ≤ 10）：

   **A 类：图形复杂度信号**（继承自 document-writer，适用于流程/拓扑类图）
   - ① 分支 / 回环密集 ② 交叉连线多 ③ 需泳道 / 分区语义 ④ 扇入 / 扇出大 ⑤ 需精确位置 / 方向控制

   **B 类：教学认知难度信号**（topic-teach 教学专属，适用于知识点讲解中的"光靠文字讲不清"场景）
   - ① **数据结构内部结构**：需展示内存布局/节点关系/索引映射（如哈希表 数组+链表、树的结构、图的邻接表）→ 用 SVG 具象化内部构造
   - ② **算法执行过程**：需分步演示状态变化（如数组插入元素逐步移动、排序过程、递归调用栈展开）→ 用 SVG 分步图 + 标注
   - ③ **抽象概念映射 / 层级结构**：需建立"抽象 → 具体"的视觉桥梁或表达多层嵌套/层级关系（如 key-value 映射、指针/引用关系、OSI/TCP/IP 分层模型、MVC 架构层）→ 用 SVG 概念模型图或层级图
   - ④ **多概念对比分类**：需并排对比多个概念的异同/分类（如线性 vs 非线性数据结构、各排序算法对比）→ 用 SVG 对比矩阵/分类图
   - ⑤ **数据 / 函数可视化**：需展示连续数据的形态/趋势/分布/对比曲线（如时间复杂度 O(n) vs O(n²) 曲线、概率分布）→ 用 SVG 轻量数据图表（坐标轴+曲线+关键点标注）

   **固定 SVG 场景**（统一用 SVG，不退回 mermaid）：学习路径总览图、阶段依赖图、阶段路径图。
   **反向约束**：默认仍用 mermaid；仅当出现上述任一触发信号才改用 SVG，不得因"更精美"随意替换简单图。
   **判断口诀**：*能讲清关系的用 mermaid；关系复杂到 mermaid 讲不清 → 用 SVG；文字讲不清的概念 → 也用 SVG。*
   SVG 独立文件入 `assets/`（kebab-case 命名，如 `{图作用}-{图主题}.svg`）。
   **配色约束**：图表（mermaid 与 SVG 通用）背景禁用黑色 / 过深颜色，一律浅色背景（含白色）+ 深色文字；深色仅用于元素强调（表头 / 高亮块，其上文字用浅色），不作大面积背景（详见 reference.md「配色与背景约束」）。
   > 完整 AI 能力边界（含 CSS 微动画、数据可视化图等）见 reference.md「AI 生成 SVG 的能力边界」。
3. **emoji 节制**：仅用于功能性标记（🎯 目标、💡 重点、🐞 陷阱、⚠️ 风险、🚀 进阶），每段 ≤ 2 个，宁少勿滥——美观服务于实用性。
4. **术语通俗化**：术语首次出现时给一句"人话"解释，中英对照（如 "幂等 Idempotent：重复做多少次，结果都一样"）。
5. **语言**：全程中文（代码注释也用中文），句式活泼但严谨，关键结论加粗。
6. **诚实**：不确定的内容按事实核查闸门标注置信度，绝不为了生动而牺牲准确。
7. **md 主载体、SVG 补充**：一切内容先落在 Markdown。图表默认 Mermaid；复杂拓扑 / 学习路径图用独立 SVG 文件（`assets/`）。**不使用 HTML**——SVG 已覆盖原有 HTML 的可视化场景，且跨平台兼容（GitHub 可正常渲染 SVG 文件）。
8. **官方文档链接**：涉及的概念 / 技术 / API / 命令如有官方文档，须在对应知识点后附「📚 官方文档」链接（如 Docker 文档、k8s 官方文档、Python 官方文档、MDN 等）；无官方文档或纯个人理解的知识点则省略，**不得编造链接**。非技术域附权威来源（监管机构 / 官方指南），不用自媒体。
