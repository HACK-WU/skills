# topic-teach · 备课与规划（Phase 0-1）

> **定位**：本文件是 `topic-teach` 的**开课与备课细则**（低频——开课 / 重构大纲时读）：Phase 0 画像确认 / Phase 0.5 模式判定 / Phase 1 备课（四个判定 / 教学效果推演 / 落盘 / Step 1.4 文档收集）/「大纲是活文档」调整。
> 由 [SKILL.md](SKILL.md)「工作流程 · 内容路由」指向本文件；**断点续学的落点判定保留在 SKILL.md**（每次续学要用）。
> ⚠️ 本文件含 **Step 1.1 四个判定**（多角色 / 动手环境 / 应用实战 / 源码解析）——被 `review-dimensions.md`、`reference.md` 等处引用，勿改名。

---

### Phase 0：确认主题与学习者画像

先向用户确认（**主题**为必答项，其余均有默认值，用户跳过则用默认值并在学习档案中标注）：

1. **主题**：学什么（用户未明确时请其一句话描述，如"k8s 基础""ETF 投资入门"）。
2. **当前水平**（默认 `入门`）：
   - `零基础`：完全没接触过 → 类比更多、术语逐个通俗化、不假设任何背景。
   - `入门`：听说过、用过皮毛 → 正常节奏。
   - `进阶`：日常使用、想深入原理 → 少讲基础、多讲机制 / 权衡 / 底层。
3. **学习目标**（默认 `理解概念`）：
   - `理解概念`：搞懂"是什么、为什么、怎么工作"。
   - `动手实操`：每课实操环节加量，产出可照着做的步骤。
   - `应试认证`：如 CKA / 证券从业，讲解贴考纲、小测加量。
   - `决策参考`：如"要不要用 k8s""该不该买 ETF"，额外产出对比分析与决策清单。
4. **输出格式**（默认 `Markdown`）：Markdown 唯一必需主载体；图表默认 Mermaid，复杂图用 SVG 独立文件（入 `assets/`，选型规则见"表现形式规范"）。**不使用 HTML**。

**问题交互规则**：**主题**为必答项，其余 3 项均有默认值。为避免轻量提问被流程拖累——若用户的提问已是明确的单点概念（如"什么是 ETF""docker 网络模式讲讲"），跳过逐项确认，直接按默认画像进入 Phase 0.5（大概率判为速览），在产物顶部标注"按默认画像生成，可要求调整"；仅当主题是完整体系（将走课程制）时，才值得花一轮确认画像。

将画像写入 `00-学习档案.md` 顶部。

### Phase 0.5：模式判定

按以下规则自动判定，判定结果告知用户（用户可覆盖）：

| 信号 | 模式 |
|------|------|
| 主题是完整体系（"学 k8s""理财入门""系统学 Python"），或预估需 ≥ 3 课才能讲透 | **课程制** |
| 主题是单点概念（"讲讲 docker 网络模式""什么是 ETF"），或用户说"快速 / 简单讲讲" | **速览** |
| 用户明确说"开个课程""分几课教我" / "一篇讲完" | 按用户说的定 |

速览模式中若发现主题实际很大（一篇讲不透），主动建议升级为课程制。

### Phase 1：备课——规划多阶段大纲（所有模式必做）

**学习是持续过程**，不能边讲边现想。课程制正式讲解前，先规划**完整的多阶段大纲**，回答"这次分几个阶段学、每阶段学什么、学到哪算一段落"。

#### Step 1.1 生成多阶段大纲 + 故事主线（一次性生成）

- 将主题拆为 **2–4 个阶段**（如「基础 → 进阶 → 实战」），每阶段一个主题段落，标注**阶段间前置依赖**。
- 每阶段细化为 **2–4 课**，每课再细化为 **2–5 个知识点**。
- 每个知识点再拆 **2–4 个关键点**（子概念 / 要点）——**关键点才是真正的最小教学单元**，确保大纲粒度足够细、目录足够详实。
- 每个知识点有清晰的教学目标，正文须**按「知识点六要素」展开**（一句话定义 → 直觉建立 → 核心原理 → 示例演示 → 常见误区 → 一句话记住，见 reference.md 单课模板），**不得只写一段泛泛而谈**。
- **同步设计故事主线**：按「教学叙事骨架」的"故事主线设计"方法，规划整个主题的叙事 spine（主角→冲突→转折→收束），每个阶段是故事的一个"章节"。故事主线写入大纲的「故事主线」字段。
- **多角色判定（仅课程制 · 决定主线之外是否划出子教程）**：识别主题的使用者是否分属**职责显著不同**的角色——信号（命中 ≥2，或学习者角色已明确 → 建议拆分）：① 官方文档本身分角色组织（如 Redis 文档的 Develop / Operate、MySQL 的用户指南 / 管理员指南）；② 现实中分岗位（开发 vs 运维 / DBA / SRE）；③ 知识块可切分（删掉次角色内容后主线仍完整）。**命中 → 主线 = 学习者画像对应的角色视角，次角色内容收敛为「子教程」**（形态与落盘见 Step 1.3 与 reference.md「子教程」）；单角色主题、次角色内容极少（<10%）、或用户明确只要单角色内容 → **不拆**，不硬造子教程。判定结果写入大纲的「角色视角」字段。
- **动手环境判定（决定是否设「环境准备」课）**：课程是否要求**读者自己运行**命令 / 代码（4.1 / 应用实战 / Phase 3 任一含实操）？**是（技术域）→ 阶段 1 首课固定为「环境准备」**（**轻量结构**：不走完整五幕，课级入口要素与 4.2 同步豁免；五要素与模板见 reference.md「环境准备课模板」；标注"已有环境可跳过"）；否（非技术域 / 纯概念无实操）→ 不设，并在大纲中一句说明理由，不硬凑。
- **应用实战判定（仅课程制 · 决定哪些课配实战篇）**：逐课过三问——① **场景可得性**：本课知识点能否自然映射到"一个现实任务"（一句话说清"拿它做什么"）？② **演进空间**：能否凑出"基础实现 → 它的问题 → 综合实现"**至少两跳**（本课知识点可组合）？③ **非硬凑**：场景**不需大量引入本课之外的知识**即可成立？**三问都过才配**（配则写入大纲与 INDEX 骨架，课内第四幕相应留 4.2 入口块）；**不配是常态、不是缺漏**——强配反而意义不大。典型不配：纯概念 / 原理铺垫 / 理论背景课、只有孤立知识点的课、速查类（直述模式）。
- **源码解析判定（仅课程制 · 限库 / SDK / 框架类主题 · 决定哪些课配解析篇）**：逐课过三问——① **功能素材**：本课核心知识点是否落在**库的功能 / API** 上（有源码可讲）？② **认知价值**：讲源码能否带来**认知增量**（更懂"怎么用对 / 为什么这么设计 / 坑的根因"）——"读完文档就够了" → 不配；③ **可读性**：源码规模是否可控（单函数 / 单类级别，教学篇幅讲得清）——巨型函数 / 深层调用链 → 不配。**三问都过才配**（配则写入大纲与 `源码解析/INDEX.md` 骨架，课内文末「🧭 课程导航」区相应留「🔬 源码解析」行）；**不配是常态**——纯概念课、服务端 / 系统组件（同「源码探索」适用对象）、文档已够透的简单功能都不配。

结构示例（阶段 → 课 → 知识点 → 关键点 四层）：

```
故事主线：一个程序员从单机部署到管理万台集群的进化之路
  主角：Pod 生命周期  |  冲突：单机扛不住流量  |  收束：声明式管理万台集群

阶段 1：容器与 k8s 基础（"单机时代的终结"——为什么需要容器）
├── 课 1：容器基础
│   ├── 知识点：镜像与容器（关键点：镜像分层 / 容器与 VM 的区别 / 镜像仓库）
│   ├── 知识点：容器运行时（关键点：runc / containerd / CRI 接口）
│   └── 知识点：隔离原理（关键点：Namespace / Cgroups / 联合文件系统）
├── 课 2：Pod 基础
│   ├── 知识点：Pod 概念（关键点：最小调度单位 / 共享网络与存储 / 生命周期）
│   ├── 知识点：Pod YAML（关键点：四要素 / 容器字段 / 探针）
│   └── 知识点：多容器共享（关键点：localhost 互通 / 共享卷 / sidecar 模式）
阶段 2：调度与工作负载（"让机器自己干活"——如何声明式管理）
├── 课 3：Deployment
│   ├── 知识点：副本管理（关键点：ReplicaSet / 副本数控制 / 自愈）
│   ├── 知识点：滚动更新（关键点：maxSurge / maxUnavailable / 更新策略）
│   └── 知识点：回滚（关键点：revision 记录 / rollout undo / 失败回退）
```

> **示例为历史形态（未含环境准备课）**：技术域有实操的课程按「动手环境判定」在阶段 1 首课加入「环境准备」（后续课号顺延）；多角色主题按「多角色判定」在阶段明细之外补「角色视角」字段与子教程规划。

#### Step 1.2 教学效果推演 → course-reviewer 评审（大纲定稿闸门，先推演后评审，顺序不可调换）

大纲生成后**先推演、修订，后评审定稿**——推演查"学完能否覆盖实战"，修订后的稿才送评审；两步都通过，大纲才算定稿。速览模式不做推演（单点概念篇幅不匹配，与不做 Phase 3 / 5 同理）。

##### Step 1.2a 教学效果推演（必做，不可跳过）

站在**教学者角度**推演：假设学习者学完了这套大纲，他能否覆盖目标领域的大部分实际工作场景？理论是否真的理解（而不是只会背术语）？方法借鉴 `scenario-rehearsal`（角色代入 + 场景提取 + 覆盖矩阵 + 问题分级），执行者为 course-reviewer 的 **`rehearsal` 模式**（已创建 → `use_agent(course-reviewer)` 委派 1 个实例；未创建 → 主 agent 内联推演，按本技能 `review-dimensions.md` 的「教学效果推演执行方法」执行）：

1. **场景提取**：按主题与学习目标列领域高频工作场景 **8–12 个**，三类必含——日常任务类（如 k8s 的"部署一个服务并对外暴露"）、故障排查类（如"Pod 起不来怎么查"）、设计决策类（如"要不要上 Helm"）；另配**理论理解问题 3–5 个**（"为什么"层面的机制问题，如"为什么 control plane 挂了已运行容器不会立刻死"），检验是否真懂而非只会背术语。
   > **多角色主题**（Step 1.1 判定启用）：场景按**主线角色**的岗位提取（主线 = 开发 → 三类场景都取自开发视角）；**次角色场景归子教程覆盖**——已规划进子教程的场景标注"子教程覆盖"，不计主线缺口；次角色高频场景**既无主线覆盖、又未规划子教程 → 仍按 🔴 补**（补子教程或补主线，二者必有其一）。
2. **覆盖矩阵**：场景 × 阶段/课 逐格判 ✅ 深覆盖 / ⚠️ 浅覆盖 / ❌ 零覆盖；理论问题逐个标注"学完哪课能答上来"。
3. **问题分级与修订**：🔴 高频场景 ❌ 零覆盖（或理论问题无课可答）→ **必须修订大纲**（增补课 / 知识点 / 关键点）；🟡 ⚠️ 浅覆盖或理论断层 → 修订或在对应知识点的关键点中加深度标注；🟢 记录备查。修订后对**修订项做一次增量重推**，确认缺口闭合。
4. **结论记录**：推演结论 + 覆盖矩阵摘要记入 `00-学习档案.md` 评审记录（方式标「教学效果推演」），并作为 Step 1.2b 评审的对照输入。

> **诚实闸门**：推演是推理不是教学实测，结论一律表述为"推演通过（未实测）"；场景清单基于领域公认实践，不确定某场景是否高频时标注置信度，不硬凑场景。
> **与评审的分工**：推演只回答"实战覆盖与理论理解够不够"，不评阶段划分 / 顺序 / 故事主线——那些归 Step 1.2b 的 pedagogy 评审。

##### Step 1.2b course-reviewer 评审大纲

- 按「course-reviewer 评审执行规则」对多阶段大纲做评审（已创建 → `use_agent(course-reviewer)`，模式 = `pedagogy`；未创建 → 直接评审），评审节点为"大纲评审"，**评审输入须附 Step 1.2a 的覆盖矩阵与问题清单**——评审核对：🔴 缺口是否全部闭合、修订是否引入新的前置依赖缺口或顺序问题。
- 评审重点：阶段划分合理性、知识点顺序递进、前置依赖无缺口、覆盖面完整、**故事主线设计合理**（主角是否清晰、冲突是否真实、转折是否递进）。
- **P0 意见必须清零**（修订后复审），P1 / P2 酌情采纳；评审结论记入 `00-学习档案.md` 的"评审记录"表。

#### Step 1.3 评审通过后落盘（大纲一次性生成，不再单独占一轮用户确认）

- 评审通过后，大纲**一次性落盘**，不再单独占一轮用户确认。
- **故事主线轻量确认**：大纲在对话中展示时，故事主线部分加一句提示："📖 故事主线方向（主角：X / 冲突：Y / 收束：Z）是否合适？不合适可调整，其余结构已落盘。"这是轻量提醒而非阻塞流程——用户不回应则按已落盘主线继续；用户提出调整则更新主线及相关阶段概览后继续。故事主线贯穿全程，选错返工成本高，故单独提醒。
- 落盘内容：
  - `01-学习路径总览.md`：学习目标 + 全阶段总览（各阶段目标 + 重点一览 + 故事主线 + 阶段依赖图 SVG）。
  - 各阶段 `stages/{N}-{阶段名}/overview.md`：阶段概览（目标 / 学习重点 / 必须掌握的知识点 + 本阶段在故事主线中的章节定位 + 本阶段路径图 SVG）。
  - `00-学习档案.md`：初始化**知识点级进度表**（多角色主题另记「角色视角」与子教程规划）。
  - 多角色主题（Step 1.1 判定启用）：落盘 `子教程/{专项名}/overview.md`（定位 / 前置 / 课清单 / 与主线的引用关系，模板见 reference.md「子教程」）——**课文件不在 Phase 1 生成**，进入子教程学习时按 Phase 2 同口径分批生成。
  - `00-评审清单.md`：初始化评审清单，**一次性占位全部评审节点**——**大纲教学效果推演 + 大纲评审** + 每课/批次内容评审（均为 `- [ ]`；前两条在 Step 1.2 已完成，占位后**立即勾选**并各附一行结论——断点续学时若发现未勾选且大纲未定稿，先补推演/评审再继续）。**课程制**另加两条收尾占位：**结课实战项目** + **实战经验 / 排障速查手册 / 场景解法库**；**速览模式不占位这两条**（速览不做 Phase 3 / 5，占位会产生永远无法勾选的死条目，干扰断点续学判定）。速览模式的「速览评审」条目由速览模式生成前自行初始化。占位粒度 = 批次：默认一课一批，占位到课即占位到批；一课需拆多批时，首批生成前将该课条目按批次拆为多条。**每课条目须叠注 learner 全部维度**（维度清单 SSOT 见 `review-dimensions.md` 的「学习者视角维度」）——只写"内容评审"时，维度有没有跑无从判定，断点续学也发现不了漏查。**本条不列举维度名，故新增维度时无需改动**（此前写死 L7 / L8 的写法已两次导致漏同步）。**勾选前须确认课首「📖 文档核对」留痕存在**——它是「官方文档学习闸门」的可检查物，缺失则本课评测不完整。**子教程的 `overview.md` 随大纲评审一并评审（不单独占位）**；子教程**课文件**的评审条目在其生成前自行占位（同速览模式）——预占位会产生永远无法勾选的死条目（学习者可能一直不学子教程）。
    > **两个收尾节点必须在课程制 Phase 1 就占位**：它们在流程末尾，若此刻不占位，AI 在长流程后极易漏掉（历史教训：评审写成流程文字 → 漏评审）。占位了 = 断点续学时可被发现并补做。
  - `02-课程目录.md`：初始化书本式目录（按阶段列出全部计划课 + 子教程〔多角色主题〕+ 速览 / 手册条目，未编写 = 纯文本，模板见 [reference.md](reference.md)）。
  - `应用实战/INDEX.md`：初始化实战索引骨架（按阶段列出**计划配实战的课**，未编写 = 纯文本，与 `02-课程目录.md` 同口径；**不配实战的课不列入**——按需配套是常态，不是缺漏）——**实战文件本体随课生成时，按 reference.md「应用实战文件与索引」模板逐槽位写**（形态 `应用实战/{NN}-{课名}.md` + `assets/`，**不另起形态**；两张分步设计图槽位不得删），写完过「落盘前自检」7 条（见 SKILL.md「应用实战」）。
  - `源码解析/INDEX.md`（配解析的课——限库 / SDK / 框架类主题）：初始化解析索引骨架（按阶段列出**计划配解析的课**，未编写 = 纯文本，与 `02-课程目录.md` 同口径；**不配解析的课不列入**）——解析文件本体随课生成，模板见 reference.md「源码解析文件与索引」。
  - `.gitignore`（产物仓库根）：不存在则**初始化基线**（模板见 [reference.md](reference.md)），只建系统/编辑器组与通用过程残留组；已存在则不动。后续增量维护（忽略 + 清理）见 [ops.md](ops.md)「产物仓库卫生」。
  - 各课骨架 `stages/{N}-{阶段名}/lessons/lesson-NN-{课名}.md`：只写课名 + **知识点清单（含每个知识点的关键点）** + 本课目标 + **本课在故事主线中的情节定位**，**正文留待 Phase 2 分批填充**（首批生成时在骨架上展开正文）。课文件名中的 `{课名}` 用**中文课名**（与阶段目录名一致，不用英文 slug）。**环境准备课**（阶段 1 首课）骨架用轻量结构：列五要素清单（最小集 / 主路径与备选 / 验证 / 常见坑 / 可跳过声明）即可，见 reference.md「环境准备课模板」。

#### Step 1.4 外部官方文档收集（大纲定稿后 · 课程制执行，速览默认不做）

> **为什么放在这里**：大纲定了才知道要讲哪些知识点、会用到哪些官方站。**先收齐再开讲**——后面几十批的「📚 官方文档」链接与事实核查，才有唯一一个取 URL 的入口。边讲边找链接，是"编造链接"和"同一个站反复现场搜"的根源。
>
> **"执行"不等于"一定建"**：本步骤是**进入判定**——按下面第 2 条走 `web-index` 的规模判断，判定不建就一句话说明后回到直接 fetch，不产出索引。

1. **列出文档站清单**：按大纲涉及的知识点，定出本主题要参考的**官方文档站**（1–3 个，宁少勿多）。例：k8s → `kubernetes.io/docs`；Python 主题 → `docs.python.org`；某框架 → 该框架官方 docs。
   - **非官方来源不建**：博客、教程站、自媒体不进索引（它们本来也不是可引用的权威来源）。
   - **非技术域通常不建**：理财 / 投资类的权威来源（监管机构 / 官方指南）多为小站点或 PDF 公告，按「事实核查闸门」临时核查即可；**但若该来源本身是多页政策/数据文档站，同样可建**。
2. **按 `web-index` 做准入与执行**（**判定规则不在此复制**，见 `use_skill("web-index")` 的「被其它 skill 集成 · 规模判断」）：
   - 站点已在**本教程索引** `{topic-slug}/web-index/INDEX.md` 在册 → **消费模式**，查表即可，**不重建**
   - 未收录 → 教学天然满足"≥2 次查阅"（多批次 + 跨会话续学）→ **建造模式**，按其阶段 0–5 执行（**落点按下方第 4 条覆盖其默认落点**）
   - **只为了核一个版本号而查一次的站 → 不建**，直接 fetch
3. **scope 按大纲覆盖面收窄**：不要整站建（文档站动辄上千页，产物大到没人读，教学也用不上）。例：k8s 基础课 → `--scope /docs/concepts`；只讲某个命令 → 收窄到该命令所在分支。**多角色主题**：scope 须一并覆盖**子教程**用到的分区（如主线取 Develop、子教程还要 Operate → 两区都纳入，或按「大纲是活文档」的索引拓展规则后续补建）。
4. **落点（覆盖 web-index 默认）**：索引**一律落在本教程目录内** `{topic-slug}/web-index/{site}/`（**不用** `web-index` 默认的仓库根 `.web-index/`）。结构与 `web-index` 一致（`INDEX.md` + `{site}/index.md` + `topics/`），只是根从仓库根换到教程目录：

   ```
   {topic-slug}/
   └── web-index/
       ├── INDEX.md            # 本教程的站点登记表（一行一站）
       └── {site}/
           ├── index.md        # 元信息 + 分区索引 + 高频直达
           └── topics/*.md
   ```

   **为什么不用默认的 `.web-index/`**：① **教程自包含**——索引与课时同目录，教程整体拷贝/分享/搬迁时索引跟着走，不会留在别的仓库变成死索引；② **多教程互不干扰**——两个主题参考同一个官方站但 scope 不同（k8s 基础课要 `/docs/concepts`、进阶课要 `/docs/tasks`）时，各自的 `web-index/` 独立维护，不会共用一个 slug 互相覆盖；③ **可见性**——不再是隐藏目录，落在教程目录里，断点续学时读 `00-学习档案.md`「外部文档索引」小节即可发现，不依赖仓库根的隐藏登记表。
   > **历史索引迁移**：若此前已在仓库根 `.web-index/` 建过同站索引，本轮**不重建**，把目录移入 `{topic-slug}/web-index/` 并更新档案中的路径即可（内容照旧，只换落点）。
   > **中间产物须登记**：`web-index` 的抓取脚本会把候选链接表写到 `temp/web-index-{slug}-map.md`。**创建即登记进本轮临时文件清单**（见 [ops.md](ops.md)「产物仓库卫生 · 临时文件清理」）——不登记的失败方向是漏清理，别让它在 `temp/` 里留成垃圾。
5. **登记进 `00-学习档案.md`**：新增「外部文档索引」小节（站点 / slug / 范围 / 生成日期 / **索引文件路径**，路径一律写 `web-index/{site}/index.md` 这样的教程内相对路径）。**断点续学时先读这一节**——否则新会话的 AI 不知道有索引，又回到现场找链接。

**后续用法（Phase 2 起全程生效）**：

- 写知识点后的「📚 官方文档」链接：**先查索引的「我要…」列拿 URL**，需要细节再 `web_fetch`；索引里没有才现场查，确认是常用页后**回补一行进索引**
- 事实核查的联网核查同样先过索引定位页面，省掉"在站内搜该看哪页"的探索
- **索引只解决"去哪一页"，不解决"内容是否过时"**——版本 / API / 行情的时效性仍由「事实核查闸门」把关（标注 `核查于 YYYY-MM`）
- **索引是快照**：跨长周期续学时若发现链接大面积失效（fetch 大量 404 / 站已改版），回到本步骤**整站重跑重建**，并更新档案「外部文档索引」的生成日期

### 大纲是活文档（动态调整）

大纲**不是一次性产物**，随学习推进持续调整，每次调整记录到 `00-学习档案.md` 的"大纲调整记录"表：

| 触发时机 | 调整动作 |
|----------|----------|
| 学完一批，发现节奏偏快 / 偏慢 | 增删知识点、拆分 / 合并课 |
| 用户目标变更（如从"理解概念"改"动手实操"） | 更新 `01-学习路径总览.md` 学习目标 + 调整各课实操比重、增删实操课 |
| 重点变更（用户想深挖某块） | 重排课程顺序、为某知识点加内容 |
| 出现新的前置知识缺口 | 在依赖图中补节点、插入前置课 |
| 新增了原文档站未覆盖的分支，或新增一个文档站 | 回到 **Step 1.4** 拓宽 scope 重建 / 补建索引，并更新档案「外部文档索引」 |

**调整规则**：每次调整后更新 `01-学习路径总览.md` / 阶段 `overview.md` → 在 `00-学习档案.md` 追加一行调整记录（日期 / 调整内容 / 原因）→ **阶段大纲的结构性调整（增删阶段/课/知识点）须重新过 course-reviewer 大纲评审，并同步增删 `00-评审清单.md` 对应占位条目**（**子教程的课清单变更视同大纲变动**，同此处理，含其 `overview.md` 的同步更新）→ 对话中告知用户"大纲已调整：X"。
> **入口要素随调整重绘**：某课范围变化（增删知识点 / 换重点）时，该课的**课级入口要素**（含「一眼全局图」「本课地图」，要素清单见「课级入口要素」）**须同步复核或重绘**——图和地图都是按旧范围画的，范围一变即失真（旧图作废、不并存）。**批次追加同理**：一课拆多批时，后续批次若新增知识点改变了本课范围，须回头更新入口要素。
> **旧课不强制回溯**：本要求自本版起对**新生成**的课生效，已落盘的旧课**不批量回填**（避免续学时大段返工）；仅在用户明确要求补齐时处理，并在对话中说明"仅补齐指定课"。
> **调整后要不要重推演**：轻量评审（仅查前置缺口与完整性）**不重跑**教学效果推演；但**增删了整个阶段**、或删掉了 Step 1.2a 覆盖矩阵中某场景唯一依赖的课时 → 须对**受影响的场景做一次增量重推演**（只推受影响项，不推全量），确认覆盖缺口没有重新打开。
