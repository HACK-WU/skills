## 产物仓库卫生（.gitignore 维护 + 临时文件清理 · SSOT）

教学产物落在 git 仓库里，而**写课过程本身就是持续产渣的过程**——尤其 Phase 3 实战项目的 `实现/` 一旦真跑起来，立刻生成依赖目录、构建产物、日志与本地配置。缺了忽略规则，`git status` 会被运行残留淹没，`git add .` 会把 `node_modules/` 这类几万文件的目录提进仓库。

**核心动作 = 两件事，每完成一个课程单元后各做一次**：

1. **忽略**：用 `git status --porcelain -- "{topic-slug}/"` 列出该主题目录下未提交的文件，逐条判为「✅ 要提交 / 🚫 要忽略 / ⚠️ 存疑」，把 🚫 项补进 `.gitignore`——**可逆**（写错了删掉那行即可），故可以放手做。具体按下方**「检查方法（五步）」**执行
2. **清理**：删掉本轮**亲手创建且已登记在案的临时文件**——**不可逆**（未提交的文件没有 git 历史可恢复），故范围极窄，见「临时文件清理」

> 下文各钩子所称的「**卫生检查**」，即指这两件事一起做。
>
> **与「运行环境约定」的分工**：本节管"跑完之后留下的东西怎么归类"，「运行环境约定」管"跑的时候用什么命令"。**环境选对了（如 `uv run --with` 而非 `pip install`、用 `pnpm dlx` 而非 `npx`），产渣就少**——两者是同一动作的两面，遇到运行相关的判断时交叉查阅。

### 检查时机（分级，不一刀切）

| 时机 | 强度 | 说明 |
|------|------|------|
| **Phase 1.3 落盘** | **初始化** | 产物仓库根无 `.gitignore` → 按 [reference.md](reference.md) 模板创建基线（只建系统/编辑器组 + 通用过程残留组） |
| **Phase 2 整课完成**（写入「🧭 课程导航」时） | **必查** | 用户要求的"每个小课程写完一次"。课级检查，不随批次重复——一批一查太碎，且拆批中间态不代表最终产物形态 |
| **Phase 3 实战项目完成** | **必查（重点）** | 产渣最大来源：技术域 `实现/` 被运行后产生依赖目录/构建产物/日志；非技术域几乎不产渣，可只做快速确认 |
| **Phase 4 手册汇总** | 顺查 | 汇总拼接过程可能产生中间草稿，顺带清理 |
| **Phase 5 落盘收尾** | 顺查 | 纯 Markdown 产物，通常无新增，确认即可 |
| 速览模式写完 | 顺查 | 单篇 Markdown + 少量 SVG，通常无新增 |
| 断点续学进入时 | 补漏 | 产物仓库根无 `.gitignore` 但已有产物（上一轮漏建/被删）→ 补建基线，不阻塞续学 |

> **优先级低于评审**：本检查是落盘后的附加动作，**不得抢在评审之前**——本批评审 P0 未清零时，先完成评审与清单勾选，再回头做卫生检查（忽略 + 清理）。长流程中 AI 注意力有限，评审漏了会产出低质量课程，`.gitignore` 漏了或临时文件没清，事后补都来得及。

### 检查方法（五步）

> **赶时间时的最小动作**：第 1 步列清单 → 第 3 步出判定表 → 第 4 步追加规则。第 2 步（状态分流）只在出现了**非 `??` 的条目**（已跟踪 / 已暂存）时才需要，第 5 步（校验）在只加了少量低风险规则（如 `.DS_Store`、`*.log`）时可合并进第 4 步顺手做。**但判定表不能省**——它是用户复核的唯一抓手。

#### 第 1 步：列出未提交文件（范围固定为 `{topic-slug}/`）

**范围不按单元类型细分，一律用 `{topic-slug}/`**（该主题的教学产物根目录）：

- 整课的阶段 `assets/`、根级临时脚本、实战项目的 `projects/{项目名}/`、速览与收尾产物——**全都在它下面**，收窄到某个子目录反而会漏掉本轮在别处落的渣
- 它同时是"教学目录"与"安全边界"：往外扩（全仓库）会混入用户自己的源码，往里收（子目录）会漏检，**`{topic-slug}/` 是唯一合适的粒度**

> **范围是判定的上界，不是"列出的都要处理"**：`{topic-slug}/` 下可能混有**非本轮产生的**未跟踪文件（用户此前有意保留的草稿、还没决定是否入库的材料）。判定与处置**只针对本轮新增**；对来源不明或明显早于本轮的文件 → 保持原样，判 ⚠️ 存疑并在对话中提示，**不擅自加规则**。

> **初始化场景例外（仅限 Phase 1.3 / 断点续学补漏 这两个时机）**：此时 `{topic-slug}/` 通常整体是 `??` 且内部只有刚写的骨架文件，确认没有意外产物即可，**不必逐条下钻**——全是教学产物，没有可忽略项。
>
> **判据是时机，不是"整体 `??`"这个状态**：提交时机归用户，若用户从未提交过该主题目录，**Phase 2 / Phase 3 时它同样整体是 `??`**，但里面已有课时与实战项目——**必须按下钻规则正常展开判定，不得套用本例外**，否则会漏掉 `node_modules/` 这类渣。

```bash
# 查该主题目录下未提交的文件（未跟踪 ?? + 已修改 M，目录聚合显示）
git status --porcelain -- "{topic-slug}/"

# 产物仓库不在当前目录时
git -C {产物仓库根} status --porcelain -- "{topic-slug}/"
```

- **（仅指首次列出、尚未追加规则时）输出为空 = 该目录下没有未提交项**：直接结束本次卫生检查的忽略部分（跳过第 2–5 步），**不必在对话中提及**；此时只看临时文件清单是否要清理。**注意**：第 5 步校验时重跑本命令若输出为空，含义完全相反——那是误伤信号，见第 5 步。输出只有 `?? {topic-slug}/` 一行 = 目录整体未跟踪（用户可能从未提交过该主题），**按下方的下钻规则正常展开判定**，不适用初始化例外（除非当前正是 Phase 1.3 / 断点续学补漏）
- **必须用上面的 pathspec 限定，不跑全仓库裸 `git status`**：产物仓库与用户工作项目同体时，全仓库结果会混入大量教学无关文件，**据此批量加规则必然误伤用户的源码**（错误忽略用户源码比漏忽略危害大得多）
- **用默认的目录聚合模式，禁止加 `-uall`**：首次检查时 `node_modules/` 之类可能尚未被忽略，逐文件展开会输出上万行淹没上下文（聚合后只是 `?? node_modules/` 一行）
- **聚合目录看不出内容时，逐层下钻一层，而不是一次性展开到底**：`git status --porcelain -- "{待确认目录}/"`，重复到看清结构为止。仍判断不了可 `du -sh {目录}` 辅助识别（依赖目录通常几十 MB 以上）

#### 第 2 步：按 git 状态分流（关键）

| porcelain 状态码 | 含义 | 处理 |
|------|------|------|
| `??` | 未跟踪——新产生、尚未入库 | `.gitignore` **对它有效** → 进入第 3 步判定 |
| 第二位是 `M`（如 `_M`） | 已跟踪 + 工作区已修改 | `.gitignore` **对它无效** → **仍须先过第 3 步判定**，判为 🚫 才另需 `git rm --cached`（见下方） |
| 第一位是 `A` / `M`（如 `A_`） | 已暂存——会被下一次 commit 带走 | 同上，且更紧急 |

> 状态码是两字符：**第一位 = 暂存区状态，第二位 = 工作区状态**（上表用 `_` 代指示意空格位）。`??` 即两位都无记录 = 尚未入库。
>
> **本步只决定"`.gitignore` 管不管得了它"，不决定它的归宿**——已跟踪项**不是自动就要移出版本库**：一个被修改的 `.md`（状态码第二位为 `M`）是"教学产物被修改了"，属 ✅ 要提交，绝不能 `git rm --cached`。**只有第 3 步判为 🚫 的已跟踪项才需要它**，且须先征询用户。

> **`.gitignore` 只对未跟踪文件生效**——这是 git 的基本语义，也是本步骤存在的理由：文件一旦被 `git add` 过，再往 `.gitignore` 里加规则**完全不起作用**，它照样出现在 `git status` 与后续 `git commit` 里。
>
> 因此**第 3 步判为 🚫 的**已跟踪 / 已暂存残留（典型：`git add .` 已把 `node_modules/` 提进去；初始化时误纳了目录），正确处理是两步：
> 1. 先补 `.gitignore` 规则（防止再生）
> 2. 再从索引移除：`git rm --cached -r {路径}`（**保留磁盘文件**）
>
> **第 2 步会改变仓库索引状态，须先向用户说明并征询同意，不擅自执行**——与「不代为提交」是同一条纪律。

#### 第 3 步：三分类判定（逐条判，输出判定表）

对第 1 步列出的每一条，**判定归入下列三类之一**，并在对话中输出判定表（与「删除前列出待删清单」同构——让判断可追溯、可被用户推翻）：

| 分类 | 判定标准 | 处置 |
|------|----------|------|
| ✅ **要提交** | 教学产物：文件丢了课程不完整 | 不动，留给 `git add` |
| 🚫 **要忽略** | 过程残留：文件丢了课程仍完整 | 追加进 `.gitignore`；**已跟踪项加规则无效**，另需 `git rm --cached`（先征询用户，见第 2 步） |
| ⚠️ **存疑** | 判不准属于哪一类 | **保持未跟踪 + 在对话中提示用户**，不加规则 |

判定表形式（路径 / 状态 / 分类 / 理由，一行一条）：

| 文件 / 目录 | 状态 | 分类 | 理由 |
|---|---|---|---|
| `lessons/lesson-03-{课名}.md` | `??` | ✅ 要提交 | 课程正文 |
| `assets/03-architecture.svg` | `??` | ✅ 要提交 | 教学配图（SVG 名用英文 kebab-case，见「文件命名规范」） |
| `node_modules/` | `??` | 🚫 要忽略 | pnpm 依赖目录，可再生 |
| `.DS_Store` | `??` | 🚫 要忽略 | 系统残留 |
| `scratch/` | `??` | ⚠️ 存疑 | 不确定是过程草稿还是示例目录，请确认 |

**归类参照**：

- 教学产物：`*.md`、`assets/*.svg`、`web-index/`（Step 1.4 的文档索引，教程自包含的一部分）、`实现/` 下的源码、`知识点对齐记录/`、`.gitignore` 自身
- 过程残留：依赖目录（`node_modules/`、`venv/`、`.venv/`、`__pycache__/`、`.mypy_cache/`、`vendor/`）、构建产物（`dist/`、`build/`、`target/`、`*.egg-info/`）、运行输出（`*.log`、`logs/`、`tmp/`、`*.tmp`、`.DS_Store`、`Thumbs.db`、`*.swp`）、本地配置与密钥（`.env`、`.env.local`、`.env.*.local`）

> **判定口诀**：*这个文件丢了，课程还完整吗？* 不完整 → ✅ 要提交；完整 → 🚫 要忽略；判不出来 → ⚠️ 存疑。**判成存疑不算失败**，拿不准就存疑，比静默吞掉教学产物安全。
>
> **但存疑不是偷懒出口**：明显能判的（依赖目录、构建产物、日志、系统残留、`*.md`、`assets/*.svg`）**必须直接归类**，把整批文件都推给"存疑"等于把判断成本转嫁给用户，与"不确定时不加"的初衷相反。
>
> **判定 ≠ 提交**：判定表的"✅ 要提交"只是分类结论，**不执行 `git add` / `git commit`**——提交时机归用户。

#### 第 4 步：只追加本轮实际出现的

命中哪类加哪条，**不预先灌满模板**——没写 Python 就不加 `__pycache__/`，避免 `.gitignore` 变成没人看得懂的噪音。追加时**加进对应分组**，宽泛目录名要锚定路径（规则见 [reference.md](reference.md)「追加规则」）。

> **加规则沿用第 1 步的同一范围**：检查范围是 `{topic-slug}/`，追加规则也**优先写成 `{topic-slug}/` 开头**（如 `{topic-slug}/projects/{项目名}/dist/`），而不是 `/dist/`（锚定仓库根）或 `dist/`（匹配任意层级）。**产物仓库与用户工作项目同体时尤其重要**——后两者会波及用户自己的项目。**这是「同体时更保守」的操作化写法**。

#### 第 5 步：校验未误伤

追加后**重跑第 1 步的命令**确认：教学产物仍以 `??` 可见，未跟踪的 🚫 项已消失。产物若已提交过则不会出现在 `git status` 里，**此时用 `git check-ignore -v {关键产物路径}` 判定——应无命中**；一旦发现教学产物被吞，**立即删掉刚加的那条规则并重验**。

> **已跟踪的 🚫 项不会消失，这是预期的，不算校验失败**——它在 `git rm --cached` 之前仍会列在 status 里（见第 2 步）。校验真正要抓的是"教学产物被吞"，不是"🚫 项全清空"。
>
> **重跑后整体输出为空 = 红色警报**：追加规则前目录里明明有未提交的教学产物，加完规则反而一条不剩——**说明规则把产物一起吞了**。立即回退刚加的全部规则并重验（这与第 1 步"首次列出为空则跳过"是两种语境，别混淆）。

### 禁止忽略清单（负向操作兜底）

以下**绝不能**进 `.gitignore`——它们是要提交的教学产物：

| 项 | 为什么不能忽略 |
|----|---------------|
| `*.md` | 全部课程正文、档案、手册、清单 |
| `assets/` 与 `**/*.svg` | SVG 图是教学产物（阶段依赖图 / 路径图 / 概念图），丢了图全废 |
| `web-index/` | Step 1.4 建的官方文档索引，是教程自包含的一部分；丢了后续每课的 📚 链接又要现编。**注意与 `web-index` skill 自带的"默认不入库、可加 .gitignore"建议冲突——本技能覆盖它，索引要入库** |
| `实现/` `推演/` 目录下的源码 | 实战项目本体，只有其内部的依赖目录/构建产物该被忽略 |
| `stages/` `projects/` `知识点对齐记录/` `子教程/` `应用实战/` `源码解析/` `场景解法库/` | 产物主体目录 |

> **判定口诀**：*这个文件丢了，课程还完整吗？* 不完整 → 是教学产物，不能忽略；完整 → 是过程残留，可以忽略。
>
> **最易踩的坑**：为图省事写 `dist/`、`build/` 这类宽泛目录名时，若实战项目的示例目录恰好同名会被连带吞掉。写成 `/dist/`、`/build/`（锚定仓库根）或更精确的 `{项目路径}/dist/`，避免误伤。

### 临时文件清理（窄范围 · 只清自己创建的）

忽略是让文件"在 git 里隐身"，清理是从磁盘上删掉。**删除不可逆**，故清理范围必须比忽略窄得多——**只删本轮亲手创建、且明确登记在案的临时文件**。

**清理时机**：与 `.gitignore` 检查同一时机（见上方「检查时机」表，不在此重复枚举以免双源漂移）。**Phase 1.3 落盘除外**——此时尚无临时文件可清。

#### 地基：先登记，后清理

AI 创建任何临时文件时，**立即把路径记入本轮临时文件清单**（在对话中维护，不落盘）。清理时**只删清单内的路径**——没有登记的，一律不删。

> 安全性不来自"删除时再判断一次该不该删"（长上下文下这种判断会失真），而来自"创建时就登记"。这是整套机制的地基。
>
> **漏登记的失败方向是安全的**：忘了登记 → 清单为空 → 跳过清理 → 临时文件留在磁盘上（顶多下次被 `.gitignore` 收编）。宁可留下垃圾，也**绝不为了"完成清理动作"而现场凑一份清单**——那等于把安全边界拆了。
>
> **清单不落盘是刻意的**：**断点续学进入新会话时，上一轮清单已随会话消失**，本轮清单从空开始——不清上一轮的临时文件（它们要么已被 `.gitignore` 收编，要么由用户自行处理）。同样，**上下文被压缩 / 截断后不得凭"看起来像临时文件"重建清单**，清单为空就是为空，跳过。

**什么是临时文件**：生成过程中的中间草稿、格式转换的中间态、临时验证脚本、跑通即弃的探针文件。

#### 三重校验（缺一不删）

| # | 校验 | 说明 |
|---|------|------|
| 1 | **是本轮会话亲手创建的** | 在临时文件清单里有登记。用户创建的、既有目录下冒出来的、来源不明的 → **一律不删** |
| 2 | **不是教学产物** | `*.md`、`assets/*.svg`、`实现/` / `推演/` 下的源码**即使由 AI 亲手创建，也是最终产物**，绝不在清理范围（见「禁止忽略清单」） |
| 3 | **不是可再生的运行时产物** | `node_modules/`、`__pycache__/`、`venv/`、`dist/` 等是"可再生依赖"而非垃圾——删了 Phase 3 实战项目直接跑不起来，下次还得重装重建。它们归 `.gitignore` 管，**不归清理管** |

> **AI 自己创建 ≠ 可删**：本轮最大宗的创建物（课时 md、SVG、项目代码）恰恰是最不能删的。判断标准是"这个文件是**过程态**还是**终态**"，不是"是不是我建的"。

#### 执行流程

1. 取出本轮临时文件清单（**为空则跳过，不必在对话中提及**）
2. 逐条过三重校验，筛出待删项
3. **删除前在对话中列出待删清单**（一行摘要即可，让删除行为可追溯）
4. 执行删除 → 说明"已清理 N 个本轮临时文件"
5. 删除失败（文件占用 / 权限不足）→ 跳过并在对话中提示，**不重试、不阻塞教学流程**

#### 目录删除规则

优先**逐文件删除**；确需删临时目录时，必须**确认该目录本轮自建、且内部文件全部在清单内**才删。

- **禁止 `rm -rf` 一个未逐项核对过的目录**
- **禁止用 `git clean -fd` 批量删除**——它会连用户自己的未跟踪文件一起删掉，范围完全不可控（**.gitignore 检查里也禁用 `git clean` 做清理，只允许精确路径删除**）

### 行为边界

- **`.gitignore` 只追加，不删规则**：用户已有的忽略规则一律不动，即使看起来冗余。判断不了某条该不该删 → 不删。（删除动作只存在于「临时文件清理」，且只针对文件本身，不针对 `.gitignore` 里的行）
- **只动产物仓库根的 `.gitignore`**：不修改产物仓库之外（如用户主项目）的忽略文件。
- **产物仓库与工作项目同体时更保守**：若教学产物就落在用户正在开发的项目里，只追加「本轮教学明确产生的残留类型」，不碰项目自身的构建产物 / 依赖配置——那是用户已有约定的地盘。
- **非 git 环境跳过忽略检查**：落盘目录不是 git 仓库（用户指定的普通产物目录）时，跳过 **`.gitignore` 相关**检查，不提示、不阻塞；**临时文件清理与 git 无关，照常执行**。
- **不代为提交**：只维护 `.gitignore`，不执行 `git add` / `git commit`——提交时机归用户。第 3 步判定表的"✅ 要提交"只是**分类结论**，不是执行动作。
- **不擅自移出索引**：需把已跟踪 / 已暂存的残留移出版本库时（`git rm --cached -r {路径}`），**先向用户说明原因与影响并征询同意**——它改变仓库索引状态，与「不代为提交」同级。用户不同意则只加 `.gitignore` 规则并提示其自行处理。
- **不确定时不加**：拿不准某文件是残留还是产物 → 保留为未跟踪并在对话中提一句，由用户决定，胜过静默吞掉。
- **清理只认清单**：清理的唯一依据是「本轮临时文件清单」，不是"现场判断它像不像临时文件"——现场判断在长上下文中会失真，清单不会。清单里没有的，一个都不删。
- **禁用 `git clean -fd`**：它会连用户自己的未跟踪文件一起删，范围不可控。清理只用**精确路径**的删除命令。
- **删除失败不重试**：文件占用 / 权限不足时跳过并在对话中提示，不重试、不阻塞教学流程。

## 运行环境约定（Python / Node · SSOT）

讲解过程中会**真的运行代码**——Phase 3 实战项目的 `实现/` 必须验证可运行（A6 可运行性是 P0 评审项），**4.1 机制验证的命令属"能跑则跑"必跑类**（本地可执行即实跑、跑不了标 `⚠️ 未实测（{原因}）`，见 SKILL.md「4.1 的实证要求」），临时验证脚本也要跑。一跑就遇到环境问题：版本不对、依赖装进全局、产物目录里冒出虚拟环境。

> **例外（应用实战）**：其代码示例**默认不要求运行**（走主 agent 的静态正确性 review，见「应用实战 · 代码要求」）；若要运行验证，仍须按本节三条硬纪律执行。

> **本节管"怎么正确地跑"，「产物仓库卫生」管"跑完留下的渣怎么处理"——同一个动作的两面，必须配套看。**

### 三条硬纪律（优先于任何工具选型）

1. **先探测，后执行**：运行前先确认项目里有什么约定文件（见下方探测表），再决定命令。**不假定**项目装了 uv、不假定用的是 Node 20。
2. **绝不污染全局**：禁止裸 `pip install <pkg>`（无环境前缀会装进系统 Python）；禁止 `npm i -g` / `yarn global add`。依赖装进项目虚拟环境或项目 `node_modules/`。
3. **不擅自安装或切换用户环境**：uv / fnm / pnpm 不存在 → **提示用户并询问，不自行安装**；不 `fnm install` 新版本、不改 `fnm default`、不换 Python 默认版本，除非用户明确要求。**安装工具链是改变用户机器状态，需要授权。**
   > 运行失败时同样不擅自改环境重试（不 sudo、不换源、不改全局配置）。**停下来报告，让用户决定**——"跑不通"本身可能就是需要讲解的内容。

### 优先级链

```
用户显式指定 > 项目既有约定 > 默认推荐
```

> **项目既有约定优先于用户口头指定**：口头指定可能随口一说，项目里的 lockfile 与版本文件是事实。

### 探测表

**Python**：

| 探测到 | 用什么 |
|---|---|
| `uv.lock` | uv → `uv run` / `uv sync` |
| `poetry.lock`，或 `pyproject.toml` 含 `[tool.poetry]` | poetry → `poetry run` |
| `Pipfile` | pipenv → `pipenv run` |
| `requirements.txt` + 已存在 `.venv/` | 用既有 `.venv/` 的解释器，**不重建** |
| `.python-version` | 按声明的版本选解释器 |
| 以上皆无 | **默认 uv** |

**Node**：

| 探测到 | 用什么 |
|---|---|
| `mise.toml` | mise（若已安装），按其声明执行 |
| `package.json` 的 `packageManager` 字段 | 遵循钉死的包管理器与版本 |
| `pnpm-lock.yaml` | pnpm |
| `yarn.lock` | yarn |
| `package-lock.json` | npm |
| `.nvmrc` / `.node-version` | 版本约定 → `fnm exec --using <ver> --` |
| 以上皆无 | **默认 fnm + pnpm** |

> **有 lockfile 就用对应的包管理器**——生成第二个 lockfile 是给项目埋雷，也是给读者示范错误做法。

**其他语言（Go / Rust / Java / …）**：

本表不逐一列举——**遵循同一条原则**：先看项目约定（`go.mod` / `Cargo.toml` / `pom.xml` / `build.gradle`），按其生态的标准命令执行（`go run` / `cargo run` / `mvn` / `gradle`）。

> **无约定或拿不准时，问用户，不自行安装工具链**。硬纪律第 3 条对所有语言一体适用——本节默认推荐只覆盖 Python / Node，是因为这两类在讲解场景里出现频率最高且环境管理分歧最大，不代表其他语言可以"随便跑"。

### 默认推荐的命令形式

**Python（uv）**：

| 场景 | 命令 | 不要这样 |
|---|---|---|
| 跑脚本 | `uv run python xxx.py` | `python xxx.py`（易命中系统 Python） |
| 跑测试 | `uv run pytest tests/` | `pytest` |
| 跑工具 | `uv run ruff check .` | `ruff check .` |
| **一次性依赖** | `uv run --with requests python probe.py` | `pip install requests`（污染项目依赖） |
| 初始化 / 加依赖 | `uv init` / `uv add <pkg>` / `uv sync` | `pip install <pkg>` |

**Node（fnm + pnpm）**：

| 场景 | 命令 | 不要这样 |
|---|---|---|
| 跑脚本（**非交互安全**） | `fnm exec --using <ver> -- node xxx.js` | `nvm use && node xxx.js`（非交互 shell 常静默失效） |
| 装依赖 | `pnpm install` | `npm install`（会生成第二个 lockfile） |
| 加依赖 | `pnpm add <pkg>` | `npm i <pkg>` |
| 跑 package script | `fnm exec --using <ver> -- pnpm run <script>` | `npm run <script>` |
| **一次性工具** | `pnpm dlx <pkg>` | `npx <pkg>`（依赖全局缓存解析，版本不如 lockfile 可复现） |

> **`<ver>` 从哪来**：读 `.nvmrc` / `.node-version` 的内容；都没有则用当前版本（`fnm current`），并在产物里标注所用版本——**读者复现时版本是硬信息**。
>
> **为什么默认 fnm 而不是 nvm**：`fnm exec` 不依赖 shell 函数，在非交互 shell 里可靠生效。AI 通过工具执行的命令通常不在交互 shell 中，`nvm use` 是高频故障点（`nvm: command not found` 或静默不生效）。**但若用户环境本来就是 nvm，遵循用户环境**——本节推荐的是"非交互下可靠"的调用形式，不是强制换工具。
>
> **`fnm exec` 跑不通时的降级链**（依次尝试，都失败就停下来报告，不硬试）：
> 1. `fnm exec --using <ver> -- <命令>`（首选）
> 2. `eval "$(fnm env)" && <命令>`（显式注入环境变量，绕开 shell 集成缺失）
> 3. 确认当前 `node -v` 后直接执行，并在产物顶部标注 `⚠️ 未锁定 Node 版本，实际运行于 v{x}`
>
> **纪律**：环境跑不通就**报告并让用户决定**，不自行 `fnm install`、不换全局默认版本（硬纪律第 3 条）。讲解材料里"用什么版本跑"必须可复现——版本不明比命令写错更误导读者。

### 与「产物仓库卫生」的联动（必读）

- **`uv run` 首次执行会自动创建 `.venv/`**——它本身就是产渣动作。跑完须确认 `.venv/` 已被忽略（基线模板已含，见 [reference.md](reference.md)）。
- `pnpm install` 会创建 `node_modules/`（基线模板已含）。
- **优先用一次性依赖形式**（`uv run --with` / `pnpm dlx`）：不写进项目依赖、不产生新增 lockfile —— **从源头少产渣，也少改动用户的项目**。这是两条规则唯一的交汇点：环境选对了，卫生检查就轻松。
