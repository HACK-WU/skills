# 强关联关系记录

## 概述

**目的**：把"浏览完整代码才能发现的跨文件强耦合"显性化、可检索化——解决 code review 或修改代码时，改了 A 却不知道必须连带改 B 的风险。

**功能**：识别跨模块/跨文件的强关联（契约耦合 + 业务耦合），判定方向与强度（改 A 必改 B vs 改 B 不用改 A），按功能模块分组写入 ki-search，供后续检索感知。

**使用场景**：
- expert-team 创建专家资产完成后，自动调用本 skill 记录该模块与外部的强关联
- 手动指定模块/范围，记录其强关联
- **查询**既有强关联记录（排查/重构/review 前了解模块间耦合），调用 `use_skill("relation-lookup")`（本 skill 只写不查）

## 定位

```
expert-team 落盘模块专家 → strong-relation（本 skill）→ 识别强关联 → 按模块分组写 ki-search
                                                                            ↓
                        后续 code review / 修改时，ki-search 检索即可感知"改A必改B"
```

- **输入**：目标模块（默认 expert-team 刚完成的模块；手动时指定模块路径/范围）+ 可选操作意图
- **输出**：强关联原子记录（写入 ki-search，按功能模块分组）
- **边界**：本 skill **记录"模块间"的强耦合关系**，不深挖单模块内部知识（那是 expert-team 的事）；不画 ER 图/数据流图（那是 data-flow-model 的事）；不分析某次具体 bug 影响（那是 bug-impact-analysis 的事）

## 强关联的定义（识别什么）

强关联 = **改了 A 必须连带改 B（或强烈建议连带改）** 的耦合。用三个维度刻画：

1. **契约耦合**（最主要）：数据源→消费端、接口签名变更牵动所有调用方、消息格式契约、DTO/字段结构共享、数据库表结构共享
2. **业务耦合**：业务规则依赖、调用顺序要求、状态一致性、事务边界
3. **粒度**：够用即可——**类名、文件位置、关键接口名**，不追求接口签名级逐字段细节

**关键区分（方向性/不对称）**：
- `改 A 必改 B`（强方向）：改数据源结构，消费端必须跟着改
- `改 B 不用改 A`（弱/无方向）：改消费端，数据源不用管

## 核心原则

1. **先查后记**：写入前先 ki-search 查该模块是否已有强关联记录，避免重复
2. **GitNexus 辅助 + 源码确认**：用 GitNexus 查调用/依赖关系定位候选，再读关键源码/数据结构确认真实耦合强度，不凭图谱臆断
3. **方向性必标**：每条关联必须标明方向（A→B）与强度（必改/建议改/可选），区分不对称
4. **够用即止**：粒度到类名/文件/关键接口，不深挖签名级细节
5. **按模块分组**：所有原子按功能模块写入，统一父分组「关联关系」+ 按功能模块动态创建的子分组（不复用专题记忆名称）
6. **可分次写入**：关联多时一次写不完，可分多次原子写入同一 group，保持分组一致
7. **ki 不可用降级**：ki 不可用时告知用户并给出关联清单（对话内），不阻塞流程

## 工作流

```
Step 0 环境检测 → Step 1 定位模块 → Step 2 识别关联 → Step 3 判定方向强度 → Step 4 分组写入 ki → Step 5 校验
```

### Step 0：环境检测

1. 确认 ki 可用（`ki_manage_index_list` / `ki_search` 可调用）
2. 确认 GitNexus 是否可用（`context`/`impact`/`query`）——可用则辅助识别，不可用则纯读源码（不阻塞）

### Step 1：定位目标模块

- **自动模式**（expert-team 完成后）：目标 = 刚创建的专家/专题。从 `.module-experts/{专家名}/` 读 `agent.md` 获取模块根路径与职责
- **手动模式**：用户指定模块路径/范围，或从上下文推断

### Step 2：识别强关联（GitNexus + 源码确认）

1. **GitNexus 定位候选**：用 `impact`/`query`/`context` 查目标模块的关键符号（类/方法）的调用方、依赖方，列出候选关联对象
2. **源码确认**：读关键源码（数据结构定义、接口签名、消息格式、消费方处理逻辑），判断是否为强耦合
3. **甄别强弱**：区分
   - **强关联**（记录）：改 A 必须/强烈建议连带改 B——数据结构共享、接口契约、消息格式、业务规则强依赖
   - **弱关联**（不记录）：普通调用、读操作、可选依赖，改了不一定会坏

> 识别重点：**数据源→消费端**、**接口定义→实现/调用方**、**DTO/结构体→所有使用方**、**消息发送→消息消费**、**共享表结构→多写方**。

> **无强关联时**：扫描后未发现任何强关联（纯独立模块），明确告知用户"该模块无跨文件强关联"，正常结束，不写入 ki。

### Step 3：判定方向与强度

每条关联输出三元组：

```
{源} → {目标} | 方向 | 强度 | 原因
```

| 字段 | 取值 | 说明 |
|------|------|------|
| 源/目标 | 关键类名/接口名（可多个） | 参与关联的两端，每端可含多个类/文件 |
| 方向 | `A→B` 或 `B→A` 或 `A↔B` | 谁改影响谁；不对称时明确写出 |
| 强度 | `必改` / `建议改` / `可选` | 改源时，目标必须跟着改的程度 |
| 原因 | 一句话 | 为什么是强关联（共享结构/接口契约/消息格式/业务规则） |

> Step 3 是判定阶段的内部整理格式，用于 AI 归纳后再写入 Step 4 的 `module_info`。`→` 在此为概念表达，写入 ki 时 `relation` 名称用 `-` 连接（不含特殊字符）。

### Step 4：分组写入 ki

按功能模块分组，写入**统一父分组 + 动态子分组**：

1. **确定 scope 与 group**：
   - **scope** = 项目标识（与 expert-team 专题记忆一致）
   - **group 父目录** = **统一固定名「关联关系」**（不复用专题记忆名称，作为所有强关联记录的根分组）
   - **group 子目录** = **按功能模块动态创建**：`关联关系/{功能模块名}`，功能模块名由本次目标模块派生（如 `订单服务`、`支付系统`）；先 `ki_manage_index_list` 查是否已有该子分组，有则复用，无则新建，避免重复节点
2. **每条关联一条原子**：用 `ki_sync_relation` 写入，`group` = `关联关系/{功能模块名}`，`relation` = 关联名（用连字符 `-` 连接两端模块名，如 `{模块A}-{模块B}`，不含 `→` 等特殊字符），`module_info` = 关联描述（**纯文本 + 列表，禁用 yaml 元数据，禁用 `##`/`###` 等 md 标题**——避免污染 ki-search 向量检索），**`tags` 统一为 `relation`**（固定，供查询侧用 `tags="relation"` 过滤）
3. **多次写入**：关联多时，每条（或每小组）单独写一条原子，全部归入同一子分组，保持分组一致
4. **写入内容模板**（`module_info`）：

```markdown
[强关联] {模块A} 与 {模块B}
强度：{必改/建议改}——改{模块A}时{模块B}{必须/建议}连带改；改{模块B}，{模块A}不用管
原因：{数据结构/接口契约/消息格式/业务规则}共享，一句话说明

源端（{模块A}）：
- {类名/接口名} @ {文件路径}
- {类名/接口名} @ {文件路径}
- ...

目标端（{模块B}）：
- {类名/接口名} @ {文件路径}
- {类名/接口名} @ {文件路径}
- ...
```

> 一个功能模块通常涉及多个文件和类，源端/目标端用列表列出所有相关的类与文件位置，不限于单个。
>
> **格式硬约束**：`module_info` 写入 ki-search 时**不得包含 yaml 元数据**（`---` frontmatter）、**不得使用 `##`/`###` 等 md 标题**、不得含 `|` 表格分隔符等 markdown 结构语法；统一用**纯文本描述 + `-` 列表**（见模板），保证 ki-search 向量化时语义纯净、检索准确。

### Step 5：校验

写入后，用 `ki_query_group`（group = `关联关系/{功能模块名}`）确认关联原子已归入正确子分组，抽查 1-2 条确认已可检索。

> 校验是**写入侧**的自我验证（确认数据落盘），与对外**查询**（`use_skill("relation-lookup")`）不同；写入校验直接查 ki 结果，不需要走 relation-lookup。

校验不通过 → 回到 Step 4 修正；ki 校验异常时降级为对话内输出清单。

## 查询强关联（调用 relation-lookup）

强关联的**查询**由独立的 `relation-lookup` skill 提供（只查不写，SSOT）。本 skill 需要查询存量记录时（如 Step 5 校验、Step 2 先查后记），调用 `use_skill("relation-lookup")`，ki 查询参数细节以 relation-lookup 为准，本 skill 不重复。
