# 设计文档模式测试策略

设计文档模式以 `DESIGN.md` 为测试来源，验证设计点在实现层面是否可测、接口契约是否一致、数据流是否完整。与需求文档模式（从验收标准关键词选策略）不同，本模式的测试来源是设计文档本身的结构化内容。

## 测试来源提取

从 DESIGN.md 按章节提取测试对象：

| 来源章节 | 提取内容 | 生成测试类型 |
|----------|----------|------------|
| 方案(TO-BE) / 关键设计点 | 设计决策、约束、选型 | 设计点可达性测试 |
| 接口设计 | 接口签名、入参出参、状态码 | 接口契约测试 |
| 数据模型 | 实体、字段、约束、关系 | 数据完整性测试 |
| 时序图 | 跨组件交互链路 | 交互链路测试 |
| 非功能需求 | 性能/安全/可用性指标 | 非功能可达性测试 |

> 若 DESIGN.md 同时引用了 requirement.md 的 REQ，应建立「设计点 → REQ」追溯，避免测了设计却漏了需求。

## 验证维度

| 维度 | 验证问题 | 严重度 |
|------|---------|:------:|
| **设计点可达性** | 每个关键设计点是否有可执行测试？是否存在"设计了但无法验证"的点？ | 🔴 |
| **接口契约一致性** | 实际响应是否符合设计的 schema/状态码？入参出参是否与设计一致？ | 🔴 |
| **数据流完整性** | 数据在设计的链路中是否按设计流转？写入/流转/消费是否闭环？ | 🔴 |
| **跨组件交互** | 时序图中每条交互链路是否有测试覆盖？异常中断是否有处理？ | 🟡 |
| **非功能可达性** | 设计中的性能/安全要求是否有可执行的验证手段？还是仅停留在描述？ | 🟡 |
| **设计-需求追溯** | 每个设计点是否能追溯到 requirement.md 的 REQ？有无"设计无需求来源"的孤儿点？ | 🟡 |

## 用例生成规则

### 设计点用例

每个关键设计点生成 2 类用例：

| 路径 | 说明 | 示例 |
|------|------|------|
| 正向可达 | 按设计执行，验证设计点成立 | 唯一约束设计 → 写入不重复值 → 成功 |
| 反向破坏 | 故意违反设计约束，验证设计被正确执行 | 唯一约束设计 → 写入重复值 → 被约束拦截 |

### 接口契约用例

每个接口生成 3 类用例：

| 路径 | 说明 |
|------|------|
| 契约符合 | 合法入参 → 响应 schema/状态码与设计一致 |
| 边界入参 | 极值/空值/超长/特殊字符 → 验证设计的校验逻辑 |
| 错误码触发 | 触发设计定义的每个错误码场景 → 验证返回码与设计一致 |

### 数据流用例

每条数据链路生成 3 类用例：

| 路径 | 说明 |
|------|------|
| 写入验证 | 数据按设计写入正确存储位置 |
| 流转验证 | 数据在组件间按设计传递，字段无丢失/篡改 |
| 异常恢复 | 链路中断后，数据是否回滚/一致 |

### 时序交互用例

每条时序链路生成 2 类用例：

| 路径 | 说明 |
|------|------|
| 正常时序 | 按设计时序走完整链路 |
| 异常中断 | 链路中某步失败/超时，验证设计的降级/重试/回滚 |

## 与 7 策略的关系

设计文档模式**复用** `references/test-strategies.md` 的 7 策略，但选择依据从"验收标准关键词"改为"设计特征"：

| 设计特征 | 启用策略 |
|----------|----------|
| 接口设计章节 | 功能型 + 否定型（契约 + 越权） |
| 非功能-性能要求 | 性能型 |
| 非功能-安全要求 | 安全型 |
| 数据模型/数据流 | 数据型 |
| 交互体验设计 | 体验型 |

## 典型缺口

- 设计点写了"使用 Redis 缓存"但无失效/一致性测试 → 设计点可达性缺口
- 接口定义了 5 个错误码但只测了 2 个 → 错误码覆盖缺口
- 时序图有 4 步交互但只测了首尾 → 跨组件交互缺口
- 性能要求写"P99 < 200ms"但无可执行压测步骤 → 非功能可达性缺口
