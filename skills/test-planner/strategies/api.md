# API 设计模式测试策略

API 设计模式以 `api-design.md` 为测试来源，聚焦接口契约的符合性、错误码覆盖、入参边界与鉴权。与需求文档模式（验收标准驱动）不同，本模式的测试来源是 API 设计文档的结构化契约。

## 测试来源提取

从 api-design.md 按结构提取测试对象：

| 来源 | 提取内容 | 生成测试类型 |
|------|----------|------------|
| 接口清单 | 每个 endpoint（路径 + 方法） | 契约符合测试 |
| 接口契约 | 请求/响应 schema、必填项、类型 | 入参边界 + 契约测试 |
| 错误码定义 | 每个错误码及其触发条件 | 错误码覆盖测试 |
| 鉴权方式 | 每个接口的鉴权要求 | 鉴权覆盖测试 |
| 关键代码设计 | 写操作、状态变更 | 幂等 + 并发测试 |

> 若 api-design.md 可追溯到 DESIGN.md / requirement.md，应建立「接口 → 设计点/REQ」追溯。

## 验证维度

| 维度 | 验证问题 | 严重度 |
|------|---------|:------:|
| **契约符合性** | 实际响应是否符合设计的 schema/字段/类型/状态码？ | 🔴 |
| **错误码覆盖** | 每个定义的错误码是否都有触发场景 + 测试？有无"定义了却测不到"的码？ | 🔴 |
| **入参边界** | 每个参数的边界值/非法值/缺省是否覆盖？必填项缺失是否拦截？ | 🔴 |
| **鉴权覆盖** | 每个接口的鉴权要求是否测试（有权限/无权限/错权限/过期凭证）？ | 🔴 |
| **幂等与并发** | 写接口是否幂等？并发调用是否安全（无重复写入/数据竞争）？ | 🟡 |
| **契约-需求追溯** | 每个接口是否能追溯到 DESIGN.md/requirement.md？有无"接口无需求来源"？ | 🟡 |

## 用例生成规则

### 每个接口的标准用例集

每个 endpoint 生成 4 类用例：

| 路径 | 说明 |
|------|------|
| 契约符合 | 合法入参 → 响应 schema/字段/状态码与设计完全一致 |
| 入参边界 | 每个参数：极值/空值/超长/类型错误/必填缺失 → 验证校验与错误返回 |
| 错误码触发 | 逐一触发设计定义的每个错误码 → 验证返回码与设计一致 |
| 鉴权用例 | 有权限(通过)/无凭证(401)/权限不足(403)/过期凭证(401) |

### 写接口的额外用例

写操作（POST/PUT/PATCH/DELETE）额外生成：

| 路径 | 说明 |
|------|------|
| 幂等性 | 重复调用相同请求 → 不产生重复副作用 |
| 并发安全 | 并发调用同一资源 → 无数据竞争/超卖/重复写入 |

## 与 7 策略的关系

API 设计模式天然偏功能型/否定型/安全型，性能型/度量型按需启用：

| API 特征 | 启用策略 |
|----------|----------|
| 接口契约 | 功能型（契约符合） |
| 鉴权/越权 | 否定型 + 安全型 |
| 性能指标（如接口 SLA） | 性能型 |
| 限流/配额 | 否定型（超限拒绝） |

## 典型缺口

- 定义了 8 个错误码但只测了 3 个 → 错误码覆盖缺口
- 写接口未测幂等 → 重复提交产生重复数据
- 接口有鉴权要求但只测了正向（有权限）→ 鉴权覆盖缺口
- 并发写未测 → 超卖/数据竞争
- 响应 schema 设计了可选字段但未测缺失场景 → 契约符合性缺口
