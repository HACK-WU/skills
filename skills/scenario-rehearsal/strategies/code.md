# 代码推演策略

> 适用特征：推演对象是代码（文件/函数/diff）
> 启用信号：输入为代码/diff，用户明确要求推演/模拟执行/走查代码

## 核心方法：纸上执行（desk check / trace）

代码模式与 code-review、challenger 的本质区别：

| | code-review | challenger | 代码推演 |
|---|---|---|---|
| 核心问题 | 代码写得对不对 | "没问题"的结论可靠吗 | 拿一个具体场景在代码上走一遍会发生什么 |
| 方法 | 逐维度静态检查清单 | 对抗式挑战已有结论 | 沿时间轴正向模拟执行，追踪状态演进 |
| 组织方式 | 属性维度（语义/安全/Bug/…） | 质疑策略（举证倒置/找反例） | 场景实例 × 执行轨迹 |
| 产出 | 分级问题报告 | 质疑报告 | 执行轨迹表 + 终态对比 |

一句话：review 横着看（切维度），challenger 反着看（挑结论），代码推演**顺着跑**（沿时间轴模拟执行）。

## 推演边界与降级（护栏，必读）

纸上执行是**静态推理**，不是真实运行——AI 在深调用栈/大函数上逐步追踪时，极易产出**看似精确实则虚构**的轨迹表（用精确外观骗取信任，比模糊结论更危险）。因此必须守住边界：

| 情形 | 处理 |
|------|------|
| 单函数逻辑清晰、外部调用点 ≤ 若干个、状态变量可枚举 | ✅ 适合纸上执行 |
| 深调用栈（跨多层未展开）、复杂三方库内部行为、状态空间过大 | ⚠️ 只推演到可确定的边界，**跨越不确定处必须标注 `[需运行验证]`**，不臆造下游轨迹 |
| 无法确定某步真实行为（如库函数副作用、并发调度顺序） | ❌ 禁止编造具体状态值；标注"此处行为不可静态确定"，作为待验证项 |

**降级出口**：当 🔴 终态偏差 / 中间态泄漏依赖不可静态确定的行为，或推演规模超出可靠追踪范围时，**不下确定结论**，输出"推演到此为止 + 待验证清单"，建议用导出的场景实例接力 demo-verify / e2e-testing 获取运行时证据。

## 与设计 profile 的边界（concurrency / transaction 等）

`strategies/concurrency.md`、`transaction-state-machine.md` 等是**设计模式**下按设计特征启用的加压视角，作用对象是**设计文档**（评估设计选型是否覆盖竞态/补偿）；代码模式的"时序鲁棒性/中间态安全"作用对象是**具体代码实例的执行轨迹**（在真实代码上追踪某个交错序列会不会出错）。二者不互斥、不叠加：走代码模式时不启用设计 profile，只用本文件维度；需要评估设计层面的并发/事务策略时走设计模式。

## 场景实例化（阶段 2 的关键）

不推演抽象的"异常场景"，而是构造带**具体值**的可执行实例。每个实例必须声明：

1. **具体输入值**：如 `余额=0.01，金额=10，重试=3 次`（不是"余额不足的情况"）
2. **初始状态**：相关变量/资源/DB 记录的起始值
3. **环境行为**：依赖是否失败/慢/乱序（如 `网络在第 2 跳超时`、`第三方返回乱序`）
4. **并发交错**（如涉及）：指定具体时序，如 `线程 A 在 T1 读、线程 B 在 T2 写`
5. **预期终态**：推演前先声明期望的最终结果（防止推演完后合理化）

三个实例来源：
- **输入域切分**：正常值 / 边界值（0、空、极大、负数）/ 非法值
- **环境状态**：依赖成功 / 失败 / 超时慢响应 / 返回乱序或错误码
- **并发时序**：无并发 / 指定交错（读-写、写-写、检查-使用 TOCTOU）

## 验证维度（代码推演全集）

| 维度 | 验证问题 | 严重度 |
|------|---------|:------:|
| **终态正确性** | 推演走到终点时，系统状态是否等于预期终态？返回值/落库/发送内容是否正确？ | 🔴 |
| **中间态安全** | 任意一步失败或进程在此崩溃时，已发生的副作用留下的中间态是否一致、可恢复？有无"半途而废留脏数据"？ | 🔴 |
| **时序鲁棒性** | 指定并发交错或外部乱序下，行为是否仍正确？有无竞态、TOCTOU、重复执行？ | 🔴 |
| **资源生命周期** | 正常与异常路径下，连接/句柄/文件/锁是否都被释放？有无泄漏？ | 🟡 |
| **可观测性** | 走这条路径时，日志/指标能否让人事后知道发生了什么？失败是否可诊断？ | 🟡 |

> 无 profile 加压：代码模式不启用设计 profile，沿时间轴对每个场景实例逐步纸上执行，逐维度判定。

## 加压点（深挖方向）

1. **中间态截断**：在每个"已产生副作用但流程未结束"的点上假设崩溃，检查留下的状态
2. **环境出牌**：把每个外部调用点都假设为失败/超时/乱序，看代码是否处理
3. **边界值代入**：把 0、空集合、负数、极大值、并发上限具体代入，逐步追踪
4. **重复执行**：同一实例执行两次（重试/消息重投），检查幂等性
5. **交错穷举**：并发场景枚举关键的读写交错点，找出破坏不变量的序列

## 典型缺口（代码推演高频问题）

- 校验通过后到落库之间存在窗口，并发下不变量被破坏（TOCTOU）
- 异常路径提前 return，已打开的资源未释放
- 多步操作无事务/补偿，中途失败留下不一致数据
- 重试逻辑不幂等，重复扣款/重复发送
- 外部依赖返回乱序或错误码时代码假设成功，继续错误路径
- 边界值（0、负数、空、溢出）未拦截直接进入主逻辑

## mermaid 提示

- 执行轨迹 `flowchart TD`：节点=代码执行步骤，标注状态变化与问题点
- 并发交错 `sequenceDiagram`：多线程/多角色按 T1/T2/T3 时序标注读写
- 状态演进 `stateDiagram-v2`：关键状态机的合法/非法迁移

## 推演输出格式调整

### 单场景推演输出

```text
🎬 代码推演：[场景实例名称]
━━━━━━━━━━━━━━━━

【调用方角色】[谁触发，如 用户请求 / 定时任务 / 并发线程 A+B]
【场景实例】
- 输入值：[具体值，如 余额=0.01，金额=10]
- 初始状态：[相关变量/资源起始值]
- 环境行为：[依赖是否失败/慢/乱序]
- 并发交错：[如有，指定时序]
【预期终态】[推演前声明的期望最终结果]

【执行轨迹表】
| 步骤 | 代码位置 | 关键状态变化 | 副作用 | 若此步中断的中间态 |
|------|---------|-------------|--------|-------------------|
| 1 | order.py:42 | balance: 0.01 → -9.99 | 无 | 一致 |

【终态对比】
| | 预期终态 | 推演终态 | 判定 |
|---|---------|---------|------|
| 结果 | 拒绝下单 | 扣款成功余额为负 | ❌ 偏差 |

【维度结论】
- 终态正确性：X 项通过 / Y 项存疑 / Z 项失败
- 中间态安全：X 项通过 / Y 项存疑 / Z 项失败
- 时序鲁棒性：X 项通过 / Y 项存疑 / Z 项失败
- 资源生命周期：X 项通过 / Y 项存疑 / Z 项失败
- 可观测性：X 项通过 / Y 项存疑 / Z 项失败
```

## 问题分类（代码模式特有）

| 分类 | 说明 | 处理建议 |
|------|------|---------|
| **终态偏差** | 推演终态与预期终态不一致 | 修正代码逻辑，使终态符合预期 |
| **中间态泄漏** | 某步失败/中断后留下不一致或不可恢复的脏状态 | 补充事务/回滚/补偿 |
| **时序缺陷** | 特定并发交错或外部乱序下行为错误 | 补充同步/幂等/顺序保证 |
| **资源泄漏** | 异常路径下连接/句柄/锁未释放 | 补充 finally/defer/context 释放 |

## 导出为测试素材（独有产出）

代码模式独有价值：推演过的**场景实例（输入值 + 预期终态）可直接导出为测试用例素材**，交给 test-planner / e2e-testing / demo-verify——静态推理链的产物直接变成执行验证的输入。这是 code-review / challenger 都给不了的。

> 代码推演仍是静态推理，不是真实执行。发现 🔴 终态偏差或中间态泄漏后，建议用导出的实例接力 demo-verify / e2e-testing 获取运行时证据。
