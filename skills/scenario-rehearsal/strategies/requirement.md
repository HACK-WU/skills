# 需求文档推演策略（requirement 模式）

> 本文件在「需求文档模式」下使用：当只有 `requirement.md`、设计尚未开始时，场景推演器改用本文件的**需求质量维度**验证需求本身，而非设计点。

## 适用信号

需求文档模式**不靠关键词扫描启用**（无设计特征可扫），而是在「阶段 0 对象类型识别」中由输入决定：

- 输入仅为 `requirement.md`（无 DESIGN.md / 设计未开始）→ 启用本模式
- 输入含 DESIGN.md → 走设计文档模式（见 2.4 的 6 个设计 profile）

## 验证维度（需求质量全集）

| 维度 | 验证问题 | 严重度 |
|------|---------|:------:|
| **场景完整性** | 需求描述的使用场景是否覆盖了各角色的关键目标？有无明显遗漏的子流程/分支？ | 🔴 |
| **验收标准可达性** | 每条验收标准是否真的能验证对应场景？是否存在"无法判定通过"的模糊验收（只说做什么、不说怎样算通过）？ | 🔴 |
| **需求一致性** | 不同场景/条目之间是否冲突或矛盾？（如 A 场景要求实时、B 场景要求异步；或同一操作的两种矛盾描述） | 🔴 |
| **角色-需求对齐** | 每个用户角色的核心诉求是否都有对应功能？是否存在"有角色无功能"或"有功能无角色（无人使用的冗余功能）"？ | 🟡 |
| **边界/异常覆盖** | 需求是否提及异常/边界处理？完全未提及的领域是否暗藏风险（默认"不会出错"）？ | 🟡 |
| **术语一致性** | 同一概念在需求中是否用同一名称？是否存在同名异义、前后定义漂移？ | 🟡 |

## 加压点（深挖方向）

需求推演不验证设计实现，重点加压于"需求自身的漏洞"：

1. **异常流程缺位**：网络超时、权限变更、第三方失败、依赖降级时，需求是否定义了行为？
2. **边界未定义**：空输入、极大值、并发操作、重复提交在需求中是否被考虑？
3. **多角色协作衔接**：跨角色的完整业务流程（如用户提交 → 审核 → 通知）在需求中是否闭环？衔接处的职责归属是否清晰？
4. **验收标准可判定性**：每条验收标准是否有明确的"通过/不通过"判定条件？模糊验收（"体验流畅""性能良好"）须标出。
5. **隐含假设**：需求是否把某些未声明的假设当作既定事实（如"用户总会填对信息"）？

## 典型缺口（需求推演高频问题）

- 异常流程完全未定义，仅描述 Happy Path
- 验收标准只写"系统应支持 XX"，无判定条件
- 多角色协作的回调/通知场景缺失
- 角色与功能不对齐：运营需要的批量操作没写、或写了无人使用的功能
- 术语前后不一致（"订单"有时含"已取消"、有时不含）

## mermaid 提示

与 design 模式一致：协作场景画 `sequenceDiagram`（参与者=角色，消息=步骤，标注需求缺口）、核心场景画 `flowchart TD`（节点=步骤，✅/⚠️/❌ 标注需求覆盖情况）、结论处画 `pie`（问题分布）。需求模式尤以"场景完整性缺口"用 flowchart 标注最直观。
