# 强关联关系查询

## 概述

**目的**：查询代码中已沉淀的**强关联关系**（跨模块契约耦合 + 业务耦合），解决"改了 A 不知道必须连带改 B"的风险——让 AI 在分析/修改代码前，快速感知被改模块牵动了哪些其他模块。

**功能**：从目标代码提取模块关键词 + 关键代码符号，用 `ki_search` / `ki_query_group` 检索 `strong-relation` 沉淀的强关联记录，输出牵动清单。

**使用场景**（供各 skill 引用或独立调用）：
- code review：审查前查询被改模块的强关联，识别漏改风险
- 排错定位（debug）：判断根因是否位于跨模块耦合处
- 设计 / 设计评审：了解模块间牵动关系，辅助设计决策
- 测试设计：判断需覆盖的集成/契约测试范围
- 修改前刹车检查：判断修改是否牵动其他模块

## 定位

```
查询请求 → relation-lookup（本 skill，只查询）→ ki_search / ki_query_group 检索
                                                    ↓
                  返回牵动清单（{模块} 与 {其他模块} 强关联：方向/强度/原因）
```

- **输入**：目标模块/代码的关键符号（类名、方法名、接口名等）
- **输出**：命中该模块的强关联清单（方向/强度/原因）
- **边界**：本 skill **只查询**不强关联记录，**不写入**（写入是 `strong-relation` 的事）；查询**存量记录**（由 `strong-relation` 在 expert-team 产出后写入 ki-search）

## 核心原则

1. **只查不写**：本 skill 查询既有强关联记录，不负责识别/判定/写入（那是 `strong-relation`）
2. **SSOT**：ki 查询参数细节只在本 skill 定义，引用方 skill 只写明调用时机，不重复写 ki 查询细节
3. **符号提准**：query 中带上关键代码符号（类名/方法名/接口名等），显著提高检索准确度
4. **降级不阻塞**：ki 不可用 / 无可用记录 / 未命中 → 静默跳过，不阻塞调用方主流程
5. **记录以代码为准**：强关联记录是辅助参考，与代码实际不符时以代码为准

## 查询流程

```
Step 1 提取符号 → Step 2 检索 → Step 3 利用结果
```

### Step 1：提取模块关键词 + 关键代码符号

从目标代码中提取功能模块名 + **关键代码符号**（2-3 个）。代码符号按实际情况选取最能标识目标的一端——如类名、方法名、接口名、函数名、枚举/常量名等；核心是选"写入 `module_info` 时会出现的、能唯一定位的符号"，带上它们能显著提高检索准确度。

### Step 2：检索强关联

- **按语义检索**（`ki_search`，**query 中带上关键代码符号**）：
  - 查"改某模块要连带改什么"：`ki_search(query="改 {模块A} 要连带改什么 {关键类名}")`
  - 查某类关联：`ki_search(query="{模块A} 数据源 消费端 {关键接口名}")`
- **按模块整组检索**（`ki_query_group`）：查某模块的所有强关联用 `ki_query_group(groups="关联关系/{功能模块名}")`
- **tags 过滤**（固定）：`ki_search` 一律用 **`tags="relation"`** 过滤（强关联记录写入时统一带 `relation` tag），收窄范围提高准确度；**若过滤后命中过少/为空**（如历史存量数据未带该 tag），回退为**去掉 tags 过滤**的语义检索，避免漏召回

### Step 3：利用结果

命中 → 记录**牵动清单**（`{被改模块} 与 {其他模块} 强关联：方向/强度/原因`；双向记录按两条影响线分别列出），作为跨模块一致性检查的重点；未命中 / ki 不可用 / 无强关联 → 静默跳过，不阻塞主流程。

## 使用要点

- **牵动识别**：命中某模块的强关联记录后，按记录标注的**方向/影响线**逐条核对——改到某条影响线的**左端（改动源）**时，务必检查其**右端（被影响方）**是否同步修改或需覆盖；**双向关联**（记录含两条影响线、两端互为源目标）时，改任一端都要核对另一端的影响线，不得漏检反方向
- **方向以记录为准，不自行推断不对称**：方向/强度以 `strong-relation` 写入的 `module_info` 标注为准，不凭"消费端/生产端"自行推断"改谁不用管谁"——记录标注双向（两端互为源目标）就按双向处理，标注单向才按单向核对
- **与专家资产互补**：本 skill 看模块**间**耦合；`expert-lookup` 看模块**内**知识，二者可协同使用
- **与写入方的关系**：记录由 `strong-relation` 在 expert-team 产出后写入；记录与代码不符时，可提示用 `strong-relation` 更新

## 调用约定

引用方 skill 在相关阶段写明调用时机与触发条件，调用 `use_skill("relation-lookup")`，ki 查询参数细节一律以本 skill 为准，不自行重复。
