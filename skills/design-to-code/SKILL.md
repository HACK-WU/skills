# Design-to-Code（设计到代码骨架）

## 概述

**目的**：将设计文档中的结构设计转化为代码骨架，并将契约信息以注释形式就地嵌入，消除 AI 编码时的文档-代码上下文切换。

**核心问题**：AI 拿到设计文档后编码，需要反复查阅文档，导致 token 消耗大、信息稀释、偏离设计意图。文档与代码是两份独立上下文，AI 在长上下文中丢失关键约束。

**解决方案**：设计完成后直接生成代码骨架（文件、类、方法），并就地嵌入契约级注释。AI 编码时打开代码文件即可看到完整实施契约，无需切换到外部文档——代码注释即文档。

## 定位

```
design-craft → ... → design-to-code → 编码实施(就地补全) → implementation-report
   设计产出         ✨ 生成代码骨架+契约注释   AI 看注释填实现        归档实现结果
```

- **输入**：design-craft 产出的设计文档目录（`design/DESIGN.md` + 子文档，也兼容单文档快速通道）
- **输出**：项目源码目录中的代码骨架文件（文件已创建、类已定义、方法已声明、契约已注释，方法体用语言原生占位符）
- **边界**：只管"从设计文档生成骨架结构 + 嵌入契约注释"，不管"怎么填充实现"（由 AI 编码决定），也不管"实现完成与否"（由 implementation-report 记录）

## 核心原则

1. **骨架即实施指南**：代码文件本身就是实施指南，注释即文档，AI 编码时无需再读外部设计文档
2. **契约级注释**：类级概述类的作用与关键约束；方法级写明参数、返回值、异常、预期行为。不抄全文，只写契约
3. **签名即契约**：接口签名（方法名、路径、参数类型、返回值、异常）必须原样从设计文档抄入骨架，编码时不得修改
4. **依赖拓扑序**：骨架生成按子需求依赖 DAG 的拓扑序分批进行
5. **分批生成**：子需求 ≥ 3 个时强制分批生成，每批独立生成+验证，防止一次性生成时上下文过长
6. **占位符合语言习惯**：方法体用语言原生占位符（Python `...`、Java `throw new UnsupportedOperationException()`、Go `panic("not implemented")`、TS `throw new Error("not implemented")`），确保骨架可被 IDE 解析无语法错误
7. **变更可更新**：设计变更后询问用户是否更新骨架，确认后仅重新生成受影响批次，不覆盖已完成批次的已填实现

## 工作流总览

```
阶段 0：定位设计文档      → 识别设计文档目录，读取父文档 + 子文档（含单文档检测）
阶段 1：提取骨架信息      → 从设计文档提取文件路径、类结构、方法签名、数据模型字段、异常定义
阶段 2：依赖排序与批次划分 → 复用设计文档 DAG，划分生成批次（子需求≥3 强制分批）
阶段 3：分批生成代码骨架  → 每批：创建文件 → 定义类 → 声明方法 → 嵌入契约级注释 → 占位方法体
阶段 4：骨架一致性验证    → 比对骨架注释与设计文档，检查遗漏或偏差
阶段 5：落盘与集成        → 写入项目源码目录
阶段 6（可选）：设计变更更新 → 检测变更后询问是否更新骨架
```

**未得到用户对当前阶段的确认前，不进入下一阶段。**

## 阶段 0：定位设计文档

### 输入来源

按优先级尝试：

1. **用户指定路径**：用户直接提供设计文档目录或文件路径
2. **默认位置**：`.requirements/{YYYY-MM-DD}-{功能名称}/design/`

### 读取内容

确定目录后，读取以下文件：

| 文件 | 内容 | 作用 |
|------|------|------|
| `DESIGN.md` | 父文档：需求背景、一览图、总体方案、全局风险 | 提取全局约束和跨子需求依赖 |
| `*_S{NN}_*_DESIGN.md` | 子文档：术语、现状、方案、数据模型、接口设计等 | 提取每个子需求的骨架信息 |

### 单文档检测

若 `*_S{NN}_*_DESIGN.md` 匹配为空，则判定为**单文档场景**（design-craft 快速通道产出）：

- 不再寻找子文档，将 `DESIGN.md` 按章节拆分为虚拟子需求（每个含方案+实现的章节视为一个骨架生成单元）
- 后续阶段 1 的提取规则照常应用，阶段 2 的排序简化为"按章节出现顺序"

### 非 design-craft 来源检测

读取 `DESIGN.md` 后检查是否包含 design-craft 的特征标记（如元数据区、mermaid 一览图、`S-XX` 编号的子需求引用）：

- **匹配**：按设计文档章节名进行提取
- **不匹配**：输出警告，列出识别到的章节名，询问用户是否继续。确认后按章节名模糊匹配提取规则，未匹配的章节按段落逐条提取并标注 `§ 章节名 [未识别类型]`

### 校验

读取完成后，校验设计文档完整性：

- 父文档包含 mermaid 代码块（关键环节一览图）
- 每个子需求节点都有对应子文档（多文档场景）
- 子文档中的接口签名在父文档中有声明（通过搜索接口路径/方法名交叉验证，而非硬编码章节编号）

校验失败则提示用户先修复设计文档。

### 输出格式

```text
📂 设计文档定位

来源：{路径}

父文档：DESIGN.md（N 个全局章）
子文档：
  - S-01：{名称}（M 章）
  - S-02：{名称}（K 章）
  ...

校验结果：✅ 完整 / ⚠️ 存在以下问题：<...>

确认后进入阶段 1 提取骨架信息。
```

## 阶段 1：提取骨架信息

从设计文档中提取生成代码骨架所需的全部信息。**只提取结构信息和契约信息，不提取决策理由、AS-IS、备选方案。**

### 提取规则

| 章节类型 | 提取内容 | 用于骨架的什么 |
|----------|----------|---------------|
| 方案(TO-BE) - 新增文件 | 每个新增文件的完整路径 | 创建文件 |
| 方案(TO-BE) - 修改文件 | 每个修改文件的完整路径 + 变更描述 | 在现有文件上追加 |
| 接口设计 | 每个接口的完整签名（方法、路径、参数、返回值、异常）+ 行为描述 | 方法声明 + 方法级契约注释 |
| 数据模型 | 每个新增/修改字段（名、类型、默认值、含义）+ 模型间关系 | 类定义 + 字段声明 + 字段注释 |
| 异常处理 | 每个异常场景 → 触发条件 → 行为 → 是否对外暴露 | 方法级注释中的异常说明 |
| 时序图 - 关键步骤 | 时序图中的关键消息传递步骤 | 方法级注释中的"实现步骤"提示 |
| 性能安全 | 每个性能/安全约束 | 类级或方法级注释中的约束说明 |
| 影响范围 | 每个受影响的外部模块/系统 | 类级注释中的"影响范围"说明 |
| 全局风险 | 每个跨子需求风险 + 缓解措施 | 全局约束文件注释 |

### 不提取的内容

- 现状章(AS-IS)：是背景，不是实施项
- 术语章：是上下文，不进入代码
- 决策理由、被否决方案：是设计过程，不是实施项
- 时序图的参与者声明、生命线：是图元，不是实施项

### 提取粒度约束

- **文件级**：每个文件改动对应一个骨架文件
- **类级**：设计文档中定义的每个类/模型独立提取
- **方法级**：每个接口/方法独立提取，不合并
- **字段级**：数据模型中每个字段独立提取
- **兜底规则**：未匹配提取规则的章节类型 → 按段落逐条提取可执行描述，标注 `§ 章节名 [未识别类型]`，确保不静默遗漏

### 输出格式

```text
🔍 骨架信息提取

S-01：{子需求名称}
  文件：X 个（新增 Y / 修改 Z）
  类：A 个
  方法：B 个
  字段：C 个
  异常场景：D 个

S-02：{子需求名称}
  ...

全局约束：K 条

确认提取全面性，有无遗漏或多余。
```

## 阶段 2：依赖排序与批次划分

### 排序规则

复用设计文档阶段 2.5 的依赖 DAG 确定生成顺序：

1. **父文档全局约束**排最前（生成一个全局约束注释文件或写入入口文件头部）
2. **无依赖的子需求**最先生成
3. **被依赖的子需求**排在依赖它的子需求之前
4. **同一子需求内**按：文件创建 → 数据模型（类+字段） → 接口实现（方法声明） → 异常处理（方法注释中的异常说明）

### 批次划分规则

| 子需求数量 | 划分策略 | 说明 |
|-----------|----------|------|
| 1-2 个 | 单批次一次性生成 | 上下文可控，无需分批 |
| ≥ 3 个 | **强制分批**，按依赖层级划分 | 防止一次性生成时上下文过长导致遗漏 |

### 顺序无关批次识别

同一依赖层级中**无交叉依赖**的批次标记为顺序无关（可按任意顺序生成）：

**判定规则**：两个批次 A 和 B 在同一依赖层级（直接依赖集合相同），且 A 不依赖 B、B 不依赖 A → **顺序无关**。

**示例**：
```
S-01（无依赖）  ─┬─→ S-03（依赖 S-01）
                 │
S-02（无依赖）  ─┼─→ S-04（依赖 S-02）
                 │
                 └─→ S-05（依赖 S-01, S-02）

批次划分：
  第 1 批 [顺序无关]：S-01, S-02 — 同层无交叉依赖
  第 2 批 [顺序无关]：S-03, S-04 — 同层无交叉依赖
  第 3 批 [依赖前批]：S-05 — 依赖前两批
```

### 排序校验

排序完成后检查：

- 每个子需求的所有前提条件是否已在之前批次完成
- 是否有循环依赖（如有，标记并提示用户）
- 顺序无关批次之间是否存在隐式共享资源（如修改同一文件、共享同一数据表），若有则标注警告

### 输出格式

```text
🔗 排序与批次划分

生成顺序：
  第 1 批 [顺序无关]（无依赖）：
    - S-01：{名称}（X 文件 / Y 类 / Z 方法）
    - S-02：{名称}（X 文件 / Y 类 / Z 方法）
  第 2 批 [依赖前批]（依赖 S-01, S-02）：
    - S-03：{名称}（K 文件 / ...）
  ...

批次说明：
  - 共 N 批，{单批次/分批次}生成
  - 第 1 批的 S-01 和 S-02 无交叉依赖，生成顺序无关
  - 第 2 批的 S-03 依赖 S-01 和 S-02，必须等两者完成后开始

确认排序合理性与批次划分。
```

## 阶段 3：分批生成代码骨架

这是核心阶段。**每批独立生成 + 独立验证**，分批机制内嵌于此阶段。

### 分批执行流程

```
┌─ 子需求 < 3：单批次 ──────────────┐
│                                    │
│  生成全部骨架 → 验证 → 落盘        │
└────────────────────────────────────┘

┌─ 子需求 ≥ 3：分批次 ──────────────────────────────┐
│                                                    │
│  第 1 批 → 生成 → 批内验证 → ✅ → 用户确认         │
│       ↓                                            │
│  第 2 批 → 生成 → 批内验证 → ✅ → 用户确认         │
│       ↓                                            │
│  ... 直到全部批次完成 → 阶段 4 全局一致性验证       │
└────────────────────────────────────────────────────┘
```

### 单批生成步骤

#### 步骤 1：批次启动确认

```text
🔨 批次 {N}/{总计}：{批次名称}

本批次包含：
  - {子需求编号}：{名称}（X 文件 / Y 类 / Z 方法）
依赖条件：{已完成的批次 / 无}

━ 同层顺序无关 ━（可选，同层无顺序无关批次则不显示）
  📎 第 {N} 批：{名称} [顺序无关] — 生成顺序不限

确认开始生成本批次骨架？[Y/n]
```

#### 步骤 2：逐文件生成骨架

对本批次每个文件，按以下顺序生成：

1. **创建/打开文件**
   - create：新建文件，从头写入
   - modify：先读取现有文件，确定插入位置后追加新类/方法，不破坏已有代码
2. **写入文件头注释**：文件用途、关联设计文档锚点、全局约束
3. **导入语句**：根据设计文档中的依赖关系添加 import
4. **定义类/结构体**：类声明 + 继承 + 实现
5. **声明字段**：字段名 + 类型 + 默认值 + 行内注释
6. **声明方法**：方法签名 + 契约级注释 + 占位方法体

#### 步骤 3：嵌入契约级注释（核心）

注释分两级，必须完整覆盖设计文档中的契约信息：

**类级注释**（写在类声明下方）：

```python
class UserService:
    """用户服务。

    职责：管理用户注册、登录、信息查询。
    关键约束：密码必须加盐哈希存储；查询接口响应时间 < 200ms。
    影响范围：被 AuthController、ProfileController 依赖。
    设计文档：§ S-01 方案
    """
```

**方法级注释**（写在方法签名下方）：

```python
def login(self, cred: LoginRequest) -> TokenPair:
    """用户登录，返回访问令牌和刷新令牌。

    参数：
        cred: LoginRequest — 登录凭证（用户名+密码）
    返回：
        TokenPair — {access_token, refresh_token, expires_in}
    异常：
        AuthError: 密码错误时抛出（对外暴露，返回 401）
        TokenExpiredError: 令牌过期时抛出（对外暴露，返回 401）
    预期行为：
        1. 根据用户名查询用户记录
        2. 校验密码（加盐哈希比对）
        3. 生成 TokenPair 并返回
    HTTP：POST /api/auth/login
    设计文档：§ S-01 接口设计
    """
    ...
```

#### 步骤 4：方法体占位

按语言习惯使用占位符，确保骨架可被 IDE 解析无语法错误：

| 语言 | 占位符 | 示例 |
|------|--------|------|
| Python | `...` 或 `raise NotImplementedError` | `def foo(): ...` |
| Java | `throw new UnsupportedOperationException("Not implemented");` | — |
| Go | `panic("not implemented")` | — |
| TypeScript | `throw new Error("not implemented");` | — |
| Rust | `todo!()` 或 `unimplemented!()` | — |

#### 步骤 5：批内验证

本批次所有文件生成后，执行批内自检：

```text
🔍 批次 {N} 骨架自检

☐ 本批次所有文件已创建/修改
☐ 所有类已定义，继承关系正确
☐ 所有方法已声明，签名与设计文档一致
☐ 所有字段已声明，类型和默认值与设计文档一致
☐ 所有方法级注释包含：参数、返回值、异常、预期行为
☐ 所有方法体使用语言原生占位符，无语法错误
☐ 所有注释包含设计文档锚点（§ 引用）

自检结果：✅ 通过 / ❌ 未通过（列出未通过项）
```

#### 步骤 6：批次完成确认

```text
✅ 批次 {N} 骨架生成完成

生成文件：X 个（新增 Y / 修改 Z）
定义类：A 个
声明方法：B 个
声明字段：C 个
嵌入契约注释：D 条

━ 同层状态 ━
  同层顺序无关批次：第 {X} 批（⏳ 待生成 / ✅ 已完成）
  → {全部完成，可进入下一层 / 等待同层批次完成}

是否继续生成下一批次？[Y/n]
```

### 多语言注释规范

根据目标语言使用对应的注释语法：

| 语言 | 类级注释 | 方法级注释 |
|------|----------|-----------|
| Python | docstring（`"""`） | docstring（`"""`） |
| Java | Javadoc（`/** */`） | Javadoc（`/** */`） |
| Go | godoc（`//` 紧贴声明上方） | godoc（`//` 紧贴声明上方） |
| TypeScript | JSDoc（`/** */`） | JSDoc（`/** */`） |
| Rust | `///` 文档注释 | `///` 文档注释 |

### 注释约束

- **不抄全文**：只写契约信息，不抄设计文档的决策理由、AS-IS、备选方案
- **方法级注释 ≤ 15 行**：超过则说明契约过复杂，提示用户拆分方法
- **必须包含锚点**：每条注释末尾标注 `设计文档：§ {子需求编号} {章节名}`，便于回溯
- **签名原样**：方法签名必须与设计文档完全一致，不得修改参数名、类型、返回类型

## 阶段 4：骨架一致性验证

全部批次生成完成后，执行全局一致性验证：将骨架中的注释与设计文档逐项比对。

### 验证维度

| 维度 | 验证内容 | 通过标准 |
|------|----------|----------|
| 文件覆盖 | 设计文档中所有新增/修改文件都已生成骨架 | 100% 覆盖 |
| 类覆盖 | 设计文档中所有类/模型都已定义 | 100% 覆盖 |
| 方法覆盖 | 设计文档中所有接口/方法都已声明 | 100% 覆盖 |
| 签名一致 | 方法签名与设计文档完全一致 | 零偏差 |
| 字段一致 | 字段名、类型、默认值与设计文档一致 | 零偏差 |
| 异常覆盖 | 设计文档中的所有异常场景都在方法注释中说明 | 100% 覆盖 |
| 行为描述 | 方法注释中的"预期行为"覆盖设计文档中的行为要求 | ≥ 95% 覆盖 |
| 锚点完整 | 每条注释都有设计文档锚点 | 100% 覆盖 |

### 输出格式

```text
📐 骨架一致性验证

验证范围：全部 N 个批次

逐项核对结果：
  ✅ 文件覆盖：{X}/{X}，100%
  ✅ 类覆盖：{Y}/{Y}，100%
  ⚠️ 方法覆盖：{Z-1}/{Z}，遗漏 1 个 → {方法名} § {锚点}
  ✅ 签名一致：零偏差
  ✅ 字段一致：零偏差
  ✅ 异常覆盖：{W}/{W}，100%
  ⚠️ 行为描述：{V-2}/{V}，遗漏 2 个 → {方法名}
  ✅ 锚点完整：100%

一致性结果：✅ 一致 / ⚠️ 存在偏差（列出偏差项）

偏差处理：
  - 遗漏项：补充到对应骨架文件中
  - 不一致项：以设计文档为准，修正骨架
```

验证通过后进入阶段 5 落盘。

## 阶段 6（可选）：设计变更更新

设计文档变更后，检测变更范围并询问用户是否更新骨架。

### 触发方式

1. **用户主动触发**：用户说"设计变了，更新骨架"、"重新生成骨架"
2. **skill 自动检测**：进入 skill 时比对设计文档修改时间与 `skeleton-status.md` 生成时间，若设计文档更新则提示

### 变更检测

```text
🔄 设计变更检测

设计文档最后修改：{时间}
骨架最后生成：{时间}

检测到设计文档已更新，变更范围：
  - {文件/章节}：{变更描述}
  - ...

是否更新代码骨架？[Y/n]
```

### 更新策略

用户确认后，按以下策略更新：

| 变更类型 | 更新策略 |
|----------|----------|
| 新增子需求 | 生成新批次骨架，追加到现有骨架中 |
| 修改接口签名 | 重新生成受影响的方法声明和契约注释 |
| 修改数据模型 | 重新生成受影响的类定义和字段声明 |
| 删除子需求 | 提示用户确认是否删除对应骨架文件（不自动删除） |
| 全局约束变更 | 更新文件头注释中的全局约束说明 |

### 更新约束

- **仅更新受影响批次**：未变更的批次骨架保持不变
- **不覆盖已填实现**：若骨架文件中的方法已被 AI 填充实现，更新时仅修改契约注释和方法签名，保留实现逻辑（若签名变更导致实现不兼容，提示用户手动调整）
- **更新后重新验证**：受影响批次重新执行阶段 4 一致性验证

### 更新输出

```text
✅ 骨架已更新

更新批次：第 {N} 批（{子需求名称}）
更新文件：X 个
更新内容：
  - {文件}：{变更描述}
  - ...

保留实现：{Y} 个方法（未受变更影响，实现已保留）
需手动调整：{Z} 个方法（签名变更，实现需适配）

一致性验证：✅ 通过 / ⚠️ 存在偏差（列出偏差项）
```

## 反模式（不要做）

### 提取层面
- ❌ 将设计文档的"决策理由"、"备选方案"、"AS-IS 描述"当作骨架信息提取
- ❌ 笼统概括为"实现 xx 模块"而不拆解到文件/类/方法级
- ❌ 自行添加设计文档中未要求的"最佳实践"条目（如"记得写日志"、"加单元测试"）
- ❌ 修改设计文档中的接口签名或数据模型定义——骨架必须原样复制

### 生成层面
- ❌ 方法体写入具体实现逻辑——骨架只放占位符，实现由编码阶段完成
- ❌ 契约注释抄写设计文档全文——只写契约信息（参数、返回值、异常、预期行为）
- ❌ 遗漏方法级注释中的"预期行为"——这是 AI 编码时的核心指引
- ❌ 使用非语言原生的占位符——必须确保骨架可被 IDE 解析无语法错误

### 使用层面
- ❌ 编码时不看骨架注释直接凭记忆写代码——契约注释就是实施指南
- ❌ 编码时擅自修改方法签名——签名即契约，发现设计问题应回到 design-craft 修订
- ❌ 子需求 ≥ 3 个时一口气生成所有批次骨架——上下文过长，必然遗漏契约
- ❌ 跳过批内验证直接进入下一批次——偏差会逐批累积
- ❌ 设计变更后不更新骨架直接编码——会导致实现与新设计不一致
