# Design-to-Code（设计到代码桥接）

## 概述

**目的**：从设计文档中提取所有可执行实施项，生成结构化对照清单，桥接"设计评审通过"到"编码实施"之间的断层。

**核心问题**：AI 拿到设计文档后编码，经常因文档冗长、信息稀释而偏离设计意图——接口签名不一致、遗漏异常处理、跳过数据模型字段、未按依赖顺序实现。

**解决方案**：将设计文档中的每一条设计要求，转译为一组「无歧义、可勾选、可定位」的 checklist 条目。编码时逐项对照，完成即打勾，未完成就是遗漏。

## 定位

```
design-craft → ... → design-to-code → 编码实施(逐批次) → implementation-report
   设计产出         ✨ 生成对照清单      逐批实现+验证       归档实现结果
```

- **输入**：design-craft 产出的设计文档目录（`design/DESIGN.md` + 子文档，也兼容单文档快速通道）
- **输出**：`checklist/` 目录（`README.md` 总览 + 每批次独立 `.md` 文件），按批次组织
- **边界**：只管"从设计文档中提取要做什么"和"分批次实施引导"，不管"怎么实现"（怎么实现由设计文档 + AI 编码决定），也不管"做完了没有"（做完由 implementation-report 负责记录）

## 核心原则

1. **逐条转译，不概括**：设计文档中每个接口签名、每个数据字段、每个文件改动、每项异常处理，都必须作为独立条目出现在 checklist 中，不允许用"实现用户认证模块"这种笼统描述
2. **签名即契约**：接口签名（方法名、路径、参数类型、返回值、异常）必须原样抄入 checklist，编码时不得修改
3. **依赖拓扑序**：checklist 条目排列顺序 = 子需求依赖 DAG 的拓扑序，确保实现顺序正确
4. **锚点回链**：每条 checklist 附设计文档的章节引用，编码时可直接跳转查上下文
5. **不增不减**：checklist 只包含设计文档中明确要求的内容，不自行添加"最佳实践"条目
6. **分批次实施，逐批验证**：checklist 按依赖批次组织，每批次实现完成后必须对照设计文档交叉验证，验证通过后方可进入下一批次。禁止一口气实现所有批次

## 工作流总览

```
阶段 0：定位设计文档      → 识别设计文档目录，读取父文档 + 子文档（含单文档检测）
阶段 1：逐文档提取实施项  → 从每个设计章节提取可执行的实施条目（含未识别章节兜底）
阶段 2：按依赖拓扑排序    → 复用设计文档的 DAG，排列条目顺序，划分依赖批次
阶段 3：生成对照清单      → 输出 checklist/（README.md + 每批次独立文件）
阶段 4：落盘与集成        → 写入 checklist/ 目录 + 需求管理集成
阶段 5（可选）：分批次实施引导 → 逐批次实施 → 每批次验证 → 通过后进入下一批
```

**未得到用户对当前阶段的确认前，不进入下一阶段。**

## 阶段 0：定位设计文档

### 输入来源

按优先级尝试：

1. **用户指定路径**：用户直接提供设计文档目录或文件路径
2. **需求管理系统**：检查 `.requirements/config`，通过 `req list` 找到当前活跃需求的 `design/` 目录
3. **默认位置**：`.requirements/{YYYY-MM-DD}-{功能名称}/design/`

### 读取内容

确定目录后，读取以下文件：

| 文件 | 内容 | 作用 |
|------|------|------|
| `DESIGN.md` | 父文档：需求背景、一览图、总体方案、全局风险 | 提取全局约束和跨子需求依赖 |
| `*_S{NN}_*_DESIGN.md` | 子文档：术语、现状、方案、数据模型、接口设计等 | 提取每个子需求的实施项 |

### 单文档检测

若 `*_S{NN}_*_DESIGN.md` 匹配为空，则判定为**单文档场景**（design-craft 快速通道产出）：

- 不再寻找子文档，将 `DESIGN.md` 按章节拆分为虚拟子需求（每个含方案+实现的章节视为一个实施单元）
- 后续阶段 1 的提取规则照常应用，阶段 2 的排序简化为"按章节出现顺序"

### 非 design-craft 来源检测

读取 `DESIGN.md` 后检查是否包含 design-craft 的特征标记（如元数据区、mermaid 一览图、`S-XX` 编号的子需求引用）：

- **匹配**：按设计文档章节名进行提取
- **不匹配**：输出警告，列出识别到的章节名，询问用户是否继续。确认后按章节名模糊匹配提取规则（如"接口" → 接口设计规则），未匹配的章节按段落逐条提取并标注 `§ 章节名 [未识别类型]`

### 校验

读取完成后，校验设计文档完整性：

- 父文档包含 mermaid 代码块（关键环节一览图）
- 每个子需求节点都有对应子文档（多文档场景）
- 子文档中的接口签名在父文档中有声明（通过搜索接口路径/方法名交叉验证，而非硬编码章节编号）

校验失败则提示用户先修复设计文档。

### 输出格式

```text
📂 设计文档定位

来源：{路径/需求管理系统}

父文档：DESIGN.md（N 个全局章）
子文档：
  - S-01：{名称}（M 章）
  - S-02：{名称}（K 章）
  ...

校验结果：✅ 完整 / ⚠️ 存在以下问题：<...>

确认后进入阶段 1 提取实施项。
```

## 阶段 1：逐文档提取实施项

从每个章节中提取可执行条目，**逐条转译、原样保留签名**。

### 提取规则

从下表中各章节类型提取对应条目：

| 章节类型 | 提取内容 | checklist 格式 |
|----------|----------|---------------|
| 方案(TO-BE) - 新增文件 | 每个新增文件的完整路径 | `- [ ] 创建文件 `src/path/to/file.py`` |
| 方案(TO-BE) - 修改文件 | 每个修改文件的完整路径 + 变更描述 | `- [ ] 修改 `src/path/to/file.py`：{变更描述}` |
| 接口设计 | 每个接口的完整签名（方法、路径、参数、返回值、异常） | `- [ ] 实现 `POST /api/xxx`：{方法签名}` |
| 接口设计 - Demo 返回 | 响应结构约束 | `- [ ] 响应体结构匹配 Demo：{关键字段列表}` |
| 数据模型 | 每个新增/修改字段（名、类型、默认值、含义） | `- [ ] 字段 `field_name: type = default` // {含义}` |
| 异常处理 | 每个异常场景 → 行为 → 是否对外暴露 | `- [ ] 异常 `{场景}`：{行为}，对外={是/否}` |
| 时序图 - 关键步骤 | 时序图中的每个消息传递步骤 | `- [ ] 时序步骤：{发送方} → {接收方}：{消息}` |
| 迁移策略 | 每个迁移步骤 | `- [ ] 迁移步骤 {N}：{描述}` |
| 性能安全 | 每个性能/安全约束 | `- [ ] 性能约束：{约束描述}` |
| 影响范围 | 每个受影响的外部模块/系统 | `- [ ] 影响适配：{模块名} - {适配描述}` |
| 全局风险 | 每个跨子需求风险 + 缓解措施 | `- [ ] 全局风险缓解：{风险描述} → {缓解}` |

### 条目标注规则

每条 checklist 末尾标注设计文档出处：

```
- [ ] 实现 `POST /api/auth/login`：`login(cred: LoginRequest) -> TokenPair`，异常 `AuthError` § S-01 接口设计
                                                                                          ↑ 锚点引用
```

锚点格式：`§ {子需求编号} {章节名}`，如 `§ S-01 接口设计`、`§ 父文档 全局风险`。

### 提取粒度约束

- **接口级**：不拆到内部私有方法（除非设计文档明确要求）
- **字段级**：数据模型中每个字段独立一条
- **文件级**：每个文件改动对应一组条目
- **不提取**：现状章(AS-IS)、术语章、决策理由、被否决方案——这些是设计上下文，不是实施项
- **兜底规则**：未匹配提取规则的章节类型 → 按段落逐条提取可执行描述，标注 `§ 章节名 [未识别类型]`，确保不静默遗漏

### 输出格式

```text
🔍 实施项提取

S-01：{子需求名称}（N 条）
  - 新增文件：X 条
  - 接口实现：Y 条
  - 数据模型：Z 条
  - 异常处理：W 条
  ...

S-02：{子需求名称}（M 条）
  ...

全局约束（K 条）

确认提取全面性，有无遗漏或多余条目。
```

## 阶段 2：按依赖拓扑排序与并行度识别

### 排序规则

复用设计文档阶段 2.5 的依赖 DAG 确定条目顺序：

1. **父文档全局约束**排最前（先建立全局认知和约束）
2. **无依赖的子需求**最先实施
3. **被依赖的子需求**排在依赖它的子需求之前
4. **同一子需求内**按：文件创建 → 数据模型 → 接口实现 → 异常处理 → 时序步骤 → 性能安全 → 影响范围 → 迁移策略

### 并行度识别

排序完成后，识别同一依赖层级中**无交叉依赖**的批次，标记为可并行：

**判定规则**：两个批次 A 和 B 在同一依赖层级（它们的直接依赖集合相同），且 A 不依赖 B、B 不依赖 A → **可并行**。

**示例**：
```
S-01（无依赖）  ─┬─→ S-03（依赖 S-01）
                 │
S-02（无依赖）  ─┼─→ S-04（依赖 S-02）
                 │
                 └─→ S-05（依赖 S-01, S-02）

排序结果：
  第 1 层：S-01, S-02 — 同层无交叉依赖 → [可并行]
  第 2 层：S-03, S-04 — 同层无交叉依赖 → [可并行]
  第 3 层：S-05 — 单批次 → 串行
```

### 排序校验

排序完成后检查：

- 每个子需求的所有条目前提条件是否已在之前完成
- 是否有循环依赖（如有，标记并提示用户）
- 可并行批次的子需求之间是否存在隐式共享资源（如修改同一文件、共享同一数据表），若有则标注警告

### 输出格式

```text
🔗 排序结果

实施顺序：
  第 1 层 [可并行]（无依赖）：
    - S-01：{名称}（N 条）
    - S-02：{名称}（M 条）
  第 2 层 [串行]（依赖 S-01, S-02）：
    - S-03：{名称}（K 条）
  ...

并行说明：
  - 第 1 层的 S-01 和 S-02 无交叉依赖，可同时实施
  - 第 2 层的 S-03 依赖 S-01 和 S-02，必须等两者都完成后才能开始
  ...

确认排序合理性与并行度判断。
```

## 阶段 3：生成对照清单

将排序后的条目生成为 checklist 文件组。**每批次一个独立文件**，外加一个 `README.md` 总览。

### 文件结构

```
checklist/
├── README.md          # 总览：批次清单 + 分批次实施规则 + 全局约束
├── B01_<名称>.md      # 批次 1：无依赖子需求
├── B02_<名称>.md      # 批次 2：依赖批次 1
└── B03_<名称>.md      # 批次 3：依赖批次 1, 2
```

> 每批次独立文件的好处：实施批次 N 时只打开 `B{N}.md`，不被已完成/未开始批次的条目干扰；进度追踪更清晰，文件即为进度标记。

### README.md 模板

```markdown
# 实施对照清单：{功能名称}

> 关联设计文档：`{路径}/design/DESIGN.md`

## 批次总览

| 批次 | 文件 | 子需求 | 条目数 | 依赖 | 模式 | 状态 |
|------|------|--------|--------|------|------|------|
| B01 | [B01_{名称}.md](B01_{名称}.md) | S-01 | M 条 | 无 | 可并行(B02) | ⏳ 待实施 |
| B02 | [B02_{名称}.md](B02_{名称}.md) | S-02 | K 条 | 无 | 可并行(B01) | ⏳ 待实施 |
| B03 | [B03_{名称}.md](B03_{名称}.md) | S-03 | P 条 | B01, B02 | 串行 | ⏳ 待实施 |
| ... | ... | ... | ... | ... | ... | ... |

## ⚡ 分批次实施规则（必须遵守）

- **必须逐批次实施，禁止一口气实现所有批次**
- 标记为 `可并行` 的批次可与同层其他并行批次同时实施，互不阻塞
- 标记为 `串行` 的批次必须等待所有依赖批次完成后才能开始
- 每批次实施完成后，对照该批次文件逐条自检 + 回看设计文档交叉验证
- 验证通过后才能将该批次状态改为 `✅ 已完成`
- 若验证发现偏差，修复后重新验证，不得带着偏差进入下一层
- 全部批次完成后，用 `implementation-report` skill 归档实现结果

## 每批次验证清单

每批次完成后必须逐项确认：
- [ ] 本批次所有 checkbox 已勾选
- [ ] 接口签名与设计文档完全一致
- [ ] 数据模型字段与设计文档完全一致
- [ ] 异常处理覆盖设计文档要求的全部场景
- [ ] 未擅自添加设计文档未要求的内容

## 全局约束（贯穿所有批次）

- [ ] 全局风险缓解：{风险描述} → {缓解措施}  § 父文档 全局风险
- [ ] 共享术语一致性校验：{术语列表}  § 父文档 共享术语速查
```

### 单批次文件模板（`B01_<名称>.md`）

```markdown
# 批次 1：{批次名称}

> 状态：⏳ 待实施
> 模式：串行 / 可并行(同层批次：B02)
> 依赖：无 / B01
> 条目数：M 条

---

### S-01：{子需求名称}

#### 文件创建 / 修改
- [ ] 创建文件 `src/path/to/file.py`  § S-01 方案
- [ ] 修改文件 `src/path/to/other.py`：添加 xxx 方法  § S-01 方案

#### 数据模型
- [ ] 字段 `verified: bool = False` // 用户是否已验证  § S-01 数据模型
- [ ] 字段 `last_login: Optional[datetime] = None` // 最后登录时间  § S-01 数据模型

#### 接口实现
- [ ] 实现 `POST /api/auth/login`：`login(cred: LoginRequest) -> TokenPair`，异常 `AuthError`, `TokenExpiredError`  § S-01 接口设计
- [ ] 响应体结构匹配 Demo：`{code, data: {token, refresh_token, expires_in}, message}`  § S-01 接口设计

#### 异常处理
- [ ] 异常 `密码错误`：返回 401 + `AuthError("invalid_credentials")`，对外暴露  § S-01 异常处理
- [ ] 异常 `Token 过期`：返回 401 + `TokenExpiredError`，对外暴露  § S-01 异常处理

#### 时序步骤
- [ ] 时序步骤：Client → AuthService：发送登录请求  § S-01 时序图
- [ ] 时序步骤：AuthService → UserDB：查询用户  § S-01 时序图
```

### 生成约束

- 每个 `§` 引用必须可定位到设计文档的具体章节
- 接口签名必须与设计文档原样一致（含参数名、类型、返回类型、异常类型）
- Demo 响应体约束只列关键字段，不抄完整 JSON
- 文件路径必须为从项目根目录开始的相对路径
- 批次文件命名：`B{NN}_{简短描述}.md`，如 `B01_数据层.md`、`B02_认证接口.md`

### 输出格式

```text
📋 实施对照清单已生成

文件组：{路径}/checklist/
  - README.md（总览 + 规则 + 全局约束）
  - B01_{名称}.md（批次 1，M 条）
  - B02_{名称}.md（批次 2，K 条）
  ...

批次：共 N 批
条目：总计 T 条
  - 文件创建/修改：X 条
  - 数据模型：Y 条
  - 接口实现：Z 条
  - 异常处理：W 条
  - 全局约束：U 条（在 README.md 中）

确认清单内容后进入落盘归档。
```

## 阶段 4：落盘与集成

### 存储位置

checklist 文件组存入设计文档目录下的 `checklist/` 子目录：

```
.requirements/{YYYY-MM-DD}-{功能名称}/design/
├── DESIGN.md
├── {功能名称}_S01_{子需求名称}_DESIGN.md
├── {功能名称}_S02_{子需求名称}_DESIGN.md
└── checklist/
    ├── README.md           ← 总览 + 规则 + 全局约束
    ├── B01_{名称}.md       ← 批次 1
    ├── B02_{名称}.md       ← 批次 2
    └── ...
```

> 独立子目录的好处：checklist 不污染设计文档目录，实施过程中频繁打勾不会触发对设计文档的误操作。

### 需求管理集成

如果项目中配置了 `.requirements/config`，落盘后自动关联（只注册 README.md 作为入口，批次文件由 README 的链接索引）：

```bash
req update {REQ-NNN} \
  --docs add design/checklist/README.md,design \
  --changelog "生成实施对照清单（N 个批次）"
```

### 输出格式

```text
✅ 实施对照清单已落盘

入口：{完整路径}/checklist/README.md
文件组：
  - README.md（总览 + 全局约束）
  - B01_{名称}.md（批次 1，M 条）
  - B02_{名称}.md（批次 2，K 条）
  ...

批次：共 N 批
需求关联：{REQ-NNN}（如有）

━━━━━━━━━━━━━━━━

## 阶段 5（可选）：分批次实施引导

> 阶段 5 在用户选择「开始分批次编码实施」后进入。若暂不实施，跳过本阶段。

### 核心约束

**子需求 ≥ 3 个时，强制分批次实施。禁止一口气实现所有子需求。** 一口气实现会导致：
- 上下文过长，AI 丢失设计约束，偏离设计意图
- 验证困难，无法定位是哪个子需求的实现出了问题
- 修复成本高，一个错误可能污染多个子需求的代码

### 引导流程

```
┌─ 同一层可并行 ─────────────────────────────────┐
│                                                 │
│  B01 (串行) ──→ 验证 ──→ ✅                     │
│       │                                         │
│  B02 (可并行) ──→ 验证 ──→ ✅                   │
│       │                                         │
│       └──→ 全部完成 ──→ B03 (串行) ──→ ...     │
└─────────────────────────────────────────────────┘
```

- **串行批次**：前一批次验证通过后，才能开始当前批次
- **可并行批次**：同层并行批次可以同时实施，互不阻塞；全部通过后进入下一层

### 并行批次实施规则

同一层中标记为 `可并行` 的批次，实施策略：

1. **优先同时启动**：告知用户"以下 N 个批次无交叉依赖，可同时实施"
2. **独立验证**：每个并行批次独立完成自检 + 交叉验证，不互相等待
3. **全部通过才能进入下一层**：同层所有并行批次（含串行批次）都 `✅ 已完成` 后，才能开始下一层的批次
4. **隐式冲突警告**：若阶段 2 发现并行批次存在隐式共享资源（修改同一文件、共享数据表），输出警告并建议串行化

**并行批次启动输出**：
```text
🔀 第 {N} 层：可并行实施

以下 {M} 个批次无交叉依赖，可同时实施：
  - B0X：{名称}（{K} 条）
  - B0Y：{名称}（{P} 条）

实施顺序任意，互不阻塞。全部完成后进入下一层。

⚠️ 注意：B0X 和 B0Y 都修改 `src/models/user.py`，建议协调改动顺序以避免冲突。
```

### 每批次实施步骤

#### 步骤 1：批次启动确认

输出当前批次摘要，等用户确认。若当前层有可并行批次，一并列出：

```text
🔨 批次 {N}/{总计}：{批次名称} [串行]

本批次包含：
  - {子需求编号}：{名称}（{M} 条）
依赖条件：{已完成的批次 / 无}

━━━ 同层可并行 ━━━（可选，同层无并行批次则不显示）
  📎 B{X}：{名称}（{K} 条）[可并行] — 可同时实施

确认开始实施本批次？[Y/n]
```

#### 步骤 2：逐条实施

按 checklist 中本批次的条目顺序逐条实现，每完成一条打 `[x]`。

实施过程中若发现设计问题（如接口签名不合理、数据模型遗漏），**暂停实施**，回到 design-craft 修订设计文档，修订后重新生成受影响的批次 checklist。

#### 步骤 3：批次内自检

本批次所有条目打勾后，执行批次自检：

```text
🔍 批次 {N} 自检

☐ 本批次所有 {M} 条 checkbox 已勾选
☐ 接口签名与设计文档完全一致
☐ 数据模型字段与设计文档完全一致
☐ 异常处理覆盖设计文档要求的全部场景
☐ 未擅自添加设计文档未要求的内容
☐ 本批次新增/修改的文件路径与设计文档一致

自检结果：✅ 通过 / ❌ 未通过（列出未通过项）
```

#### 步骤 4：设计文档交叉验证

自检通过后，回到设计文档，逐章核对本批次涉及的章节：

- 本批次的接口签名 → 对应设计文档接口设计章
- 本批次的数据模型 → 对应设计文档数据模型章
- 本批次的异常处理 → 对应设计文档异常处理章

交叉验证不是重新读取 checklist，而是直接对照设计文档原文。

```text
📐 批次 {N} 设计文档交叉验证

验证范围：§ S-{XX} 接口设计 / § S-{XX} 数据模型 / § S-{XX} 异常处理

逐项核对结果：
  ✅ 接口 `POST /api/xxx`：签名一致
  ✅ 字段 `yyy`：类型、默认值一致
  ⚠️ 异常 `zzz`：实现中额外增加了设计文档未要求的异常类型 → 需确认

交叉验证结果：✅ 一致 / ⚠️ 存在偏差（列出偏差项）
```

#### 步骤 5：批次完成标记

交叉验证通过后，将批次文件头部状态更新为已完成，并同步 README.md 中的状态：

批次文件 `B{N}.md` 头部：
```markdown
# 批次 {N}：{批次名称}

> 状态：✅ 已完成（{日期}）
```

README.md 批次总览表：
```markdown
| B{N} | [B{N}_{名称}.md](B{N}_{名称}.md) | ... | ... | ... | ✅ 已完成 |
```

然后输出批次完成摘要：

```text
✅ 批次 {N} 完成 [串行]

实施条目：{M} 条 / {M} 条
新增文件：X 个
修改文件：Y 个
偏差记录：无 / {偏差列表}

━━ 同层状态 ━━
  同层并行批次：B{X}（⏳ 待实施 / ✅ 已完成）
  → {全部完成，可进入下一层 / 等待同层批次完成}

是否继续？[Y/n]
```

当同一层所有批次（含并行批次）全部完成后，才提示进入下一层。

### 全部批次完成

```text
🎉 全部 {N} 个批次实施完成

总计实施条目：{总计} 条
批次 1：✅（{日期}）
批次 2：✅（{日期}）
...
偏差记录：无 / {汇总偏差列表}

下一步建议：
  - 使用 `implementation-report` skill 归档实现结果
  - 若存在偏差，评估是否需要回写设计文档
```

### 中断与恢复

- **中断**：用户可随时暂停，已完成批次的文件头部状态为 `✅ 已完成`
- **恢复**：读取 `checklist/README.md`，找到批次总览表中第一个状态为 `⏳ 待实施` 的批次文件，从该文件继续
- **回退**：若后续批次发现前序批次问题，将对应批次文件状态回退为 `⏳ 待实施`，修复后重新验证该批次及所有受影响的后序批次

## 反模式（不要做）

### 提取层面
- ❌ 将设计文档的"决策理由"、"备选方案"、"AS-IS 描述"当作实施项提取
- ❌ 笼统概括为"实现 xx 模块"而不拆解到文件/接口/字段级
- ❌ 自行添加设计文档中未要求的"最佳实践"条目（如"记得写日志"、"加单元测试"）
- ❌ 修改设计文档中的接口签名或数据模型定义——checklist 必须原样复制

### 排序层面
- ❌ 忽略子需求依赖关系，随意排列条目顺序
- ❌ 将依赖被依赖项之后的条目提到前面

### 使用层面
- ❌ 编码时不看 checklist 直接凭记忆写代码
- ❌ 批量打勾不经验证——必须确实实现了才打 `[x]`
- ❌ 编码过程中自行修改接口签名却不回写设计文档——发现设计问题应回到 design-craft 修订
- ❌ 子需求 ≥ 3 个时一口气实现所有批次——上下文过长，AI 必然偏离设计意图
- ❌ 跳过批次自检或交叉验证直接进入下一批次——偏差会逐批累积，最终不可控
- ❌ 带着已知偏差进入下一批次——先修复，验证通过后再继续
