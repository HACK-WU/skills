# 验收示例（acceptance-verify）

## 示例 1：首次验收「用户登录模块」（三层证据齐全）

### 阶段 0 · 对象与基线

- 验收对象：`src/auth/`（登录、登出、token 签发与校验），依赖 Redis（会话）
- 代码基线：`feature/auth` @ `a1b2c3d`（完整 `a1b2c3d4e5f6...`）｜commit「feat(auth): 实现登录与 token 签发」｜工作区 ✅ 干净
- 关联需求：REQ-012《用户登录》

### 阶段 1 · 核心目标与指标（AI 推导）

**核心目标**：用户能安全、顺畅地完成登录，并在后续请求中持续保持身份。

| 指标 ID | 类型 | 指标描述 | 判据 | 层 |
|---------|------|---------|------|----|
| M-01 | 🎯 | 正确凭证可登录 | 返回 200 + token，Redis 中存在会话 | L1 |
| M-02 | 🎯 | 错误凭证被拒绝 | 返回 401，且不签发 token | L1 |
| M-03 | 🧱 | 边界与非法输入可控 | 空密码/超长用户名/非字符串类型 → 400 且消息含字段名 | L2 |
| M-04 | 💎 | 登录失败时反馈友好 | 错误提示含【问题+原因+建议操作】，无技术黑话 | L2 |
| M-05 | 🌐 | 完整登录旅程可用 | 注册→登录→访问受保护资源→登出→再访问被拒 | L3 |
| M-06 | 🔗 | token 校验契约成立 | 过期/篡改 token 均返回 401，不泄露原因细节 | L2 |
| M-07 | 📊 | 并发登录安全 | 同一账号 10 并发登录，会话数 == 1（或按设计上限） | L2 |

### 阶段 2 · 用户确认

用户确认通过，M-01 / M-02 / M-05 标 🔴 必达，其余 🟡。**指标锁定。**

### 阶段 3-4 · 执行

**L1**：扫描得 `tests/test_auth.py`（pytest）。映射到 M-01（`test_login_success`）、M-02（`test_login_wrong_password`）→ 执行，2 条 PASS。

**L2**：新建场景脚本 3 条
- `acceptance-M03-20260909-1030.py`（边界输入，进正式套件 `tests/test_auth_boundary.py`——核心不变量）
- `acceptance-M04-20260909-1042.py`（错误提示文案走查，临时——依赖本次文案快照）
- `acceptance-M06-M07-20260909-1105.py`（token 校验 + 并发，进正式套件）

M-04 走查发现：错误提示原文为 `"auth failed: InvalidCredentials"` → **只有问题，无原因无建议，且是技术黑话** → ❌。观察记录落到 `scenario-records/2026-09-09-login-error-feedback.md`。

**L3**：调用 `e2e-testing`，传入 M-05（旅程：注册→登录→访问受保护资源→登出→再访问）。
journey 全 PASS → 映射回 M-05 ✅。

### 阶段 5-6 · 结论（节选）

```markdown
## 验收结论
⚠️ 有条件通过

- 指标总数：7　✅ 达成 5　🟡 部分 1　❌ 未达成 1　⚪ 未验证 0
- 🔴 必达指标：3 条，达成 3 条

## 未通过指标明细
### [M-04] 登录失败时反馈友好
- 判据：错误提示含【问题+原因+建议操作】，无技术黑话
- 实际：返回 `"auth failed: InvalidCredentials"`
- 证据：scenario-records/2026-09-09-login-error-feedback.md
- 影响：用户看到技术黑话，不知道是自己输错还是账号被锁，只能反复重试或放弃
- 建议：改为「密码错误，还可尝试 4 次；连续 5 次失败将锁定 10 分钟」——问题+原因+建议三要素齐全
```

> **注意**：报告到此为止，**不修改 `src/auth/` 的任何一行**。M-04 记为 ❌，建议转 `code-review` / 修复后复验。

## 示例 2：二次验收「订单导出功能」（复验 · 只看终态）

### 背景

`.requirements/acceptance/order-export/` 已存在：
- `metrics.md`：round-1 锁定 6 条指标，其中 M-02（导出 10 万行内存峰值 < 500MB）❌、M-05（导出失败后提示与重试）🟡
- `reports/round-1-2026-09-05.md`

用户：`order-export` 修复过了，**再验收一次**。

### 执行（复验特有动作）

| 步骤 | 本例实际 |
|------|---------|
| 读 `metrics.md` | 沿用 6 条指标，**不重新推导、不改判据** |
| 读上轮报告 | 只看"M-02 ❌、M-05 🟡"，**不看中间 3 个提交改了什么** |
| 重新采集基线 | `main` @ `d4e5f6g`（上轮 `main@9z8y7x6`） |
| 轮次号 | round-2 |
| 重跑范围 | **全量 6 条**（不掌握中间改动，上轮 ✅ 的也可能被破坏） |

> ❌ 错误做法：`git diff 9z8y7x6..d4e5f6g` 看看改了啥，然后只测改动点。这是 `code-review` 的视角，不是验收。

### 轮次对比（只比结果）

### 关键观察

- **M-04 是本轮最重要发现**：上轮 ✅，本轮 🟡。若复验只跑上轮失败项（M-02/M-05），这个回归会被完全漏掉——这正是「复验必须全量重跑」的理由。
- **M-05 连续两轮 🟡** → 报告标注「需重新评估方案」并提示用户，不再机械复验第三轮。
- **M-06 连续两轮 ⚪** → 列入「需补验清单」，明确标注"未验证 ≠ 通过"。
