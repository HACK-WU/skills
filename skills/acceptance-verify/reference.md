本文是 [SKILL.md](SKILL.md) 的展开。流程与纪律以 SKILL.md 为准，本文只给执行细节与模板。

## 一、验收指标推导细则

### 1.1 六型指标推导提问清单

逐型过一遍。命中不足的，在指标表中显式写「本模块无此型指标」——**防止只推导出功能正确性**。

| 类型 | 推导时问自己 | 典型判据写法 |
|------|-------------|-------------|
| 🎯 功能达成 | 核心能力在标准输入下产出预期结果吗？ | "调用 `export()` 返回文件路径，文件内容行数 == 源数据行数" |
| 🌐 场景覆盖 | 真实使用中会走哪几条路径？都通吗？ | "首次使用 / 重复操作 / 中途取消 三条路径均能完成或正确回滚" |
| 🧱 边界异常 | 空值、超长、非法、并发、极端量级下如何？ | "输入 10 万行时内存峰值 < 500MB；非法参数返回 400 且消息含字段名" |
| 💎 体验质量 | 用户犯错时系统怎么说？反馈够不够？能自救吗？ | "错误提示包含【问题+原因+建议操作】三要素，不使用技术黑话" |
| 🔗 契约集成 | 对外接口/数据结构的承诺成立吗？耦合方还对得上吗？ | "响应 schema 与设计一致；订单服务消费该事件后状态机正确推进" |
| 📊 非功能 | 性能阈值、幂等、并发安全等**可测**项达标吗？ | "同一请求重复提交 3 次，只产生 1 条记录" |

### 1.2 判据写法（可判定性检查）

判定一条判据是否合格，看能否回答三问：

1. **谁来执行验证？**（跑哪条测试 / 走哪个场景）
2. **什么算达成？**（有明确阈值或可比对的事实）
3. **什么算未达成？**（存在可观测的反例）

| ❌ 不合格判据 | ✅ 改写后 |
|-------------|----------|
| 体验良好 | 错误提示包含【问题+原因+建议操作】三要素 |
| 性能达标 | 1 万行导出耗时 < 3s（单用户，本地环境） |
| 功能正常 | 正确凭证登录返回 200 + token；错误凭证返回 401 且消息含"密码错误" |
| 兼容旧版本 | 输入 v1 格式数据仍被正确解析，输出与 v2 输入一致 |

> 判据写不出来 → 说明对该指标的理解还不足，**不要硬写**。先回到需求/设计文档或代码确认，仍不确定则标 ⚪ 并在报告中说明。

### 1.3 指标来源优先级

1. **需求/设计文档的验收标准**（权威）
2. `test/test-plan.md`（`test-planner` 产出，已做过策略匹配，可直接取用）
3. 模块对外契约（接口签名、schema、事件定义）
4. 真实使用场景推导
5. 代码结构推导（兜底，置信度 🟡）

每条指标在表中标注来源。全部来自代码推导且无需求文档时，在报告顶部标注「指标来源：代码/场景推导，无需求文档，置信度 🟡」。

## 二、三层证据执行细节

### 2.1 L1 已有测试套件（基础）

**扫描方式**（不假设固定路径，同 `test-planner` 阶段 2.5）：

| 项目结构线索 | 判定 |
|-------------|------|
| 顶层 `tests/` 或 `test/` | 测试集中存放，按被测模块分文件 |
| 与源码同目录的 `test_*.py` / `*.test.ts` / `*_test.go` | 测试与代码同目录、镜像结构 |
| `src/` 下镜像的 `__tests__/` | 前端常见 |
| `pytest.ini` / `pyproject.toml` / `package.json` / `go.mod` 声明的测试路径 | 以配置声明为准 |

**执行要点**：

- 只跑**映射到指标**的测试，不跑全量套件（除非套件很小）
- 记录**全量结果**：通过 / 失败 / 跳过（skipped 常被忽略，却是覆盖缺口的信号）
- **只跑不改写**。已有测试失败时记录为「L1 基线异常」，按影响面定级；这不等同于验收不通过，但必须进报告
- 已有测试与指标判据口径不一致（测了但没测到判据）→ 该指标转 L2，不要假装被 L1 覆盖
- **「L1 已覆盖」判定从严**：必须是「该测试的断言确实覆盖了这个判据」。判据含边界值/错误文案/副作用时，只断言了返回码不算覆盖
- L1 覆盖且 PASS → 指标可标 ✅，不重复造轮子，但报告注明「证据来自 L1，未做场景级复验」
- 🌐 场景覆盖型 / 💎 体验质量型原则上不走 L1

### 2.2 L2 临时场景测试（重点）

**写法纪律**：

| 要点 | 说明 |
|------|------|
| **按真实使用路径写** | 一个脚本模拟"用户/调用方真正会怎么用"，不是逐个函数调用。如"导出订单"应走：登录 → 构造订单 → 调导出 → 读文件 → 校验内容，而非只调 `export()` |
| **断言锚定判据** | 写断言前先读指标判据。**先读实现再写断言 = 写成"一定能过"的断言，验收失效** |
| **数据构造自包含** | 场景应能独立跑（自带 setup / teardown），不依赖手工预置数据 |
| **失败信息要说人话** | 断言失败时能直接看出"哪个指标的哪条判据没达成" |

**落盘**：`.requirements/acceptance/{slug}/temp-tests/acceptance-{指标ID}-{YYYYMMDD-HHmm}.{ext}`

**进正式套件 vs 临时**：

| 判据 | 归属 |
|------|------|
| 三个月后这条断言还值得跑吗？ | 值得 → 进项目既有测试目录；不值得 → 临时 |
| 依赖一次性构造数据 / 特定环境状态？ | 是 → 临时 |
| 是核心不变量 / 对外契约 / 边界条件？ | 是 → 进套件 |

> ⚠️ **前置准入（先于上表判断）**：**只有通过的测试才进正式套件**。指标 ❌ 或 ⚪ 时，脚本一律落 `temp-tests/`——把失败测试固化进 CI，而本技能又不许改产品代码，结果是 CI 长期红灯且无人有权修。
>
> **项目无既有测试目录时**：按项目类型给默认位置并标注「新建测试目录」（库/SDK → `tests/`；Web → `src/**/__tests__/`；CLI / 插件 → `tests/`），判断方式同 `test-planner` 阶段 2.5；不强行断言，落地时由实施方按团队约定调整。

### 2.3 L3 e2e 测试（重点）—— 调用 `e2e-testing`

**一律调用 `use_skill("e2e-testing")`，不自行实现。** 其环境准备、凭证注入（`.env.e2e` 优先、回退 `.env`）、`tests/e2e/` 隔离、teardown、安全门禁全部适用，本技能不重复定义。

**传入内容**：

```markdown
- requirement_ref：REQ-NNN（无需求时用 acceptance slug，如 `acceptance/order-export`）
- 待验指标（仅分配到 L3 的）：
  | 指标 ID | 类型 | 描述 | 判据 | 需要的终态 |
  |---------|------|------|------|-----------|
  | M-03 | 🌐 | 注册→登录→访问受保护资源 | 全程无需重新登录，最终返回 200 | 受保护资源可访问 |
- 业务旅程描述：<自然语言描述>
- 环境：<目标环境名>；凭证来源：.env.e2e / .env
```

**回收与映射（不可省）**：

e2e 的 step 与验收的指标**不是一一对应**，必须做映射后才能作为验收证据：

```markdown
| 指标 ID | e2e step | step 结果 | 映射到指标的状态 |
|---------|----------|----------|-----------------|
| M-03 | register → login → access | 全 PASS | ✅ 达成 |
| M-06 | db_check（order 落库） | ❌ 未收到事件 | ❌ 未达成 |
```

> 禁止把 journey 报告直接当作验收结论——step 全 PASS 只说明旅程跑通，不说明每条指标达成。

**失败处理**：先判断是否环境/数据/时序问题（e2e 编排配置问题自行修正）。疑似服务逻辑问题且根因不明 → 调用 `use_skill("debug")` 定位。**本技能只判定"指标是否达成"，不负责定位"服务为什么失败"，更不修产品代码**。

### 2.4 场景观察记录（💎 体验类指标的证据）

体验类结论不能凭感觉，必须有 `scenario-records/` 里的观察记录支撑。

**模板**（`.requirements/acceptance/{slug}/scenario-records/{YYYY-MM-DD}-{场景slug}.md`）：

```markdown
# 场景观察：{场景名}

- 指标 ID：M-0X
- 判据：<该指标的判据原文>
- 代码基线：`{branch}@{short_hash}`　时间：<执行时间>

## 操作序列
1. <做了什么>
2. <做了什么>

## 实际观察
- 返回/提示：<原文照抄，不加工>
- 耗时：<如有>
- 界面/日志反馈：<原文>

## 负面路径（故意犯错）
| 错误操作 | 系统反馈原文 | 是否含【问题+原因+建议】 | 能否自救 |
|---------|-------------|----------------------|---------|
| <操作> | <原文> | 是/否 | 能/否 |

## 对照判据的结论
- 达成情况：✅ / 🟡 / ❌
- 缺口：<具体描述，引用上面的观察原文>
```

## 三、代码基线采集

```bash
git rev-parse --abbrev-ref HEAD                  # 分支名
git log -1 --format='%H|%h|%s|%ci|%an'           # 完整hash|短hash|标题|时间|作者
git status --porcelain                            # 非空 = 工作区 dirty
git status --porcelain | wc -l                    # dirty 文件数
```

**报告必录三要素**：分支名、commit（短 hash + 完整 hash + 标题）、是否 dirty。

| 情况 | 处理 |
|------|------|
| 工作区干净 | 正常记录 `✅ 干净` |
| 工作区有未提交改动 | **不阻断**，报告标注 `⚠️ 存在 N 个未提交文件`。commit 锚点仍记录，但读者需知实际验证的代码可能与之不同 |
| 验收执行期间 HEAD 变化 | **停止、重新采集基线**，报告中标注原基线与实际执行基线。禁止顶着旧 commit 出结论 |
| 不在 git 仓库 / 无 git | 标注 `[无 git 上下文]`，用验收时间 + 模块 checksum 替代，并在报告中说明不可复现 |

## 四、「只判定不修改」的执行边界

验收是**判定动作，不是修复动作**。

### 4.1 允许写

| 类别 | 说明 |
|------|------|
| 单元测试 | 作为证据工具；有长期回归价值的进项目既有测试目录 |
| e2e 测试 | 作为证据工具；落在 `tests/e2e/`（遵 `e2e-testing`） |
| 临时场景脚本 | 落在 `acceptance/temp-tests/` |
| 验收文档 | 报告、指标清单、观察记录 |

### 4.2 禁止改

产品代码、配置、依赖声明、数据迁移、构建脚本、既有测试的断言语义。

### 4.3 例外处理

- **既有测试失败**（L1 基线异常）：记录 + 定级 + 建议方向，**不改测试迁就实现，也不改实现迁就测试**
- **发现产品缺陷**：记入报告「未通过指标明细」，翻译成功能影响，建议转 `debug`（定位）/ `code-review`（审查），**不在验收中修复**
- **跑不通想改一行让测试过**：禁止。改了就同时破坏了两件事——报告锚定的 commit 与实际验证的代码不一致；且这次修改本身未经 review

> 唯一能"改"的是**验收文档与验证脚本本身**。

## 五、二次验收（复验）执行清单

```
[0] 确认 slug 与已有目录匹配（避免 user-login / user-login-v2 把历史拆断）
[1] 读 .requirements/acceptance/{slug}/metrics.md —— 沿用指标，不重新推导
[2] 读上一轮报告 —— 只看"哪些未达标"，不看修复过程
[3] 重新采集代码基线（分支 + commit + dirty）
[4] 判定本轮轮次号 N = 已有轮次数 + 1
[5] L3 前置确认：环境可重复使用 + 上轮 teardown 已清理；成本过高时按风险分层并标注"抽样复验"
[6] 全量重跑指标（默认；不掌握中间改动，无法假设上轮 ✅ 仍成立）
[7] 产出 round-{N}-{date}.md，必含「轮次对比」区
[8] 更新 metrics.md 的「历史未达标」区
[9] 发现回归（上轮 ✅ → 本轮 ❌/🟡）：只记录事实 + 建议转 debug/code-review，不做归因
```

**禁止动作**：

| 禁止 | 原因 |
|------|------|
| `git diff <上轮commit>..HEAD` 看改了什么 | 退回 diff 视角，把"那个点修好了"当验收结论 |
| 读中间 commit 的 message / 变更 | 同上 |
| 只重跑上轮 ❌/🟡 的指标 | 上轮 ✅ 的可能已被破坏；除非用户明确要求且报告标注风险 |
| 修改历史轮的指标定义或判据 | 上轮 ❌ 会因判据放松而"变成" ✅，历史失去可比性 |
| 修改产品代码让验收通过 | 违反「只判定不修改」铁律 |

**追加指标**：本轮可新增指标（如复验时发现遗漏），新增项在「轮次对比」中状态记为 `—` → 新状态，并在报告中说明新增原因。**已有指标的定义与判据一律不动**。

**收敛判据**：

- 全部 🔴 必达指标 ✅ 且无 ❌ → ✅ 通过，可停止复验
- 同一指标连续两轮 ❌/🟡 → 报告标注「需重新评估方案」并提示用户，不再机械复验

## 六、metrics.md 模板

```markdown
# 验收指标基准：{功能/模块名}

- slug：`{slug}`
- 核心目标：<一句话>
- 首次锁定：round-1（{date}）　当前轮次：round-{N}
- 指标来源：需求 REQ-NNN / 设计文档 / 代码推导

## 验收指标

| 指标 ID | 类型 | 指标描述 | 判据 | 证据层 | 必达 | 加入轮次 |
|---------|------|---------|------|--------|------|---------|
| M-01 | 🎯 | <描述> | <判据> | L1 | 🔴 | round-1 |
| M-02 | 💎 | <描述> | <判据> | L2 | 🟡 | round-1 |
| M-07 | 🌐 | <描述> | <判据> | L3 | 🔴 | round-2（复验时追加） |

## 历史未达标

| 轮次 | 指标 ID | 状态 | 缺口摘要 | 本轮是否已解决 |
|------|---------|------|---------|---------------|
| round-1 | M-02 | ❌ | 错误提示仅有"失败"，无原因与建议 | round-2：✅ 已解决 |
| round-1 | M-04 | ⚪ | 环境不可用，未验证 | round-2：仍 ⚪ |
```

> `metrics.md` 是**跨轮基准**，只追加不改写。历史轮的指标定义与判据一旦锁定即冻结。

## 七、环境准备（第三方组件）

验收常依赖 Redis / MySQL / MQ / 对象存储等第三方组件。按**固定优先级**获取，命中即停——不要跳级，也不要图省事直接改代码绕开依赖（那违反「只判定不修改」）。

### 7.1 四级优先级

| # | 方式 | 触发条件 | 关键约定 |
|---|------|---------|---------|
| 1 | **复用现成实例** | 本地已装 / 项目 dev 环境 / 已有容器在跑 | 最省事。须过 7.2 检查清单 |
| 2 | **Docker 起容器** | 无现成实例，但 docker 可用 | **首选**。见 7.3 容器约定 |
| 3 | **安装 docker 后回到 ②** | 无现成实例且 docker 不可用，**仅 Linux** | 见 7.4 |
| 4 | **安装组件本体** | 以上均不可行 | 最后手段。见 7.4 |

### 7.2 复用现成实例的检查清单（三级全过才可用）

| 检查项 | 不通过时 |
|--------|---------|
| **可连接**：能 ping / 建连 / 执行一条最简命令 | 转 ② |
| **版本匹配**：与项目声明的版本一致（`docker inspect` / `redis-server -v` / `SELECT VERSION()`） | 版本不一致 → **转 ②**（用 docker 起指定版本），不要将就 |
| **非生产**：确认不是生产实例 | 指向生产 → **强告警 + 必须用户显式确认**；默认拒绝并优先起容器 |

> 现成实例的**凭证**同样走 env 文件，不得写入验收文档。

### 7.3 Docker 容器约定（优先级 ②）

```bash
# 1) 先看已有容器，能复用就复用（回到优先级 ①）
docker ps -a --format '{{.Names}}\t{{.Image}}\t{{.Ports}}\t{{.Status}}'

# 2) 起一次性容器（版本与项目声明一致）
docker run -d --name acc-{组件}-{slug} -p {宿主端口}:{容器端口} {镜像}:{版本}
# 例：docker run -d --name acc-redis-order-export -p 6379:6379 redis:7-alpine
# 例：docker run -d --name acc-mysql-order-export -p 3306:3306 \
#       -e MYSQL_ROOT_PASSWORD="$MYSQL_PWD" -e MYSQL_DATABASE=acc_test mysql:8

# 3) 确认就绪
docker exec acc-{组件}-{slug} redis-cli ping        # Redis
docker logs acc-{组件}-{slug}                        # 看启动日志

# 4) 验收结束清理（对齐 e2e-testing 的 teardown 约定）
docker rm -f acc-{组件}-{slug}
```

**约定**：
- 容器名统一 `acc-{组件}-{slug}` 前缀——一眼可辨是验收产物，便于批量清理，不会误删业务容器
- 端口优先用非默认端口或确认无冲突，避免顶掉本地已有服务
- **容器是验收副作用**：必须在报告中列入「副作用清单」，并在收尾时清理（用户要求保留以便复验时可保留，但须标注）
- 清理失败或忘记清理 → 在报告中显式提示，不静默略过

### 7.4 安装（优先级 ③④）与平台规则

| 平台 | 无 docker 时 AI 的行为 |
|------|----------------------|
| **Linux** | 可安装 docker 后回到 ②。**须先告知用户**（安装改变机器状态）：<br>`curl -fsSL https://get.docker.com \| sh` 或发行版包管理器 → `sudo systemctl start docker` → 验证 `docker version` |
| **Windows** | **禁止 AI 自行安装**。需 GUI 交互 / 管理员权限 / 可能的重启，AI 无法可靠完成 → 见下方话术 |
| **macOS 及其他** | 用户未指定，默认按 **Windows 规则**处理（由用户安装），除非用户另有说明 |

**Windows 提示话术**（AI 输出后暂停等待）：

```markdown
⚠️ 验收需要 {组件}，当前环境不可用且未安装 Docker。

请二选一后继续：
1. 安装 Docker Desktop（推荐）— https://www.docker.com/products/docker-desktop/
   装好后告诉我，我用容器起 {组件} 继续验收
2. 直接安装 {组件} Windows 版，并提供连接信息（host/port/账号；密码请放 .env.e2e）

在你完成前，依赖该组件的指标将标记为 ⚪ 未验证，并列入「需补验清单」。
```

### 7.5 组件始终不可用时

- 依赖它的指标 → `⚪ 未验证（环境不可用）`，**不降级为通过**，列入报告「需补验清单」并写明补验方式
- 若该组件可用**内存替代实现**模拟（如 fakeredis、sqlite 内存库）→ 可降级为 L2 模拟验证，但**必须在报告中标注「模拟环境，非真实组件」**，结论置信度降级
- 不得为了跑通而修改产品代码的连接配置（违反铁律）

### 7.6 与相邻约定的关系

| 约定 | 关系 |
|------|------|
| 「只判定不修改」铁律 | **不冲突**——该铁律约束的是**产品代码**；起容器、装 docker 属环境准备 |
| `e2e-testing` 敏感信息外部化 | 沿用：凭证走 `.env.e2e`（回退 `.env`），容器密码也用 `${ENV.XXX}` 注入，不写进验收文档或脚本 |
| `e2e-testing` teardown | 对齐：验收起的容器纳入 teardown 清理范围 |
| 副作用清单 | 容器、创建的库/表、写入的测试数据一并列入报告「副作用清单」 |
