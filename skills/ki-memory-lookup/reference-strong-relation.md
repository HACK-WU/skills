# 强关联查询策略参考

ki-memory-lookup 的「强关联」查询策略细则。主流程见 SKILL.md。写入方为 `ki-memory-write`（强关联策略，由 strong-relation 调用）。

## ki 检索 API

| API | 用途 | 关键参数 |
|-----|------|----------|
| `ki_search` | 语义检索强关联记录 | `scope`（项目标识）、`query`（自然语言 + 关键代码符号）、`tags`（固定 `relation`）、`limit`、`threshold` |
| `ki_query_group` | ① `subtree` 列子 Group 树 / ② `groups`+`mode="full"` 列某 Group 的全部 Relations | `scope`、**`subtree`**（子 Group 树，与 `groups` 互斥、不支持多值）、**`groups`**（Group 路径，支持逗号分隔多值）、**`mode`**（列 Relations 时必须 `"full"`）、`depth`（子树层级） |
| `ki_get_module_info` | 取 relation 的本地 KB 原文（**取多条用 `relations` 一次批量**） | `scope`、`group`（模糊匹配）、`relation`（**精确匹配**，从清单复制）/ `relations`（同 group 批量数组，**≤10 条**，与 `relation` 二选一） |
| `ki_manage_index_list` | 列出 scope 及**顶层** Group | - |
| `ki_tag_list` | 列出 scope 下已用 tag（辅助确认 relation tag） | `scope` |

> `ki_manage_index_list` **只输出顶层 Group**，看不到第二层（如 `关联关系/订单服务`）——定位模块子分组请用 `subtree`。

## 分组与 tags 约定（查询侧）

- **scope**：项目标识，与写入时一致
- **group**：`关联关系/{功能模块名}`（写入侧统一父分组「关联关系」+ 动态子分组）
- **tags**：写入侧统一为 `relation`，故查询侧固定用 `tags="relation"` 过滤

## 检索方式

### 首选：精确列举（目录优先）

强关联**漏一条 = 漏改一个模块**——语义检索的召回遗漏会直接转化为漏改风险。故用 `ki_query_group` 确定性穷举（调用示例见「检索示例」节）。

> ⚠️ **必须显式 `mode="full"`**：`ki_query_group` 默认 `mode="hot"` + `hot_count=5`，**只返回最热的 5 条 relation**——比语义检索漏得更多，且**不报错**（`auto_fallback` 会静默语义兜底，掩盖"少给了"这件事）。

**先定位 group 路径——用 `subtree` 两级导航**（不要猜模块名）：`groups` 支持模糊匹配，写错**不报错**（`auto_fallback` 静默走语义兜底，返回不相关内容却看似正常）；且**代码模块名与 ki 功能模块名常不一致**（如代码目录 `order-service` vs group `关联关系/订单服务`）。故：

| 级 | 调用 | 作用 |
|----|------|------|
| 1 | `ki_query_group(subtree="关联关系")` | 列出「关联关系」下**所有模块子分组**（不受 5 条限制、不需 `mode="full"`） |
| 2 | `ki_query_group(groups="关联关系/{模块名}", mode="full")` | 列出该模块的**全部强关联条目** |

> **为何不用 `ki_manage_index_list`**：它只输出**顶层 Group**（如 `关联关系`），**看不到第二层**（`关联关系/订单服务`），无法用于确认模块子分组名。
>
> **`subtree` 两个陷阱**（实测）：
> 1. **不支持逗号分隔多值**——传多值会被当整体模糊匹配，可能静默匹配到完全不相关的 group（score 极低仍不报错）。**一次只传一个路径**
> 2. **近似匹配会跑偏**——匹配不到时返回低分近似结果，**核对返回头部的 💡 提示行**确认实际解析出的路径
>
> **子分组很多时别靠肉眼认**：先 `subtree="关联关系"` 看全貌；若列表长，改用 `subtree="{模糊模块名}"` 让 ki **模糊匹配自动补全**（实测有效：`subtree="缓存"` → 💡 补全为 `基础设施/缓存`），再核对提示行确认补全结果。
>
> **已知确切 group 路径时可跳过第 1 级**（如同一次会话内刚列过该模块），直接走第 2 级。默认仍建议走两级——AI 容易"以为自己知道"模块名，而代码模块名与 ki 模块名常不一致。
>
> 两级都取不到 → 回退语义检索（**此兜底仅适用无变更上下文**；有 diff 时语义路是**并行发起**的，不存在"两级都取不到才退"的顺序，见下节）。

**拿到清单后，避免过度调用**：

1. 先列清单——relation 名 = `{模块A}-{模块B}`，一眼看出牵动谁
2. 清单信息已够判断 → 不必再取；不够 → `ki_get_module_info` 取原文（`group` 模糊匹配、**名称从清单复制**）
   - **取多条用 `relations: [...]` 一次提交**（同 group ≤10 条，超 10 条按批切分），不要循环单条调用

**取多少条看有无「变更上下文」**（规则 SSOT 在 SKILL.md 核心原则 3，此处给强关联的落地口径）：

- **无变更上下文**（改前评估 / 点查 / 设计——只知模块名，不知改哪）→ **全取，不许挑着看**：relation 名只含两端模块名、**不含强度与方向**，无法据此判断"必改"还是"可选"——挑着看恰恰会漏掉最该看的那条。数量有限（一个模块几条到十几条），全量取成本可接受
- **有变更上下文**（`code-review` / `bug-impact-analysis`——手上有**完整** diff）→ **双路并行**：A 筛候选（目标 **≤5 条**）+ B **同时** `ki_search` 语义检索，**取并集**核对
  - **A 路筛的是"另一端"，不是"被改模块"**：group 已是 `关联关系/{被改模块}`，**组内每条都涉及被改模块**——按它筛一条都筛不掉。按 SKILL.md 的三级筛子筛**另一端**是否落在本次改动触及的模块 / 符号 / 调用链内；强度/方向仍要取回原文按 `module_info` 核对
  - **筛不动就全取**：单模块改动、耦合方全在外部时三级筛子可能全失效，此时"挑 5 条"= 随机挑 5 条 → **≤5 是筛得动时的目标，不是硬配额**
  - **B 路命中的条目即使不在 A 的候选里也纳入核对**——别名 / ki 功能模块名与代码模块名不一致 / 耦合未写进 relation 名，这些只有语义路能捞回来
  - ⚠️ **任一路为"空"都要警惕**（不只是"合计 0 命中"）：B 空 → **改写 query 重试一次**，仍空则退回全取；A 空而 B 有 → 用 B 的结果并回看 A 的筛选条件是否写歪
  - ⚠️ **改动涉及对外契约 / 公共 API / 数据 schema / 权限 / 资金 / 持久化 → 直接全取**：漏一条的代价远高于多取几条
  - **候选 ≤5 条 → 直接全取**（成本等价）；**多模块改动 → A 路按 group 分组调用，各组独立筛后合并取并集**
  - ⚠️ **判据是"手上有无 diff"，不是 skill 名**：`code-review` / `bug-impact-analysis` 通常有 diff → 双路；`request-guard` 常常只有一句口头提议、**无 diff**，`bug-impact-analysis` 在「只有 Bug 描述、还没修复代码」时也**无 diff** → 这两种走**全取**

> **「全取」= 用 `relations` 一次提交清单里的全部条目**，不是逐条循环。一个模块超过 10 条时按 10 条/批切分，分批不是挑。

### 语义检索（`ki_search`）：兜底 或 并行补位

`ki_search` 在强关联策略里有**两种角色**，用错角色会退化成"漏了才想起来查"：

| 角色 | 适用 | 时机 |
|------|------|------|
| **兜底** | 无变更上下文 | 仅在**不确定该查哪个 group**（只知道代码符号、不知模块名）或精确列举为空时 |
| **并行补位** | 有变更上下文（`code-review` 等） | **与目录路同时发起**，不等目录路失败——它就是筛选路缺的那半边召回 |

- 查"改某模块要连带改什么"：`ki_search(query="改 {模块A} 要连带改什么 {关键类名}")`
- **并行补位模式的 query 必须带本次改动上下文**：`ki_search(query="{被改模块} {本次改动的关键符号} 牵动 联动")`，带上 diff 里的符号才能捞到按名筛选漏掉的条目
- **tags 固定 `relation`**；过滤后命中过少/为空 → 去掉 tags 扩大召回

## 检索示例

```text
# 首选：两级导航
# 第 1 级——列出「关联关系」下有哪些模块子分组（不需 mode=full，不受 5 条限制）
ki_query_group
  scope:   my-project
  subtree: 关联关系

# 第 2 级——列出该模块的全部强关联条目（注意 mode=full，否则默认只返回 5 条）
ki_query_group
  scope:  my-project
  groups: 关联关系/支付系统
  mode:   full

# 取单条原文（relation 名从上面清单复制，精确匹配）
ki_get_module_info
  scope:    my-project
  group:    关联关系/支付系统
  relation: 订单服务-支付通知服务

# 批量取原文（同 group，≤10 条——全取、或筛出的候选，都走这个）
ki_get_module_info
  scope:     my-project
  group:     关联关系/支付系统
  relations: [订单服务-支付通知服务, 支付系统-对账服务, 支付系统-风控服务]

# 语义检索：无变更上下文时作兜底（带关键代码符号）
ki_search
  scope:  my-project
  query:  改 订单服务 要连带改什么 OrderService
  tags:   relation
  limit:  10

# ── 有变更上下文（如 code-review）：A/B 两路并行，取并集 ──
# A 路：筛「另一端」（假设该模块共 12 条强关联）
#       本次 diff 改的是退款入口，且其调用链触及对账、风控两个下游
#       → 这 3 条的「另一端」落在本次改动范围内，余下 9 条无关 → 挑 3 条即可
#       （不硬凑 5 条；若筛不动则全取，12 条超过 relations 上限要分 2 批）
ki_get_module_info
  scope:     my-project
  group:     关联关系/支付系统
  relations: [支付系统-退款服务, 支付系统-对账服务, 支付系统-风控服务]

# B 路：与 A 同时发起（带本次改动的关键符号，捞按名筛选漏掉的关联）
ki_search
  scope:  my-project
  query:  支付系统 RefundService 退款 牵动 联动 消费端
  tags:   relation
  limit:  10
```

## 检索技巧

1. **先列后取**：先 `mode="full"` 精确列举拿到清单；语义路**是否并行发起**取决于有无变更上下文（无 → 不依赖语义，仅作兜底；有 → 与目录路同时跑）
2. **无上下文必须全取**：relation 名不含强度/方向，无法据此筛选，无变更上下文时必须全量取后按 `module_info` 标注的方向/强度逐条核对；全量取用 `relations` 批量提交（≤10 条/批），不要循环单条取
3. **有上下文走双路**：手上有完整 diff 时筛**另一端**（≤5 条，非硬配额）+ **同时**跑 `ki_search`，取并集——**两路一起走，不是先 A 后 B**；筛不动或改动涉及对外契约/schema/权限/资金/持久化 → 直接全取
4. **query 带符号**：走 `ki_search` 时，关键代码符号（类名/方法名/接口名）是写入 `module_info` 时的定位依据，带上能显著提高命中准确度；并行补位模式下还要带上**本次改动的关键符号**
5. **tags 回退**：固定 `tags="relation"` 过滤后若命中过少/为空（如历史存量数据未带 tag），去掉 tags 过滤扩大召回
6. **结果以代码为准**：命中的强关联记录属辅助参考，与代码实际不符时以代码为准

## 利用结果（牵动识别）

- **牵动识别**：拿到强关联记录后，对**取回的每一条**按标注的**方向/影响线**逐条核对——改到某条影响线的**左端（改动源）**时，务必检查其**右端（被影响方）**是否同步修改或需覆盖；**双向关联**（记录含两条影响线、两端互为源目标）时，改任一端都要核对另一端的影响线，不得漏检反方向
- **方向以记录为准**：方向/强度以写入的 `module_info` 标注为准，不凭"消费端/生产端"自行推断不对称；记录标注双向就按双向处理，标注单向才按单向核对
