# 决策记忆查询策略参考

ki-memory-lookup 的「决策记忆」查询策略细则。主流程见 SKILL.md。写入方为 `ki-memory-write`（决策记忆策略，由 `expert-team` Step 8.6 调用）。

## 定位

决策记忆 = **"当初为什么这么定、砍掉的备选是什么"** 的持久化记录。查询它用于回答其余五类记忆答不了的问题——**为什么**（其余五类答"是什么 / 在哪 / 怎么流 / 和谁耦合 / 怎么解"）。

**与 GitNexus 的分工**：GitNexus 答"代码现在长什么样"，决策记忆答"当初为什么这样"。两者叠加才是完整的影响分析——只知现状不知成因，改代码时无法判断"这个选择是否该被推翻"。

## 检索 API

| API | 用途 | 关键参数 |
|-----|------|----------|
| `ki_search` | 语义检索决策记录 | `scope`（项目标识）、`query`（决策主题 / 技术选型关键词 / 模块名）、`tags`（固定 `decision`） |
| `ki_query_group` | ① `subtree` 列子 Group 树 / ② `groups`+`mode="full"` 列某模块的全部决策 | `scope`、**`subtree`**（子 Group 树，与 `groups` 互斥、不支持多值）、**`groups`**（Group 路径）、**`mode`**（列 Relations 时必须 `"full"`） |
| `ki_get_module_info` | 取 relation 的本地 KB 原文（**取多条用 `relations` 一次批量**） | `scope`、`group`（模糊匹配）、`relation`（**精确匹配**，从清单复制）/ `relations`（同 group 批量数组，**≤10 条**，与 `relation` 二选一） |

- **scope**：项目标识，与写入时一致

## 检索方式

### 首选：精确列举（目录优先）

决策记忆数量有限（一个模块几条到十几条），用 `ki_query_group` 确定性穷举该模块全部决策，按 relation 名判断是否相关，再取内容——不存在语义召回遗漏（调用示例见「检索示例」节）。

> ⚠️ **必须显式 `mode="full"`**：`ki_query_group` 默认 `mode="hot"` + `hot_count=5`，**只返回最热的 5 条 relation**——比语义检索漏得更多，且**不报错**（`auto_fallback` 会静默语义兜底，掩盖"少给了"这件事）。

**先定位 group 路径——用 `subtree` 两级导航**（不要猜模块名）：`groups` 支持模糊匹配，写错不报错（`auto_fallback` 静默兜底返回不相关内容却看似正常）；且**代码模块名与 ki 功能模块名常不一致**（如代码目录 `order-service` vs group `决策记录/订单服务`）。故：

1. `ki_query_group(subtree="决策记录")` → 列出所有模块子分组（**不受 5 条限制、不需 `mode="full"`**）
2. `ki_query_group(groups="决策记录/{模块名}", mode="full")` → 列出该模块全部决策条目

> **为何不用 `ki_manage_index_list`**：它只输出**顶层 Group**，看不到第二层，无法确认模块子分组名。
> **`subtree` 两个陷阱**：① **不支持逗号分隔多值**（传多值会静默匹配到不相关 group）；② 近似匹配会跑偏，须核对返回头部的 💡 提示行。详见「强关联查询策略」中的同款说明。
>
> **子分组很多时别靠肉眼认**：可用 `subtree="{模糊模块名}"` 让 ki **模糊匹配自动补全**（实测有效：`subtree="缓存"` → 💡 补全为 `基础设施/缓存`），核对提示行确认补全结果。
>
> **已知确切 group 路径时可跳过第 1 级**（如同一次会话内刚列过该模块）。默认仍建议走两级——AI 容易"以为自己知道"模块名。
>
> 两级都取不到 → 回退语义检索（**此兜底仅适用点查 / 无变更上下文**；有 diff 时语义路是**并行发起**的，见下节）。

**拿到清单后，避免过度调用**：

1. 先列清单——relation 名 = `{分类}-{决策主题}`（如 `性能取舍-订单查询加缓存`），**分类前缀让清单一眼归拢**
2. **取原文**：用 `ki_get_module_info`（`group` 模糊匹配、**名称从清单复制**）
   - **取多条用 `relations: [...]` 一次提交**（同 group ≤10 条，超 10 条按批切分），不要循环单条调用

> **取多少条看有无「变更上下文」**（规则 SSOT 在 SKILL.md 核心原则 3，此处给决策记忆的落地口径）：
> - **点查场景**（"为什么这里用轮询"）→ **挑相关的看**：relation 名含**分类 + 决策主题**，信息量足以判断相关性
> - **无变更上下文的评审 / 设计场景** → **必须全看**：目的是判断"改动是否触及某条决策"，**事先不知道哪条相关**，挑着看会漏掉恰好被触及的那条
> - **有变更上下文的评审场景**（`code-review` / `bug-impact-analysis`，手上有 diff）→ **双路并行**：A 按 relation 名（`{分类}-{决策主题}`）筛候选（目标 **≤5 条**，**先看分类前缀**缩小范围）+ B **同时** `ki_search`（tags=`decision`）语义检索，**取并集**核对
>   - **A 路先按分类前缀筛，再按决策主题与改动面的重合度筛**（三级筛子见 SKILL.md）；**筛不动就全看**——决策主题里未必有代码符号，"挑 5 条"容易挑偏，**≤5 不是硬配额**
>   - ⚠️ **决策记忆的 A 路筛选力弱于强关联**：relation 名含的是**分类 + 决策主题**，**不含代码符号**；而决策约束的是**方案选择**（如"用轮询不用 webhook"），被改符号未必出现在主题里 → **两路权重接近，B 路不是配角**
>   - ⚠️ **任一路为"空"都要警惕**（不只是"合计 0 命中"）：B 空 → **改写 query 重试一次**，仍空则退回全看；A 空而 B 有 → 用 B 的结果并回看 A 的筛选条件
>   - **候选 ≤5 条 → 直接全看**（模块本身决策就几条时不必筛）；**改动涉及对外契约 / 公共 API / 数据 schema / 权限 / 资金 / 持久化 → 直接全看**
>   - ⚠️ **判据是"手上有无 diff"，不是 skill 名**：`code-review` / `bug-impact-analysis` 通常有 diff → 双路；`request-guard` 常常只有一句口头提议、**无 diff** → 走**全看**
>
> **与强关联的差异**：强关联在**无变更上下文**时同样全取，且 relation 名只有两端模块名（**不含强度/方向**），漏一条 = 漏改一个模块；有变更上下文时两类都走双路并行，但**决策记忆的按名筛选更弱**（主题里未必有代码符号），故更依赖 B 路。
>
> 若需按分类归拢：ki 侧**不支持按分类过滤**（分类是文本字段非 tag），取回清单后本地按 relation 前缀或 `module_info` 的「分类」字段分组。

### 语义检索（`ki_search`）：兜底 或 并行补位

`ki_search` 在决策记忆策略里有**两种角色**：

| 角色 | 适用 | 时机 |
|------|------|------|
| **兜底** | 点查 / 无变更上下文 | 仅在**不确定该查哪个 group**（不知模块名）、需跨模块检索、或按动机词检索时 |
| **并行补位** | 有变更上下文（`code-review` 等） | **与目录路同时发起**，不等目录路失败——决策主题里未必有被改符号，这半边召回主要靠它 |

- **按"为什么"检索**：`ki_search(query="为什么 {模块} 用 {方案A} 不用 {方案B}")`，如 `ki_search(query="为什么订单服务用轮询不用 webhook")`
- **按决策主题检索**：`ki_search(query="{决策主题}")`，如 `ki_search(query="轮询 webhook 选型")`
- **按分类/动机检索**：`ki_search(query="{分类词} {模块名}")`，如 `ki_search(query="性能取舍 支付系统")`、`ki_search(query="优化 避坑 订单服务")`。分类词与动机词都写在 `module_info` 里，语义检索可命中
- **tags 固定 `decision`**；过滤后命中过少/为空 → 去掉 tags 扩大召回

## 检索示例

```text
# 首选：两级导航
# 第 1 级——列出「决策记录」下有哪些模块子分组（不需 mode=full，不受 5 条限制）
ki_query_group
  scope:   my-project
  subtree: 决策记录

# 第 2 级——列出该模块的全部决策条目（注意 mode=full，否则默认只返回 5 条）
ki_query_group
  scope:  my-project
  groups: 决策记录/订单服务
  mode:   full

# 取单条原文（relation 名从上面清单复制，精确匹配）
ki_get_module_info
  scope:    my-project
  group:    决策记录/订单服务
  relation: 技术选型-轮询而非webhook

# 批量取原文（同 group，≤10 条——全看、或筛出的候选，都走这个）
ki_get_module_info
  scope:     my-project
  group:     决策记录/订单服务
  relations: [技术选型-轮询而非webhook, 性能取舍-订单查询加缓存]

# 语义检索：点查 / 无变更上下文时作兜底
ki_search
  scope:  my-project
  query:  为什么订单服务用轮询不用 webhook
  tags:   decision
  limit:  10

# ── 有变更上下文（如 code-review）：A/B 两路并行，取并集 ──
# A 路：按分类前缀筛候选（本次改的是轮询相关 → 挑 2 条「技术选型」类）
ki_get_module_info
  scope:     my-project
  group:     决策记录/订单服务
  relations: [技术选型-轮询而非webhook, 技术选型-订单状态机]

# B 路：与 A 同时发起（决策主题里未必有被改符号，这半边召回主要靠它）
ki_search
  scope:  my-project
  query:  订单服务 轮询 重试 间隔 改动
  tags:   decision
  limit:  10
```

## 利用结果

- **命中** → 得决策全貌：**分类** / 动机 / 决策内容 / 背景约束 / 被否决方案及理由 / 重新评估触发条件 / 关联代码 / 证据来源
- **分类辅助判断**：命中的「分类」提示该决策约束的是什么——判断"本次改动是否触及这条决策"时**先看分类缩小范围**（如改的是性能参数 → 优先核对「性能取舍」类决策的触发条件；改的是对外字段 → 优先核对「接口契约」类）
- **避免重复讨论**（核心价值）：命中的「被否决方案」说明该方案已被考虑并否决过——**先核对原否决理由是否仍成立**，只在"理由不再成立"时才重新提出，否则直接引用历史结论，不重复论证
- **触发条件核对**：命中记录标注了「重新评估触发条件」（可观测判据）；当前状态满足该判据 → 说明这条决策应当重新评估，作为主动提示
- **证据来源校验**：记录含证据来源（设计文档 / commit / 注释）；发现证据失效或与代码现状冲突时**以代码为准**，并按需更新或清理该记忆
- **`[推测]` 记录降级使用**：决策字段带 `[推测]` 前缀的是**低置信度线索**（无直接证据、基于代码结构推断），**不可当作既定事实引用**——引用前必须以代码/文档核实，并在结论中说明其为推测。消费方（`request-guard` / `code-review` / `bug-impact-analysis`）**不得仅凭 `[推测]` 记录否决方案或判定违背决策**，只能作为"值得核实的线索"
- **未命中 / ki 不可用** → 静默跳过，不阻塞主流程

> **记忆是辅助参考**：决策记忆多由 `expert-team` 事后提炼，可能存在遗漏或已过时；与代码实际不符时以代码为准（对齐 ki-memory-lookup 核心原则第 5 条）。

## 与其它记忆的关系

- 决策记忆答**"为什么"**（成因 / 时间维度）；其余五类答**"是什么"**（现状 / 空间维度）
- **与强关联互补**：强关联说"改 A 必须连带改 B"（约束），决策记忆说"为什么 A 当时这样定"（成因）——改代码前两者结合，才能判断"这个约束是否该被推翻"
- **与专题记忆互补**：专题记忆给模块入口路标，决策记忆给模块关键选择的成因
