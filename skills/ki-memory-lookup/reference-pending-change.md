# 待生效变更策略参考（查询侧）

ki-memory-lookup 的「待生效变更」策略细则。主流程见 SKILL.md。调用方为 `code-review`（阶段 2.3，结账检测 + 登记前查重）。写入待生效变更走 `use_skill("ki-memory-write")`。

## 定位

待生效变更查询 = **找出"该结账了"的变更登记**。

台账的价值在于条目里写好了「合并后应为」——查到的不是"这条可能过期了"，而是"改成什么"的现成答案。查询侧的核心动作是**判定变更是否已合入**，然后执行结账。

## 检索方式（只能目录直查）

**本类 `vector=false`，不进向量，`ki_search` 完全查不到**——目录直查是唯一路径，不是优选路径。

```text
① ki_query_group(subtree="待生效变更")            → 列出所有模块子分组
② ki_query_group(groups="待生效变更/{模块名}", mode="full")  → 列出该模块全部条目
③ ki_get_module_info(group=..., relation=...)     → 取条目原文（relation 从清单复制，精确匹配）
```

⚠️ **`groups` 必须带 `mode="full"`**：默认 `mode="hot"` 只返回最热 5 条且静默兜底。台账条目恰恰是**冷条目**（写完就等合入，几乎不会被访问），不带 `mode="full"` 必然漏——**漏一条 = 漏一次结账**。

⚠️ **不要用 `ki_search` 兜底**：本类查不到是设计使然，不是检索失败。`ki_search` 无结果**不等于**台账为空。

## 结账判定（核心）

逐条判断「触发来源」对应的变更**是否已合入**：

| 触发来源形态 | 判定方式 | 判定为已合入 |
|-------------|----------|-------------|
| PR（`PR#128`） | `gh pr view 128 --json state,mergedAt`；无 gh 时 `git log --oneline --merges --grep="128"` | `state=MERGED` 或存在对应 merge commit |
| commit（短 hash） | `git merge-base --is-ancestor {hash} HEAD` | 退出码 0（该 commit 已是 HEAD 祖先）。⚠️ **squash / rebase merge 后原 hash 不再是 HEAD 祖先**，会误判为"未合入"导致永远不结账——此时退到下方「代码侧佐证」判定 |
| 需求名 | **只能人工确认** | 用户明确告知该需求已完成 / 已上线 |

> **为什么需求名不做自动判定**：`code-review` 阶段 2.3 早于阶段 2.5（需求上下文感知，此时才执行 `req list`），执行结账检测时**拿不到需求状态**。与其让 AI 去猜，不如一律人工确认——需求名类触发来源本来就少，人工成本低于重排阶段顺序。
>
> **登记时优先写 PR 号而非需求名**：PR / commit 可自动判定，需求名不能。同样是"这次改动会改到资产 X"，写 `PR#128` 的条目能自动结账，写需求名的要等人。

**代码侧佐证**（判定存疑时用）：按条目的「影响资产」坐标回到代码，看目标内容是否已经变成台账里写的样子——**以代码现状为准**，git 状态说合入但代码里没变，说明该条目已过时，按「已废弃」处理。

判定结果三分支：

| 判定 | 动作 |
|------|------|
| 已合入 | 提示用户"这条已合入，现在结账吗"，确认后执行结账 |
| 未合入 | 保持不动，不提示（避免每次 review 都重复打扰） |
| 已废弃（PR 被拒 / 放弃 / 代码里已无对应内容） | 建议删除条目 + 删 AGENTS.md 指针行 |

## 结账执行（顺序不能颠倒）

确认结账后：

1. 按条目「合并后应为」落地正式变更——**按资产类型分叉**：
   - **ki 记忆** → `use_skill("ki-memory-write")`，**group 为目标资产的真实 group**（如 `错误库/支付`），不再是 `待生效变更/{模块}`
   - **专家资产 / wiki / 项目文档** → 按「影响资产」坐标定位并**直接修改对应文件**，不走 ki 写入
2. 确认变更已落盘（记忆可检索 / 文件已保存）
3. `ki_delete_relation` 删除台账条目（双侧删除 KB + 向量；**wiki 同步删除仅指 ki 导出的 wiki 中该台账条目**，不删「影响资产」指向的项目 wiki 文件）
4. 删除 `AGENTS.md` 中的指针行

> **先写后删**：反序会在"正式记忆写入失败、台账已删"时永久丢失这条待办。

> **结账前必须让用户确认**：落地正式变更是对知识资产的实质修改（改记忆或改文件），且条目可能已过时（登记时的语境和现在不同）。自动结账风险高于收益。

## 与 AGENTS.md 指针的联动

`AGENTS.md` 里有一行指针（如"共 2 条待结账，见 ki 台账 `待生效变更`"）：

- 指针行**只承担提醒职责**，不含条目内容——内容单一源在 ki，避免双源
- 台账条目数变化（新增 / 结账 / 废弃）→ 同步更新指针行的**条数**
- 台账清空 → **整行删除**，不留空标题

## 使用要点

- **清单要全取不挑**：台账条目数少，全看成本可忽略；挑着看会漏掉最该结账的冷条目
- **判定存疑按"未合入"处理**：不确定的一律保持不动，等下次再判。误结账（资产改错）的代价高于晚结账
- **台账长期有条目 = 流程没跑通**：正常情况 PR 合入即结账。若某条目挂了很久，检查是不是结账检测没执行
- **降级**：ki 不可用时跳过本策略，不阻塞调用方（`code-review` 改为让 AI 直接问用户是否有待结账变更）

## 边界

本策略**只查询 + 判定**，不负责写入与删除——落地正式变更与删台账条目均走 `use_skill("ki-memory-write")`（待生效变更策略的结账流程）。
