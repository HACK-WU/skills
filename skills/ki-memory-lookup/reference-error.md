# 错误库查询策略参考

ki-memory-lookup 的「错误库」查询策略细则。主流程见 SKILL.md。写入方为 `ki-memory-write`（错误库策略，由 `debug` Step 5 后 / `solution-capture` Step 7 后调用）。

## 定位

错误库 = **报错文本 → 根因/解法** 的语义映射原子。查询它的核心价值：**贴整段堆栈进去也能语义命中**——这是 `.solutions/` 的文件级关键词匹配做不到的（报错文本变体极多：路径不同、版本号不同、堆栈行号不同）。

## 检索 API

| API | 用途 | 关键参数 |
|-----|------|----------|
| `ki_search` | 语义检索错误库 | `scope`（项目标识）、`query`（**报错原文 / 堆栈片段 / 异常类型 + 关键 message**）、`tags`（固定 `error`） |
| `ki_query_group` | 按模块整组检索某模块的已知错误清单 | `scope`、`groups`（group 路径，如 `错误库/支付系统`） |

- **scope**：项目标识，与写入时一致

## 检索方式

- **贴报错原文检索**（首选，核心价值）：直接把**整段报错 / 堆栈**贴进 query，不必提取关键词
  - 语义检索会处理路径 / 版本号 / 行号的变体，这正是错误库相对 `.solutions/` 的优势
- **按异常类型检索**：`ki_search(query="{异常类型} {关键 message}")`，如 `ki_search(query="Redis ConnectionError 连接池耗尽")`
- **按模块整组检索**：`ki_query_group(groups="错误库/{功能模块名}")`，查某模块的已知错误清单
- **tags 过滤**（固定）：`ki_search` 一律用 **`tags="error"`** 过滤（错误库写入时统一带 `error` tag），收窄范围提高准确度；**若过滤后命中过少/为空**（如历史存量数据未带该 tag），回退为去掉 tags 过滤的语义检索，避免漏召回

## 检索示例

```text
ki_search
  scope:  my-project
  query:  Traceback (most recent call last): ... redis.exceptions.ConnectionError: Too many open files ...
  tags:   error
  limit:  10
```

## 利用结果

- **命中** → 得错误全貌：报错原文片段 / 现象 / 根因 / 解法 / 验证方式 / 关联方案
- **完整方案**：命中记录的「关联方案」指向 `.solutions/{分类}/{ID}/`——摘要不够时加载该方案按步骤执行（错误库负责"找到"，`.solutions/` 负责"照做"）
- **验证再复用**：解法是历史沉淀，执行后**必须按「验证方式」确认问题真的解决**，不因命中而跳过验证
- **解法失效时更新**：按新情况解决后，用 `ki-memory-write` 错误库策略**更新**该条目（补变体 / 更优解法），而非新建重复条目
- **未命中 / ki 不可用** → 静默跳过，不阻塞主流程，回退正常排查

## 与其它记忆的关系

| 记忆类型 | 回答的问题 |
|----------|-----------|
| 错误库 | 这个**报错**怎么解（问题维度） |
| 专题记忆 | 模块入口在哪 |
| 强关联 | 改 A 牵动 B |
| 决策记忆 | 为什么这么定 |

- **与 `.solutions/` 互补**：错误库 = 语义路标（找到），`.solutions/` = 完整方案（照做）；二者不互相复制
- **与专家资产「已知坑」互补**：已知坑是模块**设计上**的坑（使用时就要避开），错误库是**运行时报错**的解法（遇到了怎么修）
