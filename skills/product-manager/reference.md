## 一、优先级模型（Kano + 价值×成本）

### 1.1 Kano 分类判定

| 分类 | 判定问句 | 处理 |
|------|---------|------|
| **必备（Must-be）** | 没有它用户会明显不满吗？有了用户会觉得理所当然吗？ | 缺失即 P0；有缺陷优先于任何新功能 |
| **期望（One-dimensional）** | 做得越好用户越满意吗？ | 主要优化战场，按价值×成本排 |
| **兴奋（Attractive）** | 没有时用户不会不满，有了会惊喜吗？ | 价值高且成本低才做，否则列为远期 |
| **无差异（Indifferent）** | 做不做用户都无所谓吗？ | 直接砍，写进"建议不做" |
| **反向（Reverse）** | 做了反而让部分用户不满吗？ | 需用户拍板，进待确认 |

> 判定依据不足时标 `Kano 待定`，**不得默认成"期望"**——默认会让必备项被埋没。

### 1.2 价值×成本矩阵

| 价值 \ 成本 | 低 | 中 | 高 |
|---|---|---|---|
| **高** | **P0 立刻做** | **P1 排期做** | P2 拆小或远期 |
| **中** | P1 顺手做 | P2 择机 | 远期 |
| **低** | P2 有空做 | 不做 | 不做 |

**价值口径**（用户价值优先，商业价值次之）：影响用户面 × 影响深度 × 频率。
- 高：核心路径上、每次都用、卡住就办不成事
- 中：部分用户/部分场景、有明显改善
- 低：边缘场景、锦上添花

**成本口径**（粗估，不给人日）：
- 低：文案/配置/样式/单处逻辑
- 中：单个模块内改动、需改数据结构或加接口
- 高：跨模块、涉及状态机/权限/迁移/外部依赖

### 1.3 排序输出格式

```
| 优先级 | 条目 | 来源 | Kano | 价值 | 成本 | 证据 | 排序理由（一句） |
```
**P0 硬门槛**：Kano=必备，或（价值=高 且 成本=低）。不满足却想标 P0 → 必须在排序理由里写明为什么破例。

## 二、取证手段：代码直读与实测

### 2.1 判定类型 × 取证手段矩阵（详版）

| 判定类型 | 典型问句 | 代码直读 | 实测 / 画面 | 取证建议 |
|---------|---------|---------|------------|---------|
| **符合性** | "导出是异步的吗""删除有二次确认吗""错误文案带原因吗" | `🟢` 一手证据 | `🟢` 可复核 | **首选代码直读**，快且准，不必起服务 |
| **存在性** | "有没有批量操作入口""有没有审计日志" | `🟢` | - | 见第五节 M3 证据信号 |
| **行为正确性** | "点了之后真的会走异步吗""条件分支会不会被挡住" | `🟡` 只能证分支存在 | `🟢` | 涉及运行时条件/配置时须实测 |
| **体验** | "几步能完成""反馈及时吗""失败后表单还在吗" | `🟡` | `🟢` | 有分支 ≠ 用户感知到 |
| **视觉** | "对齐吗""层级清晰吗""窄屏折行吗" | `🔴` 不可用（明确样式值除外） | `🟢` 必须看画面 | 代码推不出观感 |

> **心法**：代码能证明"**实现了没有**"，不能证明"**用起来/看起来怎么样**"。前者直接读，后者想办法看。

### 2.2 业务要求 → 可判定检查项（拆分示例）

| 业务要求 | 拆成的代码事实 | 定位线索 |
|---------|--------------|---------|
| 导出是异步的 | 有任务队列/后台任务；有进度查询接口；前端非同步 await | `queue` `task` `job` `progress` `status` |
| 删除有二次确认 | 删除入口接了确认弹窗组件 | `confirm` `Modal` `dialog` `Popconfirm` |
| 错误提示带原因 | 失败分支文案含具体原因，非通用"操作失败" | `catch` `throw` `message` `toast` |
| 空态有引导 | 空数据渲染引导组件/按钮，非纯文案 | `Empty` `empty-state` `暂无数据` |
| 防重复提交 | 提交后置 disabled / 请求锁 | `disabled` `loading` `submitting` |
| 权限有校验 | 入口与接口**两层**均有鉴权（只做一层是常见漏点） | `auth` `permission` `guard` `middleware` |
| 大数据量有分页 | 列表接口有分页参数且前端传递 | `page` `size` `limit` `offset` |

### 2.3 代码直读的判定输出格式

```
| 检查项 | 判定 | 证据（file:line） | 备注 |
|--------|------|------------------|------|
| 导出走后台任务 | ✅ 符合 | src/api/report.ts:42 enqueueExportTask | |
| 有进度查询接口 | ❌ 不符合 | 未找到 | 导出后无法查进度 |
| 前端是否同步等待 | ⚠️ 部分符合 | src/pages/report.tsx:88 await download() | 小数据量走同步分支 |
```

**判定三态 + 部分符合**：不要只给符合/不符合。`部分符合` 是最有价值的发现（"做了一半"），必须写出哪一半没做。

### 2.4 代码直读的失效边界（命中即降级）

| 情况 | 处理 |
|------|------|
| 依赖运行时配置 / 特性开关 | 标 `🟡`，写明"取决于 XX 配置"，可请用户确认当前值 |
| 跨服务调用链长、前端只是透传 | 标 `🟡`，说明断在哪一环 |
| 需要真实数据才暴露（空态/大数量/并发） | 标 `🟡`，给复现方法，或请用户实测/截图 |
| 体验与视觉感受 | **不得出最终结论**，转实测或请用户上传画面 |

### 2.5 常见坑

- **只查一处就下结论**：如"入口有鉴权"就判符合 → 接口层没鉴权（越权风险）。同类检查要**穷举入口**（多页面/多端/多接口），给出清单后再判
- **把注释/文档当实现**：注释写了"已异步处理"但代码是同步 → **认代码不认注释**
- **用测试代码当实现**：`__tests__/` 里的 mock 行为不是产品行为

## 三、关联功能调研与影响评估

> 适用于 **M1 / M2 / M3**（M4 影响面通常限于页面内，可轻量）。**做需求、提优化之前先过这一关**——只描述新功能本身、不提它碰到什么，是产品工作最常见的翻车点。

### 3.1 四类关联来源（逐类过一遍，防漏）

| 类别 | 要找什么 | 例子 |
|------|---------|------|
| **同对象的其他操作** | 同一业务对象的增删改查、导入导出、审批、批量 | 改了订单状态 → 列表/详情/导出/统计全要看 |
| **共享数据与状态** | 共用表/字段/状态机/枚举/缓存键 | 新增状态值 → 所有 `switch(status)` 的地方 |
| **上下游消费方** | 报表、通知、消息、同步任务、webhook、对外 API、订阅方 | 加了字段 → 报表与 API 契约是否要跟 |
| **横切能力** | 权限、审计日志、搜索索引、缓存失效、i18n、计费配额、移动端 | 新入口要不要配权限点、要不要记审计 |

### 3.2 取证手段（按顺序，可叠加）

1. `use_skill("relation-lookup")` 查已登记的跨模块强关联（**优先**；**未安装则跳过**，它不是必需依赖——本 skill 不因它缺失而降级）
2. **代码直读**：grep 共享模型 / 状态枚举 / 事件订阅 / 权限点 / 导出字段映射
3. `use_skill("code-survey")` 做更大范围的代码现状调研（改动面大时）
4. **问用户**：最可靠——报表、外部系统、运营 SOP 这类隐性消费方**常不在代码里**

> **未查到 ≠ 没有**：没找到关联功能时标 `⚪ 未发现（需确认）`，**禁止默认"无影响"**。
> **证据第四态**：`⚪ 未发现` 与三级制并列但不同义——`🟢🟡🔴` 是"有证据、强度不同"，`⚪` 是"**本次没查到**"，二者不可混用（把 ⚪ 写成 🔴 会把"没查"伪装成"推断"）。

### 3.3 影响评估表（报告必填）

```
| 受影响功能/方 | 影响类型 | 影响程度 | 证据 | 建议处理 | 需用户拍板 |
|--------------|---------|---------|------|---------|-----------|
| 订单列表筛选 | 展示 | 降级 | 🟢 src/pages/order.tsx:31 | 本次一并改 | 否 |
| 对外 API /v1/orders | 外部契约 | 破坏 | 🟢 src/api/v1/order.ts:88 | 🔴 需拍板 | 是 |
```

- **影响类型**：数据 / 流程 / 权限 / 展示 / 性能 / 外部契约
- **影响程度**：`破坏`（已有功能不可用）/ `降级`（行为变化但可用）/ `无感`
- **建议处理**：本次一并改 / 单独立项 / 需先确认 / 砍掉此方案

### 3.4 可接受性判定（**AI 不得自行宣布"可接受"**）

| 情形 | 处理 |
|------|------|
| 影响是需求本身想要的（改状态机就是要改下游） | 标「预期内」，列出**需配套改**项 |
| 影响已有功能但可一并处理 | **必须变成需求条目**进清单，不能只写在说明里 |
| 会破坏已有用户习惯 / 数据 / 对外契约 | 🔴 标「需拍板」+ 给替代方案，**由用户决定** |
| 影响未知（查不到消费方） | 标「需确认」+ 给出查证方法（问谁、查什么） |

> 「影响是否可接受」是**业务决策**不是技术判断。AI 只负责把影响**找全、说清、给选项**。

### 3.5 常见漏点

| 漏点 | 后果 | 规避 |
|------|------|------|
| 只查代码不查人 | 漏掉报表 / 外部订阅 / 运营 SOP | 影响面涉及数据产出时，**必问用户**"谁在消费这份数据" |
| 影响项没进需求清单 | 分析提了一嘴，开发漏做 | 影响表每条「本次一并改」必须在需求清单里有对应条目 |
| 只评估"技术上能不能改" | 忽略用户感受变化 | 影响程度里区分"技术可用"与"用户习惯被破坏" |
| 只顾新增功能，不顾存量数据 | 老数据在新逻辑下异常 | 涉及状态/字段变更时，明确问"存量数据怎么处理" |

## 四、M1 档位与假设填充

### 4.1 档位判定信号表

| 信号 | 一次成型 | 严谨档 |
|------|---------|--------|
| 涉及角色数 | 1-2 | ≥3 |
| 涉及模块/页面 | 单点 | 多模块 |
| 外部依赖 | 无 / 已确认可用 | 有未确认依赖 |
| 是否改流程/状态机 | 否 | 是 |
| 预期需求条目 | ≤5 | >5 或难估 |
| 用户显式要求 | - | "严谨档""逐项确认" |
| 纠正次数 | ≤1 次 | ≥2 次自动切换 |

命中任一「严谨档」信号即切严谨档，不取平均。

### 4.2 一次成型档的假设填充指南

自主填完以下 6 项，只在报告「关键假设」章节暴露给用户确认：

1. **需求形态**：是真实需求还是伪装成需求的方案（后者要还原真实需求）
2. **目标角色**：推断最可能的角色（角色不明时列 2-3 个选项让用户挑）
3. **核心场景**：一句话场景（谁 + 什么条件 + 做什么 + 期望结果）
4. **变更面**：执行流程 / 数据流 / UI / 状态流转 / 无形状变化（命中前四类需在报告里出「现状 → 预期」图，规则同 `requirement-mining`）
5. **非功能需求**：性能/安全/可用性/兼容性里**本需求真实相关**的项，不相关的不填
6. **负向场景**：从 `negative-requirement` 七类中筛出真实相关的 3-8 条

### 4.3 一次成型档的产出下限（省交互不省内容）

- 根本性分析：这方案治本吗？不治本要给出更根本的替代思路
- 需求清单：优先级 / 预期效果 / 验收标准 三列必填
- 负向需求：至少覆盖"用户误操作""中途放弃""状态异常"三类中的相关项
- 关键假设表：每条假设写「错了会怎样」+「验证方法」
- 建议下一步：1-2 个行动 + 理由

## 五、M2 六维走查细则

| 维度 | 检查项 | 常见问题信号 |
|------|--------|-------------|
| **价值达成** | 主流程能走完吗；是否有绕路/手工替代 | 用户需要导出到 Excel 自己加工；需要开两个系统对账 |
| **路径效率** | 达成目标几步；有没有重复录入、多余确认 | 同一信息填两次；每次操作都弹确认框 |
| **反馈与容错** | 加载/成功/失败/空/超时各有反馈吗；错误后可恢复吗 | 失败无提示或只报"操作失败"；失败后表单清空 |
| **一致性** | 同类操作方式一致吗；术语统一吗；同类错误提示口径一致吗 | 同功能两种入口两种交互；"删除/移除/注销"混用 |
| **可发现性** | 新用户能找到吗；关键操作是否藏二级菜单 | 核心功能藏设置深处；无引导无空态指引 |
| **边界与异常** | 长文本、大数据量、特殊字符、并发重复提交 | 长文本截断无省略；列表无分页/虚拟滚动 |

**证据记录**：每条发现必须留痕——截图编号 / 复现步骤 / 代码位置（文件:行），便于复验与交接。

**排除项写法**：`经走查排除：反馈与容错维度——关键操作均有 loading 与失败提示（🟢，见 screenshot-3）`。排除结论与发现结论同等值钱。

## 六、M3 证据信号速查

### 6.1 代码实证（🟢）

```
TODO / FIXME / XXX / HACK / 未实现 / 敬请期待
占位组件、空函数体、throw new Error("not implemented")
路由已注册 → 组件文件缺失 或 组件为占位
按钮/菜单已渲染 → onClick 为空 / 仅 console.log
feature flag 存在但默认关闭且无开启入口
README / 文档 / 注释承诺的能力 → 代码中无对应实现
i18n key 已定义但无对应文案值
```

### 6.2 结构可证（🟡）

| 信号 | 推断 |
|------|------|
| 数据表/模型有字段，无任何读写入口 | 预留未做 |
| 有后端接口，前端无调用 | 接口先行，UI 未做 |
| 有前端页面，后端无对应接口（mock 数据） | 前端先行，接口未做 |
| 有创建接口，无列表/详情接口 | 只能建不能查 |
| 有管理端功能，无用户端入口 | 能力未对最终用户开放 |
| 有导入无导出 / 有导出无导入 | 单向能力 |
| 有操作无撤销、有写无审计 | 缺配套能力（可能是有意，需确认） |

### 6.3 推断（🔴）的合法写法

```
❌ 产品缺少批量导入功能。
✅ 待确认：是否计划支持批量导入？——同类 SaaS 普遍提供（参照：{具体产品}），
   当前代码未见相关设计与入口。若有意不做请告知，我将从清单移除。
   验证方法：询问产品负责人 / 查需求 backlog。
```

## 七、M4 走查细则与能力探测

### 7.1 能力探测怎么落地

按顺序尝试，**不要猜**：

1. 有无浏览器类工具（截图/读取页面）→ 有：L1
2. 有 `preview_url` 一类"打开预览"能力但拿不到渲染画面 → L2
3. 项目能否本地起服务（`npm run dev` / `python -m http.server` 等）→ 能起但无截图手段：仍走 L3（起了也看不见，不如请用户拍）
4. 都不可用 → L3（请用户上传）；用户也不提供 → L0

**降级声明模板**（写进报告头）：
> 证据声明：本次未获得实际渲染画面（环境无自动截图能力），以下界面相关结论基于**前端源码静态推演**，证据等级 `🟡/🔴`，未经肉眼验证。建议按 §待确认清单 复核。

### 7.2 有画面时的逐项清单

```
[ ] 视觉层级：主操作是否最显眼？一屏内能否看出重点
[ ] 对齐间距：同类元素间距是否一致？有无明显错位
[ ] 配色对比：文字/背景对比度够吗？主色是否滥用
[ ] 字体字号：层级是否清晰？有无混用过多字号
[ ] 状态完整：悬停/聚焦/禁用/加载/错误/空 各有样式吗
[ ] 响应式：窄屏是否折行/溢出/遮挡
[ ] 文案：术语一致吗？错误文案说人话吗（给原因+怎么做）
[ ] 反馈：操作后有反馈吗？长任务有进度吗
[ ] 无障碍（基础）：可点击区域够大吗？仅靠颜色区分状态吗
[ ] 长内容：长文本/长列表/大数字如何呈现
```

### 7.3 拍摄清单模板（L3）

```
为了准确评估界面，请提供以下截图（有几张给几张）：
1. {主界面}（默认/有数据状态）
2. {核心流程} 的中间步骤
3. 空状态（无数据）
4. 错误态（可随便填错触发）
5. 窄屏/移动端视图（如适用）
要求：桌面 ≥1440px 宽，移动 375px 宽；整屏截图，不要只截局部。
缺失项的说明：{第 N 项无法提供，我将按可得画面降级，相关结论标 🔴}
```

## 八、报告完整模板（长版，落盘时用）

```markdown
---
title: PM 报告 - {对象}
mode: M1 / M2 / M3 / M4
date: {YYYY-MM-DD}
evidence_level: 🟢 / 🟡 / 🔴
tested: true / false
---
```

## 九、常见坑

| 坑 | 后果 | 规避 |
|----|------|------|
| 把 `🔴` 写进执行摘要 | 整份报告可信度归零 | 出报告前扫一遍摘要，含 `🔴` 就移到待确认 |
| M2 写成代码审查 | 用户拿到一堆他看不懂也不想要的技术建议 | 每条发现自问"这是用户能感知的吗" |
| M3 把"有意不做"当缺陷 | 团队被指责做漏了，实际是 MVP 取舍 | 不确定一律标"需确认是否故意" |
| 无画面却写"界面存在 XX 问题" | 幻觉 | 强制降级声明 |
| 优先级无理由 | 用户无法判断该不该信 | 排序理由列必填，且引用 Kano/价值/成本 |
| 一次成型档仍逐条追问 | 回到用户最烦的老路 | 档位判定后严格执行 1 个确认点 |
| 两个模式各出一张表 | 用户自己合并 | M2/M3/M4 任意组合必须合并，用来源列区分 |
| Kano 硬猜 | 真正的必备项被埋在"期望"里 | 依据不足标「Kano 待定」，进待确认清单，不参与默认排序 |
| 组合模式只报最高证据档 | 用 M2 的实测为 M4 的推断背书 | 证据声明取所有模式最低档 |
| 用户只要三句话却给了 10 页报告 | 用户不看，等于白做 | 识别"简单说/只要结论"→ 轻量档 ≤30 行 |
| 符合性问题却要求先跑起来 | 服务起不来就卡住，用户白等 | 判定类型=符合性 → 直接代码直读（`🟢`） |
| 代码有分支就判"体验没问题" | 假结论（有 loading 分支 ≠ 用户看得到） | 体验/视觉类须实测或看画面 |
| 只查一处入口就下结论 | 漏掉绕过风险（前端有确认、接口没有） | 同类入口穷举成清单后再判 |
| 把注释/文档当实现 | 注释写"已异步"但代码是同步 | 认代码不认注释；测试代码的 mock 不算实现 |
