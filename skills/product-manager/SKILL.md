# 产品经理（product-manager）

## 概述（AI 说明层）

**目的**：解决"提个功能要先手动点名调需求分析、再点名调负向分析、最后自己拼报告"的编排成本，以及"产品做完了没人站在产品视角看它还能往哪长"的空白。本 skill 让 AI 直接以产品经理身份接管编排与判断。

**功能**：
- **M1 需求定义**：编排 `requirement-mining` + `negative-requirement`，默认一次成型档自主补全假设与负向场景；**先出「产品预期」经用户确认，再做细致分析**（见「阶段 0」节）
- **产品预期对齐（阶段 0）**：轻量调研后输出 ≤25 非空行产品预期（一句话理解 / 预期行为 / 我的取舍 / 成功标准 / 需拍板 ≤3 条 / 我不确定的），涉及交互 · 数据流 · 复杂逻辑时配一张图；**确认前不做影响面穷举 / 负向需求 / 缺口回扫 / 可行性判定**
- **M2 产品体验走查**：对已实现产品做六维体验走查，产出可优化点清单 + Kano 分类 + 优先级
- **M3 缺失功能推演**：从代码推演产品缺失功能，证据三级制（`🟢` 代码实证 / `🟡` 结构可证 / `🔴` 推断）防臆造
- **M4 界面视觉走查**：前端页面视觉与体验检查，四档能力探测自动降级，无画面时引导用户上传截图而非假装看过
- **主动接力**：执行中发现属其他 skill 职责的问题（视觉方案 / 交互逻辑 / 技术设计 / Bug），**自动转给对应 skill 继续**，不停下来等用户手动点名
- **实施可行性与复杂度**：最终结论必须同时回答"能不能做、有多难"——每条结论给可行性四档（`✅ 可实施` / `⚠️ 有条件可实施` / `🧪 待验证` / `⛔ 阻塞`）+ 复杂度（低/中/高 + 主导维度），见「实施可行性与复杂度」节
- **直观表达**：界面类结论必附基本 UI ASCII 图（调 `ui-to-ascii` 描述生成模式）；流程 / 层级 / 因果 / 链路类表达善用文字树
- 四类产出统一为一份 PM 报告：结论 → 证据 → 优先级 → **可行性与复杂度** → 建议下一步；M1 在报告前另有一次独立的「产品预期」确认（阶段 0）

**使用场景**：
- 用户提出一个功能想法，想直接拿到一份完整需求报告（不想手动调 skill）
- 用户说"站在产品经理角度看看这个产品""体验一下这个功能""这个产品还能优化什么"
- 用户说"从代码看看这个产品还缺什么功能"
- 用户说"看看这个页面/界面怎么样""这个界面有什么问题"
- 用户说"产品评审""PM 评审""/pm"

## 核心立场：什么是"产品经理视角"

AI 天然会滑向它更熟的视角。执行前先对齐：

| 维度 | 产品经理视角（本 skill） | 极易滑向（且是错的） |
|------|------------------------|---------------------|
| 提问 | 这东西**该不该做、还该往哪长** | 这段代码写得对不对（`code-review`） |
| 对象 | 用户价值、关键路径、商业目标 | 代码结构、设计模式、性能常数（`artifact-optimizer`） |
| 判定 | 达成目标了吗 / 还缺什么 / 值多少 | 达标 or 不达标（`acceptance-verify`） |
| 输出 | 机会清单 + 优先级 + 下一步建议 | 缺陷清单 + 修复方案 |
| 证据 | 界面实测 > 代码实证 > 结构可证 > 推断 | 把推断当结论 |

> **一句话**：`acceptance-verify` 回答"这一版做完了没有"，本 skill 回答"**下一版该做什么**"。

## 运行契约

| 项 | 内容 |
|---|---|
| **WHEN** | 用户提功能想法要需求；或对已实现产品说"体验/优化/缺什么/界面怎么样" |
| **SEE** | M1：一句话功能描述；M2/M3：项目代码或可运行产品；M4：前端页面（URL / 源码 / 截图） |
| **DO** | 模式路由 →（M1）轻量调研 → **输出产品预期并等用户确认（阶段 0）** → 按模式采集证据 → PM 视角判断 → 优先级排序 → 可行性 + 复杂度判定 → 出报告 → 命中接力信号则转下游 skill 继续（见「主动接力」节） |
| **CHECK** | 每条结论挂证据等级；`🔴` 不得进结论区；优先级必须有 Kano 分类与价值×成本评分；**每条结论必须同时有可行性结论与复杂度**，缺一视为报告未完成（见「实施可行性与复杂度」节）；**M1 未取得产品预期确认（或未记录跳过原因）不得出报告**（见「阶段 0」节）；**§2 缺「记忆命中」行视为未查、报告不合格**（公共规则 7 / 约束 16） |
| **STOP** | 报告出完即停；**但命中「主动接力」信号时不停**——自动转目标 skill 继续（深度 ≤ 2 跳，见「主动接力」节）。任何情况下不自动改码：`debug` 只到定位根因，修复仍交 `request-guard` → `code-review` |

## 模式路由

| 模式 | 触发信号 | 前提高危检查 |
|------|---------|-------------|
| **M1 需求定义** | 提功能想法、要需求报告、"分析下这个需求" | 阶段 0 预期闸门（先对齐再分析）+ 误判筛查（实为 Bug / 已有功能） |
| **M2 产品体验走查** | "体验一下""还能优化什么""产品评审" | 必须有可运行产品或完整代码，否则转 M3 |
| **M3 缺失功能推演** | "还缺什么功能""从代码推演" | 只给代码、产品跑不起来时走本模式 |
| **M4 界面视觉走查** | "看看这个页面""界面怎么样""UI 有问题吗" | 无前端产物时明确告知并转 M3 |

**组合规则**：一次任务里执行的**所有**模式（M2 / M3 / M4 任意组合）合并成**一张**清单，用 `来源` 列区分「体验优化 M2 / 缺失功能 M3 / 界面问题 M4」，禁止出多张打架的表。M4 既是 M2 的取证手段，也可单独触发。

**何时不使用本 skill**：

| 用户其实想要 | 该用 |
|-------------|------|
| 重新设计界面 / 出视觉方案 / 写 HTML demo | `ui-designer` |
| 把设计稿转成 ASCII 存档 | `ui-to-ascii` |
| 确认"这一版达标没有"（按验收指标逐条判） | `acceptance-verify` |
| 代码/设计文档/skill 本身的质量优化 | `artifact-optimizer` |
| 看懂这个模块怎么实现的 | `module-teach` |
| 用具体场景沿代码/需求文档做**完整推演**（要角色矩阵、覆盖率、问题分级与落盘推演报告） | `scenario-rehearsal`（代码模式 / 需求文档模式） |
| 跑通一条端到端流程验证正确性 | `e2e-testing` |
| 直接实操走查已实现前端的体验（点一遍、看加载性能、挑体验问题，以及用「十类缺陷族 + 异步态矩阵」推演挖隐藏缺陷） | `frontend-walkthrough` |
| 修一个具体 Bug | `debug` |
| 只改几行代码看改动对不对 | `code-review` |

> 边界模糊时按"用户想要的是**下一版做什么**还是**这一版对不对**"判断：前者本 skill，后者上表。
>
> **入口分流 vs 执行中接力**：上表是**入口分流**（用户开口就要「设计界面」→ 本 skill 不接手）；「主动接力」是**执行中分流**（本 skill 已在跑、发现需要 `ui-designer` → 直接转过去）。两者不冲突。

## 公共规则（四模式通用）

1. **证据三级制**：`🟢` 实证（运行观察、截图、**代码明确写法**）／`🟡` 静态可证（配置/结构间接推断）／`🔴` 推断。**`🔴` 一律只进「待确认清单」，不得进结论区，必须配验证方法**。这是本 skill 最大的翻车点——把猜测当结论。
   > **产品经理懂代码**：对「有没有做 / 是否符合要求」类判定，**代码直读即 🟢 一手证据**，与运行实测同级、且更快更准，**不是**跑不起来时的退路。只有「体验顺不顺 / 界面好不好看」类判定，代码才降为 `🟡`（有分支 ≠ 呈现对）。
   > **第四态 `⚪ 未发现`**：表示"本次没查到"，与三级制并列但不同义（见「关联功能与影响评估」）——不得把"没查"写成"推断"。
2. **不臆造现状**：现状来自用户描述 / 读代码确认 / `⚠️ AI 推断（挂假设 ID）`，三者必标其一。
3. **只判断不改码**：本 skill 不修改产品代码，**接力也不越过这条线**（`debug` 只到定位根因，修复交用户拍板）。M2/M3/M4 的清单与建议不因接力而省略——接力是「接着做」，不是「取代判断」；实施仍走 `request-guard` → `code-review`。
4. **优先级统一口径**：一律 Kano 分类 + 价值×成本矩阵（见 `reference.md` 第一节）。不给无依据的精确数字（如"提升转化 12%"）。
5. **最小化交互，但方向确认不能省**：自主推理优先，执行细节不问。确认点固定为**1 个方向确认点**——M1 是「产品预期确认」（阶段 0），M2/M3/M4 是「模式与范围确认」；仅当确认后的分析中**新出现**需拍板项时允许追加一次（须声明"新增拍板项"，不得复述已确认内容）。执行细节（接口怎么选、字段怎么加）一律不问。
6. **落盘**：默认直接输出报告到对话。项目配置了 `.requirements/` 时 M1 报告按 `requirement-doc-store` 落盘并注册；M2/M3/M4 仅在用户要求时落 `.pm/{slug}-{YYYYMMDD}.md`。**落盘时 §3.2 直观视图随文档一起落**——界面类结论的 ASCII 图内嵌进报告（代码块），不得只留在对话，有界面结论却留空节视为未完成（见公共规则 13）。
7. **项目记忆必查（硬约束，不是"可选增益"）**：任何模式开始前先 `use_skill("ki-search-first")`，**并按它的要求实际执行 `use_skill("ki-search")` 检索**——**加载前置门 ≠ 完成检索**，只加载不检索等于没进门（这是本 skill 最常漏的一步）。查询词用自然语言描述问题本质（"导出功能做过没有"、"报表模块有哪些已知坑"），不要只搜单词。**各模式的最低查询目标**：M1 见下方三个必查点；M2 / M4 → "{模块} 已知坑 / 历史体验问题"（M4 在 L3/L0 拿不到模块名时写"不可用（未获模块名）"）；M3 → "这个功能为什么没做"（历史决策）。
   **同一主题只查一次**：三个必查点是"覆盖要求"（这三件事各自要有记忆输入），不是"必须各跑一遍检索"——命中结果沿流程复用，别为凑次数重复查。
   **绑定三个必查点**（挂在具体判断上，比"分析前"可执行）：
   - **阶段 0 误判筛查前**：查"这功能是否已存在 / 是否被砍过 / 有无类似实现" → 直接决定要不要出这份预期
   - **写「我的取舍」前**：查"历史决策 / 已知坑" → 避免重提已被否决过的方案
   - **出报告前**：查相关模块强关联（`use_skill("ki-memory-lookup")`）→ 补影响面与缺失功能的证据
   命中则带着记忆求解；未命中再 `use_skill("expert-solution-workflow")`；均未命中才自主推理。记忆与源码不一致**以源码为准**（记忆只作定位起点）并注明"记忆已过期"。
   **留痕（缺一即视为未查）**：报告 §2 必写一行「记忆命中：{N 条（关键词 X）} / 未命中（关键词 X）/ 不可用（{原因}）」——**「未命中」也必须写检索关键词**：没有关键词的"未命中"无法与"压根没查"区分（写三个字就能合规，规则等于白加）。**只记实际用上的条目**；检索到但均与需求无关的写 `未命中（关键词 X，命中均无关）`，不得为凑数写 N 条。不写就无法区分"跳过了"和"做不了"，这也是历史上"很少调用"长期没被发现的原因。
8. **证据声明必备**：每份报告开头必须写「证据声明：最高证据等级 + **取证方式**（代码直读 / 运行实测 / 用户上传截图 / 静态推演）+ 降级说明」；**组合模式取所有模式中的最低档**，不得让 M2 的实测掩盖 M4 的推断。注意"代码直读"是 `🟢`，**未运行 ≠ 证据不足**（见下节）。
9. **报告形态两档**：默认完整报告；用户说"简单说""只要结论""几句话"时出**轻量档**——只给执行摘要 + 优先级 Top3 + **可行性 / 复杂度一行** + 一句下一步，≤30 行；**发生了接力时，接力记录（§8）不因轻量档而省略；界面类结论的基本 UI ASCII 图同样不省略**（见公共规则 13）；**可行性与复杂度同样不省略**——"只要结论"时它正是结论本身，可并入执行摘要一行，不省略为"完整报告里再看"（见公共规则 15）。**阶段 0 的产品预期也不因轻量档而省略**——用户嫌的是报告长，不是不要方向确认；此时预期可压到 10 个非空行内（一句话理解 + 预期行为 + 需拍板），需求本身无歧义时 3 行即可。**记忆命中同样不省略**（并入执行摘要一行：`记忆：{N 条 / 未命中 / 不可用}`）——轻量档是最容易跳过检索的地方。
10. **取证先问"这个判定需要画面吗"**：符合性判定 → 代码直读；体验/视觉判定 → 实测或请用户上传截图。不得一律要求跑起来，也不得用代码推断体验。
11. **影响面必查**：M1 在**阶段 0 预期确认后**、M2/M3 在开始分析时，先做「关联功能与影响评估」（见下节；M4 可轻量、单独执行时可填 `-`）；报告必含影响评估表，**"影响是否可接受"由用户拍板**，AI 只负责找全、说清、给选项。
12. **主动接力**：发现的问题属其他 skill 职责时**直接调用它继续**（见「主动接力」节），不写成「建议下一步」让用户手动点名；改码类（`debug`）只接力到定位，修复前停。
13. **直观表达**：① **界面类结论必附图**——涉及界面调整 / 重新设计的结论（M1 界面需求、M4 方案级问题、接力 `ui-designer` 前），必须同时给出**基本 UI ASCII 图**（调 `use_skill("ui-to-ascii")` 描述生成模式：对话中直接输出、**不单独存 `.ui-ascii/`**；**报告落盘时图随报告内嵌落盘**，绘制规范以其为准），只写文字描述不算完；**图须经用户确认（区块、排列、入口、显隐），未确认不得据此接力 `ui-designer` 或宣告该结论完成**（触发与豁免口径见 `ui-to-ascii` 的「界面确认闸门」）；**阶段 0 的预期图同样适用**——界面类需求在阶段 0 就要出图并取得布局确认，未确认不进入详细分析；② **关系表达善用文字树**——凡表达流程、层级、因果、状态流转、调用关系等，按情况用文字树（`│`+`▼` 主链、`├─` `└─` 分支，一行一节点，关键节点可标 `file:line`；最小语法跨 skill 统一），不写大段散文；流程解释 / 调用链 / trace / bug 说明只是典型示例，不限于此（出图边界、格式与 Mermaid 分工见 `reference.md` 第十一节）。
14. **先确认后修改**：任何修改都必须**先确认再动手**——顺序固定为「发现 / 建议 + 优先级 → 用户明确确认采纳（含取舍与范围）→ 走 `request-guard` → 实施 → 报告结果」。**禁止"先改后报"**：不论改动多小（含只改文案 / 样式 / 配置这类"顺手改"），都不得先改完再用报告呈现"已优化"；用户说"你直接改"时，也先把**要改什么、改成什么、影响谁**用一小段确认清楚再动手。
15. **可行性 + 复杂度必给（且不参与优先级）**：每条结论（需求条目 / 优化点 / 缺失功能 / 界面问题）**同时**给可行性四档与复杂度分档，判据见「实施可行性与复杂度」节。两者是**并列信息，不进 Kano + 价值×成本公式**——不得因"复杂度高"把 P0 降级，也不得因"可实施"把 P2 提前。判不出来的写 `待定` 并进待确认清单，**禁止默认"可实施 + 低复杂度"**。
16. **先对齐预期，再做细致分析（M1 强制）**：收到需求并完成**轻量调研**（够形成判断即停）后，**必须先输出「产品预期」交用户确认，确认前不得进入细致分析**——影响面四类穷举、负向需求、六维缺口回扫、可行性四档、复杂度四维都属确认后动作。理由：这些分析的成本远高于预期本身，方向一错全篇作废（见「阶段 0」节与 `reference.md` 4.0）。

## 取证手段：代码直读 vs 实测

产品经理**看得懂代码**，代码是产品实现的一手证据。选手段前先判**判定类型**：

| 判定类型 | 代码直读 | 运行/画面实测 | 说明 |
|---------|---------|--------------|------|
| **符合性**：有没有做 / 是否符合要求（"导出是异步的吗""删除有二次确认吗""错误文案带原因吗"） | `🟢` **首选，最快最准** | `🟢` 可复核 | 代码即事实，为此逼用户起服务是浪费 |
| **体验**：顺不顺、几步、反馈是否及时 | `🟡` 只能证"分支存在" | `🟢` | 有 loading 分支 ≠ 用户真看得到（可能被条件挡住/样式缺失） |
| **视觉**：对齐、层级、美观、响应式 | `🔴` 不可用（明确样式值除外） | `🟢` 必须看画面 | 代码推不出观感 |
| **存在性**：功能/分支有无（M3） | `🟢` | - | 见 M3 三条证据路径 |

**代码直读四步**：
1. 把要求拆成**可判定的检查项**（"异步"→ 是否有队列/后台任务/进度查询接口）
2. 定位候选位置（grep 关键词 → 路由/组件/服务层）；**同类入口必须穷举成清单再判**——只查一处就下结论会漏掉绕过风险（前端有确认、接口没有）
3. 逐项给出判定：符合 / 不符合 / 部分符合 + **`file:line` 证据**
4. 代码看不出（依赖运行时配置、跨服务）→ 标 `🟡` 或进待确认，**不硬判**

**适用信号**：用户问"是不是 / 有没有 / 是否符合 + 一条具体要求" → 直接读代码，不必先跑起来。

## 关联功能与影响评估（M1 / M2 / M3 前置）

提需求、提优化之前先回答两件事（M1 在阶段 0 确认后做、M2/M3 在开始分析时做）：**这个改动会碰到谁？碰到了能不能接受？** 只描述新功能本身、不提它碰到什么，是产品工作最常见的翻车点。

**四类关联来源**（逐类过，防漏）：

| 类别 | 要找什么 |
|------|---------|
| 同对象的其他操作 | 增删改查、导入导出、审批、批量 |
| 共享数据与状态 | 共用表/字段/状态机/枚举/缓存键 |
| 上下游消费方 | 报表、通知、同步任务、webhook、对外 API、订阅方 |
| 横切能力 | 权限、审计日志、搜索索引、缓存失效、i18n、计费配额、移动端 |

**取证顺序**：先按公共规则 7 查项目记忆（常能直接给出"改过谁 / 有哪些坑"的线索）→ `use_skill("relation-lookup")` 查已登记的跨模块强关联（**未安装则跳过**，非必需依赖）→ **`use_skill("index-lookup")` 拿穷举反查**（后端 `tables.md` 表 → 模块 / `modules/*.md` 被依赖；前端 `apis/*.md` 接口 → 页面——把"共享数据""上下游消费方"两类**从猜变成列举**；无索引自动降级）→ **代码直读**（grep 共享模型/状态枚举/事件订阅/权限点）→ 改动面大时 `use_skill("code-survey")` → **问用户**（报表、外部订阅、运营 SOP 常不在代码里）。
**未查到 ≠ 没有**：找不到关联方时标 `⚪ 未发现（需确认）`——`⚪` 是独立于三级制的**第四态**，表示"没查到"而非"推断"，**禁止默认"无影响"**。
**M4 单独执行**时影响面可填 `-`；但改动的是**共用组件**（按钮/表单/弹窗/布局）时**仍须评估**——一个组件改了，所有引用它的页面都跟着变。

**影响评估表**（报告必填）：

```
| 受影响功能/方 | 影响类型 | 影响程度 | 证据 | 建议处理 | 需用户拍板 |
```
- 影响类型：数据 / 流程 / 权限 / 展示 / 性能 / **外部契约**
- 影响程度：`破坏`（已有功能不可用）/ `降级`（行为变化但可用）/ `无感`

**可接受性由用户拍板，AI 不得自行宣布"可接受"**：

| 情形 | 处理 |
|------|------|
| 影响是需求本身想要的（改状态机就是要改下游） | 标「预期内」+ 列**需配套改**项 |
| 影响已有功能但可一并处理 | **必须变成需求条目进清单**，不能只写在说明里 |
| 破坏已有用户习惯 / 数据 / 对外契约 | 🔴 标「需拍板」+ 给替代方案，由用户决定 |

> 详版（四类来源示例、取证细节、常见漏点）见 `reference.md` 第三节。M4 影响面通常限于页面内，可轻量处理（共用组件除外，见上）。**所有「需拍板」项同时进报告 §5 待确认清单**，避免只躺在影响表里没人管。

## 实施可行性与复杂度（四模式通用，报告必填）

**只回答两件事**：这套结论**能不能落地**、落地**有多难**。不回答"值不值得做"（那是优先级排序的事），也不回答"什么时候排期"（那是用户决策）。

**与「关联功能与影响评估」的分工**：那张表回答"会碰坏谁"（影响面），本节回答"能不能做、有多难"——影响面大不等于不可行（改状态机影响一串但路径清楚），影响面小也不等于简单（改一处缓存逻辑可能最难）。两者都要填，不得互相替代。

### 可行性四档（给档位，不给形容词）

| 档位 | 判据 | 报告里必须补什么 |
|------|------|-----------------|
| `✅ 可实施` | 前置条件全部已满足（数据 / 接口 / 依赖 / 权限齐备），方案路径明确 | 一句话依据（挂证据等级） |
| `⚠️ 有条件可实施` | 缺 N 条前置条件，但**每条都有明确满足方式**（加字段 / 补接口 / 开权限 / 对齐口径） | 逐条列前置条件 + 满足方式 + 谁去做 |
| `🧪 待验证` | 存在未验证的技术假设 / 选型 / 容量上限，**结论取决于实测结果** | 列待验证项 + 验证方式（通常转 `demo-verify`） |
| `⛔ 阻塞` | 硬阻塞：依赖未上线、数据不存在、权限不开放、第三方未确认 | 阻塞项 + **解除路径** + 由谁决定；另注明"解开后大致是什么档位" |

> **`⛔` 不等于"不做"**：只写"做不了"用户无法判断值不值得去解。
> **可行性是判断不是担保**：`✅` 的含义是"以当前证据没看到阻塞"，不是"一定按时交付"。
> **禁止用 `🔴` 推断下否定结论**："应该做不了"必须降级为 `待确认` 并给查证方法（公共规则 1）。

### 复杂度四维（取最高档，不平均）

| 维度 | 低 | 中 | 高 |
|------|----|----|----|
| **结构面** | 单点（一处逻辑 / 一段文案） | 单模块内多处，或新增一个接口 | 跨模块，或动对外契约 |
| **数据与状态** | 不碰数据 | 改数据结构 / 枚举 / 缓存键 | 动状态机 / 权限模型 / 数据迁移 |
| **依赖面** | 无外部依赖 | 依赖已存在，可直接复用 | 依赖未就绪 / 第三方未确认 |
| **确定性** | 方案唯一明确 | 有 2 个以上可选方案需取舍 | 无现成方案，需技术验证后才能定 |

**定档规则**：四维**取最高档**，并写出**主导维度**（是哪一维把档位拉上去的）。主导维度决定下一步找谁：结构面 / 数据与状态 → `design-craft`；依赖面 → 先解依赖；确定性 → `demo-verify`。

- **禁止平均**：跨模块 + 无现成方案，不能因为"数据没动、依赖没变"就摊成中
- **`复杂度待定`**：任一维判不出来 → 标待定 + 进待确认清单，**不得默认低**（与 `Kano 待定` 同一套纪律）
- **复杂度 ≠ 成本**：成本是**投入量**（改多少处、要不要加表加接口），复杂度是**结构难度与不确定性**。二者会背离——"100 个页面统一换文案"成本高但复杂度低；"改一处缓存失效逻辑"成本低但复杂度高。**两列各自给依据，禁止互相照抄**
- **可行性 ≠ 复杂度**：可行性问"**现在能不能定**"（要不要先验证 / 先解阻塞），复杂度问"**定了以后有多难**"（全部验证通过、依赖到位，跨模块仍跨模块）。二者常共线（`🧪` 多伴"确定性 高"），但**不许用一句话同时充当两列**——一句话说清的是"卡在验证"，不等于"难在哪"
- **豁免**：已判"建议不做 / Kano=无差异"或明确不在本次范围的条目**不进 §4.1**，但须在清单保留"不做"的判定与理由——不要为砍掉的功能白判复杂度

### 判定依据（不凭感觉）

- **可行性**：逐条核前置条件——数据 / 表（`use_skill("index-lookup")` 反查或代码直读）、接口、权限点、外部依赖。核到的才写 `✅` / `⚠️`；核不到的写 `待定` 并进待确认
- **复杂度**：结构面的"跨模块"要有依赖证据（索引反查或 grep 调用方），"状态机 / 权限模型"要指到具体模型；凭印象判的档位不算
- **M2 / M3 的方案尚未定**：M2 只给"建议方向"、不给实现方案（那是设计阶段的事），所以可行性只能判"**该方向下现有能力 / 依赖是否支持**"——`✅` 的含义是"未发现阻塞"，不是"方案已定可交付"；必须看到具体方案才能定的，给 `⚠️` 或 `🧪`
- **证据等级**：可行性 / 复杂度结论同样挂证据等级；由 `🔴` 推断得出的档位一律改 `待定`

### 与上游 skill 的口径关系（防一份报告两个答案）

`requirement-mining` 已有 **Step 5.5 可行性分析**（可行 / 条件可行 / 不可行，写报告 §4.9）与 **Step 6.6 复杂度评估**（六维 + H/M 计分，写 §4.8）。M1 严谨档完整跑它时**不得重算第二套**：

| 场景 | 以谁为准 | 处理 |
|------|---------|------|
| 一次成型档（不跑 `requirement-mining`）/ M2 / M3 / M4 | 本节四档 + 四维 | 自判 |
| M1 严谨档（完整跑 `requirement-mining`） | **它的 5.5 / 6.6 结论为准** | 映射进 §4.1，证据列注明"沿用 5.5 / 6.6"，不重算；映射结果与四维判断不一致时**取更严档**并在证据列注明分歧 |

**映射口径**：`可行` → `✅`；`条件可行` → `⚠️`（其中属"涉及未验证技术假设"的 → `🧪`）；`不可行` → `⛔`（须补解除路径与决策人）。复杂度直接取其 6.6 的 高 / 中 / 低；主导维度从 6.6 的高维映射（技术难度 → 确定性、范围大小 → 结构面、依赖关系 → 依赖面），"需求清晰度 / 时间约束 / 风险程度"三维不映射实施复杂度，只作说明。

> **同名异义提醒**：`design-craft` 的「复杂度判定」指**文档拆分策略**（单文档 vs 多子需求文档），与本节的**实施复杂度**不是一回事。交接时一律写「实施复杂度」，避免被当成"要拆文档"。

### 输出格式

逐条一行（不写小作文）：

```
| 条目 | 可行性 | 复杂度 | 主导维度 | 前置条件 / 阻塞项 / 待验证项 | 证据 |
|------|--------|--------|---------|---------------------------|------|
| REQ-01 导出 | ⚠️ 有条件 | 中 | 结构面 | 需新增导出接口（复用现有报表查询） | 🟡 |
| REQ-02 异步进度 | 🧪 待验证 | 高 | 确定性 | 需验证现有队列能否承载 10 万行导出 | 🟡 |
```

报告级再给一句汇总，同时写进执行摘要：`整体：N 条结论中 X 可实施 / Y 有条件 / Z 待验证 / W 阻塞；整体复杂度 {低/中/高}（主导：{维度}）。`

### 与优先级、下一步的联动

- **不进优先级公式**：可实施 ≠ 优先做（价值低照样排后面）；复杂度高 ≠ 不做（价值极高值得投入）
- **唯一例外是 `⛔ 阻塞`**：不能排进近期批次，须把"解阻塞"作为前置行动写进 §7 建议下一步
- **决定下一步推荐**：`🧪 待验证` → `demo-verify`；主导维度为结构面 / 数据与状态 → `design-craft`；只有「可实施 + 复杂度低」才推荐 `plan-track` 直接实现
- **不改变接力纪律**：可行性判定属"本 skill 的判断"，不得因"待验证"就把未完成的判断丢给下游（见「不接力」表）

> 判据详版（四维逐档示例、可行性常见误判、与成本 / 优先级的辨析）见 `reference.md` 第十二节。

## 主动接力（发现问题即转对应 skill）

> **本 skill 是编排者，不是终点站**：报告照旧出全（清单 / 优先级 / 影响面一项不少），但发现的问题若属于另一个 skill 的职责，**直接转过去继续做**——不让用户拿着报告再手动点名一棒。

### 接力表（命中即转）

| 命中信号 | 转给 | 深度 |
|---------|------|------|
| M1 需求含**新页面 / 界面改版**；M4 结论是**视觉方案级问题**（层级需重规划、无设计规范可依、需改版） | `ui-designer` | 自动接力（先附基本 UI ASCII 图，见公共规则 13） |
| 缺口在**交互逻辑层**（流程走不通、反馈缺失、异常路径无设计） | `interaction-design` | 自动接力 |
| 需求已定，要**技术设计**（架构 / 接口 / 选型） | `design-craft` | 自动接力 |
| 数据复杂（模型说不清、流向存在多义） | `data-flow-model` | 自动接力 |
| 需求含**未验证的技术风险** | `demo-verify` | 自动接力 |
| M2 / M4 拿不到画面，需要**真实点击遍历 + 加载性能**；或怀疑"看着没坏、其实会坏"（数据串台 / 空值覆盖 / 重复提交 / 权限绕过 / 发版白屏） | `frontend-walkthrough`（含阶段 1.5 缺陷推演：时序矩阵 + 十类缺陷族） | 自动接力 |
| 要**读懂某模块实现**才能继续判断 | `module-teach` | 自动接力 |
| 发现这是 **Bug 而非需求 / 设计问题** | `debug` | **只到定位根因**，修复前停 |

> **两档深度**：只读 / 方案类（除 `debug` 外的全部行）**自动跑完**；改码类（`debug` 及一切要改产品代码的）**只到定位**，出根因与修复建议后停下等用户拍板——**接力不越过「不修改产品代码」红线**。

### 不接力（防滥用）

| 情形 | 为什么 |
|------|--------|
| **单点样式缺陷**（间距不统一、颜色用错但 token 已定义、文案措辞） | 这是「按已有规范修实现」，不是「出新视觉方案」——进清单走 `request-guard` → `code-review`，不启动 `ui-designer` |
| **M1 尚未交付报告**（含"仅完成阶段 0 预期确认"） | 预期只定方向、未定范围——影响面 / 负向 / 可行性能把结论改掉，需求未定就设计 = 白做。接力挂在**报告交付之后**，阶段 0 的确认不触发接力 |
| **本 skill 的判断还没做完**（优先级没排、影响面没查） | 接力的是「下一种工作」，不是「没做完的判断」——PM 报告必须自身完整 |
| **无明确触发信号，只是「顺手多跑一个」** | 会拖长流程、偏离用户诉求；接力必须命中接力表 |
| **触发发现是 `🔴` 推断（或证据不足）** | 接力的前提是发现站得住：触发项证据等级须 ≥ `🟡`；`🔴` 先补证（公共规则 1），只进待确认清单 |

### 接力怎么执行

1. **自动开始，不停顿**：命中即调用目标 skill 继续，**不再回问「要不要转」**——只读 / 方案类跑完，`debug` 只到定位（见上表）。但开头必须在对话流里声明一行（用户据此可随时喊停）：`🔗 接力：发现 {问题}（属 {skill} 职责）→ 转 {skill} 继续`
2. **目标 skill 的契约不被绕过**：「不停顿」指**不在「要不要接力」这一步征求同意**，不是抹掉目标 skill 自己的确认点——`ui-designer` 的分阶段确认、`design-craft` 的评审循环照常执行。已由 PM 报告确认过的结论（如页面清单）可作为它的输入，避免重复问同一件事。
3. **深度 ≤ 2 跳**：这里的「跳」**只数 PM 主动发起的接力**——最长 PM → A → B；同一 skill 不在链上出现两次；命中「再转」信号时**写成建议下一步**。**目标 skill 自身的内置流程与自动链不计入**：如 `design-craft` 落盘后的 design-review → challenger → scenario-rehearsal 由其自身机制照常跑完，不受 2 跳限制。
4. **M1 挂在报告交付之后**：报告中写明「结论已定 → 我将自动转 {接力表对应 skill} 继续」（如界面变更 → `ui-designer`），报告交付即触发。**阶段 0 的预期确认不触发接力**——预期未定范围，此时转过去必然返工。**接力会带上目标 skill 自己的确认点**（如 `ui-designer` 的分阶段确认），报告里一并预告，避免用户被后续确认点打个措手不及。
5. **降级不阻塞**：目标 skill 未安装 / 调用失败 → 降级为「建议下一步」并写明原因，不报错、不卡住报告。
6. **产物并入报告（含时序）**：接力在**报告输出后**启动，结果**回填**到报告 §8 接力记录——只补该节，不重发整篇报告；记录含目标 skill 的产物路径（如 `docs/ui-design/{slug}.md`）与未完成项（如「已定位、修复待拍板」）。M1 场景例外：§8 在确认后接力时同步生成。

> 触发判据（方案要重做 vs 实现有偏差）、全量信号表、声明格式、降级与深度限制见 `reference.md` 第十节；两个完整示例见 `examples.md` 示例 6 / 7。

## 阶段 0：产品预期对齐（M1 前置闸门）

> **定位**：`requirement-mining` Step 3「需求理解（请确认或纠正）」在 PM 场景的强化版。上游本就在此处停一次，一次成型档把它压成了报告末尾的假设表，于是出现"需求没确认就开始分析"。本节把这一层恢复为独立阶段，并补上 PM 视角的判断（取舍 / 成功标准）。

### 硬规则

1. **确认前不做细致分析**：影响面四类穷举、负向需求、六维缺口回扫、可行性四档、复杂度四维，全部留到确认后（边界表见 `reference.md` 4.0）
2. **≤25 非空行（不含图）**：超过说明已滑成"报告精简版"，砍回预期；**需求本身已无歧义时可压到 3 行**（一句话理解 + 我打算怎么做 + 需你拍板），但不省略
3. **必须有判断**：「我的取舍」与「需你拍板」不得为空——否则用户只能回"对"，等于没对齐
4. **不得自判跳过**：仅两种情形可跳——用户显式说"别问了直接出报告"；本需求是已确认结论的机械延续（用户明确说"照上次再加一个字段"）。跳过须在报告留一行 `预期对齐：已跳过（{原因}）`。**不按档位自动豁免**——模糊需求恰恰最常被误判为"单点功能"
5. **误判筛查命中即停**：轻量调研中发现"这是 Bug / 已有能力"，**先提醒用户确认，不出预期**——阶段 0 的前提是"这是要新建或变更的产品能力"，跑错赛道时预期越准越浪费

### 轻量调研边界（阶段 0 允许做什么）

**第一步固定是查记忆，不是直接 grep**：`use_skill("ki-search-first")` → **按它执行 `use_skill("ki-search")`**（只加载不检索＝没进门）。命中直接决定这份预期该不该出——"已有能力 / 被砍过的方案 / 踩过的坑"往往只在记忆里，代码里看不出"为什么没做"。

| 允许（够形成判断即停） | 禁止（留到确认后） |
|---|---|
| **记忆与索引定位（必做首步：`ki-search-first` → `ki-search`；`index-lookup` 反查）** | 影响面四类来源穷举、下游消费方全查 |
| 误判筛查：已有能力 / 是否 Bug（grep 入口 + 读关键实现） | 六维缺口回扫 |
| 现状锚定：该功能现在怎么工作（主链，不穷举分支） | 可行性四档 / 复杂度四维判定 |
| 约束发现：明显的平台 / 权限 / 数据约束 | 需求清单编号与优先级排序 |

> **成本断点**：前置阶段若把影响面查完，等于把成本最高的部分放到了确认之前，闸门价值归零。

### 输出模板

```markdown
## 我的产品预期（请确认或纠正）

**一句话理解**：用户真正要的结果是 ___（不是他要的那个功能）

**预期行为**：主链 输入 → 处理 → 输出；关键分支 / 边界 ≤5 条（非功能要求并入此处或成功标准）

**我的取舍**：打算做 A ／ 不做 B，因为 ___（1-3 条）

**成功标准**：一句话可判定的验收口径

**需你拍板**：≤3 条真分歧（是方案分歧，不是"要不要做"）

**图**：命中下方判据时给（默认 1 张，复杂最多 2 张）

**我不确定的**：___（1 句，防"预期固化"——用户容易顺着结构化预期说"对"）
```

**不写**：`REQ-xx` 编号、优先级 / Kano、影响面表、负向需求、六维回扫、可行性 / 复杂度、执行摘要。

### 图判据（复用现有引擎，不新造规范）

| 需求特征 | 出什么 | 引擎 |
|---|---|---|
| 界面 / 布局变化 | 现状 → 预期 UI 图（现状不可知只出预期并注明） | `ui-to-ascii` 描述生成模式（ASCII） |
| **交互流程**：谁在什么条件下做什么，多步 / 多分支 | 流程图 | 文字树（≤15 节点）/ Mermaid（分支多或需落盘） |
| **数据流**：新数据的产生 / 流向 / 存储 / 消费 | 数据流图 | Mermaid（对齐 `requirement-mining` 的 `diagram-guide`） |
| **复杂逻辑**：状态机 / 条件矩阵 / 并发时序 | 状态图 / 时序图 | Mermaid |
| 单步无分支 / 只读写现有字段 | 可省 | — |

> 判为"可省"时在预期末尾写一行 `本轮未出图（判断：{理由}），需要图请说`——用户不知道你判了可省，不告知就等于替他做了决定。选型理由、规模上限与确认口径见 `reference.md` 11.3。

### 确认之后

- **用户确认** → 进入 M1 详细分析；已确认条目转为「已确认结论」，报告 §0 记基线、§6 只留**确认后新出现**的假设，**同一件事不问两遍**
- **用户纠正** → 更新预期并再确认一次；纠正涉及现状 / 范围 / 成功标准时**图必须重绘**（旧图即旧错误）
- **连续纠正 ≥2 次** → 自动切严谨档（`requirement-mining` 逐项确认），与档位表一致；**切换时把已确认的预期作为它 Step 3 的输入**，只补问未确认项，不重头再问一遍
- **预期确认 ≠ 需求确认**：接力仍挂在**报告交付之后**——预期只定方向、未定范围，此时转设计等于白做（见「主动接力」不接续表）

## M1 需求定义

### 档位选择（自动）

| 档位 | 触发条件 | 交互量 |
|------|---------|--------|
| **一次成型档**（默认） | 单点功能、涉及 ≤2 个角色、无外部依赖、需求条目预期 ≤5 | 1 个方向确认点（阶段 0 产品预期） |
| **严谨档** | 命中任一：多角色/多模块、外部依赖未确认、涉及流程或状态机变更、用户说"严谨档/逐项确认"、一次成型档下用户连续纠正 ≥2 次 | 完整保留 `requirement-mining` 的逐项确认 |

### 一次成型档流程

0. **产品预期对齐（阶段 0，硬闸门）**：**首步查项目记忆**（`ki-search-first` → 实际执行 `ki-search`，见公共规则 7）→ 轻量调研 → **误判筛查命中（是 Bug / 已有能力）则先停、不出预期**（硬规则 5）→ 输出产品预期 → **等用户确认**；跳过仅限「阶段 0」节列的两种情形（**跳过预期也不跳过查记忆**）。确认前不得进入步骤 2-7。
1. **误判筛查**：是已有功能的 Bug？是系统已有能力？命中则先提醒用户确认（阶段 0 调研中已查过，此处只落结论）。
2. **关联功能与影响评估**（不可跳过，确认后才做）：按上节四类来源盘出关联功能 → 出影响评估表 → 「需配套改」项直接进需求清单；判定不了的标「需拍板」留给用户
3. **自主推理**：按 `requirement-mining` 的分析框架（形态判断 / 功能本质 / 场景 / 角色 / 非功能需求 / 变更面）补齐确认后仍需的细化判断——**阶段 0 已确认的形态 / 角色 / 场景 / 变更面直接沿用，不重推**；**假设由 AI 自主填**，不逐条问用户。`requirement-mining` / `negative-requirement` 未安装时按其框架自主推理，不阻塞、不报错。
4. **负向内联**：直接按 `negative-requirement` 的分类表（误操作 / 参数错误 / 中途放弃 / 状态异常 / 权限 / 数据异常 / 外部依赖）筛出**本需求真实相关**的 3-8 条，写入需求报告「负向需求」章节，不单独跑一轮。
5. **需求缺口回扫**（不可跳过）：拿需求质量六维清单逐项自检（场景完整性 / 验收标准可达性 / 需求一致性 / 角色-需求对齐 / 边界/异常覆盖 / 术语一致性，判定问句见 `reference.md` 4.4）。**只判不跑**——不建角色矩阵、不出推演报告、不落 `review/`。过不了维度的：能从现有信息显式化的**直接补进需求清单**；补不了的进 §5 待确认清单。**六维全过也要在报告里写一行结论**，禁止静默跳过。
6. **出报告**：含 **§0 预期对齐记录** + 影响评估表 + 需求清单（优先级 / 预期效果 / 验收标准）+ **实施可行性与复杂度**（报告 §4.1）+ 负向需求 + 缺口回扫结论 + 关键假设表（只留确认后新增）+ 建议下一步；**涉及界面变更时必附基本 UI ASCII 图**（现状 / 预期，见公共规则 13）。
7. **定稿与追加拍板**：报告默认**直接定稿交付**——方向已在阶段 0 确认，不再重复问第二遍；§6 只留确认后**新出现**的假设（阶段 0 已确认内容标「已确认」或移入 §0，不复述）。**仅当确认后的分析中新出现需拍板项**（如影响面发现破坏对外契约、缺口回扫新增条目冲突）才追加一次确认，并标注「新增拍板项，非重复确认」+ 说明为何确认前无法发现。**任何时点假设被推翻都必须回刷可行性 / 复杂度**——量级、依赖、权限类假设一旦改动，档位常整档跳变（如"十万行"改"百行"，`🧪` 可能直接变 `✅`、复杂度由高降中），只改需求清单不改这两列＝结论已失效

> 一次成型档**不省**的是：**产品预期对齐（阶段 0）**、关联功能影响面、根本性分析（这方案治本吗）、负向场景、**需求缺口回扫**、验收标准。**省的是**细致分析阶段的交互轮次——不是方向确认本身。

### 严谨档流程

完整按 `use_skill("requirement-mining")` 流程执行；需求清单确认后调用 `use_skill("negative-requirement")` 补负向需求，最终合并为本 skill 的 PM 报告。
**严谨档不豁免记忆检索**：`requirement-mining` 流程本身不含项目记忆检索（已核）——起手仍按公共规则 7 查一遍，结果作为它 Step 1 自主推理与 Step 3 假设的输入；否则最复杂的需求反而最不查历史决策。
**阶段 0 不叠加轮次**：它的 Step 3「需求理解（请确认或纠正）」本就在正确时序上——**在其现模板上追加「我的取舍」「成功标准」两节即可**（「一句话理解」由它的「功能本质」承担，不重复写第二遍；假设表与变更点表照它的格式），图按阶段 0 判据给，**不得在它之前再加一轮预期确认**（那是同一个确认点问两遍）。
**影响面不因走严谨档而省略**：关联功能盘点与影响评估**照做**（可在 `requirement-mining` 流程中一并完成），报告仍须含影响评估表——严谨档省的是交互，不是内容。
**缺口回扫同样不省略**：`requirement-mining` 全流程不含需求质量六维检查，报告定稿前仍按 `reference.md` 4.4 回扫一遍（重点看"验收标准可达性"与"需求一致性"两维）。
**可行性 / 复杂度不重算**：直接沿用它的 Step 5.5 结论与 Step 6.6 评分，按「与上游 skill 的口径关系」映射进 §4.1，并在证据列注明来源——同一份报告里不出第二套复杂度（否则用户看到两个答案）。

### 出口

报告末给出下一步推荐（对齐 `requirement-mining` Step 8 的行动集）：交互复杂 → `interaction-design`；数据复杂 → `data-flow-model`；技术不明 → `design-craft`；技术风险 → `demo-verify`；**可实施且复杂度低** → `plan-track` 建档直接实现。可行性 / 复杂度口径见「实施可行性与复杂度」节。

**接力**：前四类属只读 / 方案类，**报告交付后自动转过去继续**（不等用户点名）；`plan-track` 意味着开始改码，只写建议、不自动转。M1 的接力统一挂在**报告交付之后**——阶段 0 的预期确认**不触发接力**（预期只定方向、未定范围，此时转设计＝白做）；**接力 `ui-designer` 时，阶段 0 已确认的图随报告一并传入**，作为其设计输入，不必重画。

**复杂度判据**：一次成型档不跑完整评分，但四维（结构面 / 数据与状态 / 依赖面 / 确定性）**照过一遍**，取最高档并标主导维度，下一步按主导维度分流。拿不准标 `复杂度待定` 进待确认，不要把"看起来简单"当低复杂度。

## M2 产品体验走查

### 六维走查清单

| 维度 | 问自己 | 典型证据 |
|------|--------|---------|
| **价值达成** | 用户想办的事，现在办成了吗？有没有绕路 | 走一遍主流程 |
| **路径效率** | 达成目标要几步、几次等待、几次跳转 | 关键路径步骤数 |
| **反馈与容错** | 出错/空/加载/超时时有反馈吗？能恢复吗 | 触发一次异常 |
| **一致性** | 同类操作、术语、组件、提示口径是否一致 | 跨页面比对 |
| **可发现性** | 功能藏得深吗？新用户找得到吗 | 信息架构 |
| **边界与异常** | 超长文本、大数据量、极端输入的呈现 | 构造边界数据 |

> **六维只判"体验好不好"，不推"逻辑会不会坏"**：走查中若发现"数据串台、空值覆盖、重复提交、失败后仍能操作、权限能绕过、发版后白屏"这类迹象，直接接力 `frontend-walkthrough` 的阶段 1.5（缺陷推演：异步态矩阵 + 十类缺陷族，产出假设 + 复现步骤 + 证据等级），本 skill 不展开代码逻辑与时序分析。

### 执行

1. 界定走查对象边界（模块/页面/入口），边界不清先问一句；**先按公共规则 7 查该模块的已知坑与历史体验问题**——避免重复走查已修复过的地方，也避免把已知取舍再报一遍
2. **按判定类型选手段**（不是"能跑就跑"）：符合性维度（价值达成/一致性/可发现性，多可代码直读）→ 优先代码直读 `🟢`；体验类维度（路径效率/反馈容错/边界呈现）→ 需运行实测 `🟢`，跑不起来时代码只能给 `🟡` 并在报告头声明"未实测"
3. 每个发现写：**现象 → 影响谁 → 证据等级 → 建议方向**（不写实现方案，那是设计阶段的事）
4. 用 Kano 分类（必备/期望/兴奋/无差异）+ 价值×成本矩阵定优先级，输出 `优先级 | 发现 | Kano | 价值 | 成本 | 证据 | 建议`；每条发现**另给实施可行性 + 复杂度**（见「实施可行性与复杂度」节，单独成表不进本表公式）
5. **排除项也值钱**：明确写"经走查排除：XX 维度无问题"，避免用户重复问

## M3 缺失功能推演

### 三条证据路径（从严到宽）

| 等级 | 路径 | 具体信号 |
|------|------|---------|
| `🟢` 代码实证 | 代码里已有痕迹但没做完 | `TODO/FIXME/未实现占位`、入口已建但点击无响应、路由已注册页面缺失、配置开关存在但恒为关、文档/README 承诺但代码无 |
| `🟡` 结构可证 | 有半成品结构 | 有数据模型无操作入口、有后端接口无前端调用、有前端页面无后端接口、有管理端无用户端、有写无读（能建不能查） |
| `🔴` 推断 | 参照同类产品 | **必须写明参照物**（"同类 SaaS 普遍有 X"），且只进待确认清单 |

### 硬约束

- **禁止凭空发明**：`🔴` 项不得写成"产品缺少 X"的断定句，只能进「待确认：是否有意不做？」
- **区分"有意不做"与"漏做"**：MVP 常见的有意省略（如未做国际化、未做审计日志）要标注"可能是有意取舍，需确认"，不当成缺陷。**判据优先来自项目记忆**——"为什么没做"通常记在决策记录里，代码只能证明"没做"、证不了"为什么不做"（公共规则 7 的必查点，不查＝注定把有意取舍当漏做）
- **与 M2 合并**：M3 的缺失功能与 M2 的优化点进同一张清单，用 `来源` 列区分
- 每条缺失功能同样走 Kano + 价值×成本排序，**并给实施可行性与复杂度**——缺失功能最容易在依赖面（上游数据/接口未就绪）与确定性（不知道怎么实现）上翻车

## M4 界面视觉走查

### 先问：这个判定需要画面吗

- **不需要**（符合性/规范类："按钮都有禁用态吗""错误提示都带原因吗""间距是否统一 token"）→ **直接代码直读**，不进下面的能力探测，不必让用户起服务或截图
- **需要**（好不好看、层级是否清晰、响应式是否折行）→ 才走能力探测拿画面

### 能力探测（按顺序尝试，命中即停）

| 档 | 条件 | 做法 |
|----|------|------|
| **L1 自主** | 调 `use_skill("browser-evidence")` 判定为 A 档（有可用后端且能截图） | 起服务 → 打开页面 → 截图 → 读图走查（强制覆盖：默认态 / 空态 / 加载态 / 错误态 / 长文本 / 窄屏） |
| **L2 半自主** | 能打开页面但**拿不到画面**（如只有 `preview_url`，AI 看不到渲染结果） | AI 开预览页供用户观看 + 读前端源码/CSS 静态推演（`🟡`）；同时给出**具体肉眼检查清单**请用户逐项确认 |
| **L3 手动上传** | 项目跑不起来 / 无浏览器 / 截不了图 | AI 先给出**拍摄清单**（哪几屏、什么状态、什么分辨率），用户上传截图后 AI 读图走查（`🟢`） |
| **L0 纯静态** | 连截图都没有 | 只读源码推演，**证据等级强制 `🔴`**，报告头声明"未看到实际渲染，以下为源码推断"，禁止写成"界面存在 XX 问题" |

> **能力探测是硬步骤**：不得跳过探测直接宣称"我看过界面了"。无画面即降级，降级声明必须写进报告头。
> **判定优先调 `use_skill("browser-evidence")`**；该 skill 未安装时按 `reference.md` 7.1 的顺序自判（有可用后端且能截图 → L1，只开预览 → L2，跑不起来 → L3，都没有 → L0），不阻塞。

### 走查清单（有画面时逐项过）

视觉层级与重点 · 对齐与间距一致性 · 配色与对比度 · 字体与字号规范 · 组件状态完整性（悬停/聚焦/禁用/加载/错误/空）· 响应式与窄屏 · 文案（术语一致、语气、错误文案是否说人话）· 可发现性与操作反馈 · 明显的无障碍问题（对比度、可点击区域、键盘可达）

### 拍摄清单模板（L3 用）

```
请提供以下截图（能多屏就多屏）：
1. 首页/主界面（默认数据）
2. 核心操作流程的中间态
3. 空状态（无数据）
4. 错误/失败态（随便造一个错误）
5. 窄屏或移动端视图（如有）
分辨率：桌面 ≥1440 宽，移动 375 宽。无法提供第 N 项请说明，我会按可得画面降级。
```

### 走查之后

结论指向「视觉方案本身要重做」（不是按现有规范修实现）→ **先附基本 UI ASCII 图**（问题位置 / 预期布局，见公共规则 13）再按「主动接力」转 `ui-designer`；界面问题进报告同样给可行性 + 复杂度（单点样式缺陷通常就是 `✅ 可实施` + 复杂度低，一句话带过即可，不为此展开长篇）；指向交互流程缺陷 → `interaction-design`；确认是 Bug → `debug`（只到定位）。仅实现偏差（规范已定、实现没跟上）留在本清单走修复流程——**修复前先把范围与优先级交用户确认**（公共规则 14），确认后走 `request-guard`，不得直接改完再汇报。

## 约束

1. `🔴` 推断禁止进结论区，只能进「待确认清单」且必须配验证方法
2. 不修改产品代码，不自动实施优化建议；**接力也不越过这条线**——`debug` 只到定位根因，修复交用户拍板后走 `request-guard` → `code-review`；确需落地时按公共规则 14「确认 → 改 → 报告」，不得先改后报
3. 优先级一律 Kano + 价值×成本，不给无依据的精确收益数字
4. M4 未获得画面时必须降级声明，禁止假装看过界面
5. M3 不得把"有意不做"当"漏做"，不确定即标注待确认
6. M2 + M3 合并输出，禁止两张独立清单
7. 报告不替代人工产品决策，最终取舍权归用户
8. **确认点口径**：一次成型档固定 1 个方向确认点（阶段 0 产品预期）+ 0~1 次「新增拍板项」补充确认（须声明是新增，不得复述已确认内容）；用户纠正 ≥2 次自动切严谨档。M2/M3/M4 的确认点是「模式与范围」
9. 需求类产出落盘须走 `req` 命令（`requirement-doc-store`），禁止手拼路径
10. **Kano 不允许硬猜**：判定依据不足标 `Kano 待定`，待定项**不得默认按"期望"参与排序**，一律进「待确认清单」——把待定当期望会把真正的必备项埋掉
11. 组合模式证据声明取最低档（见公共规则 8），禁止用部分实测为全报告背书
12. **接力必须有触发信号**：只有命中「主动接力」表才转，禁止"顺手多跑一个"；深度 ≤ 2 跳，目标未安装 / 失败即降级为建议，不阻塞报告
13. **缺口回扫必做**：M1 出报告前完成需求质量六维回扫（只判不跑，不生成推演报告）；未通过项必须补进需求清单或进待确认清单——**补进清单只限把隐含信息显式化，不新增需求**，且补进的条目须同时给优先级 + Kano（判不了标 `Kano 待定` 进待确认）；全过也要显式写「六维无缺口」（轻量档压缩规则见 `reference.md` 4.4）
14. **可行性与复杂度必给**：四模式报告均须含 §4.1 实施可行性与复杂度（条目与 §4 主表一一对应；全部 `✅` 且复杂度 ≤ 中时可压成一句，其余展开成表）；可行性落四档之一（`✅` / `⚠️` / `🧪` / `⛔`），复杂度按四维**取最高档**并标主导维度；M1 严谨档**沿用 `requirement-mining` 5.5 / 6.6 并映射、不重算**；`⛔` 须给解除路径、`待定` 须进待确认；两者**不参与优先级公式**（公共规则 15）
15. **阶段 0 闸门不可绕过**：M1 必须先出产品预期并取得确认（或记录合法跳过原因）再进入细致分析；预期 ≤25 非空行、不得含需求编号 / 优先级 / 影响面 / 可行性档位；「我的取舍」「需你拍板」不得为空
16. **记忆检索必留痕**：任何模式开始前按公共规则 7 查项目记忆（加载 `ki-search-first` 后**必须实际执行 `ki-search`**），报告 §2 写「记忆命中：N 条（关键词）/ 未命中（关键词）/ 不可用（原因）」一行，轻量档并入执行摘要；**跳过阶段 0 预期不豁免本项**。无此行、或"未命中"不带检索关键词，均视为未查，报告不合格

## 反模式

- ❌ **把 requirement-mining 流程抄一遍** → 用户得到"一样繁琐 + 多一层壳"。本 skill 的价值是编排与判断，不是复刻
- ❌ **M2 滑成 code-review** → 开始点评函数职责、命名、设计模式。看到自己在写这类内容立即停，回到六维
- ❌ **M3 发明需求** → "同类产品都有所以你也该有"当结论写。必须标 `🔴` + 参照物 + 进待确认
- ❌ **无画面假装看过** → "界面存在明显的对齐问题"（实际没截图）。无画面必须降级声明
- 🔴 **把推断当结论**：`🔴` 出现在执行摘要里 = 报告作废重写
- ❌ **出两张清单**：M2 优化点一份、M3 缺失功能一份，用户自己合并 → 违反「模式路由」的组合规则
- ❌ **给假精确**："预计提升转化 12%""约 3 人日"。无数据支撑时只给价值/成本的高中低
- ❌ **直接改码**：本 skill 只判断。想改先走 `request-guard`
- ❌ **先改后报**：把建议"顺手"改成代码 / 改完页面再截图汇报——用户没确认取舍与范围，改坏了没有基线可比、责任也无从界定。顺序永远是「确认 → 改 → 报告」（公共规则 14）
- ❌ **一次成型档还逐条问执行细节**：8 个问题轮番问接口怎么选、字段怎么加 = 档位选错，回到档位表重判；但**方向确认（阶段 0）不是"逐条问"，不得一并砍掉**
- ❌ **需求没确认就开始分析**：拿一句话需求直接跑完影响面 / 负向 / 六维回扫 / 可行性，最后才问"假设对吗" → 方向一错全篇作废。阶段 0 闸门就是为此设的
- ❌ **产品预期写成报告精简版**：预期里出现 `REQ-xx`、P0/P1、Kano、影响面表、可行性档位 → 越界做了确认后的活，用户面对"已成形结论"，纠正成本回到原点
- ❌ **预期只有复述没有判断**：「我的取舍」「需你拍板」留空，只写"我理解你要 XX 功能" → 用户只能回"对"，等于没对齐
- ❌ **按"看起来简单"自判跳过预期**：模糊需求最常被误判为单点功能；跳过仅限「阶段 0」节列的两种情形
- ❌ **用阶段 0 的确认冒充报告确认**：预期已确认 ≠ 影响面 / 负向 / 可行性不用再看，报告该给的仍然全给
- ❌ **阶段 0 就把影响面查完**：前置调研做成全量调研，等于把最贵的活放在确认之前，闸门价值归零
- ❌ **只加载 `ki-search-first` 就往下走**：加载前置门 ≠ 完成检索，一条记忆都没查 → 必须实际执行 `use_skill("ki-search")` 并在报告 §2 留痕（公共规则 7）
- ❌ **跳过预期时连记忆一起跳过**："需求简单"变成"什么都不查" → 跳过预期 ≠ 跳过查记忆（M1 步骤 0）
- ❌ **符合性问题非要跑起来**：用户问"导出是异步的吗"，却要求先起服务再验证 → 读代码 30 秒可判定，起服务是浪费
- ❌ **用代码推断体验/视觉**："代码里有 loading 分支，所以加载反馈没问题" → 有分支 ≠ 用户看得到，属 `🟡`，想定论必须看画面
- ❌ **只讲新功能、不提碰到谁**：需求报告只写"要做什么"，不写"会影响到谁" → 开发做完才发现下游炸了
- ❌ **AI 自行宣布"影响可接受"**：可接受性是业务决策。破坏已有习惯/数据/对外契约的，必须标「需拍板」交给用户
- ❌ **影响项只写在说明里、不进需求清单**：分析提了一嘴，开发漏做 → 每条「本次一并改」必须在需求清单有对应条目
- ❌ **查不到就当没有**：未发现关联方要标「未发现（需确认）」并给查证方法，不能默认无影响
- ❌ **跳过需求缺口回扫**：只把需求清单列完就交付 → 漏的往往是"验收标准不可判定""两条需求互相冲突"这类要等开发阶段才炸的洞
- ❌ **该接力却只写「建议下一步」**：明明 `ui-designer` 能接着做，却留一句"建议改版"让用户手动点名 → 报告出完就接力，不把编排成本转嫁给用户
- ❌ **接力越界改码**：`debug` 定位出根因后顺手把 Bug 修了 → 红线。修复必须停、交用户拍板
- ❌ **接力当甩锅**：把没做完的 PM 判断（优先级没排、影响面没查）丢给下游 skill → 报告必须自身完整，接力的是「下一种工作」
- ❌ **无因接力 / 关键词接力**：见到「界面」二字就转 `ui-designer`（哪怕只是间距不统一）→ 按接力表的触发信号判，不是关键词匹配
- ❌ **界面结论只给文字不给图**：涉及界面调整 / 重设计却只写文字描述，用户看不到"改成什么样" → 附基本 UI ASCII 图（公共规则 13）
- ❌ **关系表达写成大段散文**：流程 / 调用链 / 层级 / 因果用长段落铺陈，读者要自己捋 → 善用文字树，一行一节点
- ❌ **复杂度只给档位不给主导维度**："这个改动比较复杂" → 用户不知道该卡在哪、该找谁；必须点名主导维度（结构面 / 数据与状态 / 依赖面 / 确定性）
- ❌ **可行性写成形容词**：写"技术上可行"却不说前置条件与阻塞 → 必须落四档之一，`⚠️` 补前置条件清单、`⛔` 补解除路径
- ❌ **把优先级当可行性**：用户问"能不能做"，回答"优先级不高先不做" → 可实施性是事实判断，优先级是取舍判断，必须分开答
- ❌ **复杂度取平均或默认低**：跨模块 + 无现成方案，却因"改动点不多"标低 → 四维取最高档，判不出标 `待定`
- ❌ **`⛔ 阻塞` 只写"做不了"**：不给解除路径与"解开后大概什么档位"，用户无法判断值不值得去解
- ❌ **复杂度与成本互相照抄**：两列写成镜像（复杂度高就成本高）→ 成本看投入量、复杂度看结构难度与不确定性，各自独立给依据
- ❌ **可行性与复杂度写同一句话**："要做技术验证，比较难"→ 可行性答"现在能不能定"，复杂度答"难在哪一维"，两列各写各的
- ❌ **为砍掉的条目白判复杂度**：Kano=无差异 / 建议不做的条目也逐条给可行性 + 复杂度 → 直接标"建议不做"并说理由，不进 §4.1
- ❌ **一份报告两个复杂度**：M1 严谨档既贴 `requirement-mining` 6.6 的"中"、又按四维判"高" → 沿用上游结论做映射，有分歧取更严档并注明，§4.8/§4.9 不进结论区
- ❌ **M2/M3 把 `✅` 当"方案已定"**：方案都还没出就说可实施 → `✅` 只代表"该方向未发现阻塞"，需要具体方案才能定的给 `⚠️` / `🧪`
