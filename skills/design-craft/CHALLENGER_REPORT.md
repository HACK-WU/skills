# Challenger 二次质疑集成

> design-review 通过后自动触发。根据需求类型选择质疑策略，产出质疑报告后由用户决定修复或落盘。

---

## 触发时机

design-review 自动评审循环通过后（无 🔴 阻断，无 🟡 警告），自动调用 challenger。

---

## 策略选择

根据需求类型自动匹配质疑策略：

| 需求类型 | 策略文件 | 质疑重点 |
|---------|---------|---------|
| 新增功能 | `strategies/feature.md` | 需求验证、边界验证、冲突验证、体验质量质疑 |
| Bug 修复 | `strategies/bug-fix.md` | 根因验证、修复验证、副作用验证、用户体验质疑 |
| 重构/优化 | `strategies/optimization.md` | 效果验证、复杂度验证、语义验证、用户体验质疑 |

> 策略详细内容见 [challenger skill](../../challenger/SKILL.md)。

---

## 质疑报告结构

challenger 输出报告包含以下部分：

```
1. 复现流程确认     → 触发条件、复现步骤、预期与实际
2. 变更概述         → 变更类型、描述、文件、目的
3. 质疑详情         → 逐条质疑（类型/位置/质疑点/验证方法/风险/置信度/建议）
   3.5 体验质量质疑  → 正向体验 + 负向体验
4. 质疑总结         → 统计 + 风险分布
5. 行动建议         → 必须处理 / 建议处理 / 可选处理
```

> 完整模板见 [challenger templates/report.md](../../challenger/templates/report.md)。

---

## 决策分支：修复还是落盘

challenger 输出质疑报告后，**不自动修复**。向用户展示选项：

```text
🔍 Challenger 二次质疑完成
━━━━━━━━━━━━━━━━━━━━━━

策略：{feature / bug-fix / optimization}
发现问题：N 个（高风险 X / 中风险 Y / 低风险 Z）

请选择后续操作：

[1] 🔧 自动修复
    - 按行动建议自动修改设计文档
    - 修复后调用 design-review 验证（仅 1 轮）
    - 仍有问题 → 输出清单，交由人工判断

[2] 📁 报告落盘
    - 将质疑报告保存到需求目录
    - 质疑项记录在案，转为人工跟进
    - 不影响当前设计评审结论

[3] ⏭️ 跳过
    - 不修复、不落盘，直接交付
```

### 选项 1：自动修复

```
报告输出 → 用户选修复
    → 按行动建议逐条修改设计文档
    → 调用 design-review 验证（仅 1 轮）
        → 无问题 → ✅ 输出修复确认
        → 仍有问题 → ⚠️ 输出剩余问题，人工判断
```

### 选项 2：报告落盘

```
报告输出 → 用户选落盘
    → 将质疑报告写入 {storage_path}/{需求目录}/review/challenge-report.md
    → 调用 req update 注册文档关联
    → ✅ 落盘完成，质疑项转为人工跟进
```

落盘命令：

```bash
req update {REQ-NNN} \
  --docs add review/challenge-report.md,review \
  --changelog "完成 challenger 二次质疑审查"
```

### 选项 3：跳过

```
报告输出 → 用户选跳过
    → 不修改、不落盘
    → 直接进入交付
```

## 质疑过滤：设计层面 vs 编码层面

challenger 的质疑非常犀利，可能产出大量尖锐问题。但**当前评审对象是设计文档**，不是代码。需要区分哪些质疑必须落在设计文档中，哪些是编码常识、留给实现阶段即可。

### 判断标准

> **核心问题**：这个质疑点如果不在设计文档中明确，编码阶段会做出错误决策吗？

| 如果答案是 | 处理方式 |
|-----------|---------|
| **是，会做错** | → 必须更新设计文档 |
| **不会，编码时会自然做对** | → 记录在质疑报告中，不修改设计文档 |

### 落在设计文档（必须修改）

这些是设计层面的问题，不在文档中明确会导致实现偏离方向：

| 质疑类型 | 示例 | 为什么必须落在设计文档 |
|---------|------|----------------------|
| 架构决策 | "单机方案在高并发下会崩溃" | 不明确的话，编码阶段会按错误架构实现 |
| 接口契约 | "返回值类型与调用方期望不一致" | 接口签名的歧义会导致集成失败 |
| 数据模型 | "缺少冗余字段会导致 N+1 查询" | 数据建模错误无法靠编码修正 |
| 交互流程 | "超时后用户没有恢复路径" | 交互断层会导致功能不可用 |
| 安全设计 | "权限校验只在入口做，内部接口裸奔" | 安全设计缺陷是系统性漏洞 |
| 异常约定 | "下游异常直接透传给用户" | 没有约定的话每人会做不同的处理 |

### 留在编码阶段（不改设计文档）

这些是编码常识或实现细节，合格开发者会在编码时自动处理：

| 质疑类型 | 示例 | 为什么不需要落在设计文档 |
|---------|------|------------------------|
| 空值校验 | "user_id 为 null 时未处理" | 编码阶段的防御性编程常识 |
| 日志记录 | "关键路径缺少日志" | 编码时自然会加上 |
| 输入格式校验 | "邮箱格式未做正则校验" | 前端/Controller 层的标准实践 |
| 并发加锁 | "map 并发读写可能 panic" | 语言/框架层面的并发安全措施 |
| 资源释放 | "文件句柄未 close" | 编码规范，或语言特性（defer/try-with） |
| 超时重试策略 | "下游超时没有设置重试次数" | 这是实现细节，默认值即可满足 |

### 灰色地带

部分质疑处于中间地带，按以下规则判断：

| 质疑特征 | 处理方式 |
|---------|---------|
| 编码常识但项目有特殊约定 | → 在文档中标注"需遵循项目编码规范" |
| 实现细节但影响接口行为 | → 只在接口设计章追加备注 |
| 编码常识但当前团队可能忽略 | → 记录在质疑报告中但不修改文档，在交付时口头提醒 |

---

## 反模式

- ❌ challenger 发现问题后不询问用户直接修复：设计类问题可能需人工权衡
- ❌ challenger 修复后再进入新的 challenger 循环：防止无限递归
- ❌ challenger 报告落盘后不调用 req update：文档关联丢失
- ❌ 将编码常识类质疑强行写入设计文档：设计文档不是代码规范手册，保持聚焦
