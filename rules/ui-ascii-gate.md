# 界面改动先出 ASCII 图确认

## 规则

任何**页面样式 / 布局**的编写与修改（新增界面、改版、调区块结构、换排列方向、改断点、改显隐与层级、修视觉缺陷），**动手前**必须先走 `ui-to-ascii` 的「界面确认闸门」：出 ASCII 图 → 与用户确认 → **确认后才可实施**。禁止"先改完再给用户看效果"。

**为什么立成规则而不只写在 skill 里**：用户可能不经过任何 skill 直接下命令（"把这个按钮挪到右边"），skill 内的闸门不会被加载；规则 `alwaysApply` 必进上下文，才能覆盖无 skill 的直接请求。

## 执行

1. **识别**：本次请求是否改变界面的**结构 / 排列 / 尺寸关系 / 断点 / 显隐与层级 / 视觉缺陷**——命中任一 → 走闸门
2. **出图**：`use_skill("ui-to-ascii")` → 描述生成模式 → 按其「界面确认闸门」出图（修改类给现状 + 预期双图；新建类给预期图 + 放置骨架；多方案各一图 + 推荐）
3. **确认**：图中歧义标 `[待确认]`；结尾明确"请确认后我再开始"；取得**明确确认**（"可以 / 确认 / 就这样"，或用户明确授权"你定 / 随便"并留痕）后才动代码
4. **改后复核**：实施完成向用户说明实际效果与确认图的差异（有能力截图时截图比对）
5. **改图重来**：用户改布局 → 重绘并重新确认；旧图即旧错误，不沿用

**豁免**（须说明依据）：只改样式**取值**且不改变结构 / 布局关系 / 换行 / 显隐（调色值、字号 ±1~2px、圆角、阴影、局部间距）；纯文案；纯后端且界面呈现不变。判定口诀："改完之后结构上能否看出区别"——看不出可豁免，看得出必须出图。

## 例外

- 用户明确说"不用出图，直接改"（留痕后按其指示执行）
- 上游已给出**经用户确认**的 ASCII 布局图 → 以其为基线实施，不重复出图
- 无人值守 / 子 agent 拿不到确认 → 输出图与变更点表交调用方取确认，**不自行实施**
