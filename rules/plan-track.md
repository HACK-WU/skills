# plan 模式（计划与进度跟踪）

## 规则

**plan 模式 = 把任务的执行状态写进 `.plans/` 文件，而不是留在对话上下文里。**

本规则负责**识别场景**（何时进入 plan 模式），`use_skill("plan-track")` 负责**执行流程**（怎么建档、怎么更新）——识别到即调用。

### 一、何时进入 plan 模式（场景识别）

| # | 场景 | 识别信号 |
|---|------|----------|
| 1 | **用户显式要求** | 说"列个计划 / 建个清单 / 跟踪一下进度 / 做完自检" → **直接进入，不再判定** |
| 2 | **规模超出单轮可控** | 涉及 ≥3 个文件路径，或出现 ≥2 个模块 / 服务名 |
| 3 | **多阶段实施** | 需要 ≥3 个可分离阶段（如 设计 → 实现 → 验证），阶段之间要交接 |
| 4 | **需要跨轮 / 跨会话续做** | 会中途中断、批量工作、长任务，或用户说"下次继续" |
| 5 | **用户表达了对进度的关注** | 问"进行到哪了"、要求分阶段汇报、要先看中间产物，或说"别一次做完" |
| 6 | **已有前置文档要落地** | 手上已有需求文档 / 设计文档 / 工作项清单，需转为可执行步骤 |

**判断依据是任务里的可观测信息，不是"我觉得复不复杂"**；拿不准时进入（成本几分钟，远低于重做）。
**用户显式优先级最高**：说"建"就直接建；说"不用建计划"就不进（已建档案保留状态、不再更新）。

**不进 plan 模式**：单文件小改、文案 / typo 修复、单步问答、纯咨询。

### 二、进入后的节奏（骨架，只增不减）

> `use_skill("plan-track")` 可在本骨架内**细化**（只增不减），不得减少节点。

| 时机 | 动作 |
|------|------|
| 开工前 | `use_skill("plan-track")` → `.plans/{日期}-{slug}/` 建 `plan.md` + `checklist.md` |
| 工作项完成 / 阻塞 / 方案或范围变更 | 更新 `plan.md`（状态 + **证据** + `updated`） |
| 每轮对话结束前（尤其要中断时） | 追加「进度日志」，写明"下次从哪继续" |
| 任务主体完成后 | 逐条自评审 `checklist.md`（P0 未清零不放行）→ 产出物跑一遍 `auto-review` → 交付类再 `acceptance-verify` → 归档 |
| 续做（新会话 / 隔天 / 换窗口） | **先读 `plan.md`** 定位续做点，不凭记忆开工 |

### 三、四条不可妥协

1. **证据绑定**：改动完成但未跑验证，只能标「已改未验」；没有证据不得标「已完成」
2. **清单不可临场放宽**：清单项须有外部依据（完成判据 / 验收标准 / 用户要求 / 任务类型增补表）；**严重度建档时定死，评审期只能回填不能改题**（来源判定细则见 skill）
3. **唯一活台账**：已有 `skeleton-status.md` 等阶段台账时纳入本计划，不另立平行台账；建档前先扫 `.plans/` 复用同源目录
4. **自评审不替代交付验收**：它只是内部闸门，交付验收仍归 `use_skill("acceptance-verify")` 或用户

### 四、退出

- 任务完成（P0 清零）→ 状态收口，`.plans/` 档案**保留不删**
- 任务放弃 → 状态置 `已放弃`，同样保留

## 执行

```
任务开始 → 场景识别 → 命中则 use_skill("plan-track") 建档
        → 执行中按证据更新（每次只改几行）
        → 完成后自评审 → P0 清零 → 收尾（按任务类型可选交接）
```

> **SSOT 分工**：**场景识别、节奏、四条不可妥协**以本规则为准；**建档流程、模板、状态枚举、清单骨架与增补、续做流程、收尾交接**以 `use_skill("plan-track")` 为准。skill 侧可能以同义措辞复述这四条（提注意力用），**一旦出现出入以本规则为准**。

## 例外

- 用户明确说"不用建计划" → 不进入；已建档案保留状态、不再更新
- `.plans/` 下的台账文件是**执行过程记录（非交付物）**，其常规更新**不触发 `auto-review`**（按 auto-review「临时 / 缓存文件」类处理）；任务收尾产出的报告类文档仍照常走审查
