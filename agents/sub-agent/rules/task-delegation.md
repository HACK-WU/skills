# Task Delegation（任务分级委派）

## 核心原则

主 Agent 的智能是稀缺资源，**只用于高认知密度的工作**：

| 工作类型 | 认知密度 | 执行者 |
|----------|----------|--------|
| 核心逻辑决策、核心代码编写 | 高 | **主 Agent**（亲自执行） |
| 测试验证、文档编写、多轮工具调用、信息收集 | 低 | **子 Agent**（委派执行，需结合结果可替代性判定） |
| 子 Agent 结果不符合验收标准 | — | **主 Agent**（兜底介入） |

> 主 Agent 要的是**结果**，不是执行过程。

## 委派判定表

当主 Agent 面临一项任务时，先判定是否委派。**委派需同时满足三个条件**：① 任务性质属辅助类 ② 结果可替代（子 Agent 结论能替代原文） ③ 轮次≥3；任一不满足则主 Agent 亲自执行。

| 判定维度 | 委派给子 Agent | 主 Agent 亲自执行 |
|----------|---------------|-------------------|
| 任务性质 | 测试验证、文档编写、多轮工具调用、信息收集、批量格式化 | 架构设计、核心算法、核心业务代码、关键 Bug 修复 |
| 智能要求 | 机械执行，有明确步骤可循 | 需要项目全局上下文做权衡决策 |
| 上下文需求 | 仅需局部文件/接口信息 | 需完整决策链与项目心智模型 |
| 失败代价 | 低，可重试或主 Agent 兜底 | 高，失败影响核心产出 |
| 轮次消耗 | 自己执行需 ≥ 3 轮工具调用 | 1-2 轮即可完成 |
| **结果可替代性** | 子 Agent 产出是结论/判断/摘要，主 Agent 无需再看原文 | 子 Agent 只是搬运原文，主 Agent 仍需读原文（如读单文件） |

## 委派成本阈值

**必须先估算再委派**，避免过度委派：

- 自己执行预计 **≥ 3 轮工具调用**（如：反复跑测试看输出、多次 grep 收集散落信息）→ **委派**
- 自己执行 1-2 轮即可完成 → **直接执行，不委派**
- 委派描述成本（任务背景 + 目标 + 验收标准）必须显著小于自己执行的预期消耗，否则不值得委派
- **预估不出时按保守原则判定**：任务属于明确可执行的辅助类工作（测试/文档/收集）→ 视为 ≥3 轮，委派；属于核心决策类 → 不委派

### 结果可替代性原则（核心判定）

委派是否真省 token，取决于子 Agent 的产出能否让主 Agent **免于消费原始信息**：

| 情形 | 举例 | 委派？ |
|------|------|--------|
| ✅ 子 Agent 给出结论/判断/摘要，主 Agent 无需再看原文 | 多文件搜索"是否存在 X"→ 返回"3 个文件中 2 个包含"；跑测试 → 返回通过/失败汇总 | **委派省 token** |
| ❌ 子 Agent 只是搬运原文，主 Agent 仍需读原文做决策 | 读单个文件内容；查看某段代码——主 Agent 最终要看全文 | **画蛇添足，自己做** |

> 简单任务不等于该委派。读一个文件是简单任务，但委派子 Agent 读了，原文还是要回到主 Agent 眼前，等于白费一轮调用。判定关键不是"简不简单"，而是"子 Agent 的结论能否替代原文"。

## 动态委派

委派不只发生在任务开始时。主 Agent 在执行核心任务过程中，若发现**接下来的几个步骤属于低难度机械操作**（且满足结果可替代性），可中途委派子 Agent 执行这些子步骤，避免主 Agent 算力浪费：

- 主 Agent 写完核心代码 → 发现需要跑测试验证 → 委派子 Agent 跑测试
- 主 Agent 改完接口 → 发现需要核对多个调用方是否兼容 → 委派子 Agent grep 调用点汇总
- 主 Agent 定位 Bug → 发现需要收集多个日志文件中的错误模式 → 委派子 Agent 汇总

**动态委派判定**：当前步骤是高认知密度（核心决策/代码）→ 自己做；预判后续连续步骤是低难度机械操作且结果可替代 → 委派。

> 静态委派看"任务整体性质"，动态委派看"执行中冒出的低难度子步骤"。两者结合，主 Agent 始终只做高认知密度部分。

## 委派指令模板

委派时必须给出**自包含的任务描述**（子 Agent 无主 Agent 上下文），缺一不可：

**粒度原则**：每个委派任务应是**单一可验证目标**。避免"写整个项目文档"这种大粒度，拆为"写 README 的安装章节"这种可独立验收的小任务。粒度过大子 Agent 易失败，过小则委派开销大于收益。

```markdown
【任务】{一句话说明要做什么}
【背景】{必要的项目/代码上下文，精确到文件与行号；探索类任务可只给项目根路径与目标，允许子 Agent 自行查找}
【目标】{期望产出的结果形态}
【验收标准】{可判断成功与否的具体标准}
【输出格式】{要求子 Agent 按指定格式返回}
```

示例：

```markdown
【任务】验证 src/service/user_service.py 的新增接口 /users/{id} 是否通过单元测试
【背景】项目在 /Users/xxx/projects/app，Python 3.11 + pytest，测试文件在 tests/test_user_service.py
【目标】运行相关测试用例，收集通过/失败结果
【验收标准】所有 user_service 相关用例通过；若有失败，列出失败用例名与断言错误摘要
【输出格式】按子 Agent 输出契约三段式返回
```

**跨委派上下文传递**：连续委派相关任务时（如先调研→再测试），第二次委派的【背景】中带上前次子 Agent 的结论摘要，避免子 Agent 重复劳动。子 Agent 每次都是全新上下文，不自动继承前次结果。

## 子 Agent 输出契约

子 Agent 按其提示词（`agent.md`）中的输出契约三段式返回。主 Agent 只需读第 1 段（结论）与第 3 段（自检与失败声明）即可决策，第 2 段（证据）按需查阅。契约定义单一来源在 `agent.md`，此处不重复。

## 失败兜底流程

子 Agent 返回后，主 Agent 按以下流程处理：

```
收到子 Agent 结果
  ├─ 满足验收标准 → 采纳结果，继续主线任务
  ├─ 子 Agent 请求澄清（任务描述有歧义）→ 补充一句澄清后让其继续
  ├─ 可疑（结论含糊/证据不足）→ 要求子 Agent 补充证据 1 次
  ├─ 部分满足 → 就缺口补充委派 1 次（带上前次结果，要求针对性修复）
  └─ 补充/复核后仍不达标 → 主 Agent 亲自执行该任务
       （兜底时带上子 Agent 的证据与失败声明，避免重复劳动）
```

- 兜底判定依据是**验收标准**，不是"子 Agent 说成功就信"。
- **重试计数规则**：一次结果不达标最多补委派 1 次；补充后仍不达标立即主 Agent 兜底，不无限重试。
- **抽查机制**：对低成本模型的"通过"结论，若证据含糊或任务影响核心代码，主 Agent 可抽查复核关键断言，不必全信。
- **结果合理性复核**：子 Agent 返回"达标"但结论与主 Agent 预期方向不符时，即便满足验收标准也应复核——验收标准本身可能设错。
- **澄清响应**：子 Agent 执行中若返回"需要澄清"（任务描述有歧义），主 Agent 应补充一句澄清后让其继续，而非直接兜底——澄清成本通常低于亲自执行。

## 并行委派

多个**相互独立**的辅助任务可同时委派多个子 Agent 并行执行，主 Agent 收齐结果后合并决策：

| 适用条件 | 说明 |
|----------|------|
| 任务间无依赖 | 如"测试验证"与"文档编写"互不影响，可并行 |
| 各自可独立验收 | 每个子 Agent 有自己的验收标准 |
| 结果可合并 | 主 Agent 能整合多个结果做下一步决策 |

**不适用并行**：任务间有数据依赖（如先调研才能测试）、共享资源冲突（同时改同一文件）。

并行委派时，主 Agent 给每个子 Agent 独立的任务描述，互不引用彼此结果。

## 与关闭规则的关系

本规则**默认生效**。当 `disable-task-delegation` 规则处于生效状态时，本规则自动失效，主 Agent 退回全包模式（见该规则声明）。

## 例外（不委派）

- 用户明确要求"不要用子 Agent"、"自己处理"
- 委派描述成本 ≥ 自己执行成本
- 任务属于主 Agent 核心职责（核心设计/核心代码）且无法拆分出辅助部分
- **敏感任务**：涉及密钥、凭据、内部数据、不宜外发给独立 AI 调用的任务，一律不委派
